## Executive summary

M3.2.X.12 ships the **Recommendations engine** — a rule-based (co-purchase + same-category fallback) recommendation system with three HTTP surfaces (public per-product, authenticated personalized, admin debug). Pre-computed by a nightly cron, read through indexed lookups in sub-millisecond latency. ML upgrade pathway preserved: same denormalized table shape accommodates future scores from collaborative-filtering or matrix-factorization models (operator follow-up #37).

What this phase delivered:

- New `product_recommendations` table — 7-column denormalized index, UNIQUE constraint, composite read-path index + admin-explain index, both FK columns with ON DELETE CASCADE for automatic graph cleanup.
- New `ProductRecommendation` Doctrine entity with three source constants (copurchase / category / fallback_popular) + invariants enforced at setter level (defense in depth with SQL-level guards).
- New `CoPurchaseAffinityCalculator` — CTE-based SQL with ROW_NUMBER() PARTITION BY for per-source top-N cap; 365-day window; min support of 3; self-JOIN on order_items with both-sides status filtering.
- New `CategoryAffinityCalculator` — parallel service with same public API shape; SQL-level self-recommendation guard; constant 1.0000 score ranking below copurchase MIN_SUPPORT floor.
- New `BuildRecommendationsCommand` Symfony cron — `--dry-run` support, truncate + bulk insert in single transaction with rollback on failure, merge logic (copurchase first then category top-up excluding already-recommended targets), TOP_N_TARGET=20.
- New `RecommendationsService` — hot read path with popular fallback when pre-computed empty + personalized user path (category-affinity from user's 180-day history, anti-joined against user's purchase history) + admin explain method returning all rows with ranks.
- New `RecommendationsSerializer` — `shape()` for hot path (each row wrapped through ProductSerializer::listShape) and `explainShape()` for admin grouped-by-source breakdown.
- Three new HTTP endpoints with route placeholders + middleware gating + audit emission where required.
- Six new architectural patterns reinforced (cron-driven denormalized index, parallel calculator services sharing public API, bulk graph computation via CTE-based ROW_NUMBER, defense in depth invariants at SQL + entity layers, sequenced executeQuery mock for testing multi-query paths, admin debug 'explain' endpoint shape).

Before this phase:

- Product detail pages had no "you might also like" surface. The `related_products` field in ProductSerializer was an empty array reserved for this.
- The "/me" endpoint surface had no personalized discovery. Customers had to browse manually.
- No cross-product affinity data existed in the codebase anywhere.

After this phase:

- Every product detail page can render a recommendations row. Products with copurchase history get high-signal recommendations; new products get marketplace-popular fallback.
- Authenticated customers get a "for you" feed based on their actual purchase history (most-purchased category → popular products in that category they haven't already bought).
- Admins can debug recommendations via the explain endpoint when vendors escalate ("why is competitor X on my product page?").

## Architectural patterns reinforced

This phase exercised the following patterns:

1. **Single-table additive migration with composite indexes** — standard X-series pattern; UNIQUE + read-path composite + admin-filter index combination.

2. **FK ON DELETE CASCADE for graph cleanup** — when a Product is deleted, both `WHERE product_id=X` and `WHERE recommended_product_id=X` rows vanish automatically.

3. **Doctrine entity with public source constants + VALID_SOURCES whitelist** — same shape as `Currency::supportedCodes` (X.15-B) and `EmailTemplate` (X.11).

4. **Setter-level invariant enforcement with defense in depth** — `ProductRecommendation::setRecommendedProduct` throws on self-recommendation; `CategoryAffinityCalculator` SQL `p2.id != p1.id` enforces the same invariant at the database layer (X.12-D, NEW informal pattern).

5. **Parallel calculator services sharing public API shape** (X.12-C / X.12-D, NEW informal pattern locked here) — both calculators expose `computeFullGraph()` returning identical array shape so the cron command iterates them uniformly. Reusable for any "multiple algorithm sources merging into one output" pattern.

6. **Bulk graph computation via single CTE-based query** (X.12-C, NEW informal pattern) — `WITH ... ROW_NUMBER() OVER (PARTITION BY ... ORDER BY ...) ... WHERE rn <= N` computes per-group top-N in a single query. Much cheaper than per-source LIMIT queries.

7. **Self-JOIN on same table with `!=` filter for pairwise relationship discovery** (X.12-C / X.12-D) — `JOIN order_items b ON b.order_id = a.order_id AND b.product_id != a.product_id` discovers all pair combinations within each order. Reusable for social ("people who follow X also follow Y") and similar pairwise affinity queries.

8. **Cron-driven denormalized index with truncate + bulk insert in single transaction** (X.12-E, NEW informal pattern locked here) — much simpler invariants than upsert; rollback on failure means read tier never sees partial state. Batched INSERT with placeholder spreading (500 rows / batch) for write throughput.

9. **Drop `final` from services that need PHPUnit doubles** — X.12-C / X.12-D / X.12-F all dropped `final` matching the locked pattern from X.10-C / X.17-C / X.11-F / X.13-A / X.15-E. SIXTH instance.

10. **PSR-3 timing observability with `slow_response` warning threshold tuned per-service** — X.12-C uses 30-second statement timeout (much higher than other services because copurchase is the slowest SQL); X.12-D uses 10 seconds; X.12-F uses 2 seconds.

11. **SET LOCAL statement_timeout with try/catch fail-soft** — degrades cleanly on non-PostgreSQL test setups (locked pattern reused).

12. **Denormalized-index read pattern with on-the-fly fallback** (X.12-F) — single indexed lookup for hot path; defensive query only when cached path is empty. Hydrate-and-filter handles deleted-row race conditions gracefully.

13. **Boolean fallback observability flag** (X.12-F) — `used_fallback=true|false` in the DEBUG log lets ops dashboards track fallback hit rate.

14. **Status exclusion sets shared across multiple domains** — `['rejected', 'refunded']` shared between X.13-B revenue, X.12-C copurchase, X.12-F popular, X.12-G category-affinity. Single canonical "broken transaction" definition applied consistently.

15. **Service-layer clamping rather than 400'ing on out-of-range params** — X.12-F limit clamped to [3, 20] in service rather than rejecting at controller layer. Read-only endpoints degrade cleanly.

16. **Two-CTE classification queries** (X.13-D pattern reused) — X.12-G `findUserTopCategory` is single-CTE but uses the same "filter + aggregate + ORDER BY + LIMIT 1" shape.

17. **Triple-endpoint pattern (public + authenticated + admin audited) sharing service + serializer** (X.12-G, NEW informal pattern) — three HTTP surfaces for three audiences with one backing service + serializer.

18. **Admin debug "explain" endpoint pattern** (X.12-G, NEW informal pattern locked here) — grouped-by-source breakdown shape (by_source.copurchase.{count, rows}, etc) with rank preservation. Reusable for any algorithm-transparency surface.

19. **Real-service-with-fake-deps integration test for observability** (X.12-H — SIXTH instance after X.14-E / X.17-E / X.11-H / X.15-G / X.13-F) — pattern firmly locked.

20. **Sequenced executeQuery mock dispatch by call-index** (X.12-G test, NEW informal pattern) — test helper mocks `executeQuery` with `willReturnCallback` that switches on a tracked `$callIdx` counter to return different result sets per query in the service path. Reusable for testing any multi-query service method.

## Security considerations

1. **No SQL injection surface** — all DBAL queries use parameter binding with explicit ParameterType arrays.
2. **Cross-tenant isolation N/A** — recommendations are marketplace-wide (Q-VendorScope = A). No vendor isolation needed.
3. **Admin gate enforced by middleware** — AdminAuthMiddleware → AuthMiddleware stack runs before the controller; controller doesn't re-check role.
4. **Auth gate on /me endpoint** — AuthMiddleware rejects anonymous requests before reaching controller.
5. **Path placeholder regex constraints** — `{product_id:[0-9]+}` rejects non-numeric URLs before the controller runs.
6. **Audit trail mandatory for admin explain** — `AuditEmitter::recordView` fires on every successful call with Product as subject. Helps detect surveillance patterns.
7. **No PII in logs** — `recommendations.product.served` carries product_id + limit + used_fallback; `recommendations.user.served` carries user_id + path tag but no order/cart details.
8. **Self-recommendation guard at TWO layers** — entity setter throws AND SQL `p2.id != p1.id` prevents it at the database level. Defense in depth.
9. **Statement timeouts prevent runaway queries** — 30s for copurchase, 10s for category, 2s for request-time popular fallback.
10. **Rollback on cron failure** — if any INSERT batch fails, the transaction rolls back; the read tier sees the previous (stale-but-consistent) data rather than partial state.
