## Executive summary

M3.2.X.6 ships the formal vendor lifecycle (pending / approved / suspended) on the Vendor entity, closes the deferred-enhancement gap in `VendorAuthMiddleware`, and adds self-serve onboarding so users can submit stores for admin approval without admin intervention.

Before this phase:
- Four overlapping boolean flags (`is_active`, `is_verified`, `is_store_approved`, `is_featured`) with no formal lifecycle
- No path for self-serve vendor onboarding (admin-created only via `POST /v3/admin/vendors`)
- Temporary suspension was indistinguishable from soft-delete
- `VendorAuthMiddleware` checked only `is_vendor` role flag; its own docblock flagged the lifecycle gate as "deferred enhancement"
- Status not a first-class audit subject

After this phase:
- New `status` column on `vendors` table with 3 states (pending/approved/suspended)
- State-transition methods on the Vendor entity enforce valid transitions
- `is_store_approved` legacy flag stays in sync with status changes (Q-LegacyFlags=A invariant)
- `VendorAuthMiddleware` gates by approved lifecycle status
- 3 admin endpoints for explicit state transitions with full audit trail
- 2 vendor self-serve endpoints (submit onboarding + check status)
- Migration backfills existing vendors via heuristic + operator review

## Master plan correction

Per the M3.2.X.6 plan's pre-flight inspection, the master plan row for M3.2.X.6 contained an architectural inaccuracy:

> **Was:** "Add `vendor_status` enum to **User entity**; migration with default 'approved' for existing vendors..."
> **Corrected:** "Add `vendor_status` enum to **Vendor entity**..."

The architecture is `User has is_vendor boolean` (a role flag) and `Vendor has owner_user_id FK` (many Vendor records per User possible — multi-store vendors). Status logically belongs on the store (Vendor), not the role (User). The corrected text is reflected in the master plan via this commit.

## State machine reference

```
        ┌─────────┐  approve()  ┌──────────┐  suspend()  ┌───────────┐
        │ pending │ ──────────► │ approved │ ──────────► │ suspended │
        └─────────┘             └──────────┘             └───────────┘
                                     ▲                         │
                                     │                         │
                                     └─────────────────────────┘
                                          reactivate()

Valid transitions:
  pending   → approved   (initial admin approval)
  approved  → suspended  (admin disciplinary action)
  suspended → approved   (via reactivate() OR via approve())

Invalid transitions (raise InvalidArgumentException):
  pending   → suspended  (must approve first)
  approved  → pending    (regression)
  approved  → approved   (duplicate call)
  suspended → suspended  (duplicate call)
  pending   → pending    (no-op; can't happen via the entity API)
```

## Schema reference

```sql
ALTER TABLE vendors
    ADD COLUMN status VARCHAR(16) NOT NULL DEFAULT 'pending',
    ADD COLUMN status_changed_at TIMESTAMPTZ NULL,
    ADD COLUMN status_reason TEXT NULL;

ALTER TABLE vendors ADD CONSTRAINT chk_vendors_status
    CHECK (status IN ('pending', 'approved', 'suspended'));

CREATE INDEX idx_vendors_status_owner ON vendors (status, owner_user_id);
```

## Wire contract reference

### Admin endpoints (require admin JWT)

```
POST /v3/admin/vendors/{id}/approve
POST /v3/admin/vendors/{id}/suspend
POST /v3/admin/vendors/{id}/reactivate

Body: { "reason"?: string }  // max 1000 chars

200 Response:
{
  "vendor": {
    "id": 42,
    "slug": "almas-fashion",
    "status": "approved",                       // or suspended
    "status_changed_at": "2026-05-17T10:00:00+00:00",
    "status_reason": "KYC verified",
    "is_store_approved": true,
    ...
  }
}

Errors:
  404 — Vendor not found
  422 — Invalid transition (e.g. approving an already-approved vendor)
  403 — Caller not admin
```
