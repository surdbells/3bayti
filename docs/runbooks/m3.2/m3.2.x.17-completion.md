## Executive summary

M3.2.X.17 ships the **Order timeline** surface — a chronological event feed for any order showing every state change, notification, return event, and dispute event in one paginated stream. Enables ops to investigate "what happened to this order" without piecing together queries across 5 tables. Also ships a vendor-scoped view so vendors can see their own involvement in an order's lifecycle.

What this phase delivered:

- A new `OrderTimelineBuilder` domain service aggregating events from 5 sources (entity-derived Order events, audit_log, notification_logs, order_return_requests, order_disputes) into a single chronological feed with 14 canonical event types.
- Vendor-scope filtering built into the builder from day one — dispute events hidden, audit rows narrowed to vendor's items, notifications filtered by vendor email, returns joined through item ownership.
- A gap-closure commit (X.17-B) adding `AuditEmitter::recordUpdate` emission to `TransitionVendorOrderItemController`. Before this commit, vendor-driven item-status changes left no `audit_log` row and were invisible to the timeline.
- Two new HTTP endpoints with appropriate auth posture:
  - `GET /v3/admin/orders/{id}/timeline` — admin full visibility, audited
  - `GET /v3/vendor/orders/{id}/timeline` — vendor scope with multi-store routing
- PSR-3 observability following the X.10-D / X.14-A pattern: `order_timeline.computed` debug log per call with duration + filter shape; `order_timeline.slow_response` warning when > 300ms (threshold tuned higher than X.14's 200ms because timeline aggregates 5 sources vs metrics' 3).
- An `OrderTimelineSerializer` shaping the `{ data, meta }` envelope with order_id + order_reference for client display.
- An end-to-end integration test (X.17-E) verifying the observability survives the full controller stack across both endpoints.

Before this phase:

- 3bayti ops had no programmatic way to see "what happened to this order". They'd query audit_log, notification_logs, order_return_requests, and order_disputes separately, then mentally merge the timelines.
- Vendor item-status changes (e.g. "vendor accepted item", "vendor marked item shipped") had no persistent record beyond structured logs — forensic investigation of vendor performance issues was hampered by missing audit data.
- Vendors couldn't see their own activity on an order. When customer-facing notifications fired, vendors had no way to confirm "did the customer get told their item shipped?" without asking ops.

After this phase:

- Ops loads the admin timeline endpoint and sees the complete narrative of an order in chronological order. Investigations that took 20+ minutes of SQL joining now take one URL.
- Vendor transitions are first-class audit_log entries with before/after snapshots. The timeline shows "vendor accepted item at 09:32, vendor shipped at 14:17" naturally.
- Vendors see their own scope of an order's lifecycle. Cross-tenant attempts are rejected with opaque 404; multi-store users disambiguate via `?vendor_id=N` exactly as in X.14-C.

2. **Sub-phase B** — None. ## Architectural patterns reinforced

This phase exercised the following locked patterns from prior X-phases:

1. **Raw SQL via DBAL with parameter binding** (X.10-A) — required because the audit query needs PostgreSQL-specific UNION ALL across subject types with different join paths.
2. **Lazy EM resolution** (X.4-B) — `OrderTimelineBuilder` holds `EntityManagerInterface`, resolves `Connection` inside each method.
3. **Drop `final` from domain services that need to be mocked in HTTP tests** (X.10-C) — same posture as `FacetAggregator`; `@internal` docblock prevents accidental subclassing in production code.
4. **PSR-3 timing observability with slow-response warning** (X.10-D / X.14-A) — `service.computed` debug + `service.slow_response` warning, threshold tuned per service profile.
5. **Defensive `SET LOCAL statement_timeout`** (X.10-D) — try/catch fail-soft for non-PostgreSQL test setups.
6. **`LoggerInterface` required not nullable+default** (X.5/X.7-D/X.8-D/X.18-G/X.10-D) — reflexive at this point.
7. **`{ data, meta }` response envelope** — data is the events array, meta carries order identity + pagination.
8. **Audit ACTION_VIEWED on admin read endpoints with filter context** (X.4-C / X.14-D) — admin timeline endpoint; vendor endpoint does NOT audit (self-view).
9. **Existence-leak prevention via opaque 404** (X.4-C / X.18 / X.14-C) — vendor endpoint returns 404 for cross-tenant order access AND cross-tenant vendor_id.
10. **Multi-store ?vendor_id pattern** (X.14-C) — exact reuse: same VENDOR_AMBIGUOUS error code, same resolveVendorId helper structure, same opaque 404 for unowned ids.
11. **Real-service-with-fake-deps integration test for observability** (X.14-E) — second instance establishing the pattern; promote to named pattern in the playbook on the next instance.
12. **Builder shared between admin + vendor endpoints; per-scope filtering is a service-level concern** (NEW informal pattern, X.17) — when an event-stream service needs to serve both admin (unfiltered) and tenant-scoped (filtered) views, build the filter into the service from day one, not bolted-on per endpoint.

No new numbered architectural patterns locked this phase. Pattern #12 above is informal documentation only.

## Security improvements shipped

1. **Audit gap closed for vendor transitions** (X.17-B) — before this commit, a vendor could change item statuses with NO persistent record beyond structured logs. Forensic investigation of "did the vendor actually ship this on time?" was hampered. Now every transition writes an `audit_log` row with before/after snapshot.
2. **Cross-tenant existence-leak prevention on vendor timeline** — `GET /v3/vendor/orders/999/timeline` from a vendor who has no items in order 999 returns 404 (not 403). Same posture as X.4-C audit log access and X.14-C metrics endpoint.
3. **Dispute events admin-only in vendor view** — `dispute.*` event types are HIDDEN entirely when the timeline is requested through the vendor endpoint. Vendors don't see dispute lifecycle data; that's admin-only forensic.
4. **Notification scoping by recipient** — vendor timeline shows only notifications addressed to the vendor's `contact_email`. Customer-addressed notifications (e.g. "your order shipped") are not exposed to vendors who happen to have items in the order. **Operator follow-up #22** documents the per-item attribution gap (notifications carry order_id but not vendor_id today).
5. **Admin timeline emits audit trail** — every admin call writes an `audit_log` row with subject=Order, actor=admin, changes=filters. Forensic reconstruction of "who looked at order X's timeline when" is straightforward.
6. **Parameter binding everywhere** — all SQL uses DBAL's parameter binding. The UNION ALL audit query passes `:orderId` once and DBAL handles repetition across the 3 subqueries safely.

## Operator follow-up (consolidated in §2.Q of operator-playbook.md)

The X.17 phase adds 3 new items to the operator deferred-tasks list (items #21–23 in the playbook):

21. **Timeline event archival** — current implementation aggregates events live across 5 tables on every request. For very-old orders with 100+ events (typical of a long return + dispute lifecycle that drags out for months) the merge-sort + pagination overhead grows. Trigger condition: `order_timeline.slow_response` warnings > 5/hour during peak. Fix: archive timeline events into a denormalized `order_timeline_events` table populated by an async cron, with the live aggregation as a fallback for recent orders. ~3 days of work.

22. **Per-item notification attribution** — notifications today carry `order_id` but not `vendor_id`. The vendor timeline filter uses `recipient = vendor.contact_email` as a proxy for "this notification was about my items", which works for vendor-addressed emails but doesn't distinguish customer-addressed notifications by which vendor's items triggered them. Fix: add `vendor_id` column to `notification_logs` (nullable, set at send time when the notification is item-attributed). ~1 day migration + backfill + 1 day notification-emitter updates.

23. **Actor label hydration** — timeline events include `actor.type` and `actor.id` but not `actor.label` (a human-readable identifier like email). Adding labels requires joining user_id → users.email in the builder. Deferred because the admin UI can hydrate labels client-side from the existing /v3/admin/users surface; revisit if a "show me what alice@3bayti.ae did across all orders" feature surfaces. ~0.5 day if it's wanted.

## What's NOT in X.17 (deferred or scoped out)

- **Real-time event stream** — current implementation is request-response. Webhook-style real-time event push (e.g. for vendor portals that want to react instantly to dispute creation) is out of scope. Defer until vendor product surfaces a use case.
- **Customer-facing timeline** — admin + vendor only in v1. A customer-facing "track your order" timeline is a separate UX challenge (which events should the customer see? Notifications-to-me only? Item shipped/delivered without revealing operational detail?). Track as a M4 enhancement.
- **Filter by event type** — current implementation returns ALL event types. Adding `?types[]=return.*` for filtered views is a small change to the builder; deferred until ops asks for it.
- **Search across timelines** — "find all orders where dispute.created happened in Q1" requires cross-order indexing. Out of scope; add to operations dashboards instead.
- **Event payload versioning** — Q-EventShape locks the v1 envelope. If the shape ever needs to change non-backward-compatibly, ship as `v2.*` event types alongside the existing ones rather than mutating in place.
- **Mean-time-to-* aggregations** — same as X.14: would need per-item lifecycle timestamps. Operator follow-up #19 from X.14 applies here too.
- **Actor label hydration** — operator follow-up #23. Today the events return actor.type + actor.id; clients hydrate the label client-side.
- **Per-item notification attribution** — operator follow-up #22. Notifications today are filtered by recipient email; per-item vendor attribution is a future enhancement.
