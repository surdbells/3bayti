## Executive summary

M3.2.X.7 ships Arabic translations of the 9 user-facing email templates (7 customer + 2 vendor) with full RTL HTML markup and per-recipient locale routing. The admin dispute template stays English-locked per Q-VendorAdminLocale = A.

Before this phase:
- 10 email templates, all English-only, despite the M1.7.0 `User.locale` field being explicitly docblocked as "Used to: Localise transactional emails (M3)"
- `wrapHtml()` lacked `lang=` and `dir=` attributes (Arabic content would render LTR in email clients)
- No locale-resolution logic in `OrderNotificationService`
- No way for vendor businesses to opt into Arabic email confirmations independently of their owner user

After this phase:
- All 9 user-facing templates render in Arabic when `User.locale='ar'` or `Vendor.preferred_locale='ar'`
- `wrapHtml()` emits proper `<html lang="..." dir="ltr|rtl">`
- `LocaleResolver` service implements per-recipient routing (customer / vendor / admin)
- New `Vendor.preferred_locale` column for vendor opt-in
- `PUT /v3/admin/vendors/{id}` accepts `preferred_locale` field
- Existing `PATCH /v3/me/profile` continues to accept `locale` field (no consumer-side endpoint changes needed)

## Master plan correction

The M3.2.X.7 plan's pre-flight inspection (Section 1.1) stated:

> Verified absence of `locale` / `language` / `preferredLanguage` columns on User, Order, Vendor entities

This was incorrect. The `User.locale` field has existed since M1.7.0 with the explicit docblock intent "Used to: Localise transactional emails (M3)". The pre-flight missed it because the search was for the wrong field names.

The Q-Unification mid-flight pivot (in sub-phase D) corrected the architecture by:
- Removing the `User.preferred_locale` column that sub-phase A had added (and the associated entity getter/setter + 8 tests)
- Refactoring `LocaleResolver` to read the existing `User.locale` field with normalization (`'en-AE'` → `'en'`, etc.)
- Keeping the new `Vendor.preferred_locale` column (Vendor genuinely had no existing locale field)

Net result: one new column instead of two; cleaner architecture; no parallel locale fields on the same entity.

## Architecture reference — locale routing flow

```
┌─────────────────────────────────────────────────────────────────┐
│ OrderNotificationService::safeSend(to, template, order)         │
└─────────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────────┐
│ LocaleResolver::resolveForRecipient(to, order, adminRecipients) │
│                                                                  │
│  1. Customer email match? → normalize(User.locale)              │
│     ('en-AE' → 'en', 'ar-AE' → 'ar', etc.)                      │
│                                                                  │
│  2. Vendor email match?  → Vendor.preferredLocale ?? 'en'       │
│     (Vendor's narrower constraint: en/ar/null only)              │
│                                                                  │
│  3. Admin recipient?     → 'en' (always; Q-VendorAdminLocale=A) │
│                                                                  │
│  4. Default              → 'en' (fail safe)                     │
└─────────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────────┐
│ OrderEmailTemplateRenderer::render(template, order, extra,      │
│                                    locale)                       │
│                                                                  │
│  match (template) {                                              │
│    ORDER_PLACED_CUSTOMER => isArabic ? *Ar() : *En(),           │
│    ... (8 more cases pair *En/*Ar) ...                          │
│    DISPUTE_OPENED_ADMIN => *En() always (admin lock)            │
│  }                                                               │
│                                                                  │
│  wrapHtml emits: <html lang="..." dir="ltr|rtl">                │
└─────────────────────────────────────────────────────────────────┘
                              │
                              ▼
                        Mailer ships
                  (locale in context dict
                   for observability)
```

## Schema reference

```sql
-- Existing (M1.7.0; not added by M3.2.X.7)
users.locale VARCHAR(10) NOT NULL DEFAULT 'en'
  -- Allows: 'en', 'ar', 'en-AE', 'ar-AE'
  -- Read at email send time; normalized to short tag by LocaleResolver

-- Added by M3.2.X.7 (Version20260518000001)
vendors.preferred_locale VARCHAR(8) NULL
  -- Allows: 'en', 'ar', NULL
  -- CHECK constraint: preferred_locale IS NULL OR IN ('en', 'ar')
  -- NULL → defaults to English at send time
```

- Admin tool UI to view/manage vendor or user locale (consumer-side)
- Mobile app changes
- Additional locales beyond `en` / `ar` (future scope)

- Per-order locale snapshot (resolver reads at send time; locale change between events is acceptable)
