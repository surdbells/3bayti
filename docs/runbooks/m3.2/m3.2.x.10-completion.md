## Executive summary

M3.2.X.10 ships the **Faceted search backend** — a single read-side endpoint that returns the refinable filter set for the catalog list page. With it, the mobile / web / portal catalog screens can render a "filter by" sidebar showing live counts ("Black (47)", "S (12)", "Under AED 100 (231)") so users can refine their browse without trial-and-error reload cycles. Treated as a Tier 2 ecommerce baseline.

What this phase delivered:

- A new `FacetAggregator` domain service computing 5 disjunctive facets (size + color + price-bands + vendor + category) against the same filter context as `ProductRepository::findActivePaginated`. Algolia-style disjunctive: each facet's counts drop its own filter so the user can see alternative values to switch to.
- A new `ProductFilterParser` shared service centralizing slug-resolution + query-string parsing across both `ListProductsController` (existing M3.1.5.5d) and the new `ListFacetsController`. Type-safe sentinels (`int|null|false`) replacing the legacy `int -1` `FILTER_NOT_FOUND` sentinel.
- A new public endpoint `GET /v3/products/facets` accepting the same query-string vocabulary as `/v3/products` plus two refinement keys (`sizes[]` / `colors[]` — both array form and comma-separated string form work).
- Soft-fail on unknown slugs: 200 with empty data + applied-filters echo (matches existing catalog semantics; stale links don't 404 the catalog page).
- PSR-3 observability: every `compute()` emits a `facets.computed` debug log with duration + active filter shape; > 100 ms emits a `facets.slow_response` warning that operations can grep for to trigger the deferred Q-Caching = B Redis enablement.
- Defensive per-statement timeout (`SET LOCAL statement_timeout = 2000`) wrapped in try/catch so non-PostgreSQL test setups degrade silently.
- A new reusable `InMemoryLogger` test helper (under `tests/Support/`) for asserting PSR-3 log output.

Before this phase:

- Mobile/web could filter products by individual facets (vendor, category, price range) but had no way to know what other facet values were even available without trial-and-error API calls.
- "Show me sizes that exist for black abayas under AED 200" required a full product list + client-side aggregation.
- Disjunctive filter counts (the standard ecommerce "alternative-values" UX) were impossible.

After this phase:

- One API call returns the complete refinement context for any combination of active filters.
- The UI can render an "active filters" chip row (echoed from `applied_filters` meta block) and a refinable sidebar with live counts.
- All within an observed performance envelope (~50 ms target; warning logs trigger if exceeded).

## Mid-flight catches (handled before each commit)

1. **Sub-phase A** — `Bayti\Api\Domain\Order\Order` was imported but never used in `FacetAggregator` (residual from copy-pasting the `ProductRepository::findActivePaginated` template that had a `best_seller` join). phpstan flagged it; removed cleanly in -D when the file was already being touched for the logger addition.

2. **Sub-phase B** — `FacetAggregator` was declared `final` (reflexive habit, not a deliberate design decision). PHPUnit cannot doubled `final` classes, and the controller test mocks the aggregator. Caught on first run; dropped the `final` keyword. The class has no production subclasses and the change has no production impact — it just unblocks the standard `createMock` pattern. Pattern documented but not promoted to a numbered architectural pattern: this is closer to a "test-readability hint" than a system-level design choice. Future services that controllers will mock should similarly not be `final`.

3. **Sub-phase C** — initial design had the controller import 3 separate repository interfaces and resolve slugs inline. Refactored mid-pass into the shared `ProductFilterParser` service so future filter additions land in one place. `ListProductsController` is deliberately NOT migrated in this commit — it currently uses the legacy `int -1 FILTER_NOT_FOUND` sentinel which works for its needs; migrating it is mechanical noise that belongs in its own focal commit (tracked as operator follow-up #16).

4. **Sub-phase D** — RECURRING PATTERN CAUGHT. Initial constructor used `?LoggerInterface = null` nullable+default. This is the PHP-DI autowire trap locked in X.5 / X.7-D / X.8-D / X.18: when DI's `useAttributes=false` mode evaluates a nullable+default constructor parameter, the `= null` default wins over the bound `LoggerInterface` service even though the binding exists. Caught immediately before commit by checking the locked-patterns list. Fix: make the logger required. `LoggerInterface` IS DI-bound (di.php section "Logger — Monolog instance"), so autowire works cleanly. Dropped the now-unused `NullLogger` import.

5. **Sub-phase D** — existing `FacetAggregatorTest` had 16 `new FacetAggregator($em)` call sites that broke when the constructor gained a required parameter. Fixed by global sed replacement to pass `new \Psr\Log\NullLogger()`. Semantics preserved — the pre-existing tests don't assert on log output; the new X.10-D tests use the `InMemoryLogger` helper for that.

## Architectural patterns reinforced

This phase exercised the following locked patterns from prior X-phases:

1. **Lazy EM resolution** (X.4-B) — `FacetAggregator` holds `EntityManagerInterface`, resolves `Connection` inside `compute()` rather than at construction.
2. **Raw SQL via DBAL `Connection::executeQuery`** with parameter binding (escapes injection); used because DQL doesn't speak `jsonb_array_elements_text()` natively and is biased toward entity hydration when we need aggregations.
3. **Status / taxonomy enforcement via class constants** — `PRICE_BANDS`, `SIZE_ORDER`, `MAX_VALUES_PER_FACET`, `STATEMENT_TIMEOUT_MS`, `VALID_SORTS`. Single source of truth, no string literals scattered across the codebase.
4. **DTO normalize-in-constructor** equivalent at the parser level — `parsePrice` returns "50.00" not "50.0", `parseSearchQuery` trims + truncates, `parseStringList` collapses both array and CSV forms. All inputs normalize at the entrance.
5. **Soft-fail on unknown slugs** (X.1 / M3.1.5.5d) — 200 with empty data, not 404. Catalog pages don't break on stale URLs.
6. **HttpException factory shapes** — not used in this phase since the only failure mode is "filter resolved to nothing" and the soft-fail semantics handle that without throwing.
7. **PHP-DI nullable+default trap** (Pattern #19 from X.5 / X.18) — caught and avoided in X.10-D; logger made required.

No new architectural patterns locked in X.10. The phase fits cleanly within existing patterns — a sign the architecture is maturing well.

## Performance + observability strategy

The phase ships a deliberate non-optimization: **no Redis caching in v1**. Reasoning:

- 6 aggregation queries against indexed columns + GIN-indexed JSONB on a 2k-product staging catalog: pre-flight analysis projects < 50 ms total.
- PostgreSQL parallelizes simple `GROUP BY` scans well; pool connection round-trips dominate at small data volumes.
- Premature caching adds invalidation complexity (product writes need to bust the cache; product writes are frequent).

Instead, X.10-D ships **observability that surfaces the trigger condition** for enabling caching later:

- Every `compute()` emits `facets.computed` at debug level with `{ duration_ms, total_products, filter_keys, has_search }`. Operators can grep these to characterize traffic patterns.
- `facets.slow_response` warning fires when `duration_ms > 100`. Configured threshold matches the Q-Caching = A acceptance bar.
- Operator playbook §2.O documents: **"if `facets.slow_response` count exceeds 10/hour across any 4-hour window, ship Q-Caching = B (Redis 5-min TTL)"**. Future operator follow-up #15.

This is the disciplined version of "measure before optimizing":
- We KNOW we don't need caching today (analysis-driven).
- We have a CONCRETE trigger to enable it (warning count threshold).
- The aggregator is already structured to support caching (single `compute()` entry point, deterministic output keyed on the filter shape).

## Security improvements shipped

None — this is a read-side public endpoint. No new sensitive data exposure, no new authorization surface, no new attack vectors. Worth noting:

- The endpoint is **deliberately public** (no auth required) to match `GET /v3/products`. Anonymous catalog browsing must stay unimpeded.
- Slug filters are looked up via Doctrine repos (parameterized queries), not concatenated into SQL. No injection vector.
- The new raw-SQL aggregator binds all parameters via DBAL's typed parameter binding (`$conn->executeQuery($sql, $params, $types)`). The `?|` JSONB array-key syntax uses `ArrayParameterType::STRING` so the array values are bound, not interpolated.
