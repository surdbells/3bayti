## Executive summary

M3.2.Z.5 is the **mobile half of push notifications** — it turns the
device-token endpoints + sender built in Z.4 into a working on-device
experience. The app now asks for push permission after sign-in,
registers its FCM token with the backend, deactivates it on logout,
and deep-links a tapped notification to the relevant order.

This replaced a placeholder `initPush()` scaffold in AppComponent (the
one with a literal `// send token to your server here` TODO and a
log-only tap handler) with a proper, tested lifecycle owned by a
dedicated `PushManager`.

What this phase delivered:

- `PushRegistrationService` — register / deactivate against
  `POST` / `DELETE /v3/me/device-tokens` (Z.5-A).
- `PushManager` — the lifecycle owner: attaches plugin listeners once,
  requests permission after sign-in, caches + syncs the device token,
  deactivates on logout, and delegates tap routing (Z.5-B/C).
- `resolvePushDeepLink()` — a pure, tested mapper from the push `data`
  payload to `/orders/:id` (Z.5-C).
- Wiring: AppComponent (listeners + tap handler), LoginPage
  (`onSignedIn`), SettingsPage (`onSignedOutReadingToken` before
  session clear).
- Two net-new v3 route-keys in `@3bayti/api-client` and an optional
  body on `MobileNetworkAdapter.delete_v3` (Z.5-A).
- A `ChromeHeadlessNoSandbox` Karma launcher so the mobile suite runs
  headless / in CI (Z.5-A).

## Runtime flow (what happens on a device)

1. **Launch (native):** AppComponent sets the deep-link tap handler and
   calls `PushManager.initListeners()`. No permission prompt yet.
2. **Sign-in:** LoginPage stores the user, then calls
   `PushManager.onSignedIn()` → permission prompt → on grant,
   `PushNotifications.register()` → the `registration` event caches the
   FCM token and POSTs it to `/v3/me/device-tokens`.
3. **Push received (foreground):** presented by the OS per
   `presentationOptions` in capacitor.config.ts.
4. **Push tapped:** `pushNotificationActionPerformed` → tap handler →
   `resolvePushDeepLink(data)` → `router.navigateByUrl('/orders/:id')`.
5. **OS token rotation while signed in:** the `registration` event
   re-syncs the new token automatically.
6. **Sign-out:** SettingsPage awaits `onSignedOutReadingToken()` (reads
   the still-valid token, DELETEs `/v3/me/device-tokens`) BEFORE
   clearing the session.

## Operator follow-up (REQUIRED before push works on devices)

1. **Sync native projects:** `cd apps/mobile && npx cap sync`. This
   pushes the `@capacitor/push-notifications` plugin + capacitor.config
   into the iOS/Android native projects.
2. **Android:** ensure `google-services.json` (Firebase Android app) is
   in `android/app/`. FCM works once the app is registered in the
   Firebase project.
3. **iOS:** push needs APNs.
   - In Xcode, enable the **Push Notifications** capability for the app
     target.
   - In the Apple Developer portal, create an **APNs Auth Key** (.p8).
   - In **Firebase Console → Project settings → Cloud Messaging →
     Apple app configuration**, upload the APNs Auth Key. FCM then
     relays to APNs (Q-Z4.1=A — one FCM credential set serves both
     platforms).
   - Ensure `GoogleService-Info.plist` (Firebase iOS app) is in the iOS
     project.
4. **Backend creds:** complete the Z.4 follow-up — FCM service-account
   in env + run migration `Version20260520000003` (see
   m3.2.z.4-completion.md). Without these the backend uses
   NullPushSender (logs only, no delivery).
5. **End-to-end smoke (staging):** sign in on a real device → confirm a
   `device_tokens` row appears (is_active=true). Trigger an order event
   (place / pay / ship / cancel) → confirm the push arrives and tapping
   it opens the right order. Sign out → confirm the row flips to
   is_active=false. Uninstall + trigger an event → confirm the dead
   token is pruned (UNREGISTERED handling from Z.4-B).
