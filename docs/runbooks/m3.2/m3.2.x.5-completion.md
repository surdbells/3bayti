## Executive summary

The original M3.2.X.5 plan called for an operator to trigger a manual dispute in the Noon sandbox to empirically capture the `eventType` string values, then update the `DISPUTE_EVENT_TYPES` constant in `NoonWebhookController`. This blocked the phase indefinitely on operator action.

Per the product decision (May 18, 2026) that the 3bayti deployment runs against **live Noon credentials from legacy**, the path forward changed. We no longer need a manual sandbox trigger — real production traffic will deliver real dispute eventType values, and we need machinery to ensure unknown values surface visibly rather than being silently classified as non-disputes.

X.5 therefore closes with two pieces:

1. **Observability hook in `NoonWebhookController`** — when an eventType arrives that contains `'dispute'` or `'chargeback'` (case-insensitive substring) but isn't in the recognized `DISPUTE_EVENT_TYPES` list, the controller emits a `warning` log line `noon.webhook.unknown_dispute_event_type` with the event_type + idempotency_key + recognized_types context. This makes future unknown dispute strings self-surface in production logs and Sentry.

2. **Read-only operator audit script** `apps/api/bin/audit-dispute-event-types.php` — enumerates every distinct `event_type` value in `payment_webhook_events`, flags any that contain `'dispute'` or `'chargeback'` substring but aren't in our recognized list. Operator can run this against the production DB at any time to retroactively check the full webhook history. Read-only, safe for production.

The placeholder strings in `DISPUTE_EVENT_TYPES` (`CHARGEBACK_OPENED`, `CHARGEBACK_RECEIVED`, `DISPUTE_OPENED`, `DISPUTE_RECEIVED`) remain in the constant — they're based on Noon's published API contract docs and are reasonable defaults. When a real dispute arrives:
- If its eventType matches one of these, the existing happy-path runs (OrderDispute persisted, admin notified)
- If not, the new warning hook fires, the operator sees the unknown string in logs, adds it to the constant, and ships a one-line update

## Changes shipped

### Source code (apps/api)

- `src/Http/Controllers/Checkout/NoonWebhookController.php`
  - Added private `emitDisputeShapedWarning(?string $eventType, string $idempotencyKey): void`
  - Called from `__invoke` right after `$events->save($event)` — every webhook checks for suspicious unknown dispute types
  - Constructor signature changed: `LoggerInterface $logger` no longer has `= new NullLogger()` default. PHP-DI's `useAttributes(false)` autowire skips nullable+default parameters; with the default removed, DI auto-injects the bound LoggerInterface. Same pattern as M3.2.X.8-D's resolver fix.
  - Dropped unused `Psr\Log\NullLogger` import

### CLI tools (apps/api/bin)

- `bin/audit-dispute-event-types.php` (NEW)
  - Operator-runnable read-only audit script
  - Enumerates every distinct event_type in `payment_webhook_events` with counts + first/last seen timestamps
  - Flags any event_type containing `'dispute'` or `'chargeback'` substring that isn't in the recognized list
  - Exit codes: 0=clean, 1=bootstrap failure, 2=action required
  - Output includes a SQL query template for backfilling historical `order_disputes` rows if the operator finds unknown strings

### Tests

`tests/Http/Controllers/Checkout/NoonWebhookControllerTest.php`:

## Operator follow-up

### Required after staging deploy

1. Run the audit script against staging:
   ```bash
   cd /www/wwwroot/3bayti/apps/api
   /www/server/php/83/bin/php bin/audit-dispute-event-types.php
   ```

   Expected output: "CLEAN — no action required" OR a list of unknown dispute-shaped strings to add to the constant.

2. If the audit reports unknown strings, decide for each:
   - Is it a real Noon dispute eventType? (Cross-check Noon merchant portal docs.)
   - If yes: add to `DISPUTE_EVENT_TYPES` constant; ship a follow-up commit; backfill any `payment_webhook_events` rows that should have created `order_disputes` rows

### Required after production deploy

Same as staging — run the audit against production. Production has more traffic and more chance of having received a real dispute, so this is where the actual answer lands.

### Ongoing observability

Monitor the application log (and Sentry) for `noon.webhook.unknown_dispute_event_type` warnings. If any appear:
1. Pull the full payload via `SELECT payload FROM payment_webhook_events WHERE idempotency_key = '...'`
2. Verify the eventType is a legitimate Noon dispute string
3. Add to `DISPUTE_EVENT_TYPES` + run the backfill template from the audit script's output
