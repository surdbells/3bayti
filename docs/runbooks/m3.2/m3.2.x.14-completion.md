## Executive summary

M3.2.X.14 ships the **Vendor performance metrics** surface — four status-derived performance rates (fulfillment, cancellation, return, dispute) computed per vendor over a rolling window, exposed through three HTTP endpoints serving distinct consumer surfaces (admin single-vendor detail, admin list-across-all-vendors dashboard, vendor self-serve portal view). All Tier 2 marketplace baselines treat this as a standard operations capability.

What this phase delivered:

- A new `VendorMetricsCalculator` domain service computing 4 rates per vendor with two public APIs: `computeForVendor($id, $days)` for single-vendor (3 queries) and `computeForVendorList($ids, $days)` for cross-vendor (still 3 queries total, GROUP BY vendor_id keeps the query count flat regardless of N).
- Three HTTP endpoints with appropriate auth posture:
  - `GET /v3/admin/vendors/{id}/metrics` — admin single-vendor detail, audited
  - `GET /v3/admin/vendor-metrics` — admin list across all vendors with pagination + status filter + dual-strategy sort (DB-pushdown for vendor fields, PHP-side for metric values with null-sorts-last semantics)
  - `GET /v3/vendor/metrics` — vendor self-serve, supports multi-store users via `?vendor_id=N`, returns 422 `VENDOR_AMBIGUOUS` with `available_vendor_ids` when a multi-store user omits the parameter
- PSR-3 observability following the X.10-D pattern: `vendor_metrics.computed` debug log per call with duration + filter shape; `vendor_metrics.slow_response` warning when > 200ms (threshold tuned higher than X.10's 100ms because metric queries scan a 30-day order window vs indexed catalog rows).
- Defensive `SET LOCAL statement_timeout = 2000ms` with try/catch fail-soft for non-PostgreSQL test setups.
- A `VendorMetricsSerializer` shaping single + list responses with canonical `{ data, meta }` envelope including per-vendor identity (id/slug/name) for client display without a second lookup.
- An end-to-end integration test in X.14-E verifying the observability survives the full controller stack — the difference between "logs work in unit tests" and "logs work in production".

Before this phase:

- 3bayti operations had no programmatic way to identify underperforming vendors. Manual queries against order tables required SQL expertise + ad-hoc joining of orders/items/returns/disputes.
- Vendors had no way to see their own performance — they learned about issues only when ops reached out, which made performance feedback slow and reactive.
- Multi-vendor disputed orders had no consistent attribution model — discussions about "whose fault was this" were case-by-case.

After this phase:

- Ops has a one-call dashboard sorting all vendors by any of the 4 rates with a 30-day default window.
- Vendors see their own performance in the portal and can self-correct before issues escalate.
- Multi-vendor disputed orders consistently attribute to every vendor with items in the order (Q-DisputeAttribution = A locked) — admin investigates which items triggered, vendors don't argue about apportionment.

## Architectural patterns reinforced

This phase exercised the following locked patterns from prior X-phases:

1. **Lazy EM resolution** (X.4-B) — `VendorMetricsCalculator` holds `EntityManagerInterface`, resolves `Connection` inside each method.
2. **Raw SQL via DBAL with parameter binding** (X.10-A) — used because the aggregation queries need PostgreSQL-specific `FILTER (WHERE ...)` syntax and `EXISTS` subqueries that DQL doesn't handle ergonomically.
3. **PSR-3 timing observability** (X.10-D) — same `service.computed` debug + `service.slow_response` warning pattern, just renamed and threshold-tuned for the different query profile.
4. **Defensive `SET LOCAL statement_timeout`** (X.10-D) — try/catch fail-soft for non-PostgreSQL drivers.
5. **`LoggerInterface` required not nullable+default** (X.5/X.7-D/X.8-D/X.18-G/X.10-D) — the PHP-DI nullable+default trap is now reflexive to avoid.
6. **Existence-leak prevention via opaque 404** (X.4-C/X.18) — cross-tenant `vendor_id` attempts in the self-serve endpoint return 404 not 403. Same posture as photo serving in X.18.
7. **Audit ACTION_VIEWED on admin read endpoints** (X.4-C) — subject=admin for list views (no single subject entity); subject=Vendor for single-vendor detail. Changes block carries filter context for forensic reconstruction.
8. **Route ordering: literal segments before `{param}` matchers** (X.10-B) — `/v3/admin/vendor-metrics` registered before `/v3/admin/vendors/{id:[0-9]+}/metrics`.
9. **`{ data, meta }` response envelope** — single endpoints use `{ data: {...} }`; list endpoints add `{ meta: { total, limit, offset, window } }`. The serializer transparently handles both.
10. **Dual-strategy sort with null-sorts-last semantics** (NEW pattern, X.14-D) — when a sort key can be null (e.g. metric values for empty-data vendors), nulls go to the END regardless of asc/desc direction. They're "unknown", not "worst" or "best".

No new numbered architectural patterns locked this phase — the architecture continues to fit cleanly within the existing canon (patterns 1-22).

## Security improvements shipped

1. **Cross-tenant existence-leak prevention** — `GET /v3/vendor/metrics?vendor_id=999` from a user who doesn't own vendor 999 returns 404 (not 403). Same response as a non-existent vendor. Prevents enumeration of vendor IDs.
2. **Multi-store ambiguity surfaced explicitly** — rather than silently picking one vendor for a multi-store user, the endpoint 422s with `VENDOR_AMBIGUOUS` and `available_vendor_ids` in the details. Client app must explicitly choose. Avoids accidental data leak across the user's own stores when the client is confused about state.
3. **Admin metrics emit audit trail** — every admin call to either single-vendor or list endpoints emits an `audit_logs` row with the actor + subject + filter context + result counts. Forensic reconstruction of "who looked at what when" is straightforward.
4. **No self-audit on vendor portal** — vendors viewing their OWN data don't emit audit (it's their data; audit would be noise without forensic value). Audits scoped to cross-user/admin/sensitive actions only.
5. **Parameter binding everywhere** — all SQL uses DBAL's parameter binding (`$conn->executeQuery($sql, $params, $types)`). No string interpolation in queries. `ArrayParameterType::STRING` and `ArrayParameterType::INTEGER` used for array params (`ANY(:array)` syntax).

## Operator follow-up (consolidated in §2.P of operator-playbook.md)

The X.14 phase adds 3 new items to the operator deferred-tasks list (items #18–20 in the playbook):

18. **Vendor metrics cache-warming** — current list-with-metric-sort path runs `computeForVendorList` over ALL vendors (not just the page) on every request. At ~500 vendors with sustained traffic this becomes a real concern. Trigger condition: `vendor_metrics.slow_response` warning rate > 5/hour during peak hours. Fix: nightly cron warms a Redis cache of `(vendor_id, days)` → metrics shape; controller falls back to live compute on cache miss. ~2 days of work.
19. **Per-item lifecycle timestamps** — X.14 ships status-derived rates only. Adding mean-time-to-accept, mean-time-to-ship requires `accepted_at`/`shipped_at`/`delivered_at` columns on `order_items`. Migration + backfill + transition-controller updates. ~3 days of work, but only valuable if vendor performance investigation cases regularly demand timing data.
20. **Configurable cancellation taxonomy** — Q-CancellationDef = B locks "vendor-initiated rejections only" as the cancellation rate's numerator. If business analysis later wants to track "customer cancellations after vendor accept" as a separate signal, add a `cancellation_breakdown` block to the response with rejected/customer-cancelled/admin-cancelled counts. ~1 day.

## What's NOT in X.14 (deferred or scoped out)

- **Mean-time-to-accept, mean-time-to-ship** — Q-MetricSet = A locked status-derived rates only. The `order_items` table has no `accepted_at`/`shipped_at`/`delivered_at` timestamps; adding them is a separate migration + backfill. Tracked as operator follow-up #19.
- **Acceptance rate** — Q-MetricSet locked at 4 metrics. Acceptance rate ("of items the vendor saw, what fraction did they accept") is conceptually similar to cancellation but inverted. Add it via a 5th metric method if a use case surfaces.
- **Redis caching** — original plan considered caching the metric computations. Deferred per the X.10-D pattern of "ship observability, react to warnings". Trigger condition documented in operator follow-up #18.
- **Brand / category breakdowns** — current endpoints return vendor-level rollups. Per-category drilldown ("how does this vendor perform on abayas specifically?") is a separate aggregation. Defer to M4 if needed.
- **Time-series / trend analysis** — X.14 ships point-in-time rates for a window. Showing "fulfillment rate over time" requires storing daily snapshots or computing across multiple windows. Out of scope; tracked as a M4 enhancement.
- **Anomaly detection / alerting** — "alert me when vendor X's fulfillment drops below 80%" is monitoring infrastructure, not metrics infrastructure. Operator follow-up if ops asks for it.
