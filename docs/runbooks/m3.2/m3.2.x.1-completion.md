## Executive summary

M3.2.X.1 is the first feature phase of M3.2 Stream X. It completes
the M3.1.5 mobile catalog migration that was deferred because
`best_sellers` ranking needed `order_items` aggregation, which only
became available after M3.1.6 shipped (`171fc0a`).

The phase adds a sixth sort value (`best_seller`) to `GET /v3/products`
and migrates the two mobile call sites (`account.page` strip and
`best-sellers.page` listing) through `MobileNetworkAdapter` so they
consult the feature-flag system. Initial target is `'old'` for the
7-day shadow window; a separate M3.2.X.1-C-FLIP commit flips to `'new'`
after operator sign-off.

Discovery during -C revealed a follow-up phase is needed: the M3.1.5
catalog migration finished the **infrastructure** (transforms +
feature-flags + adapter) but left most catalog call sites bypassing
the adapter. A dedicated M3.2.X.1.5 plan will systematically migrate
the remaining ~10-15 catalog call sites before Stream X continues with
M3.2.X.2 (featured-vendors).

## Detailed phase ledger

### M3.2.X.1-A — Backend `sort=best_seller` (`86454d3`)

**Delivered:**

- `ListProductsController::parseSort` accepts `'best_seller'`
- `ProductRepository::findActivePaginated` branched sort handling:
  - Pre-existing 5 sorts: unchanged in the `match` expression
  - `'best_seller'`: `LEFT JOIN OrderItem` with `WITH` clause filtering to in-scope `Order` rows via `EXISTS` subquery
  - Status filter: `Order::STATUS_PAID + STATUS_FULFILLING + STATUS_SHIPPED + STATUS_DELIVERED`
  - Window filter: `paidAt >= NOW() - 30 days` (anchored on `paidAt` not `createdAt`)
  - `addSelect COALESCE(SUM(oi.quantity), 0) AS HIDDEN bsSales`
  - `groupBy p.id`
  - `orderBy bsSales DESC`, tie-break `createdAt DESC` then `id DESC`
- Count query unchanged (cloned BEFORE the JOIN, so `COUNT(p.id)` over the unjoined filter set remains correct)
- `ListProductsControllerSortTest.php`: 10 new tests / 40 assertions covering happy path + regression coverage for all 5 pre-existing sorts + unknown-fallback + category-filter combination

**Quality gate:** backend phpunit `535 → 545` / `1809 → 1849` (+10 / +40). phpstan `60 baseline` preserved.

### M3.2.X.1-B — `best_sellers_listing` endpoint decision (resolved into -A)

Pre-flight inspection of `apps/mobile/src/app/customer/best-sellers/best-sellers.page.ts` revealed the legacy `best_sellers_listing` endpoint was used as a flat paginated list, NOT vendor-grouped despite the misleading name. Both call sites can be served by a single `/v3/products?sort=best_seller` with different `limit`/`offset` parameters.

Per locked Q-Listing=B3 this collapses to no new endpoint. Mobile-side, the two routing entries (`'GET /mobile/best-sellers'` and `'GET /mobile/best-sellers-listing'`) BOTH point at `/v3/products` with `target='old'` initially.

## Discovery: M3.2.X.1.5 follow-up needed

During M3.2.X.1-C implementation, the call-site inspection revealed:

- `apps/mobile/src/app/service/network.service.ts` is plain `HttpClient.post` with NO interceptor wiring
- Most catalog pages (`new-arrivals.page`, `featured`, `search.page`, `vendor-products.page`, `single-product.page`, `category-listing.page`, etc.) call `networkService.post_request` directly, bypassing `MobileNetworkAdapter`
- This means current `target='new'` feature-flag entries for these endpoints have **no observable effect** — the call sites never consult the flag
- The M3.1.5 catalog migration shipped the infrastructure (transforms + flags + adapter) but stopped short of migrating call sites

**Impact:** Stream X phases that assume flag-driven routing (M3.2.X.2 featured-vendors, M3.2.X.3 categories-augment) need the call sites migrated FIRST or they'll exhibit the same no-op behavior.

**Action:** A dedicated M3.2.X.1.5 implementation plan will be drafted as the next deliverable (separate plan; needs your approval before any migration code). Estimated scope:

- Audit all catalog call sites currently using `networkService.post_request` (~10-15 sites)
- Migrate each via drop-in `networkService` → `networkAdapter` swap (same signature)
- Verify each transform exists in `CATALOG_REQUEST_TRANSFORMS` and each routing entry exists in `ENDPOINT_ROUTING`
- Add transform unit tests where missing
- Maintain mobile tsc baseline (6)
- Estimated effort: 2-3 days

The plan will be drafted as `docs/plans/m3.2.x.1.5-implementation-plan.md` and committed for your approval BEFORE M3.2.X.2 begins.
