## Executive summary

M3.2.Z.4 ships the **backend foundation for push notifications** — the persistence, transport, orchestration, and registration endpoints that Z.5 (mobile) and Z.6 (lifecycle wiring) build on. It mirrors the existing email-notification subsystem (MailerInterface + OrderNotificationService) so push and email fan out through structurally identical, independently-failing pipelines.

What this phase delivered:

- A `device_tokens` table + `DeviceToken` entity + `DeviceTokenRepository` storing per-device FCM registration tokens, keyed unique on the token (re-registration upserts; a device that changes owner is re-owned on its existing row).
- A push transport abstraction (`PushSenderInterface`) with three implementations: a real `FcmHttpV1Sender` (FCM HTTP v1 with service-account OAuth2), `NullPushSender` (dev), and `InMemoryPushSender` (tests) — exactly the MailerInterface adapter shape.
- A `PushNotificationService` orchestrator with the same 7 customer lifecycle methods as OrderNotificationService, fanning out across a user's active tokens, pruning dead (UNREGISTERED) tokens, and never blocking the calling action on a push failure.
- Env-gated DI selection (prod + creds → FCM; else Null), credential loading from JSON-inline / file / individual env fields.
- Two authenticated endpoints — `POST` / `DELETE /v3/me/device-tokens` — for the app to register and deactivate its token.

Q-Z4.1=A (FCM-only): FCM relays to APNs for iOS, so one adapter and one credential set cover both platforms; no direct APNs HTTP/2 adapter was built.

## What exists now (contracts)

### Persistence
`device_tokens(id, user_id→users CASCADE, token TEXT UNIQUE, platform, is_active, created_at, updated_at, last_seen_at)`, INDEX (user_id, is_active).

`DeviceTokenRepository`: `findActiveTokenStringsForUser`, `findActiveForUser`, `findOneByToken`, `register` (upsert), `deactivateForUser` (owner-scoped), `deactivateByToken` (sender-side pruning).

### Transport (`src/Notification/Push/`)
- `PushMessage { title, body, data: array<string,string> }`
- `PushException` (+ `KIND_UNREGISTERED` / `isTokenDead()`)
- `PushSenderInterface::sendToToken(token, message, context)`
- `FcmHttpV1Sender` — OAuth2 (RS256 JWT assertion → access token, cached to ~60s pre-expiry) + FCM v1 send; maps 404/UNREGISTERED→dead, 401/403→auth, 429→rate-limit
- `NullPushSender`, `InMemoryPushSender`

### Orchestration
`PushNotificationService` lifecycle methods (mirror OrderNotificationService): `orderPlaced, orderPaid, orderPaymentFailed, itemShipped, itemDelivered, orderCancelled, orderRefunded`. Each fans out to the customer's active tokens; prunes UNREGISTERED; never throws. data payload = `{ type, order_id, order_reference }` for deep-linking.

### Endpoints
- `POST /v3/me/device-tokens { token, platform }` → 201 (new) / 200 (refresh); body = token metadata (no token string)
- `DELETE /v3/me/device-tokens { token }` → 204 (idempotent, owner-scoped)

### DI / env
`PushSenderInterface` binding: `APP_ENV=prod` + creds, or `PUSH_PROVIDER=fcm` → `FcmHttpV1Sender`; else `NullPushSender`. Creds via `FCM_SERVICE_ACCOUNT_JSON` | `FCM_SERVICE_ACCOUNT_FILE` | `FCM_PROJECT_ID`+`FCM_CLIENT_EMAIL`+`FCM_PRIVATE_KEY`. All documented in `.env.example`.

## Operator follow-up

2. **Provide FCM credentials** in staging/prod env (Firebase Console → Project settings → Service accounts → Generate new private key). Set ONE of the three supply methods. Until then, `NullPushSender` is used (would-send logging only) — safe, but no real delivery.
3. **Set `PUSH_PROVIDER=fcm`** if you want FCM delivery in a non-prod env that has creds (otherwise FCM only activates when `APP_ENV=prod`).
4. **Staging smoke** (after Z.5 mobile lands): register a real device token via the app, trigger an order lifecycle event (once Z.6 wires them), confirm the push arrives and a tapped notification deep-links correctly. A dead token (uninstall the app, then trigger an event) should get pruned to `is_active=false`.
