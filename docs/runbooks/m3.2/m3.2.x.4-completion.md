## Executive summary

M3.2.X.4 closes the M3.1.7-H observability gap. Every email sent by
`OrderNotificationService` now produces a row in the new
`notification_logs` table — regardless of outcome (sent / failed /
skipped) — and admins can query/triage these via
`GET /v3/admin/notification-logs` with 8 filters.

Before this phase:
- M3.1.7-H shipped the full email infrastructure but explicitly
  deferred persistence ("Future: add notification_log if we get
  reports of duplicate emails from genuine retries")
- Failures logged to PSR-3 only — required `kubectl logs | grep` for triage
- "Did customer X get email Y?" was unanswerable without log dives

After this phase:
- `notification_logs` table records every send attempt
- 3 statuses captured: `sent`, `failed`, `skipped` (with reason short-codes)
- Repository write failures swallowed defensively — primary action never blocked
- Admin endpoint with 8-filter set (order_id, template, status, recipient, error_kind, since, until, limit/offset)
- Audit trail (`ACTION_VIEWED`) per admin query

### M3.2.X.4-B — Wire safeSend to NotificationLogRepository (`bd766de`)

**Delivered:**
- Modified `OrderNotificationService` constructor to accept optional `?EntityManagerInterface $em`
- Three new private helpers: `persistSent`, `persistFailed`, `persistSkipped` each calling `safePersist`
- `safePersist` wraps the repository save in try/catch — write failures NEVER propagate to caller
- `safeSend` success path calls `persistSent`
- `MailerException` catch calls `persistFailed` with `$e->kind`
- Generic `\Throwable` catch calls `persistFailed` with `$e::class`
- Skip-path guards in `sendToCustomer`, `sendToVendors`, `disputeOpened` call `persistSkipped` with stable reason short-codes
- DI binding updated to pass EM directly (LAZY repository resolution avoids eager Doctrine metadata loading that broke test mocks)
- 10 new tests in `OrderNotificationServicePersistenceTest.php`

**Architectural shift discovered mid-implementation:** Original plan injected `NotificationLogRepository` directly. The DI binding `$c->get(EM)->getRepository(NotificationLog::class)` eagerly triggered Doctrine metadata loading, which failed in test setups with mocked EMs. 40 admin order tests regressed with HTTP 500. Fix: hold EM, resolve repository lazily inside `safePersist`. This:
- Decouples service construction from EM state
- Lets test mocks return null for unmapped entities (instanceof check defensively handles)
- Production behavior unchanged (single `getRepository` per send; Doctrine caches metadata after first lookup)
- Mirrors the established `AuditEmitter` pattern

**Quality gate:** backend phpunit `596 → 606` (+10 / +40). phpstan `60` preserved. Zero regressions across 596 prior tests.

## Schema reference

```sql
CREATE TABLE notification_logs (
    id              BIGSERIAL    PRIMARY KEY,
    order_id        INTEGER      NULL REFERENCES orders(id) ON DELETE SET NULL,
    template        VARCHAR(64)  NOT NULL,            -- EmailTemplate enum string value
    recipient       VARCHAR(255) NOT NULL,            -- to-address at attempt time
    status          VARCHAR(16)  NOT NULL,            -- sent | failed | skipped
    sent_at         TIMESTAMPTZ  NOT NULL DEFAULT NOW(),
    error_kind      VARCHAR(64)  NULL,                -- MailerException kind | exception class
    error_message   TEXT         NULL,                -- exception message OR skip reason short-code
    raw_event       JSONB        NULL,                -- future ZeptoMail webhook payload
    created_at      TIMESTAMPTZ  NOT NULL,
    updated_at      TIMESTAMPTZ  NOT NULL
);

CREATE INDEX idx_notification_logs_order_id        ON notification_logs (order_id);
CREATE INDEX idx_notification_logs_template        ON notification_logs (template);
CREATE INDEX idx_notification_logs_status          ON notification_logs (status);
CREATE INDEX idx_notification_logs_sent_at         ON notification_logs (sent_at DESC);
CREATE INDEX idx_notification_logs_recipient       ON notification_logs (recipient);
CREATE INDEX idx_notification_logs_status_sent_at  ON notification_logs (status, sent_at DESC);
```

## Wire contract reference

`GET /v3/admin/notification-logs` (Bearer admin JWT required)

**Query parameters:**

| Param | Type | Description |
|---|---|---|
| `order_id` | int | Exact match |
| `template` | string | `EmailTemplate` enum value (e.g. `order.placed.customer`) |
| `status` | string | `sent` \| `failed` \| `skipped` |
| `recipient` | string | Exact email match |
| `error_kind` | string | MailerException kind or exception class name |
| `since` | ISO-8601 | Lower bound on `sent_at` |
| `until` | ISO-8601 | Upper bound on `sent_at` |
| `limit` | int | Default 20, clamped to [1..100] |
| `offset` | int | Default 0 |

**Response envelope (200):**
```json
{
  "data": [
    {
      "id": 1,
      "order_id": 100,
      "template": "order.placed.customer",
      "recipient": "alice@example.com",
      "status": "sent",
      "sent_at": "2026-05-17T08:30:00+00:00",
      "error_kind": null,
      "error_message": null,
      "raw_event": null,
      "created_at": "2026-05-17T08:30:00+00:00",
      "updated_at": "2026-05-17T08:30:00+00:00"
    }
  ],
  "meta": {
    "total": 1,
    "limit": 20,
    "offset": 0,
    "has_more": false
  }
}
```

**Error responses:**
- `401` — Missing or invalid token (handled by `AuthMiddleware`)
- `403` — Authenticated but not admin (handled by `AdminAuthMiddleware`)
- `422` — Invalid filter value (status not in enum, template not recognized, malformed date)

## Skip reason taxonomy

`status='skipped'` rows store the reason in `error_message` with `error_kind=NULL` (distinguishes them from failed rows where both are populated):

| Reason short-code | Cause | Lifecycle context |
|---|---|---|
| `no_email` | Recipient email is empty string | `sendToCustomer`, `sendToVendors` |
| `contact_email_unset` | Typed property uninitialized (rare; defensive) | `sendToVendors` |
| `no_admin_recipients` | Admin recipient list is empty | `disputeOpened` |

Admin queries can filter by status='skipped' + recipient pattern to find skipped-send incidents.

## What is NOT in M3.2.X.4

- ZeptoMail webhook receiver for bounce / complaint events (deferred; column `raw_event` pre-allocated)
- Async notification queue / retry mechanism (deferred; fire-and-forget preserved)
- Apps/web or apps/portal admin UI consuming the endpoint (consumer-side work)
- Apps/mobile changes (no mobile interaction with notification logs)
- Idempotency keys to deduplicate sends (M3.1.7-H "Future" note remains the design rationale)
- Data retention policy / auto-purge (Q-Retention=A; defer until volume warrants)
- Backfilling historical notifications from PSR-3 logs (Q-Backfill=A)
- Email open / click tracking (not in scope)
- Re-send / retry endpoint for failed sends (operator manually re-triggers via existing lifecycle methods)
- Single-row GET endpoint `GET /v3/admin/notification-logs/{id}` (list with `?order_id=N` filter covers the use case)
- Full-text search on error_message (`?q=`; Q-FilterSet=A rejected this)
