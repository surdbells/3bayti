## Executive summary

M3.2.X.1.5 fixes the correctness gap discovered during M3.2.X.1-C: the
M3.1.5 catalog migration shipped infrastructure (transforms registry,
feature flags table, MobileNetworkAdapter) but most call sites still
bypassed the adapter, so existing `target='new'` flags had no observable
effect today.

Per locked Q-Scope=C (broader scope), the phase migrated **all ~98
user-facing `networkService.post_request` call sites across 33 files**
to `networkAdapter.post_request` via a drop-in signature swap. The
adapter consults feature-flag entries and routes accordingly:

- Endpoints with `target='new'` flag → routed to v3 (now ACTIVE)
- Endpoints without an entry → adapter falls through to legacy NetworkService

After this phase:
- 6 catalog read endpoints + payment endpoint + billing endpoints now ACTIVELY route to v3
- All other endpoints behave identically to today (fallthrough)
- Future Stream X phases (M3.2.X.2 onwards) can rely on flag-driven routing actually working

## Risk treatment retrospective

### Payment migration (sub-phase E) — Q-E-Payment=A

**Risk:** Migrating `initiatePayment` flips production payment routing from legacy `/customer/payment/initiate_payment` to v3 `/v3/checkout/initiate` (shape='v2').

**Mitigation applied:**
- Documented in commit message + this runbook
- Required staging Noon sandbox verification before production deploy (above checklist)
- Adapter has been production-verified routing identical flag-aware traffic since M3.1.7-A
- Revert is one line in feature-flags.ts if regression surfaces

**Status:** Awaiting operator staging verification.

### read_vendor path-param substitution (sub-phase C)

**Risk:** `/v3/vendors/by-legacy-id/:id` requires path-param substitution from the legacy body. Pre-flight identified this as a discovery during planning.

**Mitigation applied:**
- Adapter's route resolver was production-verified handling this pattern for orders + auth since M3.1.7-A
- No adapter changes were needed in M3.2.X.1.5; the substitution path already existed

**Status:** Implicit verification via existing single-product flips already in production.

### Mobile tsc baseline preservation

**Risk:** Baseline of 6 errors could be inadvertently grown by migration.

**Mitigation applied:**
- Per-sub-phase tsc verification (`pnpm --filter @3bayti/mobile type-check`) before each commit
- Halt-and-fix protocol when sub-phase H surfaced 45 errors (chat service + cart-merge constructor + async callback annotation)

**Status:** PRESERVED throughout. 6 errors at entry, 6 errors at exit, all pre-existing.
