## Executive summary

M3.2.X.11 ships the **Abandoned cart recovery email** surface — a cron-driven recovery flow that identifies idle carts and emails their owners a reminder. Industry uplift from this kind of recovery typically runs 5-15% of abandoned carts converted to completed orders. Also ships the marketing opt-out infrastructure required to send marketing emails legally under UAE PDPL / Bahrain PDPL / Saudi PDPL.

What this phase delivered:

- Two new DB columns: `notification_logs.cart_id` (sibling to `order_id` for cart-scoped notifications) + `users.marketing_emails_opt_out` (opt-IN default, set via unsubscribe link).
- New `CartAbandonmentFinder` domain service with a 5-criteria eligibility query (status=active + items present + updated_at past threshold + user has email + no prior reminder), ordered oldest-first, batched.
- New `CartEmailTemplateRenderer` with EN + AR templates for `cart.abandoned.customer`. Defensive HTML escaping for XSS prevention in user-supplied product names.
- New `UnsubscribeTokenIssuer` using JwtSettings::signingSecret with a distinct `action: 'unsubscribe'` claim so access tokens can never satisfy unsubscribe and vice versa.
- New `CartNotificationService` mirroring `OrderNotificationService` with the only material difference being opt-out gating (marketing-class templates honour `marketing_emails_opt_out`; transactional ones ignore it per PDPL requirements).
- New `SendAbandonedCartRemindersCommand` Symfony Console command with `--dry-run`, `--threshold-hours` (default 24, clamped [1, 168]), and `--batch-size` (default 100, clamped [1, 500]) options.
- New public unsubscribe endpoint `GET /v3/notifications/unsubscribe?token=...` returning branded HTML pages (success / error / transient-error), no login required (PDPL Article 13 compliance).
- New `EmailTemplate::isMarketing()` classifier with defense-in-depth gating at both the enum level and the dispatch level.
- Integration test exercising the full cron stack with real services to catch silent-DI-regression failure modes.

Before this phase:

- Customers who added items to a cart and didn't complete checkout simply abandoned them. No outreach, no recovery path. Industry standard is to email these customers; absent that, 3bayti was leaving conversion on the table.
- No marketing-email opt-out flag at all. The codebase couldn't legally send any marketing email without one — UAE PDPL Article 13 requires it.
- No precedent in the codebase for cart-scoped notifications. The notification_logs table existed but was order-only; the renderer/service classes were Order-centric.

After this phase:

- Cron runs every 1-2 hours. Finds carts idle past 24h with at least one item, sends the owner a reminder email (English or Arabic depending on user preference) with a CTA to resume their cart. Operator-configurable threshold and batch size.
- Recipients can unsubscribe with one click — no login required. Sets `marketing_emails_opt_out = TRUE`, which suppresses cart reminders and any future marketing-class templates. Transactional emails (order confirmations, shipping updates, refunds, etc.) continue to send regardless.
- Each cart receives at most one reminder, ever. The NOT EXISTS guard in the Finder ensures re-running the cron doesn't double-send. Even FAILED and SKIPPED outcomes act as 'persistent suppression markers' — the cart is permanently excluded from future scans once evaluated.
- Cart-scoped notifications are first-class citizens of the notification_logs table (cart_id column + partial index), visible through the existing `/v3/admin/notification-logs` surface.

## Mid-flight catches (handled before each commit)

1. **Sub-phase A** — None. Clean migration + entity wiring.

2. **Sub-phase B** — One catch: adding `EmailTemplate::CART_ABANDONED_CUSTOMER` broke `OrderEmailTemplateRenderer::render`'s exhaustive match in both phpstan (`match.unhandled`) and 2 runtime tests iterating `EmailTemplate::cases()`. Fixed with a defensive throw case in the order renderer + cart-prefix skip in the 2 all-cases test loops. This is the "exhaustive match must be updated when adding enum cases" pattern from prior X phases — locked in firmly here.

3. **Sub-phase C** — One catch: initial draft used `\PDO::PARAM_*` constants for the DBAL types array. phpstan flagged that `Connection::executeQuery` expects `Doctrine\DBAL\ParameterType` constants, not PDO ones. Fixed by importing `Doctrine\DBAL\ParameterType` and using `ParameterType::STRING` / `ParameterType::INTEGER`.

4. **Sub-phase D** — One catch: phpstan flagged missing `@param array<string, mixed>` on the public `render()` method's `$extra`. Standard fix; phpstan green.

5. **Sub-phase E** — Three catches: (a) `NotificationLogRepository` is a class extending `EntityRepository`, not an interface — initial test capture tried to implement as interface; fixed by extending the class directly. (b) `MailerException` ctor signature is `(kind, message)` not `(message, kind)`; fixed using named arguments. (c) `LocaleResolver` is order-tied (its `resolveForRecipient` takes an `Order`); cart context doesn't need multi-recipient resolution since the cart owner is the only recipient. Replaced with local `normalizeLocale()` helper. Documented in service docblock why we don't reuse LocaleResolver.

6. **Sub-phase F** — One catch: command test failed with `ClassIsFinalException` because PHPUnit can't mock `final` classes. Same X.10-C / X.17-C gotcha. Dropped `final` from both `CartAbandonmentFinder` and `CartNotificationService`, added `@internal` docblocks explaining production code MUST NOT subclass.

7. **Sub-phase G** — Three catches: (a) phpstan flagged missing `@param array<string, string>` on `__invoke`'s `$_args`; standard fix. (b) Test class's helper `makeUser()` collided with the parent `HttpTestCase::makeUser()` — PHP fatal: "access level must be protected or weaker"; renamed local helper to `makeOptedUser()`. (c) Transient-error-page assertion `'try the link again'` failed because the page wraps text across newlines; fixed by asserting on `'Something went wrong'` which is on a single line.

8. **Sub-phase H** — None. Integration test passed on first run.

## Architectural patterns reinforced

This phase exercised the following patterns:

1. **DB migration via two ALTER TABLE statements with reversible down()** — standard pattern from every prior migration.
2. **FK ON DELETE SET NULL on audit-style tables** (X.11-A `notification_logs.cart_id`) — preserves audit trail when parent hard-deleted.
3. **Partial index `WHERE col IS NOT NULL`** — keeps index small + fast when the column is mostly NULL.
4. **Exhaustive `match` expressions on enum cases with `default => throw` for defense** — required for phpstan exhaustiveness checks.
5. **Marketing vs transactional template classification at the enum level** (X.11-B) — defense in depth; the dispatch layer (X.11-E) also checks.
6. **Centralised eligibility policy on the entity** (`Cart::isAbandoned()`) — testable in isolation, reused by both the Finder (via the SQL) and any future call sites.
7. **Raw SQL via DBAL `Connection::executeQuery` with parameter binding** (X.10-A pattern) — used by Finder for the 5-criteria query.
8. **DBAL `ParameterType` constants, not `\PDO::PARAM_*`** — locked in this phase as a phpstan-enforced rule.
9. **PSR-3 timing observability with slow-response warning** (X.10-D / X.14-A / X.17-A pattern) — `cart_abandonment_finder.computed` debug + `slow_response` warning > 500ms.
10. **Defensive `SET LOCAL statement_timeout` with try/catch fail-soft** — degrades cleanly on non-PostgreSQL test setups.
11. **Drop `final` from domain services that need PHPUnit doubles** (X.10-C / X.17-C / X.11-F — now three instances; firmly locked) — `@internal` docblock prevents accidental production subclassing.
12. **Locale-aware rendering via `match` + `(isArabic ? *Ar : *En)` dispatch** (X.7-C pattern) — used in CartEmailTemplateRenderer.
13. **HTML escape every interpolated string in email body templates** — defense in depth against stored XSS via product names.
14. **Defensive `default => throw` in renderer match expressions** — wiring-bug guard between OrderEmailTemplateRenderer and CartEmailTemplateRenderer.
15. **`safePersist()` that catches repository failures and never propagates** (X.4-B pattern) — notification log persistence MUST NEVER block the primary action.
16. **'Persistent suppression marker' via SKIPPED notification_log rows** (NEW pattern locked in X.11-E) — opt-out + ineligibility both write log rows so the Finder's NOT EXISTS guard excludes the cart from re-evaluation forever. Reusable for any "evaluate once, remember the answer" flow.
17. **Per-recipient JWT for opt-out actions with distinct `action` claim** (NEW pattern locked in X.11-E) — reusable for future "verify your email", "reset password via link", etc. The distinct `action` claim prevents cross-purpose token replay.
18. **Opaque-on-failure verify() semantics** (NEW pattern locked in X.11-E / X.11-G) — for security-sensitive endpoints, verify methods should return null on ALL failures without leaking the cause. A recipient learning 'token expired' vs 'wrong action' could craft targeted retry patterns.
19. **Symfony Console command with `--dry-run` + threshold + batch-size options** (X.11-F follows ReconcilePendingOrdersCommand pattern from M3.1.7-B).
20. **Per-iteration flush for durable 'suppression marker' semantics in async batch processors** (NEW informal pattern locked in X.11-F) — when each iteration writes a row that future iterations check, flush after each iteration so a mid-batch crash doesn't lose the markers.
21. **HTML response from a controller** (NEW pattern, first occurrence) — if a second HTML endpoint appears, promote the `wrap()` helper to a shared trait.
22. **Idempotent state-mutation endpoints** (X.11-G) — already-opted-out returns the same success page as a successful unsubscribe; no "you were already unsubscribed" message (that's confusing UX).
23. **Real-service-with-fake-deps integration test for observability** (X.14-E / X.17-E / X.11-H — three instances; firmly locked) — bind real services with mocked Connection + capturing logger + InMemoryMailer; verify observability survives the full composition.

## Security improvements shipped

1. **PDPL-compliant marketing opt-out** (X.11-A + X.11-G) — UAE PDPL Article 13 requires withdrawal of consent to be "as simple as giving consent". The signed-token public unsubscribe endpoint satisfies this — no login required.
2. **No enumeration leak on unsubscribe failures** (X.11-G) — invalid token, expired token, wrong action, missing user all return the SAME 400 + generic error page. A recipient probing the endpoint cannot tell whether a user_id is valid.
3. **Distinct `action` claim on unsubscribe tokens** (X.11-E) — prevents access tokens from accidentally satisfying unsubscribe verification and vice versa. Even if an attacker recovers the signing secret, an access token can't be used to opt out an arbitrary user.
4. **Defense in depth on marketing classification** (X.11-B + X.11-E) — `EmailTemplate::isMarketing()` classifies templates at the enum level; `CartNotificationService` checks the user's opt-out flag at dispatch time. Both layers would need to be wrong for an opted-out user to receive a marketing email.
5. **XSS defense in email HTML bodies** (X.11-D) — every interpolated user-supplied string (product names, URLs) is escaped via `htmlspecialchars(ENT_QUOTES | ENT_HTML5)`. A malicious product name `<script>alert(1)</script>Lamp` renders as `&lt;script&gt;alert(1)&lt;/script&gt;Lamp` in the HTML body. Plain text bodies preserve the raw text (they're not an XSS vector).
6. **Parameter binding everywhere** — Finder uses DBAL prepared statements with `ParameterType` constants. No SQL injection surface.
7. **Token leak risk acknowledged** — if an email is forwarded, the recipient can unsubscribe the original user. Documented in `UnsubscribeTokenIssuer` docblock; acceptable per industry norms (Mailchimp, Klaviyo all use this model). Token only sets `opt_out=TRUE`; no other mutations possible.
8. **30-day token TTL** — long-lived because recipients may not open the email immediately. Outside the 30-day window, the link shows the generic error page. Operators can adjust the TTL by changing `UnsubscribeTokenIssuer::TTL_DAYS`.
