## Executive summary

M3.2.X.13 ships the **Vendor analytics dashboard** — a read-side aggregation layer over existing orders/order_items/users/products data, surfacing 7 dashboard sections per vendor across a configurable rolling time window. Two endpoints: vendor self-serve (no auth needed beyond approved-vendor) and admin (audited, sees any vendor).

What this phase delivered:

- New `VendorAnalyticsCalculator` service with six SQL queries computing: window-anchored totals (revenue, orders, items, AOV, unique_customers), daily revenue time-series with `generate_series` hole-filling, top-10 products by units, top-10 products by revenue, customer mix (vendor-scoped new vs returning via two-CTE classification), and item-status mix (delivered/cancelled/returned with single-pass COUNT FILTER aggregate).
- New `VendorAnalyticsSerializer` wrapping the envelope with vendor identity + `meta.computed_at` + `meta.cache='miss'`.
- New `GET /v3/vendor/analytics?days=30&vendor_id=...` endpoint (vendor self-serve, multi-store routing identical to X.14 self-metrics, no audit).
- New `GET /v3/admin/vendors/{id}/analytics?days=30` endpoint (admin view, AuditEmitter::recordView on success).
- Five new architectural patterns reinforced (skeleton-first envelope contract, CTE classification, generate_series time-series, SQL identifier whitelist, real-service-with-fake-deps integration test for 5th time).

Before this phase:

- The X.14 metrics endpoint surfaced 4 performance rates (fulfillment, cancellation, return, dispute) but no business-level analytics. Vendors couldn't see their own revenue trend, top sellers, or customer-mix breakdown without exporting raw orders.
- Admin had no consolidated per-vendor analytics view.

After this phase:

- Vendors hit `/v3/vendor/analytics` and see all the dashboard signals needed for "what should I be doing about my store" decisions: revenue trending up or down, what's selling, which customers are returning vs new.
- Admin hits `/v3/admin/vendors/{id}/analytics` to investigate any vendor (e.g. customer-support escalation, payout reconciliation question, performance review). Audit trail captures who looked at whose data.

## Architectural patterns reinforced

This phase exercised the following patterns:

1. **Skeleton-first with locked envelope contract** (X.13-A, NEW informal pattern locked here) — stub all per-section computations to return empty-shape, lock the response envelope as a contract before any SQL lands, downstream consumers (serializer + tests) bind against the stable shape from day one. Reusable for any multi-query aggregator service where the response shape is the contract.

2. **Drop `final` from services that need PHPUnit doubles** (X.13-A — fifth instance after X.10-C / X.17-C / X.11-F / X.13-A) — `@internal` docblock prevents accidental production subclassing while allowing controller-level integration tests to mock the calculator.

3. **Raw DBAL ParameterType with placeholder spreading** (X.10-A pattern) — used across all 6 X.13 queries for IN clauses and parameter binding.

4. **`generate_series` with LEFT JOIN for hole-filled time-series** (X.13-B, NEW informal pattern locked here) — `generate_series(start, end, '1 day'::interval)` + LEFT JOIN the daily aggregate ensures zero-revenue days appear with explicit 0.00. Reusable for any dashboard time-series.

5. **CTE-based two-pass classification queries** (X.13-D, NEW informal pattern locked here) — `WITH window_set AS (...), prior_set AS (...) SELECT ... LEFT JOIN ... FILTER (WHERE prior IS NULL/NOT NULL)` for new-vs-returning style classifications. Reusable for any "is X first-time-something in window" question.

6. **`COUNT(*) FILTER (WHERE ...)` aggregate for single-pass multi-bucket counts** (X.13-D) — more efficient than multiple subqueries or CASE-sum.

7. **SQL identifier whitelist via `match()`** (X.13-C) — never string-interp user input into ORDER BY / column names, even when internal.

8. **bcmath HALF_UP via bias-add-then-truncate** — reused from X.15-C in the X.13-B `money()` helper.

9. **Tiebreaker on monotonic column for deterministic ordering** (X.10-A pattern) — `ORDER BY units DESC, product_id ASC` in top-N queries.

10. **INNER JOIN to display fields in aggregate queries** (X.13-C) — avoids N+1 hydration after the fact.

11. **PSR-3 timing observability with slow_response warning threshold tuned per-service** — `vendor_analytics.computed` debug + `vendor_analytics.slow_response` warning at 500ms (higher than X.14's 200ms for wider scope).

12. **SET LOCAL statement_timeout with try/catch fail-soft** — degrades cleanly on non-PostgreSQL test setups.

13. **Multi-store routing with disambiguation 422** (X.14 pattern) — single-store no param needed; multi-store without param gets `VENDOR_AMBIGUOUS` with `available_vendor_ids`; unowned id gets opaque 404.

14. **Audit `recordView` with structured context for read-side admin endpoints** (X.14 / X.17 pattern) — Vendor as subject_type, `admin_vendor_analytics` context tag, `window_days` change.

15. **Read-only endpoint clamping rather than rejecting on out-of-range params** (X.14 pattern) — non-numeric falls back to default; out-of-range clamps to boundary.

16. **Opaque 404 for cross-tenant lookups** — no enumeration leak between vendor accounts.

17. **Two-endpoint pair pattern** — vendor self-serve + admin audited share calculator + serializer.

18. **Real-service-with-fake-deps integration test for observability** (X.14-E / X.17-E / X.11-H / X.15-G / X.13-F — FIFTH instance) — pattern firmly locked.

## Security considerations

1. **No SQL injection surface** — all DBAL queries use parameter binding with explicit ParameterType. ORDER BY column whitelisted via `match()`.
2. **No PII in audit_log** — analytics audit rows contain context tag + window_days. The actual analytics data is in-flight only; not persisted in audit changes.
3. **Cross-tenant isolation** — vendor self-serve endpoint rejects unowned `vendor_id` with opaque 404 (not 403 — no enumeration leak about which IDs exist).
4. **Admin gate enforced by middleware** — controllers don't re-check role; AdminAuthMiddleware → AuthMiddleware stack runs first.
5. **Multi-store disambiguation prevents accidental wrong-store views** — multi-store user without explicit `vendor_id` gets 422 with the list rather than defaulting to "first store" (could surface another store's data unexpectedly).
6. **Audit trail mandatory for cross-tenant admin views** — `AuditEmitter::recordView` fires on every successful admin call with vendor as subject. Helps detect surveillance patterns ("admin keeps looking at vendor X").
7. **Statement timeout prevents runaway queries** — 3000ms hard cap so a poorly-indexed scan can't tie up DB connections.
8. **No raw amounts in revenue_series logs** — observability logs `vendor_id` + `window_days` + `duration_ms` only. Revenue figures only appear in the HTTP response.
