# M3.1.5 — Device Test Checklist (Mobile Catalog Reads on v3)

**Phase:** M3.1.5
**Status:** Required gate before declaring M3.1.5 production-stable
**Performed by:** Whoever runs the off-hours mobile deploy (App Store Connect TestFlight + Play Store internal track)
**Estimated time:** 60–90 minutes per platform

---

## Why this exists

Mobile CI runs type-check + build only (pre-existing constraint flagged in `m3.1.2-completion.md`). The catalog flip work in commits `753f74b` → `0341a41` has been compile-verified and unit-tested at the boundary (PHP controllers 19/19 in `tests/Http/Controllers/Catalog/`; TypeScript transforms 64 assertions across `catalog-request.transforms.spec.ts` + `catalog-response.transforms.spec.ts`) but NOT runtime-verified end-to-end against real v3 data.

Before the broader M3.1 rollout continues, we need on-device confirmation that:

1. The 10 flipped catalog endpoints produce visible UI without rendering errors (no `[object Object]`, no inert `<img src>`, no blank price)
2. The POST→GET conversion in the adapter routes calls correctly (network inspector shows GET to `/v3/products`, not POST to `/customer/...`)
3. The 22 synthesized size flags on the product detail page correctly mirror v3's `sizes` array
4. Comma-separated `images` and `colors` strings on the detail page split correctly back to arrays
5. Pagination (`limit`/`offset`) on listing endpoints behaves identically to legacy
6. The four documented response gaps render acceptably (or are flagged for M4)
7. Slug-style URLs (where applicable) and legacy-id URLs both reach the right v3 controller

Each documented gap from M3.1.5d's commit message gets an explicit row below — the device run classifies severity (acceptable / minor regression / blocker for M4) for each.

---

## Setup

Before running the checklist:

1. Deploy the new mobile build to TestFlight + Play Store internal track from commit `0341a41` (or latest M3.1.5 commit).
2. Confirm `https://api-v3.3bayti.ae` is reachable from the test device's network.
3. Have ready:
   - A **device with network inspection available** (Charles Proxy, Chrome DevTools via remote debug, or Safari Web Inspector for iOS)
   - A **mobile user account** signed in (some flows go through `/account`)
   - The **legacy ID of at least one known product** and **one known vendor** for direct-URL testing (find these in the production database or in a working legacy app session — the IDs are stable across the migration)
   - **Two test devices on different networks** OR ability to switch the same device's network rapidly (for cold/warm-cache comparisons)
4. Note: phase 1 endpoints (M3.1.5e) flipped first, phase 2 (M3.1.5f) second. Both batches need testing in this run since they shipped close together; future runs can scope by batch.

## A. Home page strips (M3.1.5e)

Goal: confirm `new_arrivals` and `featured` strips on the home page render correctly via v3.

| Step | Action | Expected | If wrong |
|---|---|---|---|
| A1 | Open app (logged in or not), land on home page | Page renders; product strips populate within ~2s | If strips stay blank: check network inspector for failed `/v3/products` calls |
| A2 | Network inspector: filter for `/v3/products` | Two requests: `?sort=newest&limit=10` (new_arrivals strip) and `?featured=true&limit=5&offset=0` (featured strip) | If you see POST to `/customer/new_arrivals` instead: routing didn't flip — confirm build is `0341a41`+ |
| A3 | Inspect response of the `?sort=newest&limit=10` call | Response body: `{data: [{id, slug, name, price: {amount, currency}, primary_image: {url, ...}, ...}], meta: {...}}` | If `response_code`/`status` fields present: legacy still active. Build mismatch. |
| A4 | Visually check the new_arrivals strip — product cards display | Each card shows: image, name, price (e.g. "Ð 299"), vendor name | If image is broken: `image_1` transform issue; if price shows `[object Object]`: `price` transform didn't flatten; if vendor name blank: response shape may have changed |
| A5 | Tap a product card on the strip | Navigates to product detail page (covered in section D) | If nothing happens or wrong page: card's `(click)` handler uses `product_id` — confirm transform emits this field |
| A6 | Pull-to-refresh the home page | Strips reload from a fresh GET | If old data persists: caching issue (out of scope for M3.1.5) |

## J. Backend metrics (post-run, smoke check)

After the device run completes, check backend dashboards (or DB query logs):

- v3 `/v3/products` call volume: should be 10× to 100× higher than pre-flip baseline (mobile is the highest-volume catalog consumer)
- v3 `/v3/products/by-legacy-id/:id` call volume: roughly proportional to product-detail-page views
- v3 `/v3/vendors/by-legacy-id/:id` call volume: roughly proportional to storefront views
- Legacy `/customer/{new_arrivals,featured,explore_listing,...}` traffic: should drop to zero or near-zero (web doesn't call these; only mobile)
- 404 rate on v3 by-legacy-id endpoints: should be very low. A spike indicates broken navigation passing bad ids, or a product/vendor that legacy returned but v3 considers inactive
