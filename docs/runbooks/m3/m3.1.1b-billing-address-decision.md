# M3.1.1b — Billing address data model decision (ADR)

**Date:** May 13, 2026
**Decision by:** Sodiq's pair (Claude), under Sodiq's authority
**Status:** Locked
**Supersedes:** M3.1.1 phase plan §M3.1.1b ("Doctrine entity + migration for billing_addresses table")

## Context

The original M3.1.1 phase plan called for creating a new `billing_addresses` table + `BillingAddress` entity + migration, to back the new `GET /v3/me/billing-address` and `PATCH /v3/me/billing-address` endpoints.

Audit during M3.1.1b implementation kickoff revealed:

1. The existing `addresses` table (created in `Version20260507000001`) already has BOTH `is_default_shipping` and `is_default_billing` boolean columns.

2. The existing `Address` entity (`apps/api/src/Domain/User/Address.php`) has:
   - `isDefaultBilling()` / `setDefaultBilling()` methods
   - All UAE-flavored address fields (`emirate`, `area`, `street_address`, `building_details`, `postal_code`, `recipient_name`, `recipient_phone`)
   - A separate per-user-billing partial unique index (`uq_addresses_one_default_billing`)

3. The existing `AddressRepository` already has `findDefaultBillingForUser(User $user): ?Address`.

In other words: **the data model already supports per-user billing addresses.** The only thing missing is the HTTP surface exposing it.

## Decision

**Use the existing `addresses` table.** No new table. No new entity. No new migration. The M3.1.1c controllers query the `addresses` table via the existing `findDefaultBillingForUser` repo method.

## Semantics

The M3.1.1c controllers will:

### GET /v3/me/billing-address

1. Call `AddressRepository::findDefaultBillingForUser($currentUser)`.
2. If non-null: serialize using `AddressSerializer::publicShape()` (same as other address endpoints).
3. If null: return `{ data: null }`. User has no billing address set.

### PATCH /v3/me/billing-address

Two modes, chosen based on request body:

**Mode 1: Promote an existing address.** Request body `{ address_id: number }`. Find the address, verify ownership, call `setAsDefaultBilling()` (analogous to existing `setAsDefaultShipping()` — needs to be added to repository). Result: existing address now has `is_default_billing = true`; previous default-billing demoted in same transaction.

**Mode 2: Update fields on existing billing address.** Request body with `emirate`, `area`, etc. (no `address_id`). Find current default-billing via `findDefaultBillingForUser`. If exists: update its fields (Merge Patch semantics). If none exists: 404 `BILLING_ADDRESS_NOT_SET` — instruct client to use Mode 1 first or create a new address via `POST /v3/me/addresses` then promote.

**Decision rationale for the two-mode shape:** Customers may want either workflow. The legacy mobile pages have separate "set billing same as shipping" (promotion) and "edit billing details" (update) flows. The same endpoint serves both via body inspection.

**Alternative considered:** Single mode (always-update-fields). Rejected because customers should be able to set billing == shipping without duplicating data.

**Alternative considered:** Single mode (always-id-based promotion). Rejected because customers should be able to update billing fields without creating a separate address record.

## What this decision does NOT cover

- Whether `addresses.country` (currently always `'AE'` per schema default) should be exposed in v3 API. Decision: yes, expose; only emit in responses for forward-compat.
- Postal code emission: yes; already in `Address` entity.
- Whether `Address` entity needs a separate `billing_*` field set (e.g. `billing_email` distinct from user's email). Decision: NO — billing email defaults to user's email; no override field needed in M3.1.1. M4 can add if explicitly requested by vendor for tax invoicing.
- The contract amendment for `GET /v3/me/billing-address` response shape (the actual shape will reflect what's emitted by `AddressSerializer::publicShape()`). Folded into M3.1.1h.
