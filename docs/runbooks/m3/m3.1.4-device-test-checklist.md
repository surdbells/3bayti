# M3.1.4 — Device Test Checklist (Mobile Register + Reset + Refresh)

**Phase:** M3.1.4
**Status:** Required gate before declaring M3.1.4 production-stable
**Performed by:** Whoever runs the off-hours mobile deploy (App Store Connect TestFlight + Play Store internal track)
**Estimated time:** 60–90 minutes per platform (longer than M3.1.3 because three flows cover more surface)

---

## Why this exists

Mobile CI runs type-check + build only (pre-existing constraint flagged in `m3.1.2-completion.md`). The register, reset, and refresh-rotation work in commits `a05965d` → `0a4158e` has been compile-verified but NOT runtime-verified. Before the broader rollout (M3.1.5+ flips touching catalog and profile endpoints), we need on-device confirmation that:

1. The restructured register page works end-to-end with v3
2. The restructured reset page works end-to-end with v3
3. The 401-refresh-retry transparently keeps authenticated calls alive past access-token expiry
4. Concurrent 401s (rare in normal use but possible) collapse to a single refresh
5. Refresh failure (revoked / expired refresh token) cleanly redirects to /login

The checklist below covers each systematically.

---

## Setup

Before running the checklist:

1. Deploy the new mobile build to TestFlight + Play Store internal track from commit `0a4158e` (or latest M3.1.4 commit).
2. Confirm `https://api-v3.3bayti.ae` is reachable from the test device's network.
3. Have ready:
   - A **test phone number** that you can receive SMS on (for register Stage 2)
   - A **disposable email address** you can register for the first time
   - A **pre-existing customer account** with known credentials (to test reset)
   - A **vendor account** (for refresh test in vendor pages)
   - A **device with a cached `'user'` blob from M3.1.3** (has access_token + refresh_token; used for the refresh test)
4. Note the access-token TTL (current v3 default: 24h). The refresh test ideally runs against a pre-expired token; if you can't wait, the test plan below includes a "force expiry" approach via revoking + replaying.

## A. Register flow (new user, end-to-end)

Goal: confirm the restructured 2-stage register flow works and produces a usable session.

| Step | Action | Expected | If wrong |
|---|---|---|---|
| A1 | Fresh install (clear app data first), open app → tap "Register" link from login | Lands on Register page in Stage 1 | If terms modal opens or page crashes: HTML wiring issue |
| A2 | Form is empty; all fields visible together (first_name, last_name, email, phone, password, confirm_password, accept terms checkbox) | All 6 inputs render; layout consistent | If only phone field shows: HTML still on legacy 3-stage layout — the commit didn't apply |
| A3 | Fill in info with a phone you can receive SMS on. Check the "Accept terms" checkbox. Tap "Create Your Account" | POST `https://api-v3.3bayti.ae/v3/auth/register` fires (check network inspector). Request body: `{email, phone, password, country_code: "AE", first_name, last_name}` — confirm `country_code` (snake_case, ISO not dial). Response 201 with `{verification_id, user: {email, phone, ...}}` | If 422: validation issue — the transform may have dropped a required field. If 409 with `CONFLICT_PHONE_TAKEN`/`CONFLICT_EMAIL_TAKEN`: use different credentials |
| A4 | Page advances to Stage 2; subtitle shows "We sent a verification code to <phone>" | UI flips to code-entry screen | If still on Stage 1: `ui_controls.stage` didn't advance; check verification_id parse |
| A5 | SMS arrives on the phone within ~30s with a 6-digit code | Code arrives | If no SMS: server-side OTP provider (MessageCentral) issue, not M3.1.4 |
| A6 | Enter the 6-digit code, tap "Validate" | POST `/v3/auth/confirm` fires with `{verification_id, code}`. Response 200 with `{access_token, refresh_token, user (full publicProfile)}` | If 401 with `AUTH_INVALID_CREDENTIALS`: code wrong or expired (try resend); if 401 with `VERIFICATION_FAILED`: code wrong |
| A7 | Wait for navigation | App navigates to `/account` | If stays on Stage 2: response shape problem — check Preferences blob (next step) |
| A8 | Inspect Preferences (`adb shell` or Xcode console or temp `console.log`) | Blob has: `id` (number, from user.id), `token` (string, from access_token), `refresh_token` (string), `first_name`, `last_name`, `email`, `phone`, `is_vendor: false` | If missing `refresh_token`: the M3.1.3 transform stripped it (shouldn't — transform copies it through). If `is_vendor: undefined`: roles derivation issue |
| A9 | Force-kill the app, reopen | Auto-resumes session; lands on `/account` | If lands on `/login`: blob parse failed |

### A — Resend OTP path

| Step | Action | Expected |
|---|---|---|
| A10 | Repeat A1-A4 with NEW credentials but DO NOT enter the code on Stage 2 | Lands on Stage 2 |
| A11 | Tap "Resend OTP" button | POST `/v3/auth/send-otp` fires with `{email}`. Response 200 with new `verification_id`. New SMS arrives within ~30s |
| A12 | Enter the NEW code (not the first one) | A6 onward should succeed; entering the OLD code now returns 401 (it was invalidated) |

### A — Change details / back button

| Step | Action | Expected |
|---|---|---|
| A13 | On Stage 2, tap "Change Phone number" | Returns to Stage 1; form data preserved (not blanked) |
| A14 | Edit phone, tap "Create Your Account" again | New register call fires; new verification_id issued; advances to Stage 2 again |

## B. Reset flow (existing user, end-to-end)

Goal: confirm restructured 2-stage reset flow works and produces a logged-in session.

| Step | Action | Expected | If wrong |
|---|---|---|---|
| B1 | From login page, tap "Forgot password" → lands on Reset page Stage 1 | Email field visible, "Request OTP" button below | If still asking for phone: HTML wasn't updated |
| B2 | Enter email of a pre-existing account; tap "Request OTP" | POST `/v3/auth/reset` fires with `{email}`. Response 200 with `verification_id` | If 400/422: client-side email validation issue; check transform |
| B3 | Page advances to Stage 2 with subtitle "We sent a verification code to the phone linked to <email>" | UI flips to code+new-password screen | If stays on Stage 1: verification_id parse issue |
| B4 | Enter the OTP code, choose a new password, confirm it, tap "Reset Password" | POST `/v3/auth/reset/confirm` fires with `{verification_id, code, new_password}`. Response 200 with token pair + user | If 401 with `AUTH_INVALID_CREDENTIALS` / `VERIFICATION_FAILED`: code wrong, expired, or email isn't registered (anti-enumeration — see B5) |
| B5 | After B4 success, auto-navigate to /account | Logged in as the user whose password just changed | If lands on /login: response shape issue |
| B6 | Sign out, try to sign in with the OLD password | 401 — old password rejected | If still works: reset didn't actually update the password server-side |
| B7 | Sign in with the NEW password | Success | If 401: password update didn't persist |

| Step | Action | Expected |
|---|---|---|
| B8 | From login → forgot password → enter a deliberately-unregistered email (e.g. `random-{nonce}@example.com`) | Same Stage 2 UI shows as for B3 (same response — anti-enumeration) |

## C. Refresh-token rotation

Goal: confirm 401-refresh-retry works transparently and degrades gracefully.

### C — Happy path (transparent refresh)

| Step | Action | Expected | If wrong |
|---|---|---|---|
| C1 | Sign in. Inspect Preferences — note the `token` (access_token) value. | `token` field present | If missing: M3.1.3 transform regression |
| C2 | **Force access-token expiry**. Easiest method: manually edit Preferences and set `token` to an obviously-wrong value (e.g. append `INVALID` to the end). | Preferences shows the modified `token` | Editing Preferences on iOS Capacitor requires plist edit or temporary debug button; on Android it's in SharedPreferences via `adb shell` |
| C3 | Navigate to a tab that loads authenticated data (Profile, Cart, Orders) | Network: first request goes out with the INVALID token, gets 401. **Then a SECOND request fires to `/v3/auth/refresh`** with the stored `refresh_token`. Refresh returns 200 with new tokens. Then the original request RETRIES with the new Bearer header and succeeds. Page loads as if nothing happened. | If page shows blank/error: refresh wasn't triggered — check whether the call site uses the adapter's v3-routed path or legacy fallthrough. The 401-refresh only works for v3 routes; legacy fallthrough still uses {id,token} in body and won't refresh. |
| C4 | Inspect Preferences after C3 | `token` AND `refresh_token` have new values; user.* fields preserved (first_name, billing_*, etc.) | If `token` unchanged: updateStoredTokens didn't run. If billing_* fields disappeared: updateStoredTokens overwrote instead of merged |

### C — Concurrent 401s (single-flight)

| Step | Action | Expected |
|---|---|---|
| C5 | Repeat C2 to force a stale token | Token invalidated |
| C6 | Navigate to a page that fires 3+ authenticated requests in parallel (Account dashboard typically loads featured, best-sellers, new-arrivals, cart — 4 calls in parallel) | In network inspector: 3+ calls go out, all return 401. Then EXACTLY ONE `/v3/auth/refresh` call fires. Then ALL 3+ original calls retry and succeed. | If multiple refresh calls fire (4 refresh calls for 4 401s): single-flight didn't work — `refreshInFlight$` field issue. If only 1 retry succeeds and others fail: shareReplay didn't share the new token correctly. |

### C — Refresh failure (force a dead refresh token)

| Step | Action | Expected | If wrong |
|---|---|---|---|
| C7 | Edit Preferences and set BOTH `token` AND `refresh_token` to invalid values | Both invalidated | |
| C8 | Navigate to authenticated tab | First request 401s. /auth/refresh fires with the bad refresh_token. Refresh returns 401. **Adapter clears Preferences['user']**. Original 401 surfaces to call site. App SHOULD redirect to /login (if call sites are set up to do so). | If app crashes: error path issue. If app stays on the page with no data: call sites don't currently treat 401 as session-expired — this is a *known acceptable behaviour* for M3.1.4 (call-site session-expired handling lands in M3.1.5+ when other consumer pages migrate). For now, force-close + reopen, confirm app starts at /login (cached blob is gone). |

### C — Refresh works for v3-direct calls (post_v3)

| Step | Action | Expected |
|---|---|---|
| C9 | This requires a v3-direct authenticated endpoint to test. The only one currently in use is `/v3/auth/me` (if a page wires it up — none does yet at M3.1.4 close). Defer this test to M3.1.5 when consumer pages call /v3/me/profile etc. | Deferred to M3.1.5 device test |

## D. Backward compatibility (pre-M3.1.4 cached sessions)

| Step | Action | Expected |
|---|---|---|
| D1 | On a device with a cached `'user'` blob from M3.1.3 (has refresh_token already), open the new M3.1.4 build WITHOUT signing out | Cached session works; authenticated calls proceed normally; 401 → refresh flow works as in C1-C4 |
| D2 | On a device with a cached `'user'` blob from PRE-M3.1.3 (legacy `{id, token, ...}` shape with NO refresh_token), open the new M3.1.4 build | The 401-refresh path detects missing `refresh_token` in Preferences, returns null from tryRefresh, surfaces the 401. App should redirect to /login on the next 401. Until then, all current-session legacy calls work as before. |
| D3 | Sign out and sign in fresh on the D2 device | New session has refresh_token; subsequent 401-refresh works. |

## Pass/fail gate

This phase is considered production-stable when:

- ✓ All A* steps pass on both iOS and Android
- ✓ All B* steps pass on both platforms
- ✓ C1-C6 pass (happy path + single-flight). C7-C8 SHOULD pass; if C8 requires force-close to recover, document as known issue
- ✓ D1-D3 pass
- ✓ No regression in the M3.1.3 login flow (run the M3.1.3 checklist's A section as a smoke test)

If C5-C6 (single-flight) fails on either platform, do NOT promote to stable — single-flight protects against thundering-herd refresh-spam that would lock out an account. Fix or roll back M3.1.4e.

---

## What's NOT in this checklist

- Performance benchmarks (refresh latency, register-to-confirm latency). M4 hardening.
- Localization rendering of new i18n keys in Arabic UI (visual verification of right-to-left layout for the new screens). Spot-check during the test, document if anything looks wrong.
- Multi-device session invalidation (if user logs in on device A then device B, does A still work? Refresh-token revocation strategy is M5 hardening).
- 24h aged-token natural expiry (would require waiting 24h). C2 / C7 simulate this via Preferences edit.
- Token theft / leakage scenarios. Security audit is M5.
- Logout flow (/v3/auth/logout-all). Out of scope; M3.1.4 didn't wire logout. Tracked for M3.1.5+.
