# M3.1.6g — Billing address controllers (CLOSED as duplicate)

**Status:** Closed without code changes. Determined to be a duplicate
of M3.1.1c work.

## Original plan

The M3.1.6 phased plan included sub-phase `M3.1.6g — Billing address
controllers (2 endpoints: get + upsert; may share UserLocation infra).`

## Discovery

When implementing M3.1.6f1 (InitiateCheckoutController), the address
lookup logic was wired against `AddressRepository::findDefaultBillingForUser`
and `findDefaultShippingForUser`. These methods, and the billing-address
endpoints that maintain them, already exist:

| Endpoint                                | Controller                       | Origin commit |
| ---                                     | ---                              | ---           |
| GET   /v3/me/billing-address            | GetBillingAddressController      | M3.1.1c       |
| PATCH /v3/me/billing-address            | UpsertBillingAddressController   | M3.1.1c       |

The M3.1.6 InitiateCheckout flow uses these endpoints' underlying
repository directly, and the checkout DTO supports overriding the
addresses-of-record via `billing_address_id` and `shipping_address_id`
parameters (which look up entries in the same address book).

## Decision

No new code is required for M3.1.6g. The original plan's budget for
this sub-phase was based on a partial understanding of M3.1.1c's
scope; M3.1.1c already built what M3.1.6g would have built.

## What's NOT in M3.1.6g (but might be added later)

- **Order-time address overrides** (e.g. "ship this one order to a
  different address than my default"): supported via the InitiateCheckout
  DTO's `billing_address_id`/`shipping_address_id` overrides. The user
  must already have the alternate address in their address book; we
  don't support inline ad-hoc address entry at checkout time. This is
  intentional: it keeps the order's address snapshot traceable back to
  an Address entity for receipts / customer service lookups.

- **Multiple-shipping-addresses-per-order** (e.g. shipping one item to
  a friend and another to yourself): explicitly out of scope for v3.
  The data model supports it (OrderAddress is per-order-not-per-item),
  but the customer flow doesn't expose it. Reconsider if there's
  product demand.

## What gets unblocked

M3.1.6g closure unblocks M3.1.6h (legacy data migration) immediately.
The plan's remaining sub-phases continue in order:

- M3.1.6h — Legacy data migration (orders / order_items / order_addresses)
- M3.1.6i — Mobile routing entries + transform files
- M3.1.6j1 — Flip mobile traffic from old → new
- M3.1.6j2 — Plan closure docs
