## What the v3 backend will do (when M3.1.6j1 flips):

### Cart

- Server-side, per-user, persisted in PostgreSQL `carts` + `cart_items`
- Variant-aware merge: same product + size + color + is_custom +
  measurement + extra_measurement = same line, qty adds (capped 999)
- Auto-creation of active cart on first add
- Guest cart (device-local) merges into server cart on sign-in via
  `POST /v3/cart/merge`
- Skipped items (deleted products) surface in `skipped` array;
  don't block sign-in

### Order

- Read-only customer view (vendor / admin views in M3.1.7)
- Paginated list (limit 1-50, default 10; offset 0+)
- Single-detail with billing + shipping addresses + items
- Cross-tenant 404 (not 403) to avoid leaking existence
- `store` alias in items matches mobile's existing my-orders.page binding

### Checkout

- `POST /v3/checkout/initiate`:
  - Server-derived totals from cart items + delivery_fee + discount
  - Server-generated order_reference: `V3-{epoch_ms}-{4-char hex}` (20 chars)
  - Address snapshotting (Order decoupled from later address-book edits)
  - Idempotent on (user, cart_id, cart_updated_at): double-tap returns
    same checkout URL, not double-charge
  - Calls Noon INITIATE; returns hosted checkout URL + provider_order_ref
  - Mobile opens URL in webview
- Noon redirects to `https://api.3bayti.ae/v3/checkout/return/{ref}` on
  completion (path-based; no query string — Noon hard-rejects '?'
  in returnUrl)
- Mobile observes webview URL, polls `GET /v3/checkout/status/{ref}`
- Poll cheap: reads only v3 local state. Webhook receiver is the
  authoritative source-of-record (calls Noon's GET_ORDER server-to-
  server, then v3 mutates Order state)

### Webhook safety

Three layers:

1. **Signature header verification** via `NoonWebhookSignatureVerifier`.
   M3.1.6 ships `LoggingOnlyVerifier` (accepts everything, logs
   SHA-256 of body + signature for M3.1.7 algorithm reverse-
   engineering). M3.1.7 binds the real verifier.

2. **Idempotency** on the `payment_webhook_events` UNIQUE constraint.
   Key = `noon:<eventId>` if present, else `noon:body:<sha256>`.
   Duplicate POST returns 200 `'duplicate'`, no state mutation.

3. **Retrieve-order-before-acting** (LOAD-BEARING). Even with no
   signature verification, a spoofed webhook cannot mark an order
   paid: controller calls `gateway.retrieveOrder` server-to-server
   (authenticated with our merchant credentials) to confirm the true
   state with Noon directly. The webhook body is informational, not
   authoritative. Endorsed by Noon's own docs.

State transitions are conservative:
- `terminal && paid` → `markPaid()` (already idempotent)
- `terminal && !paid` → `markFailed()` (catches DomainException on race)
- `!terminal` → record event, no Order mutation

Webhook ALWAYS returns 200 on receipt (except 401 for sig fail).
We don't want Noon retrying because of our bugs.

## Critical operator actions before M3.1.6j1 flip

1. **Obtain Noon merchant portal credentials.** Set in production env:
   - `NOON_API_BASE` (live) — typically `https://api.noonpayments.com`
   - `NOON_BUSINESS_IDENTIFIER` — merchant account identifier
   - `NOON_APP_IDENTIFIER` — application within the merchant
   - `NOON_APP_KEY` — the secret key
   - `NOON_WEBHOOK_SECRET` — for M3.1.7 HMAC verification

2. **Email Noon support** to enable uniqueness of merchant order
   reference field. Default is NOT unique per merchant; we need it
   on so duplicate references hit `resultCode 19012` and our
   defensive UNIQUE constraint is reinforced server-side.

3. **Test on a device** with real Noon sandbox. See `m3.1.6-device-
   test-checklist.md` for the full procedure (cannot be done from
   the dev sandbox; no live Noon test environment in CI).

4. **Verify legacy schema before `--include-orders` migration.** See
   `m3.1.6h-order-migration.md` for the operator pre-flight checklist.
   In particular: edit candidate table/column name lists if the
   legacy schema differs from what the probes try.

5. **Run the order migration on staging FIRST.** Verify counts match
   expectations and orphan rate is acceptable before touching prod.

## How M3.1.6 differs from the original plan

Two scope changes worth documenting (full rationale in the relevant
runbooks):

1. **M3.1.6g billing address** — was planned as 2 new endpoints; on
   inspection, both already exist from M3.1.1c, and the
   `InitiateCheckoutController` already integrates against them.
   Closed as duplicate; the M3.1.6 plan's budget reflected
   incomplete awareness of M3.1.1c's scope.

2. **M3.1.6i mobile work split into M3.1.6i + M3.1.6i.2** — the
   original plan budgeted M3.1.6i for "routing entries + transforms
   + sign-in flow rewrite". The actual work includes an adapter
   architecture change (path-param-from-body extraction), a
   checkout-flow rewrite (polling instead of URL-param parsing),
   and a new auth-flow integration (cart merge on sign-in). M3.1.6i
   shipped the routing-table corrections (the part that doesn't
   require mobile code changes); M3.1.6i.2 will ship the rest.

Neither scope change adds work to the plan; both surface work that
was implicit in the original plan but accounted-for in the wrong
sub-phase.
