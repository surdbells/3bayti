routing entries to `target='new'`. Several of these tests cannot pass

## A. Smoke tests (run while routing is still on legacy)

These verify the v3 backend works in isolation. Use curl / Postman
against `api-v3.3bayti.ae`.

### A.1 Auth + cart basics

- [ ] `POST /v3/auth/login` returns a token pair
- [ ] `GET /v3/cart` with that token returns `{cart: {id: 0, items: [], cart_code: 'PND', subtotal: '0.00', item_count: 0}}` (empty-cart shape)
- [ ] `POST /v3/cart/items` with `{product_id: <known-id>, quantity: 2}` returns 201 with item visible
- [ ] `GET /v3/cart` now returns the item
- [ ] Second `POST /v3/cart/items` with same product_id + same variant fields adds to quantity (no new line)
- [ ] `PATCH /v3/cart/items/{id}` with `{quantity: 5}` sets absolute qty
- [ ] `PATCH /v3/cart/items/{id}` with `{quantity: 0}` returns 422 with "DELETE to remove" message
- [ ] `DELETE /v3/cart/items/{id}` returns 200 with updated cart
- [ ] `POST /v3/cart/items` with unknown product_id returns 404
- [ ] All cart endpoints return 401 without Authorization header

### A.2 Cart merge

- [ ] `POST /v3/cart/merge` with `{items: [{product_id: X, quantity: 1}, ...]}` adds new lines
- [ ] `POST /v3/cart/merge` with empty `items: []` returns the existing cart unchanged
- [ ] `POST /v3/cart/merge` with an unknown product_id puts that item in `skipped` array; doesn't 4xx
- [ ] `POST /v3/cart/merge` with item matching an existing variant merges (adds quantities)

### A.3 Checkout initiate

(Note: requires a default billing + shipping address in the user's
address book; create one via PATCH `/v3/me/billing-address` if needed.)

- [ ] `POST /v3/checkout/initiate` with empty body returns 200 with `{checkout_url, order_reference, provider_order_ref, order_id, idempotent: false}`
- [ ] `checkout_url` is a `https://` URL pointing at noonpayments.com
- [ ] `order_reference` matches pattern `V3-\d{13}-[0-9a-f]{4}`
- [ ] Second call within ~30s with same cart returns `idempotent: true` and same `checkout_url`
- [ ] Modify cart (add or remove an item), then call again — returns `idempotent: false` with a NEW `checkout_url`
- [ ] After `POST /v3/checkout/initiate`, `GET /v3/cart` returns the empty-cart shape (cart marked converted)
- [ ] `POST /v3/checkout/initiate` with empty cart returns 422 "Cart is empty"
- [ ] `POST /v3/checkout/initiate` for user without billing address returns 422 "No billing address on file"
- [ ] `POST /v3/checkout/initiate` with `channel: 'TABLET'` returns 422

### A.4 Checkout status

- [ ] `GET /v3/checkout/status/{ref}` for the order returns `{status: 'pending_payment', terminal: false, paid: false, ...}` immediately after initiate
- [ ] `GET /v3/checkout/status/V3-NONEXISTENT-0000` returns 404
- [ ] `GET /v3/checkout/status/{ref}` for another user's order_reference returns 404 (cross-tenant defence)
- [ ] All status calls require auth (401 without header)

### A.5 Orders read

(After completing at least one paid order — A.7 below.)

- [ ] `GET /v3/orders` returns paginated list, newest first
- [ ] `GET /v3/orders/{id}` for own order returns full detail
- [ ] `GET /v3/orders/{id}` for another user's order returns 404
- [ ] `limit=999` clamps to 50

### A.6 Webhook receiver (server-to-server smoke)

This is harder to test from outside — Noon must send the webhook.
But you can verify the endpoint accepts POSTs:

- [ ] `curl -X POST https://api-v3.3bayti.ae/v3/payment/webhook/noon -d '{}'` returns 200 (LoggingOnlyVerifier accepts everything in M3.1.6)
- [ ] Server log shows the webhook was received and idempotency-keyed
- [ ] Repeated POST with identical body returns 200 with `{status: 'duplicate'}` (idempotency working)

### A.7 End-to-end checkout

(After M3.1.6j1 flip, or manually via Postman before the flip.)

- [ ] User authenticates and has a non-empty cart
- [ ] Initiate checkout — receive `checkout_url`
- [ ] Open `checkout_url` in a browser (or in-app webview after flip)
- [ ] Complete payment with a Noon test card (e.g. 4111111111111111
      with any future expiry and any 3-digit CVV per Noon docs)
- [ ] Noon redirects to `https://api.3bayti.ae/v3/checkout/return/{ref}` —
      this is currently a 404 from a browser perspective (the API
      doesn't render HTML); mobile parses the URL and closes the webview
- [ ] **Within ~30s**, Noon's webhook hits our endpoint
- [ ] Server log shows: webhook received → retrieve-order → markPaid → 200
- [ ] `GET /v3/checkout/status/{ref}` now returns `{status: 'paid', terminal: true, paid: true, paid_at: '<ISO timestamp>'}`
- [ ] `GET /v3/orders/{id}` shows the order in `paid` status
- [ ] `GET /v3/orders` includes the order in the list

### A.8 End-to-end failure case

- [ ] Initiate checkout, get `checkout_url`
- [ ] Cancel from inside Noon's hosted checkout (typically a "Cancel" button)
- [ ] Verify: Noon webhook arrives within ~30s with a non-CAPTURED status
- [ ] Server log: retrieve-order confirms non-paid → markFailed → 200
- [ ] `GET /v3/checkout/status/{ref}` returns `{status: 'failed', terminal: true, paid: false}`

## B. Mobile flow tests (require M3.1.6i.2 + M3.1.6j1)

These cannot pass until the mobile-side rewrite ships and the
routing entries are flipped.

### B.1 Cart UI

- [ ] App is on the v3 backend (verify by `console.log(GlobalComponent.baseURL)` or in DevTools network panel)
- [ ] As guest: add 2 items to cart from product detail page → device-local persistence
- [ ] Close + reopen app — guest cart persists locally
- [ ] Sign in — device cart merges into server cart; device cart cleared on success
- [ ] My-cart page renders correctly; quantities + variant attrs visible
- [ ] Increase/decrease quantity buttons work (PATCH /v3/cart/items/{id})
- [ ] Remove-item button works (DELETE /v3/cart/items/{id})
- [ ] Subtotal updates correctly after each mutation

### B.2 Checkout flow

- [ ] From cart, tap "Checkout" — opens checkout review page
- [ ] Review page shows correct totals (subtotal + delivery_fee +
      discount = total — all server-computed)
- [ ] Tap "Pay" — webview opens with Noon's hosted checkout
- [ ] Complete payment with test card
- [ ] Webview closes when Noon redirects to the return URL
- [ ] App shows a "Processing..." spinner while polling
      `GET /v3/checkout/status/{ref}` every ~1-2 seconds
- [ ] Spinner resolves to success screen within ~5-30 seconds
- [ ] Tap "Done" — returns to my-orders page; new order at top of list

### B.3 Cart merge edge cases

- [ ] As guest, add a product that is later deleted by admin
- [ ] Sign in — `skipped` array contains the deleted product; mobile
      shows a one-line notice "Some items in your cart are no longer
      available"
- [ ] Other items in the cart merged successfully
- [ ] Sign-in flow does NOT fail on this; user lands in the home screen

### B.4 Idempotency in the wild

- [ ] Open checkout, get checkout_url
- [ ] DON'T complete payment; instead, tap "Back" on the webview
- [ ] Tap "Pay" again immediately — observe in DevTools that the
      adapter received `idempotent: true` and the SAME checkout URL
- [ ] Add an item to the cart, then tap "Pay" again — observe
      `idempotent: false` and a NEW checkout URL (different order_ref)

### B.5 Failure recovery

- [ ] Initiate checkout but cancel at Noon
- [ ] App polls status, sees `failed`, shows failure UI
- [ ] User taps "Try again" — should NOT 422 due to "Cart is empty"
      (the failed order's items should still be in the cart, since
      the original cart was marked converted but the user's NEXT cart
      is empty and the items aren't auto-restored — this is a known
      M3.1.6 limitation; user must re-add items)
- [ ] Note: if "auto-restore items on payment failure" is desired,
      that's a follow-up enhancement for M3.1.7+

### B.6 Cross-tenant defence (manual; requires two accounts)

- [ ] Account A: complete an order, note the order_reference
- [ ] Account B (different user): in DevTools, change auth token to B's,
      then issue `GET /v3/checkout/status/<A's ref>` — must return 404
- [ ] Similarly `GET /v3/orders/<A's order id>` returns 404 for B
- [ ] Similarly `PATCH /v3/cart/items/<A's item id>` returns 404 for B

## C. Post-deploy production checks

After M3.1.6j1 flips and traffic begins flowing through v3:

- [ ] First customer order completes end-to-end (verify in server logs +
      Noon merchant portal)
- [ ] No 4xx/5xx spike on `/v3/cart/*`, `/v3/orders/*`, `/v3/checkout/*`
      vs the previous day's baseline (the legacy equivalents)
- [ ] No 4xx/5xx on `/v3/payment/webhook/noon` (Noon's retries should
      not be triggered)
- [ ] `payment_webhook_events` table is growing — confirms Noon is
      actually hitting the new endpoint
- [ ] `payment_transactions` table has corresponding `INITIATE` rows
      with `responsePayload.result.checkoutData.postUrl` populated
- [ ] Spot-check 5 random successful orders in the DB — `paid_at` is
      set, status is `paid`, items + addresses are populated
- [ ] No `pending_payment` orders older than 24 hours (would indicate
      webhook delivery failures or mobile poll loop terminating early)

If any of the post-deploy checks fail, the per-endpoint rollback is:
edit the relevant `target` in `feature-flags.ts` back to `'old'`,
rebuild + deploy mobile. Per-endpoint rollback granularity is the
key strangler-fig invariant.

## D. Known issues to NOT block on

These are documented limitations carried into M3.1.7; don't fail
the device test for them:

- Webhook signature is not yet cryptographically verified
  (LoggingOnlyVerifier accepts everything). The retrieve-order-before-
  acting pattern provides the safety. M3.1.7 binds the real verifier.
- A `pending_payment` order whose webhook never arrives is stuck
  in that state forever in M3.1.6. M3.1.7 adds a reconciliation cron.
- Mobile's failure-recovery UI doesn't auto-restore cart items
  after a failed checkout. User must re-add. M3.1.7+ may improve.
- Vendor + admin endpoints aren't shipped yet (M3.1.7).
- Refund + cancel + dispute flows aren't shipped yet (M3.1.7).
