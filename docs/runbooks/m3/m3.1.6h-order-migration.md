# M3.1.6h — Order migration runbook

**Migrates:** `orders` → `orders`, `order_items` → `order_items`,
inline-order shipping addresses → `order_addresses`

**Does NOT migrate:** `carts`. Carts are transient state. Active
legacy carts are lost on cutover by design (users see an empty v3
cart on first login and re-add items).

## Pre-flight checks — REQUIRED before running

1. **Verify legacy table names.** The migration probes these
   candidates in order; the first match wins:

   | What | Candidates probed (in order) |
   | --- | --- |
   | Orders parent | `orders`, `order`, `order_master`, `customer_orders` |
   | Order items | `order_items`, `orderitems`, `order_item`, `order_details`, `order_lines` |
   | Order addresses (separate table — optional path) | `order_addresses`, `order_address`, `order_shipping_address` |

   If none match, the migration logs which candidates it probed and
   skips that step gracefully. If the actual legacy table name isn't
   in any candidate list, edit `MigrationSteps::migrateOrders()`
   (and siblings) and add it.

2. **Verify required columns.** Each migration also probes columns.
   For `orders`, required: `id` (or `order_id`), `user_id` (or
   `customer_id`), and `total` (or `total_amount`, `grand_total`).
   Optional probed columns: `status`, `created_at`, `subtotal`,
   `delivery_fee`, `discount`, `currency`, `order_reference`, `paid_at`.

3. **Verify users + products were migrated first.** Order migration
   uses `users.legacy_user_id` and `products.legacy_product_id` to
   resolve foreign keys. Orders referencing a user that wasn't migrated
   are SKIPPED (logged, not errored — so a 422 for an orphan order
   doesn't abort the run).

4. **Dry-run first.** Run on a staging copy of the legacy DB before
   touching production:

   ```
   php migrate-all.php --include-orders
   ```

   Without `--include-orders`, the order steps are skipped entirely
   (default behaviour — the M3.1.6h sub-phase is opt-in).

## Status mapping

Legacy `status` values are mapped to v3 statuses in
`mapLegacyOrderStatus()`. Default behaviour for unrecognised values
is to mark as `paid` (the safer assumption — a migrated order
"existed" so the customer likely paid). Update the match expression
if your legacy schema uses different status strings.

| Legacy (case-insensitive) | v3 status |
| --- | --- |
| `pending`, `pending_payment`, `0` | `pending_payment` |
| `paid`, `completed`, `1` | `paid` |
| `fulfilling`, `processing`, `2` | `fulfilling` |
| `shipped`, `in_transit`, `3` | `shipped` |
| `delivered`, `4` | `delivered` |
| `cancelled`, `canceled`, `5` | `cancelled` |
| `refunded`, `6` | `refunded` |
| `failed`, `7` | `failed` |
| anything else | `paid` (default) |

## Order reference

Legacy may not have an order_reference column. When absent, the
migration synthesises one with the format:

```
V3M-{10-digit zero-padded legacy_order_id}
```

The `M` distinguishes migrated orders from v3-native orders (whose
references start with `V3-` followed by an epoch_ms timestamp). This
lets customer service identify migrated-vs-native orders at a glance
without checking the database.

## Order_addresses migration: two paths

The migration handles two legacy schemas:

1. **Separate addresses table** (path probed first, candidates listed
   above). If a separate table is found, the migration logs an info
   message but currently does NOT migrate from it — the migration code
   would need real legacy column mapping. Falls through to path 2.

2. **Inline-on-orders** (the more common pattern). Extracts
   shipping_address / shipping_city / etc. columns from the legacy
   orders row itself and inserts both a shipping AND a billing
   record into `order_addresses` (billing duplicates shipping when
   the legacy schema doesn't separate them).

If neither path finds usable columns, the migration logs a skip
message. Migrated orders will exist without addresses — they're
read-only history so this is acceptable. New v3 orders always have
both billing and shipping (enforced by InitiateCheckoutController).

## Idempotency

Every migration step uses `WHERE legacy_X_id = ?` lookups to skip
already-migrated rows. Safe to re-run; partial migrations resume
where they left off.

## Rollback

If a migration goes wrong:

1. The step's transaction rolls back automatically on any thrown
   exception, so a crash mid-run doesn't leave partial state.

2. To wipe migrated orders entirely (e.g. to re-test after fixing
   a column mapping), run:

   ```sql
   TRUNCATE order_addresses CASCADE;
   TRUNCATE order_items CASCADE;
   TRUNCATE orders CASCADE;
   ```

   (PostgreSQL TRUNCATE CASCADE handles the FK chain.)

3. **DO NOT** wipe `users` or `products` to re-test orders — that
   would force a full re-migration including the prerequisite tables.

## What's NOT in this migration

- **Payment transactions:** Legacy orders have payment data on the
  orders row (or in a separate `payments` table that's not v3-modelled).
  v3's `payment_transactions` table is only populated for v3-native
  orders (those that go through InitiateCheckoutController).
  Migrated orders show no transaction history in `payment_transactions`;
  this is intentional. The order row's status + paid_at is the source
  of truth for historical orders.

- **Refunds / cancellations / disputes:** M3.1.7 territory.

- **Webhooks:** Legacy webhooks aren't replayable; the migration
  doesn't try.

- **Carts:** Explicitly out of scope. See top of this document.

## Verification queries (run AFTER migration)

```sql
-- Migrated order count vs legacy
SELECT count(*) FROM orders WHERE legacy_order_id IS NOT NULL;

-- Orders without any items (data anomaly — investigate)
SELECT o.id, o.legacy_order_id FROM orders o
LEFT JOIN order_items oi ON oi.order_id = o.id
WHERE oi.id IS NULL AND o.legacy_order_id IS NOT NULL
LIMIT 20;

-- Orders without addresses (acceptable if legacy schema lacked them)
SELECT o.id, o.legacy_order_id FROM orders o
LEFT JOIN order_addresses oa ON oa.order_id = o.id
WHERE oa.id IS NULL AND o.legacy_order_id IS NOT NULL
LIMIT 20;

-- Status distribution sanity check
SELECT status, count(*) FROM orders
WHERE legacy_order_id IS NOT NULL
GROUP BY status ORDER BY count(*) DESC;
```
