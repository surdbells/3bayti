## Phase summary

M3.1.2 builds the **strangler-fig adapter** at mobile's data layer. It provides the same public API as the existing `NetworkService` (`post_request(body, url)`, `get_request(url)`) while internally routing through `@3bayti/api-client`'s `ENDPOINT_ROUTING` table. This unlocks the mobile auth flip (M3.1.3) and subsequent feature flips without requiring all 120 call sites to be rewritten upfront.

### Architecture

```
   ┌─────────────────────────────────┐
   │ Mobile call sites (120 of them) │
   │ networkService.post_request(...)│  ← unchanged
   └────────────┬────────────────────┘
                │
                ▼
   ┌─────────────────────────────────┐
   │ MobileNetworkAdapter (NEW)      │
   │ Same public API as NetworkService│
   └────────────┬────────────────────┘
                │
        ┌───────┴───────┐
        ▼               ▼
   [routed?]       [unrouted]
   target=new:     fall through to
   v3 + xlate      legacy NetworkService
```

The adapter is a **drop-in replacement** by design — its public API matches `NetworkService` exactly, so M3.1.3+ call-site migrations are mechanical injection swaps (`inject(NetworkService)` → `inject(MobileNetworkAdapter)`).

## Design decisions made during M3.1.2

### 1. Reverse-index from ENDPOINT_ROUTING (not separate mapping table)

**Decision:** Build the URL→routeKey map at module load by walking `ENDPOINT_ROUTING` and indexing by `oldPath` + HTTP method.

**Why:** A separate mapping table would drift from `ENDPOINT_ROUTING` over time. By deriving at load time, every routing-table edit (M3.1.1g-style ENDPOINT_ROUTING additions) automatically updates this lookup with no co-edit.

### 2. Token-in-body → Authorization: Bearer header

**Decision:** Adapter extracts `token` from legacy request bodies and injects `Authorization: Bearer <token>` header for v3 routes. Drops `id` from body entirely (v3 derives user from JWT).

**Why:** Legacy mobile authenticates by including `{id, token}` in every request body. v3 uses standard `Authorization: Bearer` headers via `AuthMiddleware`. Centralising this translation in the adapter means call sites don't need to know about JWT vs token-in-body. They keep doing exactly what they already do.

**Edge cases handled:**
- Empty string token (`token: ''`): no header emitted. Matches legacy unauthenticated calls (e.g. `/users/login`).
- Missing token: no header emitted.
- Non-string token (e.g. number): drop, no header. Defensive against future mis-types.

### 3. Response envelope translation — v3 unwrap → legacy wrap

**Decision:** v3 responses are unwrapped from `{data: ...}` (or pass through if no `data` key) and re-wrapped in the legacy envelope `{response_code: 200, status: 'success', message: '', data: <unwrapped>}`.

**Why:** Mobile call sites have a deeply embedded pattern: `if (response.response_code === 200) { use response.data; }`. Preserving this pattern is the entire value of the adapter — call sites stay unchanged.

**Special case:** Login response has custom top-level shape (`access_token`, `refresh_token`, `user`), NOT `{data: ...}`. Adapter forwards the entire response object as `envelope.data`, so call sites accessing `response.data.access_token` still work.

### 4. HTTP errors via SUCCESS channel, network errors via ERROR channel

**Decision:** When v3 returns 4xx/5xx with a response body, the adapter resolves the Observable SUCCESSFULLY but with an error envelope (`{response_code: <status>, status: 'error', message: ..., data: null}`). Only network-level errors (status 0) propagate via the error channel.

**Why:** Legacy NetworkService propagates HTTP-level errors via Observable's error channel using a string message. But legacy call sites typically have TWO handlers:
- `next` checks `response.response_code === 200` (handles 4xx/5xx the legacy backend returned with response_code !== 200)
- `error` shows a toast for transport errors

Without this translation, call sites that previously got 4xx via `response_code` would suddenly get them via `error` callback — surprising regression. The shipped behaviour preserves the pattern.

### 5. Fall-through to NetworkService for unrouted URLs

**Decision:** When `resolveRouteKey()` returns null (URL not in `ENDPOINT_ROUTING`), the adapter delegates to the original `NetworkService`. Same when an entry has `target: 'old'`.

**Why:** ~30 of mobile's 88 legacy endpoints aren't in `ENDPOINT_ROUTING` yet (chat, wishlist, payment internals, etc.). Those keep working via the legacy path until M3.1.x adds entries for them.

### 6. Function extraction for testability

**Decision:** `translateRequestBody` and `toLegacyEnvelope` are top-level exports, not class-private methods.

**Why:** Pure functions are easier to unit-test than class methods. Module-scope exports avoid the `(adapter as any).translateRequestBody(...)` test-pollution pattern. The class still calls them internally.

### 7. No path parameter support in this commit

**Decision:** `callV3()` passes `undefined` for `resolveUrl`'s params argument.

**Why:** No current mobile call site uses parameterised paths via this entry point. When M3.1.3+ flips a call site that needs path params (e.g. `/me/addresses/:id`), extend the adapter then. YAGNI for M3.1.2.

## Discrepancies between M3 plan and what shipped

The M3 plan's description of M3.1.2 had several specific points that turned out to be inaccurate when I dug into the codebase. Documenting these honestly:

| M3 plan claimed | Reality |
|---|---|
| "Mobile's NetworkService has interceptor-like behavior (token attachment, OTP user-id handling, response unwrapping)" | NetworkService is a thin HttpClient wrapper. ~40 lines. Does NONE of that. Token attachment happens at each call site by copying `{id, token}` into the body. |
| "37 call sites" | 120 call sites across 80 unique endpoints. |
| "RoutedHttpClient" exists and can be wrapped | RoutedHttpClient exists only in apps/web. Mobile uses HttpClient directly. The adapter calls HttpClient directly (NOT a re-wrap of apps/web's class). |
| "Adapter has tests for translate functions (small Jasmine suite)" | ✅ Tests written, but mobile CI doesn't actually run them — type-check + build only. |

None of these caused real problems; they just changed the shape of the work. The adapter I built handles the real complexity (token-in-body translation, response envelope translation) which the plan understated.

## Pre-existing CI/test limitations (NOT fixed in M3.1.2)

1. **Mobile CI doesn't run tests.** `Mobile — type-check & build` workflow runs `pnpm type-check` and `pnpm build` only. No `pnpm test` step. My Jasmine spec compiles but doesn't execute in CI.

2. **`checkout.page.spec.ts` is broken in main.** Imports `CheckoutComponent` but the actual class is `CheckoutPage`. Blocks running `ng test` locally. Discovered during 1.2c when I tried to run my tests. Out of M3.1.2 scope; flagged for separate cleanup work.

3. **No HttpClient testing harness in mobile.** `HttpClientTestingModule` is never imported anywhere. Means we can't unit-test the class methods that wrap HttpClient (the `route`, `callV3`, `translateError` methods) without first introducing the testing harness. Pure functions are testable; HTTP-touching methods aren't.

These are all M4-or-later hardening concerns, not M3.1.2 blockers.

## What's NOT in M3.1.2 scope

- **Path parameter support** for routed calls. Add when first call site needs it (M3.1.3+).
- **Token refresh on 401.** Adapter doesn't handle refresh. When v3 returns 401, the call site sees `response_code: 401` in the envelope and handles per existing logic (typically: redirect to login). If automatic refresh is wanted, add in M3.1.3+ or M4 hardening.
- **Retry on transient failures.** Call-site decision.
- **Caching.** Call sites manage their own caches.
- **Migration of any call sites.** M3.1.3+ phases.
- **Test runner wiring in CI.** Pre-existing limitation; M4 hardening.
- **Fix of `checkout.page.spec.ts`.** Pre-existing rot; separate cleanup.
- **HttpClient testing harness for class-method tests.** Pre-existing limitation; M4 hardening.
