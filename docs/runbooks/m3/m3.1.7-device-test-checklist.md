# M3.1.7 — Device-Test Checklist

**When to run:** Before promoting M3.1.7 to production. Several of these
flows touch live Noon endpoints (refund, dispute simulation) so run in
sandbox first.

**Pre-flight (operator):**

- [ ] Production env has all required env vars set:
  - [ ] `NOON_API_BASE` (sandbox for staging tests, live for prod)
  - [ ] `NOON_BUSINESS_IDENTIFIER`, `NOON_APP_IDENTIFIER`, `NOON_APP_KEY`
  - [ ] `NOON_WEBHOOK_SECRET` (required when `NOON_VERIFY_SIGNATURE=true`)
  - [ ] `NOON_VERIFY_SIGNATURE` (default `false` for initial deploy)
  - [ ] `ZEPTOMAIL_API_TOKEN` (only if `APP_ENV=prod`)
  - [ ] `ZEPTOMAIL_FROM_EMAIL` + `ZEPTOMAIL_FROM_NAME`
  - [ ] `ADMIN_NOTIFICATION_EMAILS` (CSV; can be empty in dev)
- [ ] Cron job for `orders:reconcile-pending` scheduled at 5min cadence
- [ ] Test admin user with `is_admin=true` provisioned
- [ ] Test vendor user with `is_vendor=true` + linked Vendor entity
- [ ] At least one paid + delivered order from a previous milestone to
      use as a refund test target
- [ ] Mobile app build deployed to test device (Android + iOS if possible)

## A. Backend smoke (curl / Postman against api-v3.3bayti.ae)

### A.1 Webhook signature verifier (Phase A)

- [ ] With `NOON_VERIFY_SIGNATURE=false`: `POST /v3/payment/webhook/noon`
      with arbitrary body returns 200 (LoggingOnlyVerifier behaviour)
- [ ] With `NOON_VERIFY_SIGNATURE=true` AND `NOON_WEBHOOK_SECRET` set:
      same POST without `X-Noon-Signature` header returns 401
- [ ] Same POST with a valid HMAC-SHA256 signature returns 200
- [ ] Same POST with tampered body but original signature returns 401
- [ ] Boot the API without `NOON_WEBHOOK_SECRET` set AND
      `NOON_VERIFY_SIGNATURE=true` — container resolution should throw
      a `RuntimeException` (fail-fast safety)

### A.2 Reconciliation cron (Phase B)

- [ ] Manually mark a recent test order's `created_at` to >15min ago
      while keeping status `pending_payment`
- [ ] Run `php bin/console orders:reconcile-pending --dry-run`
- [ ] Verify it reports the order would be reconciled (no DB change yet)
- [ ] Run without `--dry-run`
- [ ] Verify order transitioned to PAID or FAILED based on Noon's
      authoritative response
- [ ] Run again immediately — should be a no-op (idempotent)

### A.3 Vendor orders surface (Phase C)

(Bearer = vendor user's token)

- [ ] `GET /v3/vendor/orders` returns paginated list with only orders
      containing this vendor's items
- [ ] `GET /v3/vendor/orders?status=fulfilling` filters correctly
- [ ] `GET /v3/vendor/orders?status=pending_payment` returns empty
      (pending_payment excluded from vendor view)
- [ ] `GET /v3/vendor/orders/{id}` returns single order with items
      filtered to caller's vendor
- [ ] Cross-vendor `GET /v3/vendor/orders/{other-vendor-only-id}`
      returns 404 (NOT 403)
- [ ] Non-vendor user gets 403 `vendor_required` on all vendor routes
- [ ] PATCH item to `accepted` (from pending) succeeds, returns 200
- [ ] PATCH item to `delivered` (from pending — illegal jump) returns
      422 with `allowed_transitions: ['accepted', 'rejected']`
- [ ] Cross-vendor item id in PATCH returns 404
- [ ] All items marked delivered → order status rolls up to DELIVERED

### A.4 Admin orders surface (Phase D)

(Bearer = admin user's token)

- [ ] `GET /v3/admin/orders` returns cross-vendor list with full counts
- [ ] `GET /v3/admin/orders?user_id=X` filters to specific customer
- [ ] `GET /v3/admin/orders/{id}` emits an `audit_log` row with
      `action='viewed'`, `subject_type='Order'`, `subject_id=id`
- [ ] `PATCH /v3/admin/orders/{id}/status` with body `{status: 'paid'}`
      from any state succeeds (admin bypasses transition validation)
- [ ] Audit row with `action='overridden'` emitted with full
      before/after diff in `changes` JSONB
- [ ] Non-admin user (regular customer) gets 403 on all admin routes

### A.5 Refund flow (Phase E)

(Use a sandbox order in `delivered` state with a real Noon ref)

- [ ] `POST /v3/admin/orders/{id}/refund` with body
      `{amount: '10.00', reason: 'partial test'}` returns 200
- [ ] Order status unchanged (partial refund doesn't roll status)
- [ ] `payment_transactions` has new row: `operation='REFUND'`,
      `status='Refunded'`, amount matches
- [ ] Audit row emitted with `refund_amount`, `is_full_refund: false`
- [ ] Issue a second partial refund for the remaining balance — should
      succeed AND roll order to REFUNDED
- [ ] Third refund attempt (over-balance) returns 422
      `refund_exceeds_balance`
- [ ] Refund with `reason` missing returns 422
- [ ] Refund of a `pending_payment` order returns 422 `order_not_refundable`

### A.6 Cancellation flow (Phase F)

- [ ] Admin: `POST /v3/admin/orders/{pending-payment-order-id}/cancel`
      with `{reason: 'test'}` returns 200, order CANCELLED, NO gateway
      call (verify no REFUND row in `payment_transactions`)
- [ ] Admin: same on a PAID order returns 200, order CANCELLED, REFUND
      row created with `status='Refunded'`
- [ ] Admin: same on a SHIPPED order returns 422
      `cancellation_not_allowed`
- [ ] Admin: same on an already CANCELLED order returns 200 with
      `cancellation.was_already_cancelled: true`, NO new audit row
- [ ] Customer: `POST /v3/orders/{pending-payment-order-id}/cancel`
      with `{reason: 'changed mind'}` returns 200 (reason optional)
- [ ] Customer: same on a PAID order returns 422 with 'contact support'
      message
- [ ] Customer: cross-user order id returns 404 (NOT 403)
- [ ] Cancellation email sent to customer (check ZeptoMail logs or
      InMemoryMailer in test env)

### A.7 Dispute persistence (Phase G)

- [ ] Send a synthetic webhook payload with
      `eventType: 'CHARGEBACK_OPENED'` and a `disputeId` matching a
      known `provider_order_ref`
- [ ] Returns 200; `order_disputes` row created with status `open`
- [ ] Re-deliver the same webhook — second call should NOT create a
      duplicate row (idempotency via unique `provider_dispute_id`)
- [ ] Synthetic webhook with `provider_order_ref` that doesn't match
      any local order — row IS created with `order_id=NULL` (orphan
      capture)
- [ ] `GET /v3/admin/disputes` returns paginated list
- [ ] `GET /v3/admin/disputes?status=open` filters correctly
- [ ] `GET /v3/admin/disputes/{id}` emits ACTION_VIEWED audit row
- [ ] `PATCH /v3/admin/disputes/{id}` with `{status: 'resolved_won',
      resolution_note: 'evidence provided'}` returns 200, audit
      ACTION_OVERRIDDEN row emitted
- [ ] Admin alert email sent (if `ADMIN_NOTIFICATION_EMAILS` set)

### A.8 Email notifications (Phase H)

(In production: verify with real test recipients. In dev: check
`NullMailer` structured logs.)

- [ ] Place a test order → confirm `mail.would_send` (or
      `mail.zeptomail.sent`) log lines for:
  - [ ] Customer (template `order.placed.customer`)
  - [ ] Each vendor in the order (template `order.placed.vendor`)
- [ ] Complete payment → customer gets `order.paid.customer`
- [ ] Cancel payment (use Noon test card that fails) → customer gets
      `order.payment_failed.customer`
- [ ] Vendor marks item shipped → customer gets `order.shipped.customer`
      WITH the correct item_name
- [ ] Vendor marks item delivered → customer gets
      `order.delivered.customer`
- [ ] Cancel paid order → customer gets `order.cancelled.customer`
      WITH refund_amount; vendors get `order.cancelled.vendor`
      WITH 'do not ship' language
- [ ] Issue partial refund → customer gets `order.refunded.customer`
      WITH 'partial refund' language
- [ ] Issue full refund → customer gets 'full refund' language
- [ ] Webhook fires dispute event → admins in
      `ADMIN_NOTIFICATION_EMAILS` get `dispute.opened.admin` with
      ALERT prefix in subject
- [ ] Re-deliver any webhook → NO duplicate emails (idempotency
      via transition kind / dispute null return)

### A.9 Production smoke after flag flips

After flipping `NOON_VERIFY_SIGNATURE=true` in production:

- [ ] Watch logs for 24 hours for `noon.webhook: signature
      verification failed` warnings
- [ ] If any seen: capture the body + signature header, verify HMAC
      manually, decide whether to roll back the flag or update the
      verifier

## B. Mobile (Phase I)

Test on physical device (Android first, iOS second).

### B.1 Customer cancel button

(Log in as a customer who has a recent `pending_payment` order — i.e.
abandoned a checkout webview)

- [ ] Open `/my-orders` — pending_payment order visible
- [ ] 'Cancel order' button visible ONLY on pending_payment orders
      (not paid/delivered)
- [ ] Tap button → ActionSheet appears with 'Yes, cancel order' /
      'Keep order'
- [ ] Tap 'Yes' → order pill updates to CANCELLED immediately,
      success toast appears
- [ ] Pull-to-refresh OR re-navigate — order still CANCELLED
- [ ] Tap cancel on an already-cancelled order → toast says 'already
      cancelled' (idempotent path)
- [ ] Airplane mode → tap cancel → error toast, order stays in
      original state
- [ ] Cancel button does NOT appear on customer's PAID/FULFILLING/
      SHIPPED orders

### B.2 Vendor orders list

(Log in as a vendor user with at least one fulfilment-stage order)

- [ ] Open store-dashboard — 'Manage orders' action card visible at
      top of quick-actions grid
- [ ] Tap → navigates to `/vendor-orders`
- [ ] List renders with status filter chips: All / Paid / Fulfilling /
      Shipped / Delivered
- [ ] Tap 'Fulfilling' chip — only fulfilling-status orders shown
- [ ] Tap 'All' — full list restored
- [ ] Each order card shows: order reference, date, status pill,
      item count, total
- [ ] Tap 'View items' — items expand inline showing image/name/qty/price
- [ ] Tap 'Hide items' — items collapse
- [ ] Tap 'Manage' button → navigates to `/vendor-orders/:id`
- [ ] Scroll to bottom — infinite scroll loads next page

      gets bounced to home with error toast

### B.3 Vendor order detail + state machine

(Use a vendor order with items in `pending` status)

- [ ] Open order detail — order summary card shows reference + date
      + total + status pill
- [ ] Each item card shows image + name + qty + price + item status
      pill
- [ ] For `pending` items: 'Accept' (success-color) and 'Reject'
      (outline danger) buttons visible
- [ ] For `accepted` items: 'Mark preparing' button visible
- [ ] For `preparing` items: 'Mark shipped' visible
- [ ] For `shipped` items: 'Mark delivered' visible
- [ ] For `delivered` items: NO action buttons
- [ ] For `rejected` items: NO action buttons
- [ ] Tap 'Accept' → ActionSheet confirmation appears
- [ ] Confirm → item status pill updates immediately to ACCEPTED,
      'Mark preparing' button appears
- [ ] Order summary status pill may roll up (e.g. paid → fulfilling)
      after re-fetch
- [ ] Marking all items delivered → order summary rolls to DELIVERED
- [ ] Airplane mode → tap transition → item status rolls back to
      original (verify by checking pill state before/after)
- [ ] Rapid double-tap on a transition button — only one PATCH fires
      (verify in network panel or backend logs)
- [ ] Try transitioning a `shipped` item to `accepted` (by editing
      the request manually) — backend returns 422 with
