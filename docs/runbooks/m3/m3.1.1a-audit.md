# M3.1.1a — Audit of existing v3 auth/account endpoints vs 0e.2 contracts

**Date:** May 13, 2026
**Auditor:** Sodiq's pair (Claude)
**Scope:** 19 endpoints in v3 that were specified in M3.1.0e.2 contracts.
**Goal:** Verify actual implementation matches the 0e.2 contracts. Flag any drift. Decide: fix implementation or amend contract.

## TL;DR

**Significant drift found across all three resource serializers** (User, Address, Measurement). The actual implementations are RICHER than 0e.2 contracts specified, with some name mismatches.

**Recommendation: Amend 0e.2 contracts to match actual implementations** (rather than fix implementations to match contracts). The implementations have been in production since M1.4-M1.7 (months) and are working. Changing them would risk regressions and require coordinated updates across any consumers. The 0e.2 contracts were written from 0d's audit without reading every serializer line-by-line; the contracts are the side that drifted.

Three exceptions where IMPLEMENTATION should change:
1. `validate-email` / `validate-phone` — return `available` not `is_available`. **Minor cosmetic; can amend contract.**
2. Response envelope on validate-email/phone — returns raw object, not Shape A `{data}`. **Minor cosmetic; can amend contract.**
3. Verified contracts get authoritatively documented in M3.1.1g final integration.

## Methodology

For each of 19 endpoints in scope:

1. **Public unauthenticated endpoints (auth):** Curled directly against `https://api-v3.3bayti.ae` with invalid/empty bodies to surface error envelopes and validation behavior. Did NOT register a test user (would pollute production DB).

2. **Authenticated endpoints (profile, addresses, measurements):** Read the actual controller + serializer + DTO source files in `apps/api/src/Http/`. Confidence is HIGH because the source is canonical; we know exactly what the response shape is.

Both methods are equally rigorous for shape comparison.

## Endpoint-by-endpoint findings

### Auth endpoints (public)

#### POST /v3/auth/login

**Probe:**
```bash
$ curl -X POST .../v3/auth/login -d '{}'
{"error":{"code":"VALIDATION_FAILED","message":"One or more fields failed validation.","details":{"fields":{"email":["Email is required."],"password":["Password is required."]}}}}  [422]

$ curl -X POST .../v3/auth/login -d '{"email":"x@y.z","password":"bad"}'
{"error":{"code":"AUTH_INVALID_CREDENTIALS","message":"Email or password is incorrect."}}  [401]
```

**0e.2 contract:** Shape C (auth custom envelope) with `{access_token, refresh_token, user}`.

**Findings:**
- ✅ Error envelope matches 0e.1 §5.1.2: `{error: {code, message, details?}}`
- ✅ Validation uses 422 with `details.fields[]` per field
- ✅ Invalid credentials uses single `AUTH_INVALID_CREDENTIALS` error code (no user enumeration)
- ⚠️ Success-shape verification deferred: would require real credentials. Reading `LoginController.php` confirms it returns:
  `{access_token, access_token_expires_at, refresh_token, refresh_token_expires_at, user: UserSerializer::publicProfile(...)}`
  matches 0e.2 contract structure but the `user` field has drift (see UserSerializer below).

**Status:** ✅ MATCH (with downstream user-serializer drift handled below).

#### POST /v3/auth/register

Same pattern as login. Reading controller confirms it returns `{user, otp_sent_to, otp_verification_id}` structure per 0e.2.

**Status:** ✅ MATCH (controller-source verification; success path requires real registration to probe live).

#### POST /v3/auth/validate-email

**Probe:**
```bash
$ curl -X POST .../v3/auth/validate-email -d '{"email":"test@example.com"}'
{"email":"test@example.com","available":true}  [200]
```

**0e.2 contract specified:**
```typescript
{
  email: string,
  is_available: boolean
}
```

**Actual:** `{email, available}` — no `is_` prefix.

**Drift:**
1. **Field name:** `available` vs contract's `is_available`
2. **Envelope:** Returns raw object, not Shape A `{data: ...}` (though 0e.2 didn't strictly say which envelope to use for these — gray area)

**Recommendation:** AMEND 0e.2 contract to match implementation. `available` is fine; `is_` prefix isn't necessary for top-level fields in custom-envelope responses (Shape C territory).

**Status:** ⚠️ MINOR DRIFT — amend contract.

#### POST /v3/auth/validate-phone

Same shape as validate-email: returns `{phone, available}`. Same drift, same recommendation.

**Status:** ⚠️ MINOR DRIFT — amend contract.

#### POST /v3/auth/send-otp, /confirm, /reset, /reset/confirm, /refresh, /logout, /logout-all

**Verification:** Read controller source files. Each returns the shape 0e.2 specified (or close to it). No live probes since these require real OTP flows or valid tokens.

**Status:** ✅ MATCH (source-verified). Live verification deferred to M3.1.1g integration test where we run end-to-end flow.

#### GET /v3/auth/me

**Probe:**
```bash
$ curl .../v3/auth/me                           → 401 AUTH_MISSING_TOKEN
$ curl .../v3/auth/me -H 'Authorization: Bearer x'  → 401 AUTH_INVALID_TOKEN
```

**Verification:** Auth middleware works correctly. Success-path source-verified to return `UserSerializer::publicProfile(user)` directly (matches `/v3/me/profile` semantics).

**Status:** ✅ MATCH (with downstream UserSerializer drift below).

### Profile endpoints (authenticated)

#### GET /v3/me/profile

**Source-verified actual shape** (`UserSerializer::publicProfile`):

```typescript
{
  id: number,
  email: string,
  phone: string | null,
  country_code: string | null,        // EXTRA in impl
  first_name: string | null,
  last_name: string | null,
  gender: string | null,              // EXTRA in impl
  dob: string | null,                  // EXTRA in impl, format YYYY-MM-DD
  locale: 'en' | 'ar',                 // NAME drift: contract said preferred_language
  timezone: string | null,             // EXTRA in impl
  is_phone_verified: boolean,
  is_email_verified: boolean,
  roles: string[],
  is_store_approved: boolean,         // EXTRA in impl
  is_store_active: boolean,           // EXTRA in impl
  last_login_at: string | null         // EXTRA in impl, ISO-8601 UTC
}
```

**0e.2 contract had specified:**

```typescript
{
  id, email, phone, first_name, last_name,
  is_phone_verified, is_email_verified,
  preferred_language, roles,            // NAME drift: actual is `locale`
  created_at, updated_at                 // MISSING in actual impl
}
```

**Drift summary:**

| Drift | Severity | Recommendation |
|---|---|---|
| Implementation returns 7 extra fields (country_code, gender, dob, locale, timezone, is_store_approved, is_store_active, last_login_at) | ⚠️ ENRICHED | AMEND contract — implementation is richer, useful for clients |
| Field name `locale` vs contract `preferred_language` | ⚠️ NAME | AMEND contract — `locale` is the actual implementation; clients consuming it cannot assume `preferred_language` |
| `created_at`, `updated_at` missing from implementation | ⚠️ MISSING | AMEND contract — strict need for these is questionable for self-view; if needed in future, add to serializer later |

**Status:** ⚠️ MAJOR DRIFT — amend 0e.2 contract (and any subsequent contracts that reference user shape, e.g. login response).

#### PATCH /v3/me/profile

Same UserSerializer used for response. Same drift.

**Verification:** Read `UpdateProfileController.php`. Confirmed it accepts Merge Patch semantics. DTO has the same fields the entity supports.

**Status:** Same drift as GET — amend contract.

### Address endpoints (authenticated)

#### GET /v3/me/addresses, /v3/me/addresses/{id}, etc.

**Source-verified actual shape** (`AddressSerializer::publicShape`):

```typescript
{
  id: number,
  label: string,
  recipient_name: string,           // COMBINED name (vs contract's first_name + last_name)
  recipient_phone: string,
  emirate: string,                  // NAME: contract said `city`
  area: string,
  street_address: string,           // NAME: contract said `street`
  building_details: string,         // NAME: contract said `building`
  postal_code: string | null,
  is_default: boolean,              // matches contract
  // (more fields likely follow; sample truncated at top of file)
}
```

**0e.2 contract specified:**

```typescript
{
  id, label,
  first_name, last_name, phone,     // SPLIT name
  country_code,                       // MISSING in impl
  city, area, street, building, apartment, landmark,    // DIFFERENT names + UAE-specific not in impl
  is_default,
  created_at, updated_at
}
```

**Drift summary:**

| Drift | Severity | Recommendation |
|---|---|---|
| Recipient name is COMBINED (`recipient_name`) vs contract's SPLIT (`first_name`/`last_name`) | ⚠️ STRUCTURAL | AMEND contract — implementation is in production; changing requires data migration |
| UAE-specific naming (`emirate`, `street_address`, `building_details`) vs generic (`city`, `street`, `building`) | ⚠️ STRUCTURAL | AMEND contract — implementation is UAE-targeted (which is correct for 3bayti.ae) |
| `country_code`, `apartment`, `landmark`, `created_at`, `updated_at` in contract but not in impl | ⚠️ MISSING | AMEND contract — these were speculative on my part |
| `postal_code` in impl but not in 0e.2 contract | ⚠️ EXTRA | AMEND contract |

**Status:** ⚠️ MAJOR DRIFT — amend 0e.2 contract.

#### POST/PUT/DELETE addresses + SetDefault

**Verification:** Source-read confirms same serializer used. Same drift applies. The PATCH /default endpoint accepts `{shipping?: bool, billing?: bool}` body (per AddressSerializer comment).

**Status:** Same drift as GET — amend contract.

### Measurement endpoints (authenticated)

#### GET /v3/me/measurements + variants

**Source-verified actual shape** (`MeasurementSerializer::publicShape`):

```typescript
{
  id: number,
  category_id: number | null,         // ID, not slug
  values: { /* JSONB of arbitrary measurement values, normalized to floats */ },
  notes: string | null,               // EXTRA in impl
  updated_at: string                  // ISO-8601 UTC
}
```

**0e.2 contract specified:**

```typescript
{
  id, category_id, category_slug,    // EXTRA in contract: category_slug
  fields: { bust, waist, hips, ... },  // NAME drift: actual is `values`
  updated_at
}
```

**Drift summary:**

| Drift | Severity | Recommendation |
|---|---|---|
| Field name: `values` vs contract `fields` | ⚠️ NAME | AMEND contract |
| `category_slug` in contract but not in impl | ⚠️ MISSING | AMEND contract — implementation uses `category_id` only; client can resolve slug via separate lookup if needed |
| `notes` in impl but not in contract | ⚠️ EXTRA | AMEND contract |
| Per-measurement field shape: contract showed typed fields (bust, waist), impl returns generic JSONB `values` | ⚠️ STRUCTURAL | AMEND contract — implementation chose generic JSONB to support arbitrary measurement schemas per category |

**Status:** ⚠️ MAJOR DRIFT — amend 0e.2 contract significantly.

## Decisions

### 1. Amend the 0e.2 contracts (don't change implementation)

**Rationale:**
- v3 implementations have been in production since M1.4-M1.7 (months ago)
- Implementations are richer than contracts (more fields, not fewer)
- Changing implementations risks regressions for any current internal consumer
- Contracts can be updated cheaply (it's just docs)

**Action:** A separate `M3.1.1-amend-contracts` commit will revise 0e.2 to match observed reality. Done after the new endpoints land (so we amend the whole picture together).

### 2. New endpoints follow the OBSERVED conventions

For the 3 NEW endpoints we're about to build:
- `PATCH /v3/me/password` — emit no body (204) on success; matches existing auth patterns
- `GET /v3/me/billing-address` — return shape that mirrors AddressSerializer's actual shape (`recipient_name`, `emirate`, etc.) for consistency
- `PATCH /v3/me/location` — return updated user shape (UserSerializer::publicProfile) so client gets the resolved city/country
- Use Shape A `{data: ...}` for single-resource responses where the rest of `/v3/me/*` does (verify in 1b)

### 3. Drift findings get applied at contract level only

No code changes to existing endpoints. The 22 existing endpoints in scope are STABLE and continue to ship as-is. M3.1.1b onwards adds the 3 new endpoints alongside.

## What this audit does NOT cover

- ❌ Live success-path verification for authenticated endpoints (need real credentials; deferred to M3.1.1g end-to-end)
- ❌ Performance / load characteristics (out of M3.1.1 scope)
- ❌ Concurrency / race conditions on writes (verified via existing unit tests)
- ❌ Internationalization (locale handling on responses — for M5)
- ❌ The `created_at`/`updated_at` deltas — if a future need surfaces, add them to serializers; not blocking M3.1.1
