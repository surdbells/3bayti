# M3.1.7 — Completion Runbook

**Status:** ✅ Complete.
**Date:** Friday, May 15, 2026
**Final commit on `main`:** `9fa99f7` (M3.1.7-I)

## Executive summary

M3.1.7 was the **vendor + admin + safety hardening** milestone. With
M3.1.6 closing the customer checkout flow against Noon (cart →
hosted checkout → webhook-confirmed order), M3.1.7 built out the
operator-facing surface that turns those orders into a real
two-sided marketplace:

- Vendors can see and act on their orders (per-line-item lifecycle
  through accept → preparing → shipped → delivered)
- Admins have cross-vendor oversight, with safety overrides and a
  full audit trail of every action including reads
- Refunds (full and partial) and cancellations flow through a
  shared policy layer with auto-refund on paid-order cancels
- Payment disputes (chargebacks) are persisted with first-class
  admin triage
- Webhook signature verification is config-flag gated for safe
  roll-out
- A reconciliation cron unsticks orders that webhooks miss
- Email notifications fire on every meaningful order transition
  to the right audience (customer, vendor, admin)
- Mobile vendor pages let store operators fulfil orders from their
  phones; customers can self-serve cancel pending-payment orders

## Phase ledger

### M3.1.7-A — Config-flag-gated webhook signature verifier (`1fbf5f8`)

**Problem.** M3.1.6 shipped a `LoggingOnlyVerifier` for the Noon
webhook that accepted every payload as authentic — necessary
during early integration when Noon's signature format was being
discovered, but unsafe for production.

**Fix.** Bound `NoonWebhookSignatureVerifier` in DI based on a
config flag `NOON_VERIFY_SIGNATURE`:

- `false` / unset / unknown value → `LoggingOnlyVerifier` (M3.1.6
  behaviour)
- `true` / `'1'` → `HmacSha256SignatureVerifier` with
  fail-fast on missing `NOON_WEBHOOK_SECRET`

Roll-out plan documented in `.env.example`:

1. Capture real Noon webhook payloads + signatures in sandbox
2. Verify `HmacSha256SignatureVerifier::verify()` accepts them
3. Flip flag in staging; monitor logs for false negatives
4. Flip flag in production

**Decision** (Q2=B): config flag chosen over hard-coded enable so
we can flip without redeploy and roll back instantly if Noon's
signature scheme turns out to differ from the documented contract.

**Tests:** 10 cases inline-replicating the DI factory logic; covers
all flag-truthiness/falsiness combinations + missing-secret path.

### M3.1.7-B — Reconciliation cron (`86e0398`)

**Problem.** A webhook failure (network blip, Noon outage, our
500) leaves an order in `pending_payment` indefinitely. The
customer paid; we just don't know it.

**Fix.** New Symfony Console command `orders:reconcile-pending`:

```bash
php bin/console orders:reconcile-pending --dry-run --cutoff-min=15 --batch-size=50
```

For each order stuck in `pending_payment` for ≥15 minutes (Q3=B
locked), call `gateway.retrieveOrder` server-to-server to get
Noon's authoritative status, then `applyAuthoritativeStatus` (same
function the webhook handler uses). Idempotent — re-running on the
same stuck orders converges.

**Production deployment:** add to system cron with 5-minute cadence
(decision Q3=B). 50-order batch size keeps memory bounded.

**Tests:** 9 cases using Symfony's `CommandTester` — dry-run mode,
batch limit, cutoff window, mixed-terminal-status response handling.

### M3.1.7-C — Vendor orders surface API (`6b2afa9`)

**Problem.** Vendors couldn't see their own orders or transition
items through the fulfilment lifecycle.

**Fix.** Three endpoints under new `VendorAuthMiddleware`:

- `GET /v3/vendor/orders?limit&offset&status` — paginated list
  scoped to the authenticated user's stores
- `GET /v3/vendor/orders/{id}` — single order detail with items
  filtered to caller's vendor
- `PATCH /v3/vendor/orders/{orderId}/items/{itemId}/status` —
  vendor-driven per-item transition

**Per-line-item state machine** (Q4=A locked decision) — vendor
allowed transitions:

```
pending    → accepted | rejected
accepted   → preparing
preparing  → shipped
shipped    → delivered
```

Other transitions (cancelled / returned / refunded) restricted to
admin path. Order-level status rolls up from item statuses via
`Order::recomputeStatusFromItems()`:

- All items DELIVERED → order DELIVERED
- All items SHIPPED-or-later → order SHIPPED
- Any item ACTIVE → order FULFILLING

**Cross-vendor isolation: defense in depth.** Both the repository
(filters by vendor ids at SQL time) AND the serializer (strips
other vendors' items from the response) enforce isolation.
Cross-vendor 404 not 403 to avoid leaking existence.

**Tests:** 19 cases including legal transitions, illegal transitions
(422 with `allowed_transitions` list), cross-vendor 404
preservation, order-level rollup verification.

### M3.1.7-D — Admin orders surface + audit log (`a950e2e`)

**Problem.** Admins had no cross-vendor view, no safety overrides
when orders got stuck, and no forensic audit of operator actions.

**Fix.** Four admin endpoints:

- `GET /v3/admin/orders` — paginated cross-vendor list with
  optional filters (status, user_id, vendor_id)
- `GET /v3/admin/orders/{id}` — full unfiltered detail
- `PATCH /v3/admin/orders/{id}/status` — order-level status
  override (bypasses transition validation)
- `PATCH /v3/admin/orders/{orderId}/items/{itemId}/status` —
  item-level override (uses `OrderItem::setItemStatus(adminOverride: true)`)

**Q5=A locked decision: ALL admin actions audited including reads.**
Added `ACTION_VIEWED` and `ACTION_OVERRIDDEN` constants to existing
`AuditLog` entity. Every admin GET emits a `viewed` audit row;
every mutation emits an `overridden` row with full before/after
diff in `changes` JSONB.

**Volume note:** auditing reads ~10x the row volume of writes-only
auditing. Existing index `audit_log_user_created_idx (user_id,
created_at DESC)` handles forensic queries; **retention policy of
1 year recommended** for `audit_log` rows with `action='viewed'`
(write actions retained indefinitely).

**Tests:** 15 cases including audit emission verification on every
endpoint, override of illegal transitions (admin bypass), filter
parameter forwarding.

### M3.1.7-E — Refund flow, full + partial (`0b00148`)

**Problem.** No way to refund a paid order — chargeback was the
only path back.

**Fix.** `POST /v3/admin/orders/{id}/refund` with body:

```json
{ "amount": "50.00", "reason": "customer changed mind" }
```

- `amount` optional — if omitted, refunds the full remaining
  balance (order total minus already-refunded sum)
- `amount` validated: > 0 AND ≤ refundable balance
- `reason` required for audit accountability

**Q6 locked decision:** full AND partial refunds, expanded from the
original Q6=A "full only" to cover the realistic operator workflow
where a customer is unhappy with one item of three.

**Flow:**

1. Validate order is refundable (PAID/FULFILLING/SHIPPED/DELIVERED;
   not already fully refunded)
2. Compute refundable balance via `PaymentTransactionRepository::sumRefundsForOrder` (bcmath 2dp aggregation)
3. Generate idempotency key (`bin2hex(random_bytes(16))`)
4. Call `gateway.refund(providerOrderRef, amount, currency, reason)`
5. On success: persist `Refunded` REFUND `PaymentTransaction`
6. If cumulative refunds ≥ order total: `order.overrideStatus(REFUNDED)`
7. Audit emission with full diff + idempotency_key
8. On gateway failure: persist `Failed` REFUND row (forensic
   record), 502 to caller

**Tests:** 9 cases covering happy path, partial refunds with
balance recalculation, gateway failure recording, full-refund
state rollover, over-balance rejection.

### M3.1.7-F — Cancellation flow (`813fa24`)

**Problem.** No way to cancel orders. Customers stuck with abandoned
checkouts; admins unable to handle support-driven cancellations.

**Fix.** Shared `CancelOrderService` encapsulates the policy, used
by two thin controllers:

- `POST /v3/admin/orders/{id}/cancel` — admin path (any state with
  auto-refund for paid/fulfilling)
- `POST /v3/orders/{id}/cancel` — customer self-serve (pending_payment only)

**State machine:**

```
pending_payment   → cancel locally, NO gateway call
paid / fulfilling → admin: cancel + auto-refund remaining balance
                    customer: 422 "contact support"
shipped / delivered → 422 (use refund flow instead)
cancelled         → 200 idempotent
refunded / failed → 422 (already terminal)
```

**Safety property:** auto-refund failure leaves order in ORIGINAL
state. We don't half-cancel. Failed refund attempt persisted (for
forensics), 502 to caller, retry-safe.

**Tests:** 13 cases (8 admin + 5 customer) including idempotent
re-cancel, gateway failure handling, cross-user 404 preservation
for customer path, reason-required validation for admin path.

### M3.1.7-G — Dispute persistence (`c7743a0`)

**Problem.** Noon emits webhook events when a customer files a
chargeback/dispute, but we had no structured surface to triage them
— they disappeared into `payment_webhook_events` raw payloads.

**Fix.** New `order_disputes` table + entity + admin endpoints:

- Migration `Version20260515000001.php` creates `order_disputes`
  with columns: `provider_order_ref`, `provider_dispute_id`
  (UNIQUE where non-null), `event_type`, `status` enum
  (open/in_review/resolved_won/resolved_lost/withdrawn), `amount`,
  `currency`, `reason`, `resolution_note`, `resolved_by_user_id`,
  `resolved_at`, `raw_event` JSONB
- Indexes: `(order_id, created_at DESC)`, `(status)`,
  `(provider_dispute_id)` partial unique, `(provider_order_ref)`
- Constraint `chk_disputes_resolution_pair` ensures terminal
  statuses always have `resolved_at` set
- Webhook controller detects dispute event types
  (`CHARGEBACK_OPENED`, `DISPUTE_OPENED`, `CHARGEBACK_RECEIVED`,
  `DISPUTE_RECEIVED` — placeholder strings pending empirical
  sandbox capture) and persists via
  `OrderDisputeRepository::findByProviderDisputeId` for
  idempotency
- Three admin endpoints:
  - `GET /v3/admin/disputes` (paginated list, status filter)
  - `GET /v3/admin/disputes/{id}` (single, audit ACTION_VIEWED)
  - `PATCH /v3/admin/disputes/{id}` (resolve with status + note,
    audit ACTION_OVERRIDDEN)

**Known limitation:** the exact eventType strings Noon emits are
NOT empirically confirmed at ship time. We catch the documented
patterns; if sandbox observation reveals different values, the
constant `DISPUTE_EVENT_TYPES` in `NoonWebhookController` is the
single seam to update.

**Orphan dispute handling:** if Noon reports a dispute for a
`provider_order_ref` we can't match to a local order, we still
store the dispute (with `order_id = NULL`) for operator
investigation. Better to capture than drop.

**Tests:** 14 cases including idempotent re-delivery, orphan
storage, resolve transitions, audit emission.

### M3.1.7-H — Email notifications (`9b91814`)

**Problem.** No outbound email at all. Customers didn't know their
payment was confirmed; vendors didn't know they had orders to
fulfil; admins didn't know about disputes.

**Fix.** Built `src/Notification/` from scratch:

```
MailerInterface
├── ZeptoMailHttpMailer (production: HTTPS to api.zeptomail.com)
├── NullMailer          (dev/test: logs only)
└── InMemoryMailer      (tests: collects sends)

EmailTemplate enum (10 cases) → OrderEmailTemplateRenderer
                                   → RenderedEmail (subject + text + html)

OrderNotificationService orchestrates:
  orderPlaced       → customer + vendors
  orderPaid         → customer
  orderPaymentFailed→ customer
  itemShipped       → customer (per-item)
  itemDelivered     → customer (per-item)
  orderCancelled    → customer + vendors
  orderRefunded     → customer
  disputeOpened     → admins (from ADMIN_NOTIFICATION_EMAILS env CSV)
```

**Q10 locked decision:** notifications across the full lifecycle
to customer + vendor + admin audiences. Decided HTTPS over SMTP
for cleaner failure semantics and observability.

**Fire-and-forget contract:** every `safeSend()` catches both
`MailerException` and `Throwable`, logs structured, doesn't
rethrow. Notification failures must NEVER abort the primary action.

**Production gate:** `APP_ENV=prod` without `ZEPTOMAIL_API_TOKEN`
throws at container build time — prevents silent mail drops in
prod. Dev/test default `NullMailer` logs would-be sends with
template/order_id correlation.

**Idempotency at the webhook layer:**

- `applyAuthoritativeStatus()` returns `'paid'`|`'failed'`|`''`
  signalling transition kind. Re-deliveries see `''` and skip
  notifying.
- `persistDispute()` returns `OrderDispute|null`. Duplicate
  events return `null` and skip the admin alert.

**Wired into 5 controllers:** InitiateCheckout, NoonWebhook,
TransitionVendorOrderItem, CancelOrderService (both paths),
RefundOrderController.

**Tests:** 32 cases — 13 renderer (incl. XSS escape verification),
10 orchestrator (fan-out, vendor isolation, fire-and-forget),
9 ZeptoMail adapter (5 HTTP status code → exception kind mappings).

### M3.1.7-I — Mobile vendor pages + customer cancel (`9fa99f7`)

**Problem.** Phase C built the vendor API but vendors had no UI to
use it. Customers had no way to abandon a stuck checkout.

**Fix.** Two new mobile pages + cancel button on customer
my-orders:

**Customer cancel button.** Shown conditionally when
`order.status === 'pending_payment'`. ActionSheet confirmation +
optimistic local update + idempotent-aware toast.

**Vendor orders list** (`/vendor-orders`). Status filter chips
(paid / fulfilling / shipped / delivered / all), infinite scroll,
per-card 'Manage' button → detail page. Non-vendor users bounced
back to home.

**Vendor order detail** (`/vendor-orders/:id`). Per-item action
buttons rendered conditionally per state machine (mirroring backend
`legalTransitions()`):

- pending → Accept | Reject
- accepted → Mark Preparing
- preparing → Mark Shipped
- shipped → Mark Delivered

Optimistic UI update + rollback on PATCH failure. Re-fetch after
success to pick up order-level rollup. `is_transitioning` debounce
prevents double-tap.

**Infrastructure:**

- `MobileNetworkAdapter`: added `patch_v3()` mirroring `post_v3`,
  plus `queryParams` support across `post_v3`/`get_v3`/`patch_v3`
- `NetworkService`: added `patch_request()` for completeness
- `feature-flags.ts`: registered 4 new v3-only routes (no legacy
  equivalents)

**i18n:** 27 new keys in both `en.json` and `ar.json` covering
button labels, headings, status filter chips, dashboard nav.

**No new mobile tests** — mobile is integration-tested manually
per the device-test checklist below.

## Production readiness checklist

Before flipping `NOON_VERIFY_SIGNATURE=true` in production:

- [ ] Capture 5+ real Noon webhook payloads + their X-Noon-Signature
      headers in sandbox
- [ ] Verify `HmacSha256SignatureVerifier::verify()` accepts each
      payload with the correct shared secret
- [ ] Confirm `NOON_WEBHOOK_SECRET` is set in production secret
      manager (NOT in committed code or Docker images)
- [ ] Flip flag in staging, monitor `noon.webhook: signature
      verification failed` log line for 24 hours
- [ ] Flip flag in production

Before enabling email notifications in production:

- [ ] `ZEPTOMAIL_API_TOKEN` set in prod secret manager
- [ ] `ZEPTOMAIL_FROM_EMAIL` matches DKIM-verified sender domain
- [ ] `ADMIN_NOTIFICATION_EMAILS` set to ops/security list
- [ ] Verify SPF/DKIM records configured on `3bayti.ae` per
      ZeptoMail onboarding (else mail goes to spam)
- [ ] `APP_ENV=prod` — without this flag, NullMailer is used and
      no real mail goes out

Before depending on the reconciliation cron in production:

- [ ] Add `orders:reconcile-pending` to system cron with 5-minute
      cadence
- [ ] Set up log monitoring on `orders.reconcile.success` and
      `orders.reconcile.error`
- [ ] Verify ENV vars `NOON_API_KEY`, `NOON_API_IDENTIFIER` are
      accessible to the cron user

For the admin audit retention policy:

- [ ] Schedule a quarterly cleanup of `audit_log` rows with
      `action='viewed'` older than 365 days (write actions
      retained indefinitely for compliance)

For the dispute eventType placeholders:

- [ ] On first real dispute in sandbox, capture the actual
      eventType string from `payment_webhook_events.payload`
- [ ] Update `DISPUTE_EVENT_TYPES` constant in
      `NoonWebhookController` if Noon's strings differ from our
      placeholders
- [ ] Backfill any historical dispute rows if the event_type
      column shows our placeholder vs. the real string
