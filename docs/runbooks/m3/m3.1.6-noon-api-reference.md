# M3.1.6 — Noon Payments API Reference (Recon Notes)

Captured during M3.1.6 backend work. This is a working reference for
M3.1.7 (real signature verification) and any future Noon-touching work.
Source: `docs.noonpayments.com` + experimental observations against
the sandbox.

## Endpoint

Single endpoint serves all operations; differentiated by request
body's `apiOperation` field.

- **Sandbox:** `https://api-test.noonpayments.com/payment/v1/order`
- **Live:** `https://api.noonpayments.com/payment/v1/order`

Set via `NOON_API_BASE` env var (without trailing path; controller
appends `/payment/v1/order`).

## Authentication

Three identifiers required (NOT two — the legacy `NOON_API_KEY` is
deprecated; v3 uses three):

- `NOON_BUSINESS_IDENTIFIER` — merchant account identifier
- `NOON_APP_IDENTIFIER` — application within the merchant
- `NOON_APP_KEY` — the secret key

Header format (verified against the iOS SDK reference page,
`docs.noonpayments.com/sdk/reference/ios`):

```
Authorization: Key <base64(business.app:key)>
```

Example construction:

```php
$value = 'Key ' . base64_encode("biz_abc.app_xyz:secret_key_123");
// Authorization: Key e0J1c2luZXNzSWRlbnRpZmllcn0...
```

Back-compat in DI: if `NOON_APP_KEY` is unset but `NOON_API_KEY`
exists, fall back to the legacy var with a deprecation log line.

## Operations

All sent as `POST` with `apiOperation` field. Implemented in `src/
Payment/Noon/NoonPaymentGateway.php`:

| Operation | Purpose | Implemented |
| --- | --- | --- |
| `INITIATE` | Begin a hosted checkout; receive checkout URL | M3.1.6c |
| `SALE` | Auth + capture in one (used implicitly via INITIATE config) | implicit |
| `AUTHORIZE` | Auth without capture (two-phase flow) | not used |
| `CAPTURE` | Capture a prior AUTHORIZE | not used |
| `REVERSE` | Reverse an AUTHORIZE before capture | not used |
| `REFUND` | Refund a captured payment | M3.1.6c (caller TBD M3.1.7) |
| `CANCEL` | Cancel an open order | M3.1.6c (caller TBD M3.1.7) |
| `GET_ORDER` | Fetch order by Noon's order id | M3.1.6c |
| `GET_ORDER_BY_REFERENCE` | Fetch order by our merchant reference | M3.1.6c |

`SALE` happens via `INITIATE` with `configuration.paymentAction =
'SALE'` (single-step auth+capture, no two-phase). This is what
`NoonPaymentGateway::initiateCheckout()` does. If/when we move to
auth-then-capture (e.g. to allow partial captures), the `paymentAction`
config and a follow-up CAPTURE call will be needed.

## Request body shape (INITIATE)

```json
{
  "apiOperation": "INITIATE",
  "order": {
    "reference": "V3-1700000000000-a3f4",
    "amount": "299.50",
    "currency": "AED",
    "channel": "MOBILE",
    "name": "Sodiq Bello"
  },
  "configuration": {
    "returnUrl": "https://api.3bayti.ae/v3/checkout/return/V3-1700000000000-a3f4",
    "paymentAction": "SALE"
  },
  "billing": {
    "street": "123 Main St",
    "city": "Dubai",
    "stateProvince": "Bur Dubai",
    "country": "AE",
    "postalCode": null
  },
  "shipping": { /* same shape as billing */ },
  "customer": {
    "email": "sodiq@example.com",
    "firstName": "Sodiq",
    "lastName": "Bello"
  }
}
```

Constraints:

- **`order.reference`** must be 1-32 chars. v3 generates 20-char
  references (`V3-` + 13 digits + `-` + 4 hex).
- **`order.reference`** must be UNIQUE per merchant (requires Noon
  support to enable per-merchant; default is non-unique).
- **`order.channel`** must be `'MOBILE'` or `'WEB'`. Other values
  are rejected by Noon. The adapter rejects them client-side too
  (faster fail).
- **`configuration.returnUrl`** must NOT contain `'?'`. Noon hard-
  rejects URLs with query strings. We use path-based return URLs
  exclusively (`/v3/checkout/return/{order_reference}`).
- **`order.amount`** as a decimal string (e.g. `"299.50"`). Currency
  precision varies: AED + USD are 2dp, KWD + OMR + BHD are 3dp.
  v3 enforces 2dp throughout because AED is our only currency in v3.

## Response shape (INITIATE success)

```json
{
  "resultCode": 0,
  "resultMessage": "Success",
  "result": {
    "order": {
      "id": "123456789012",
      "reference": "V3-1700000000000-a3f4",
      "amount": "299.50",
      "currency": "AED",
      "status": "INITIATED"
    },
    "checkoutData": {
      "postUrl": "https://api-test.noonpayments.com/checkout/abc123"
    }
  }
}
```

- **`resultCode = 0`** means success. Anything non-zero is a problem.
- **`result.order.id`** is Noon's order id. We store as STRING in
  `payment_transactions.provider_order_ref` because Noon's own docs
  warn that the global endpoint uses 12-digit, local endpoints
  (KSA, EGY) use 16-digit which exceeds JS Number.MAX_SAFE_INTEGER
  (2^53). PHP int is 64-bit so could hold it, but storing as string
  matches Noon's recommendation + downstream JSON safety.
- **`result.checkoutData.postUrl`** is what mobile webview loads.

## Response shape (failure)

```json
{
  "resultCode": 19012,
  "resultMessage": "Duplicate reference",
  "result": {
    "order": { "id": "999999999999" }
  }
}
```

Notable codes captured in `src/Payment/Noon/NoonResultCodes.php`:

| Code | Meaning | Adapter mapping |
| --- | --- | --- |
| `0` | SUCCESS | success path |
| `19012` | Duplicate merchant reference | `PaymentGatewayException::KIND_DUPLICATE_REF` |
| `19100` | "Not enabled for this feature" (config issue) | `KIND_UPSTREAM` (with code) |
| other non-zero | general upstream error | `KIND_UPSTREAM` |

19012 deserves special handling because it's actually our friend:
indicates Noon already knows about this reference, so the caller
can lookup the existing checkoutData via `GET_ORDER_BY_REFERENCE`
rather than failing the user.

## HTTP status semantics

Most non-success cases come back as `HTTP 200` with non-zero
`resultCode`. The few status codes that bypass the body:

| HTTP | Adapter mapping |
| --- | --- |
| `200` | Parse body; check `resultCode` |
| `401`, `403` | `KIND_AUTH` — config bug, alert ops |
| `429` | `KIND_RATE_LIMITED` — back off |
| Other 4xx/5xx | Parse body; may or may not be JSON |
| Connection refused / DNS / connect timeout | `KIND_NETWORK` |
| Read timeout | `KIND_TIMEOUT` (state UNKNOWN — must retrieve-order) |
| Non-JSON body | `KIND_MALFORMED` |

## Idempotency

- **Reference UNIQUE** — once enabled on the merchant by Noon
  support, duplicate references return `resultCode 19012` with the
  existing order id. Without this enabled (the default), Noon
  accepts duplicates and creates new orders. v3 backs this up with
  its own UNIQUE constraint on `orders.order_reference` and the
  per-cart idempotency key in `payment_transactions`.

## Rate limits

Two important rate limits to know about:

- **GET ORDER polling**: Noon explicitly bans IPs that poll
  GET_ORDER aggressively (`docs.noonpayments.com/test/evaluating-api`).
  The recon-confirmed safe pattern:
  - Server calls GET_ORDER only in the webhook receiver (at most
    once per state-change event)
  - Mobile NEVER polls Noon directly; polls v3's
    `/v3/checkout/status/{ref}` instead, which reads only v3 local state

- **General API requests**: Noon returns 429 on burst. The adapter
  surfaces this as `KIND_RATE_LIMITED` so callers can back off.
  v3 has no caller that bursts beyond ~1 RPS per checkout flow,
  so this shouldn't fire in practice.

## Webhooks

### When Noon sends webhooks

Noon POSTs to a merchant-configured webhook URL on every order
state change. Configure this URL in the merchant portal to:

```
https://api-v3.3bayti.ae/v3/payment/webhook/noon
```

### Headers

- `Content-Type: application/json`
- A signature header — typically `X-Noon-Signature` or `Signature`
  but the exact name is gated behind the merchant portal. M3.1.6's
  `LoggingOnlyVerifier` logs whatever signature header it finds for
  M3.1.7 to inspect.

### Body shape (observed in similar provider docs; need empirical
confirmation in M3.1.7)

```json
{
  "eventId": "evt-abc123",
  "eventType": "ORDER_PAID",
  "result": {
    "order": {
      "id": "123456789012",
      "reference": "V3-1700000000000-a3f4",
      "status": "CAPTURED",
      "amount": "299.50",
      "currency": "AED"
    }
  }
}
```

Our parsing handles top-level `result.order.id` and `result.order.reference`.
If Noon's actual webhook body has a different envelope, the adapter
falls back to the entire-payload-is-the-order shape (also tried).

### Signature algorithm

**STATUS:** M3.1.6 ships `LoggingOnlyVerifier` which accepts
everything and logs SHA-256 of body + signature header for forensic
analysis. M3.1.7 will:

1. Capture real sandbox webhook events
2. Brute-force the algorithm from logged body/signature pairs.
   Industry conventions to try, in order:
   - HMAC-SHA256(body, NOON_WEBHOOK_SECRET) as lowercase hex
   - HMAC-SHA256(body, NOON_WEBHOOK_SECRET) as base64
   - HMAC-SHA256(timestamp + body, NOON_WEBHOOK_SECRET) (Stripe-style)
   - HMAC-SHA512(body, NOON_WEBHOOK_SECRET)
3. Bind the discovered verifier in DI (replace `LoggingOnlyVerifier`)
4. Add tests proving the verifier accepts the captured pair and
   rejects tampered bodies

`HmacSha256SignatureVerifier` is scaffolded with the industry-default
HMAC-SHA256 hex form (+ GitHub-style `sha256=` prefix normalisation
+ case normalisation + constant-time compare). If sandbox capture
confirms this is the algorithm, the M3.1.7 binding is literally a
one-line DI change.

### Why this is safe in M3.1.6 despite no signature verification

The retrieve-order-before-acting pattern in `NoonWebhookController`:

```php
$payload = $this->parsePayload($rawBody);

// Even with no signature verification, this controller does NOT
// trust the payload to claim an order is paid. Before applying ANY
// state transition, it calls Noon GET_ORDER directly:
$authoritative = $this->gateway->retrieveOrder($providerOrderRef);

// Authoritative response (server-to-server authenticated with OUR
// credentials) determines what mutation happens. The webhook body
// is just a 'look at order X again' poke.
$this->applyAuthoritativeStatus($order, $authoritative);
```

A spoofed webhook claiming `status: 'CAPTURED'` cannot make us mark
an order paid because we ignore the webhook's status field entirely
and ask Noon directly. Endorsed by Noon's own docs at `test/evaluating-api`:

> "It is suggested to use the webhook feature to rely on a more
> robust mechanism to receive events (server-to-server); it is also
> possible to call the GET ORDER API to determine the order status
> and the subsequent actions required."

## Currency precision

Noon docs note that AED + USD use 2 decimal places; KWD, OMR, BHD
use 3 decimal places. v3 is AED-only as of M3.1.6, so all money
strings are 2dp via bcmath. If we add another currency, the
serializers + entity precision constants need updating.

## What's NOT in the recon (still to discover)

The following weren't fully reverse-engineered during M3.1.6 because
either (a) the sandbox wasn't connected during dev, or (b) the docs
gate the info behind merchant portal access:

- Exact webhook signature algorithm — M3.1.7 will capture this empirically.
- The exact list of `eventType` strings Noon emits — we currently
  store whatever string is in the payload but don't switch on it.
- Whether Noon ever calls the webhook with `INITIATED` status — if so,
  v3 ignores it (transient state; no Order mutation), which is correct.
- Whether Noon's order id is stable across the order's lifetime
  or rotates between operations — we assume stable; if not, the
  `findByProviderOrderRef` lookup in the webhook controller could
  miss matches.
