## Design decisions made during M3.1.1

Below are the calls that required explicit user decisions or constituted material deviations from the M3.1.0e.2 contract specs. All are documented inline in the relevant controller docblocks and reconciled in the inventory contracts.

### 1b ADR — No new `billing_addresses` table

**Decision:** Back the new billing-address endpoints with the existing `addresses` table, using its `is_default_billing` column.

**Rationale:** Audit discovered `addresses.is_default_billing` already exists and `AddressRepository::setAsDefaultBilling()` is already implemented (M1.7.2 phase B). Building a new table would have duplicated infrastructure.

**Saved:** ~0.5-1 day of migration + entity + repository work.

### 1c deviation — PATCH /v3/me/billing-address is upsert, not 404

**Original:** ADR proposed 404 `BILLING_ADDRESS_NOT_SET` if no billing exists.
**Shipped:** Upsert (creates if missing).

**Why:** Legacy mobile's `updateBilling` is upsert; 404 on PATCH for a singleton resource forces client workflow complexity for no UX benefit. Documented in `UpsertBillingAddressController` docblock + 1b ADR retrospective + inventory reconciliation note.

### 1c also-deviation — billing field shape

**Original 0e.2:** Fields named `first_name`/`last_name`/`company_name`/`tax_id`.
**Shipped:** Existing addresses fields (`recipient_name`/`recipient_phone`/`emirate`/`area`/`street_address`/`building_details`/`postal_code`).

**Why:** Implicit consequence of 1b ADR (table choice). Adding B2B fields (`tax_id`, `company_name`) is deferred to M4+ if business surfaces the need.

### 1d decision — Structured `user_locations` table (user choice: "Option B")

**Choice asked:** A (single text field on `users`), B (new table with lat/lng/city/country/permission), or C (flat location_* columns on `users`).
**Selected:** B — new table.

**Rationale (per user input):** Future-proof for location history. Sparse data justifies separation from users. Independent update cadence reduces write contention.

### 1e deviation — Response is `{location: ...}`, not `{user: ...}`

**Original 0e.2:** Response was `{user: <full UserSerializer profile>}`.
**Shipped:** `{location: <UserLocation data>}`.

**Why:** `UserSerializer::publicProfile` does not include location fields (verified in 1a audit). Returning the location data directly is honest. Documented in controller docblock + inventory reconciliation note.

### 1f deviation — Response is 200 + fresh token pair, not 204 + no reissue (user choice: "Option B")

**Original 0e.2:** Status 204, no body, "Does NOT revoke other sessions".
**Shipped:** Status 200, body includes new access + refresh tokens + user profile. Revokes ALL refresh tokens (including this session's) then issues a fresh pair for this device.

**Rationale (per user input):** Mirrors `/v3/auth/reset/confirm`'s session-handling pattern. The `pwd_changed_at` invalidation mechanism means the original spec ("don't revoke others") was incorrect — changing the hash always invalidates the current access token on next request. The shipped behavior gives consistent UX (stay logged in here, kicked out elsewhere) and consistent security posture.

### 1e failure + fix — AuditEmitter snapshot strategy

**Problem:** Initial 1e push failed CI with 5 controller tests returning 500.
**Cause:** `AuditEmitter::snapshot()` is a runtime `match()` with `throw` default. Didn't add UserLocation case.
**Fix:** Commit `4ef113d` added case + `snapshotUserLocation()` helper.
**Lesson logged:** Any new entity that goes through audit needs a snapshot case. No compile-time check; must remember.

## What's NOT in M3.1.1 scope

- **Rate-limiting for PATCH /v3/me/password.** A stolen-token attacker could brute-force `current_password`. Mitigated by bcrypt slowness + 30-min token TTL + WAF/proxy global rate limits. Per-user lockout deferred to M4 hardening.
- **Reverse-geocoding for /v3/me/location.** Server stores whatever client sends; doesn't currently translate lat/lng → city/country. M4 work.
- **Location history.** Single row per user (UNIQUE constraint on `user_id`). M4+ could drop the unique constraint and add captured_at-keyed pointer if history becomes relevant.
- **GET /v3/me/location endpoint.** 0e.2 only specified PATCH. Clients can read by calling PATCH with empty body (returns current state). Add dedicated GET if a real need surfaces.
- **B2B billing fields.** No `tax_id`, `company_name`, etc. Add via `addresses` schema extension in M4+ if vendors request for tax invoicing.
- **Password-history / common-password-blocklist.** M4+ hardening.
- **Email notification on password change.** M4 ZeptoMail work.
- **Mobile/web/portal consumer flips.** Routes defined; no app yet calls them. M3.1.3+ (mobile), M3.2.x (web), M3.3.x (portal).
