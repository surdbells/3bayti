# M3.1.6i — Mobile routing + transforms (scope reduction)

**Status:** Routing table corrections shipped. Full call-site rewrite
deferred to M3.1.6i.2 / M3.1.7.

## What this sub-phase originally planned

The M3.1.6 plan budgeted M3.1.6i for "Mobile routing entries (12 new
feature-flag entries `target='old'`) + 6 transform files
(cart/order/checkout request+response). Sign-in flow calls
POST /v3/cart/merge."

## Discovered constraints

Implementing the full plan requires three pieces that turned out to
be larger than budgeted:

### 1. Adapter doesn't support path-param-from-body extraction yet

Mobile's cart pages call e.g. `POST /customer/IncreaseItem` with body
`{item: <id>, quantity: <n>}` — the item id is in the BODY, not the
URL. v3's equivalent is `PATCH /v3/cart/items/{id}` with the id in
the URL.

The existing `MobileNetworkAdapter::callV3()` has a comment marking
this gap explicitly:

> `// path params: not yet supported via this entry point`
> `// — see class docblock (M3.1.3+ extension)`

The adapter would need a new pathway that:
- Looks up a path-param extractor (analogous to the catalog request
  transforms but returning `pathParams` for mutations rather than
  `queryParams` for GET conversions)
- Removes the extracted key from the body before sending
- Substitutes via `resolveUrl(routeKey, urls, pathParams)`

This is a small extension (~30 LOC in the adapter, plus a registry),
but it warrants its own commit + tests to keep blast radius small.

### 2. Call sites need rewriting, not just transforms

Mobile's checkout flow currently looks like:

```typescript
// checkout.page.ts (legacy flow, simplified)
this.network.post_request(orderBody, 'customer/payment/initiate_payment')
  .subscribe(res => {
    this.webview.navigate(res.data.checkoutUrl);
    // ... legacy completion handling reads URL params on return
  });
```

The v3 flow is fundamentally different — instead of reading URL
params on return, mobile must POLL `GET /v3/checkout/status/{ref}`
until `terminal=true`. That's not a transform; that's a flow change.

Similarly, the post-login cart merge isn't a transform — it's a new
operation that needs to be added to the sign-in success handler.

### 3. Risk of regression to a working flow

The cart/order/checkout flows currently work via the legacy backend.
Flipping them to v3 with incomplete transforms risks a regression
that breaks a working customer flow. The strangler-fig invariant
mandates that the per-endpoint rollback works; the easiest way to
guarantee that is to keep the entries on `target='old'` until the
full mobile-side work is ready, then flip atomically in M3.1.6j1.

## What shipped in this commit

**Routing table corrections** in `packages/api-client/src/feature-flags.ts`:

| Change | Before | After |
| --- | --- | --- |
| `PUT /cart/items/:id` → `PATCH /cart/items/:id` | (mismatched verb) | matches M3.1.6d backend |
| Both `cart/items/:id` entries flipped back to `target='old'` | prematurely flipped 'new' (would have 404'd) | safe 'old' |
| `POST /checkout` → `POST /checkout/initiate` | wrong path | matches M3.1.6f1 backend |
| `GET /orders/:id` flipped back to `target='old'` | prematurely flipped 'new' (would have 404'd) | safe 'old' |
| `POST /cart/merge` | (missing) | added at 'old' |
| `GET /checkout/status/:order_reference` | (missing) | added at 'old' |
| `POST /payment/webhook/noon` | (missing) | added at 'old' (informational; mobile never calls) |

Tally: 4 corrections + 3 additions = 7 entries touched. The plan's
"12 new entries" count was a brainstorm estimate; the actual delta
is 7 (4 of which were corrections to entries that already existed
but pointed at the wrong target / path / verb).

## What's deferred to M3.1.6i.2 / M3.1.7

1. **Adapter path-param-from-body extension** — small architectural
   addition to `MobileNetworkAdapter::callV3()` (~30 LOC + registry +
   tests).

2. **Cart transforms** — request/response shape mappers between
   legacy cart pages and v3's `POST /v3/cart/items` body shape.

3. **Checkout flow rewrite** — change from "open webview, read URL
   params on return" to "open webview, poll status endpoint after
   webview closes". This touches `checkout.page.ts`, `process.page.ts`,
   and the webview event handlers.

4. **Cart merge on sign-in** — call `POST /v3/cart/merge` with the
   device-local cart after a successful login, then clear the device
   cart on success. Touches `login.page.ts` + the auth service.

5. **Order list transforms** — likely a near-no-op (v3 was designed
   to match mobile's `my-orders.page` binding, including the
   `store`/`vendor_id` alias). Verify with a focused test.

6. **Target flip** — `target='old'` → `target='new'` for all seven
   entries above + the two cart routes whose entries existed already
   (`GET /cart`, `POST /cart/items`). Net: 9 entries flipped en bloc
   in M3.1.6j1.

## Why "ship the corrections now, defer the rewrite"

Three reasons:

1. **Backend's safety surface improves.** The four corrections fix
   broken state where mobile pointed at v3 endpoints that didn't
   exist yet. Those entries would have 404'd on every call had
   anyone been routed to them. Fixing the routing table eliminates
   that latent bug regardless of when the rewrite lands.

2. **The plan's budget for this sub-phase was wrong.** "6 transform
   files" assumed transforms-only. The actual work includes adapter
   architecture changes + flow rewrites + new mobile features
   (cart merge on sign-in). That's a multi-commit body of work; one
   commit per piece keeps the strangler-fig rollback granularity.

3. **The backend ships in M3.1.6 anyway.** All v3 endpoints are
   reachable at `api-v3.3bayti.ae/v3/cart`, `/v3/orders`, etc., with
   passing tests (423/423) and phpstan clean. The backend is the
   risky part; it's already done. The mobile rewrite is incremental
   feature-flag work that can land any time without breaking
   anything.

## Resumed plan for M3.1.6 closure

- **M3.1.6i** — Routing corrections (this commit). ✓
- **M3.1.6j1** — Originally "flip target='old' → 'new'". Now becomes
  a placeholder — the flip cannot happen until M3.1.6i.2 lands the
  mobile-side rewrite. Marked as "blocked on M3.1.6i.2" in the plan.
- **M3.1.6j2** — Completion docs. Updated to reflect the actual
  shipped state (backend complete, mobile uses legacy until the
  rewrite ships separately).
- **M3.1.6i.2 (new)** — Mobile call-site rewrite, the deferred work
  listed above. Will be its own sub-phase with its own plan, budget,
  and rollback procedure.

## Operator action required

None. The routing-table corrections take effect on next mobile build;
the entries remain `target='old'` so no behaviour changes for end
users. Backend operators should still complete the M3.1.6h runbook
checklist + obtain Noon merchant credentials so that when M3.1.6j1
flips, the v3 path is operationally ready.
