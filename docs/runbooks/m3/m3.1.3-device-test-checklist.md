# M3.1.3 — Device Test Checklist (Mobile Login Flip)

**Phase:** M3.1.3
**Status:** Required gate before declaring M3.1.3 production-stable
**Performed by:** Whoever runs the off-hours mobile deploy (App Store Connect TestFlight + Play Store internal track)
**Estimated time:** 30–40 minutes per platform

---

## Why this exists

Mobile CI runs type-check + build only (pre-existing constraint flagged in `m3.1.2-completion.md`). The login flip in commit `e27e1db` has been compile-verified but NOT runtime-verified. Before the broader rollout (M3.1.5+ flips touching catalog and profile endpoints), we need on-device confirmation that:

1. The HTTP layer correctly attaches `Authorization: Bearer <token>` headers on the next authenticated call
2. The stored `'user'` blob has the right shape for the 35 downstream readers
3. Pre-flip cached sessions still work (legacy `single_user` blobs in Preferences from before the deploy)
4. Edge case: a vendor user sees `is_vendor=true` and the store-dashboard / vendor-chat-list pages load correctly

The checklist below covers each of those concerns systematically.

---

## Setup

Before running the checklist:

1. Deploy the new mobile build to TestFlight + Play Store internal track from commit `e27e1db` (or whichever M3.1.3 commit is latest).
2. Confirm `https://api-v3.3bayti.ae` is reachable from the test device's network (the adapter hardcodes this URL — see `mobile-network-adapter.ts:208`).
3. Have ready:
   - A pre-existing **customer** account (registered before M1 v3 cutover; has bcrypt hash that v3 accepts)
   - A pre-existing **vendor** account (`roles` includes `'vendor'`, `is_store_active=true`)
   - A device with a cached `'user'` blob from a pre-M3.1.3 build (i.e. someone who logged in before the deploy)
4. Note the device's clock; the access token is ~24h TTL so expiry shouldn't surface in a single test session.

---

## A. Cold-start login (new device, no cached session)

Goal: confirm v3 login works end-to-end and the stored blob is correct.

| Step | Action | Expected | If wrong |
|---|---|---|---|
| A1 | Fresh install, open app | Lands on `/login` | App init issue — unrelated to M3.1.3 |
| A2 | Enter customer email + password, tap Sign In | Network request goes to `https://api-v3.3bayti.ae/v3/auth/login` (check Charles/Proxyman/Network Inspector). Returns 200 with `{access_token, refresh_token, user:{...}}` | If 404: ENDPOINT_ROUTING wired wrong. If 401: bcrypt compat issue or wrong credentials. If 5xx: v3 backend issue, NOT M3.1.3 |
| A3 | Wait for navigation | App navigates to `/account` | If stays on `/login`: response shape problem — open Preferences and check the `'user'` blob (step A4) |
| A4 | Inspect Capacitor Preferences (`adb shell` on Android, Xcode device console on iOS, or temporarily add a debug `console.log(await Preferences.get({key:'user'}))` in account.page.ts) | Blob contains: `id` (number, matches v3 user.id), `token` (string, starts with `eyJ`), `first_name`, `last_name`, `email`, `phone`, `is_vendor: false`, `is_store_active: false`, `is_store_approved: false`, `refresh_token` (string, starts with `eyJ`) | If missing fields: bug in `login-response.transform.ts`. If `is_vendor: true` for a customer-only account: roles derivation bug. If shape is `{access_token, user: {...}}` (unwrapped v3 shape): transform didn't run — check the import |
| A5 | Force-kill and reopen the app | Lands on `/account` directly (not `/login`) — confirms cached session resume reads the stored shape | If lands on `/login`: `getObject()` in account.page.ts couldn't parse the stored blob. Inspect Preferences as in A4 |

## B. Authenticated downstream call (the critical test)

Goal: confirm the `token` we stored gets attached as `Authorization: Bearer` on the next request, and that legacy code paths using `single_user.id` / `single_user.token` continue to work.

| Step | Action | Expected | If wrong |
|---|---|---|---|
| B1 | From `/account`, navigate to Profile (or any tab that loads user-specific data) | Network requests fire to legacy endpoints (`api.3bayti.ae/...`) containing `id` and `token` in the request body. Profile data displays. | If 401 or empty profile: the stored `token` value isn't being read correctly — likely the transform produced an empty string. Re-check A4. |
| B2 | Navigate to Cart, Wishlist, Orders, Addresses (4 separate pages, all read `single_user`) | Each loads without crashing; data displays for the logged-in user | If any page crashes with "cannot read property 'id' of undefined": the stored blob is missing `id`. If any page is empty: the legacy backend isn't recognizing the token (most likely the token is fine but the request shape changed) |
| B3 | (Customer only) navigate to checkout from a cart with items | Checkout page loads. The `single_user.billing_*` fields (billing_name, billing_phone, billing_street, billing_city, billing_area) and `single_user.delivery_address` / `villa_number` are read at lines 329, 658-663 of checkout.page.ts | **EXPECTED PARTIAL FAILURE**: these fields are not in the v3 login response. The checkout page will see `undefined` for them. **This is the known-issue flagged in commit e27e1db's message.** Verify what actually happens: does checkout still proceed? Does it offer to fill in the address? Does the order POST fail silently? Document the outcome in the post-test notes section below. |

## C. Vendor login + vendor-only pages

| Step | Action | Expected | If wrong |
|---|---|---|---|
| C1 | Sign out, sign in with the vendor account | A4-style blob inspection: `is_vendor: true`, `is_store_active: true` | If `is_vendor: false`: roles derivation bug in `transformV3LoginResponse`. Check the v3 response's `user.roles` field |
| C2 | Navigate to Store Dashboard | Page loads (the guard at store-dashboard.page.ts:155 `if (!this.single_user.is_vendor) return` passes through) | If redirected away: `is_vendor` is falsy in the stored blob |
| C3 | Navigate to Vendor Chat List | Page loads (the guard at vendor-chat-list.page.ts:107 `if (!this.single_user.is_vendor || !this.single_user.is_store_active) return` passes through) | Same as C2; also check `is_store_active` |

## D. Upgrade path (pre-flip cached session)

Goal: confirm users who already had a `'user'` blob in Preferences (from a build that talked to legacy `/users/login`) continue to work after the new build is installed.

| Step | Action | Expected | If wrong |
|---|---|---|---|
| D1 | On the device with the pre-flip cached blob, launch the new build WITHOUT logging in fresh | Cached `single_user` is read on `/login`'s `ngOnInit`; user is auto-routed to `/account`. All authenticated calls work because the cached blob has the legacy `{id, token}` from the previous login | If session is lost or `/account` crashes: the legacy blob shape isn't being preserved. This shouldn't happen — the transform only runs on NEW logins; cached blobs are read verbatim |
| D2 | Sign out (clears Preferences). Sign in again with the same account | Now goes through the v3 login path. New blob has the new shape | Compare the D1 blob and D2 blob: D1 may have `billing_*` fields; D2 will not (the known gap). |

## E. Error paths

| Step | Action | Expected | If wrong |
|---|---|---|---|
| E1 | Sign in with bad password | Error toast shows; stays on `/login`. Network call returns 401 from v3 with `{error: {code: 'AUTH_INVALID_CREDENTIALS', message: '...'}}` | If error toast doesn't fire: the adapter's `translateError` at mobile-network-adapter.ts:354 isn't mapping the 401 correctly |
| E2 | Sign in while offline (airplane mode) | "Check your connection" toast; no crash | If crash: connection service / adapter error path issue |
| E3 | Sign in while v3 is intentionally unreachable (DNS-block `api-v3.3bayti.ae` if possible) | Error toast; no crash. Note: there's NO automatic fallback to legacy — if v3 is down, login fails. | If anything else happens: investigate. M4 may want to add resilience but that's out of scope for M3.1.3 |

## Pass/fail gate

This phase is considered production-stable when:

- ✓ All A* steps pass on both iOS and Android
- ✓ All B1-B2 steps pass on both platforms
- ✓ B3's known gap is empirically classified: blocker (regression for existing users) / acceptable (UI handles missing fields gracefully) / latent risk (works today, will fail when checkout flow changes)
- ✓ All C* steps pass IF a vendor account is available for testing; otherwise note as deferred
- ✓ All D* steps pass
- ✓ All E* steps pass

If B3 is classified as "blocker", do NOT merge the M3.1.3 completion runbook. Open a follow-up ticket to either:
- (option α) extend the login transform to fetch billing/location separately via `/v3/me/billing-address` + `/v3/me/location` and bundle them into the stored blob — couples login to two extra round-trips
- (option β) refactor the three consumers (process, checkout, settings) to read billing/location from those new endpoints directly instead of from `single_user` — preferred long-term but is essentially the M3.1.5 / M3.1.6 work brought forward

## What's NOT in this checklist

- Performance benchmarks (login latency comparison legacy vs v3). M4 hardening.
- Localization (Arabic UI rendering of error messages from v3). M4 hardening.
- Multi-device session invalidation (if a user logs in on device A then device B, does A still work?). Not in scope until M3.1.4 refresh-token rotation lands.
- Token expiry behaviour past 24h. Would require waiting 24h between A2 and B1; cover in a separate aged-token test if needed.
- Concurrent register + login (the OTP-required register flow lands in M3.1.4).
