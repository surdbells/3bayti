# M3.1.5.5 — Device Test Checklist (4 Additional Catalog Reads on v3)

**Phase:** M3.1.5.5
**Status:** Required gate before declaring M3.1.5.5 production-stable
**Performed by:** Whoever runs the off-hours mobile deploy (App Store Connect TestFlight + Play Store internal track)
**Estimated time:** 30–45 minutes per platform
**Prerequisite:** Run `m3.1.5-device-test-checklist.md` first. M3.1.5's batch flipped 10 endpoints; M3.1.5.5's adds 4 more. Without the M3.1.5 gate, regressions across the larger batch surface here unnecessarily.

---

## Why this exists

Mobile CI runs type-check + build only. The work in commits `ecc8654` → `0ebe29c` has been compile-verified and unit-tested at the boundary (28 new PHP controller tests, 30 new TypeScript spec assertions across 5 test files) but NOT runtime-verified end-to-end against real v3 data.

Before declaring M3.1.5.5 production-stable, we need on-device confirmation that:

1. The 4 newly-flipped catalog endpoints produce visible UI without rendering errors
2. The PostgreSQL `tsvector` search returns relevant results for representative queries
3. Per-vendor label filter chips render and filter correctly
4. Styles page renders styles with their embedded product strip
5. The legacy data migration (`migrate-all.php`) ran successfully — vendor_labels + styles populated, products.label_id remapped from legacy → v3 ids
6. The four documented gaps from the M3.1.5.5 completion runbook render acceptably or are flagged for follow-up

---

## Setup

1. **Confirm migration ran in staging.** SSH to the staging API host and verify:
   ```
   psql -d bayti_v3 -c "SELECT COUNT(*) FROM vendor_labels WHERE legacy_label_id IS NOT NULL"
   psql -d bayti_v3 -c "SELECT COUNT(*) FROM styles WHERE legacy_style_id IS NOT NULL"
   psql -d bayti_v3 -c "SELECT COUNT(*) FROM products WHERE label_id IS NOT NULL"
   ```
   Non-zero counts on all three confirm migration. Zero counts on vendor_labels or styles mean the defensive probe in `MigrationSteps` couldn't find the legacy table — edit the `$candidates` array with the correct table name and re-run.

2. **Deploy the mobile build** to TestFlight + Play Store internal track from commit `0ebe29c` or later.

3. Have ready:
   - A **device with network inspection available** (Charles Proxy, Chrome DevTools via remote debug, or Safari Web Inspector for iOS)
   - A **mobile user account** signed in
   - The **legacy ID of at least one vendor known to have labels** in production
   - Two test devices on different networks OR one device with rapid network-switching for cold/warm-cache comparisons

| Step | Expected | Pass/Fail |

### Migration verification

After live deploy, re-run the verification query block from `migrate-all.php`:
```
psql -d bayti_v3 <<EOF
  SELECT 'categories' AS phase, COUNT(*) FROM categories
  UNION ALL SELECT 'vendor_labels', COUNT(*) FROM vendor_labels WHERE legacy_label_id IS NOT NULL
  UNION ALL SELECT 'styles', COUNT(*) FROM styles WHERE legacy_style_id IS NOT NULL
  UNION ALL SELECT 'products.label_id remapped', COUNT(*) FROM products WHERE label_id IS NOT NULL;
EOF
```

| Step | Expected | Pass/Fail |
|---|---|---|
| vendor_labels count | Matches the legacy `labels` (or `vendor_collections`) row count modulo any orphans | ☐ |
| styles count | Matches legacy styles row count | ☐ |
| products.label_id remapped count | Sanity-check non-zero; orphan label_ids were nulled (see migrateVendorLabels post-write step) | ☐ |
| `fk_products_label` is VALIDATED | `SELECT conname, convalidated FROM pg_constraint WHERE conname='fk_products_label'` returns `convalidated = true` | ☐ |

### Documented gaps from completion runbook

| Gap | Acceptable? | Pass/Fail | Notes |
|---|---|---|---|
| Vendor name not searchable | UX impact: searching the vendor's name doesn't find their products. Document and revisit if user reports | ☐ | |
| Only English locale | Arabic search will work for ASCII characters but no stemming. UX impact varies by region | ☐ | |
| Single-label per product | If a product belongs in two labels, it appears under one. Document for vendor onboarding | ☐ | |
| Styles read-only | Users can't create styles in mobile. Was this a feature in legacy? If yes, log as regression | ☐ | |
| style_products join unmigrated | Styles show without products until the join migration ships. Severe if many styles in production are non-empty in legacy | ☐ | Block release if styles are commonly used + showing empty |

- **Hard fails on adapter routing, product filtering, or styles join migration** → Per-endpoint rollback (`feature-flags.ts` flip back to `target: 'old'` for the affected endpoint(s)) and ship fixes before re-flipping. The strangler pattern makes this safe.
