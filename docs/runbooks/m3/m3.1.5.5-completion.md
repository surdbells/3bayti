## Phase summary

M3.1.5.5 closed the second of two streams in the M3.1.5-era catalog migration. M3.1.5 itself flipped 10 of 16 mobile catalog endpoints to v3, deferring 6 because the v3 side had no equivalent. M3.1.5.5 built the v3 backends for 4 of those 6 and flipped them too. The remaining 2 (best_sellers + best_sellers_listing) stay deferred to post-M3.1.6 because they require the order_items schema that M3.1.6 builds.

The phase was structural work disguised as "wire up some endpoints":

1. **New schema artefacts** — products.search_tsv generated column + GIN index for fulltext search; vendor_labels table + FK from products.label_id; styles + style_products tables.
2. **New domain entities** — VendorLabel and Style with their repositories.
3. **Custom DQL functions** — TSMATCH and TSRANK to bring PostgreSQL fulltext into the QueryBuilder layer.
4. **Defensive legacy migration steps** — the legacy schema for labels/styles wasn't fully understood when the migration scripts were written; both methods probe for tables/columns via INFORMATION_SCHEMA before reading.
5. **Drive-by fixes** — line-410 parse error in MigrationSteps.php that had been silently corrupting the migrateUsers UPDATE path; DBAL 4.x constant rename (PARAM_INT_ARRAY → ArrayParameterType::INTEGER).

The four deferred endpoints and their v3 destinations:

| Mobile constant | Legacy URL | v3 endpoint |
|---|---|---|
| `search` | `customer/search` | `GET /v3/products?q=…` |
| `store_labels` | `customer/read_vendor_collection` | `GET /v3/vendors/by-legacy-id/:id/labels` |
| `products_by_labels` | `customer/products_by_labels` | `GET /v3/products?label_id=…&vendor_id=…` |
| `styles_list` | `customer/styles_list` | `GET /v3/styles?type=…` |

## What shipped per sub-phase

### M3.1.5.5a — Schema (1 commit)

One Doctrine migration (`Version20260514000002.php`) ships four schema artefacts:

1. **products.search_tsv** — `tsvector` generated column (`GENERATED ALWAYS AS STORED`) computed from `name || ' ' || description`. GIN index for `@@` query performance. Vendor name is NOT included — generated columns can't reference other tables. Vendor-name search becomes a follow-up enhancement (would use a denormalised products.vendor_name_cache column or a trigger).

2. **vendor_labels** — per-vendor merchandising collections. `legacy_label_id` BIGINT UNIQUE for compat resolution; `vendor_id` FK to `vendors(id)` ON DELETE CASCADE; UNIQUE (vendor_id, slug). Display order is NULLABLE smallint (NULL = "no explicit order → sort by name").

3. **products.label_id → vendor_labels.id FK** — added as `NOT VALID`. Existing label_id values are LEGACY ids at this point. M3.1.5.5c remaps and VALIDATEs.

4. **styles + style_products** — Style with smallint enum (1=community, 2=editorial) + CHECK constraint. style_products join table with composite PK (style_id, product_id) and display_order. Both FKs ON DELETE CASCADE.

### M3.1.5.5b — Domain entities + repositories (1 commit)

Four files:

- `VendorLabel.php` entity
- `VendorLabelRepository.php` — `findActiveBySlug(Vendor, string)`, `findActiveByLegacyId(int)`, `listActiveByVendor(Vendor)` with NULLS-LAST ordering via `CASE WHEN ... IS NULL` (DQL pre-2.14 doesn't directly support `NULLS LAST`)
- `Style.php` entity with `TYPE_COMMUNITY=1` / `TYPE_EDITORIAL=2` constants; `setStyleType()` validates the value

Per existing codebase convention, no dedicated repository unit tests — controller tests with mocked EntityManager cover repo behaviour.

### M3.1.5.5c — Legacy data migration + drive-by fixes (1 commit)

`MigrationSteps.php +395`:

- **`migrateVendorLabels()`** — defensive probe of candidate legacy table names (`labels`, `vendor_collections`) via INFORMATION_SCHEMA. Status-result on missing. Defensive probe of candidate column names. After INSERT/UPDATE, **re-maps products.label_id from legacy ids to v3 ids in the same transaction**, nulls orphans, VALIDATEs `fk_products_label`. Bumps `vendor_labels_id_seq`.
- **`migrateStyles()`** — same defensive probe pattern (candidates: `styles`, `stylist`). Maps legacy type string → smallint. Does NOT migrate style_products join rows (legacy schema for that table isn't yet known; method logs a follow-up note pointing at candidate `stylist_products`).

`LegacyDb.php +56`:
- `tableExists(string)` — INFORMATION_SCHEMA.TABLES check with DATABASE() filter
- `columnExists(string, string)` — INFORMATION_SCHEMA.COLUMNS check
- `escape(string)` private helper wrapping `mysqli::real_escape_string`

`migrate-from-legacy/migrate-all.php +42`:
- Two new steps wired after reviews
- Summary table widened from 12 to 15 chars for the longer `vendor_labels` phase name
- Status field on each phase row handles the skip cases with a one-line note rather than a count row
- Verification block adds `vendor_labels` + `styles` counts

**Drive-by fix 1: parse error at MigrationSteps.php:410.** The pre-existing line `$set[] = 'updated_at = date_trunc('second', NOW())';` had inner single quotes that broke PHP's string parser (bareword `second` between two strings). Fixed by swapping the outer quotes to double quotes. This was a real bug in the `migrateUsers` UPDATE path that would have produced malformed SQL on any user-row drift. **Fixing it unblocked phpstan for the WHOLE API codebase** — the parse error was previously short-circuiting analysis.

**Drive-by fix 2: DBAL 4.x constant rename.** `Connection::PARAM_INT_ARRAY` was removed in DBAL 4.0 (the project is on 4.4.3). Replaced with `ArrayParameterType::INTEGER` in `StyleRepository::loadProductsForStyles`. Caught by phpstan after the line-410 unblock.

### M3.1.5.5d — Fulltext search + label_id filter (1 commit)

Three new files:

- `src/Doctrine/DqlFunction/TsMatchFunction.php` — compiles `TSMATCH(col, query)` to `(col @@ websearch_to_tsquery('english', query))`. Used in WHERE clauses.
- `src/Doctrine/DqlFunction/TsRankFunction.php` — compiles `TSRANK(col, query)` to `ts_rank(col, websearch_to_tsquery('english', query))`. Used in ORDER BY.
- `tests/Http/Controllers/Catalog/ListProductsControllerSearchTest.php` — 8 tests / 32 assertions

Modified:
- `config/doctrine.php` — registers TSMATCH (custom STRING function) + TSRANK (custom NUMERIC function)
- `src/Domain/Catalog/Product.php` — adds `searchTsv` property mapped to the column with `insertable: false, updatable: false` (DB-managed generated column; entity reads it for DQL but never writes)
- `src/Domain/Catalog/ProductRepository.php` — extends `findActivePaginated` filters with `labelId` (filter by `products.label_id`), `searchQuery` (TSMATCH WHERE clause; trimmed, non-empty), `sort='relevance'` (TSRANK ORDER BY; falls back to 'newest' if no q)
- `src/Http/Controllers/Catalog/ListProductsController.php` — `parseSort` accepts `'relevance'`; `parseSearchQuery` helper (trim, nullify empty/whitespace, 200-char cap)

**Why `websearch_to_tsquery`** rather than `to_tsquery` or `plainto_tsquery`: tolerates user input gracefully — quoted phrases, OR/AND/NOT operators, arbitrary punctuation without throwing. Web-style semantics match consumer expectations.

## What's deferred to future phases

- **best_sellers + best_sellers_listing** — need `order_items` schema; deferred to post-M3.1.6.
- **Vendor-name search** — generated tsvector columns can't reference other tables. Follow-up: trigger-maintained tsvector OR denormalised `products.vendor_name_cache` column.
- **Multi-language search** — current `'english'` tsvector locale only. Arabic / multi-language needs per-row config (M4+).
- **style_products data migration** — legacy schema for the join table isn't yet known. `migrateStyles()` logs a follow-up note pointing at the candidate (`stylist_products`).
- **Multi-label products** — current `products.label_id` is single-label. If multi-label assignment becomes a requirement, drop `label_id` and add a `product_labels` join table (additive evolution).
- **User-facing style CRUD** — styles are read-only in v3. Admin/future-admin-UI creates them.
- **Slim by-legacy-id controllers** — all by-legacy-id variants are compat shims, retired when mobile rebuilds against slug semantics (M3.1.10+).
