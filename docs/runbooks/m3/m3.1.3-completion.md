## Phase summary

M3.1.3 was originally scoped to flip **both** `login.page.ts` and `register.page.ts` from `NetworkService` to `MobileNetworkAdapter`. Phase 1 reconnaissance discovered three blockers on the register side that were not visible from the M3 plan or M3.1.2 closeout:

1. **Field-name + format mismatch** — legacy sends `countryCode: "+971"`, v3 expects `country_code: "AE"` (ISO 3166-1 alpha-2). Legacy also sends `confirm_password` and `accepted_terms`, neither of which v3 accepts.
2. **Flow divergence** — legacy register returns 200 and auto-logs-in; v3 register returns **201 Created** with `{verification_id, user: {is_phone_verified: false}}` and **requires phone OTP confirmation via `/v3/auth/confirm` before login is meaningful**. The existing register page has its own custom OTP flow (MessageCentral-based) that doesn't go through v3's OTP endpoints.
3. **Response code mismatch** — v3 returns 201 not 200. The MobileNetworkAdapter hardcodes `response_code: 200` in its legacy envelope wrap (line 112 of adapter), so call sites' `response.response_code === 200` checks still pass — semantically wrong but not behaviourally broken. Worth flagging.

Per the approved revised plan, **register flip moved to M3.1.4** where it belongs alongside OTP and reset flows operationally. M3.1.3 ships login only.

### Why the login flip is non-trivial

Mobile's existing login handler stores `response.data` directly into Capacitor Preferences under the `'user'` key. 35 downstream call sites then `JSON.parse` that blob into a local `single_user` field and read `single_user.id`, `single_user.token`, `single_user.is_vendor`, etc. directly.

v3's login response shape diverges substantially:

```text
Legacy POST /users/login -> data = { id, token, first_name, last_name, ..., is_vendor, is_store_active, ... }
v3 POST /v3/auth/login   -> data = { access_token, refresh_token, ..., user: { id, email, ..., roles: ['customer', ...] } }
```

If we stored the v3 shape unchanged, `single_user.id` would be undefined, `single_user.token` would be undefined, and `single_user.is_vendor` would be undefined. The next authenticated request would attach `{id: undefined, token: undefined, ...}` to its body, which the legacy backend would reject as unauthenticated.

The solution: a small **pure transform** at the single point of storage. v3 shape → legacy shape mapping happens once, in the login handler, before `Preferences.set`. Every downstream reader stays unchanged. This matches the "preserve legacy shape" philosophy of the adapter itself.

## Design decisions

### 1. Transform location: file alongside login.page.ts, not a shared utility

Considered putting the transform at `apps/mobile/src/app/core/http/auth-shape.ts` for sharing with the register flip. Decided against it because:

- The register flip (M3.1.4) needs **request-shape translation** (legacy → v3 body before sending), not response-shape translation. The two transforms have nothing in common.
- Locality: a developer modifying login behaviour finds the transform next to login.page.ts, not buried in core/http.
- Spec lives next to the transform; ng test would discover it via the same conventions.

If a future need for a shared shape utility emerges (e.g. an /auth/refresh flip also wants to update the cached blob), promote the transform then. Premature sharing is the worse failure mode.

### 2. Defensive null return for unrecognized shapes

The transform returns `null` rather than throwing for shapes that match neither v3 nor legacy. The caller (`login.page.ts`) does `transformV3LoginResponse(response.data) ?? response.data` — i.e. fall back to the raw response data if the transform doesn't recognize it.

Rationale: if v3 ever returns an unexpected shape (e.g. an error envelope wrapped through the adapter's success path due to a misconfigured response_code), throwing would crash the login flow. Storing the raw `.data` reproduces today's behaviour — possibly broken downstream, but no worse than before the flip, and easier to debug than an opaque crash. The transform's `null` is observable: a developer adding logging would see when the path triggers.

### 3. Legacy passthrough path (path 2) is the rollback insurance

`transformV3LoginResponse` recognizes inputs that already have `{id: number, token: string}` and returns them verbatim. This means flipping `ENDPOINT_ROUTING['POST /auth/login'].target` from `'new'` back to `'old'` requires no code changes to the login handler — the adapter's fall-through to NetworkService returns the legacy shape, the transform's path 2 preserves it, storage is unchanged.

This was a deliberate insurance policy. The cost is ~5 lines of code in the transform; the benefit is a ~5-minute rollback path.

### 4. `is_vendor` is derived from `roles`, not stored separately

v3's response has `user.roles: ['customer', 'vendor', ...]`. Mobile's `single_user` has independent booleans `is_vendor`, `is_admin`, `is_customer`. The transform derives `is_vendor` from `roles.includes('vendor')`. Did NOT also derive `is_admin` / `is_customer` because:

- Zero readers across mobile/src use `single_user.is_admin` or `single_user.is_customer`. Confirmed via grep.
- Including unused fields would commit to keeping them in the transform forever; omitting them now keeps the surface minimal.

If a future page reads `single_user.is_admin`, that page should either (a) derive it from `roles` directly via a shared utility, or (b) we extend this transform. Either is fine — the omission isn't a one-way door.

### 5. Response param typed as `any`, not a precise interface

The MobileNetworkAdapter's `post_request` returns `Observable<unknown>`. Strictly typed, the subscribe callback would need:

```ts
next: (response: {response_code: number; status: string; message: string; data: unknown}) => ...
```

Used `any` instead to match the file's existing convention (the rest of login.page.ts has many `any`-typed objects). Mixing strict typing for one callback while the rest of the file is loosely typed creates an inconsistent reading experience. A workspace-wide tightening of `any` usage is M4 hardening.

### 6. `refresh_token` stored in the legacy blob even though nothing reads it

The transform includes `refresh_token` in the output even though no current call site reads it. Rationale: M3.1.4 will add a refresh-token rotation handler that needs to read it from `single_user`. Adding it now means M3.1.4 doesn't have to revisit login storage — it can just consume what's already there.

### 7. Device test checklist is a separate runbook, not embedded in this completion doc

Two reasons:
- The checklist is **executable** — someone literally walks through it. Living in its own file makes it easier to copy into a test session, fill in, and archive.
- The completion doc closes the phase; the test checklist is open-ended (will be re-run for each subsequent deploy + cutover).

## Known issues to address in M3.1.4 / later

### 1. Register flip (descoped from M3.1.3)

Three blockers covered in the "Phase summary" section above. M3.1.4 must handle:
- Request body translation: `{first_name, last_name, email, phone, password, confirm_password, countryCode: "+971", accepted_terms}` → `{email, phone, password, country_code: "AE", first_name, last_name}`. The simplest place for this is **inside the call site**, similar to how the login flip handles the response shape there. A `transformLegacyRegisterRequest` next to register.page.ts.
- Flow change: legacy auto-logs-in after register; v3 requires OTP confirmation first. M3.1.4 must decide whether to:
  - (α) Keep the existing custom OTP flow as a separate parallel path, only flipping the `/users/register` POST to v3. The auto-signin after register fails for unverified-phone users — that's a UX regression.
  - (β) Replace the custom OTP flow with v3's `/auth/send-otp` + `/auth/confirm` endpoints. Larger change but consolidates around one OTP system.
  - (γ) Stagger: ship α first as a holding pattern, then β. Two PRs.
- Response code: v3 returns 201 not 200. The adapter normalizes to 200 (semantically wrong but not breaking). Consider whether to teach the adapter about 201 vs 200, or accept the lossy normalization. Adapter change is the right answer long-term; for M3.1.4 it's enough to document.

### 2. Missing billing/location fields after login flip

Three pages read fields from `single_user` that are NOT in the v3 login response:
- **`apps/mobile/src/app/customer/checkout/checkout.page.ts`** — `billing_street`, `billing_city`, `billing_area`, `billing_phone`, `billing_name`, `billing_email`, `delivery_address`. Read at line 329-335 into the order's shipping address, and updated at lines 657-663. **Highest risk** — if the user goes from login straight to checkout, the address fields will be blank.
- **`apps/mobile/src/app/customer/process/process.page.ts`** — `billing_name`, `billing_phone`, `billing_email`, `billing_city`, `billing_area`, `delivery_address`, `villa_number`. Lines 58-64.
- **`apps/mobile/src/app/customer/settings/settings.page.ts`** — `location`. Line 133 and 250.

Three resolution options, in increasing order of work:
- (α) **Wait and measure** — let the device test reveal whether checkout breaks in practice; the legacy backend endpoints these pages call may fill in the gap server-side. If so, do nothing.
- (β) **Bundle billing/location into login** — extend the login handler to also call `/v3/me/billing-address` and `/v3/me/location` after a successful login, merge the results into the stored blob. Adds 2 round-trips to login latency.
- (γ) **Refactor consumers** — change `checkout`, `process`, `settings` to read from the v3 endpoints directly via the adapter, rather than from cached `single_user`. Effectively brings M3.1.5 / M3.1.6 work forward for those three pages.

The device test checklist (B3) is designed to surface which option is needed. Decision deferred until after on-device cutover.

### 3. End-to-end testing on real devices

Pre-existing limitation per M3.1.2 closeout. The off-hours cutover window is when this gets exercised. The checklist in `m3.1.3-device-test-checklist.md` is the operational artefact.
