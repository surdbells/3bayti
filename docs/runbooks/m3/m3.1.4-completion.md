## Phase summary

M3.1.4 was the second of two mobile auth flip phases. M3.1.3 shipped login only; M3.1.4 finished the remaining auth surface — register, reset, refresh — and the supporting infrastructure (routing fixes + v3-direct adapter methods).

The phase grew mid-flight from its original 5–7-day estimate to ~6–8 days of effective scope because Phase 0 reconnaissance surfaced three issues not visible from the M3 plan or M3.1.3 closeout:

1. **5 routing table entries had wrong `newPath` values.** They were wired in M2 Day 5 against anticipated route names; M1 shipped with different final names (`verify-phone` → `validate-phone`, `forgot-password` → `reset`, `reset-password` → `reset/confirm`, plus `refresh` and `logout` with `oldPath` cleared because mobile has no legacy equivalents). The login flip in M3.1.3 happened to work because login was the one route that was named correctly.

2. **Register and reset pages collected phone OTP FIRST**, then user info, then registered/reset. v3 is identifier-first (email is canonical per Decision A.6.5) and bundles OTP delivery into `/register` and `/reset`. The legacy ordering is structurally incompatible with v3 — there's no way to preserve "validate phone first, collect info later" because v3 ties OTP to the user row, not to a standalone phone. **Per the approved decision in conversation, this became a full UX restructure** (collect info → register → confirm code; collect email → request OTP → confirm code + set password).

3. **The adapter's strangler-fig contract (`post_request(body, legacyUrl)`) had no path for v3-native endpoints.** The URL-resolver lookup needs a legacy URL to translate FROM, but `/auth/confirm`, `/auth/send-otp`, `/auth/refresh`, `/auth/reset`, and `/auth/reset/confirm` have no equivalent legacy URL the page would call. Either (a) bypass the adapter (loses Bearer attach + envelope wrap + 401-refresh-retry benefits) or (b) extend the adapter with a v3-direct entry point. **We extended the adapter** in M3.1.4b with `post_v3(routeKey, body, opts?)` / `get_v3(routeKey, opts?)`.

These three findings turned what looked like a tactical translate-and-flip into a structural piece of work. The phase was broken into five commits (a/b/c/d/e) so each could be reviewed and rolled back independently if anything went wrong on device test.

5 entries renamed + corrected; 5 entries added; 2 entries had `oldPath` cleared. The audit was matched directly against `apps/api/config/routes.php`'s `$app->group('/v3/auth', ...)` block so the routing table is now an accurate mirror of what's deployed.

- `'POST /auth/forgot-password'` → `'POST /auth/reset'`; newPath `/v3/auth/forgot-password` → `/v3/auth/reset`
- `'POST /auth/reset-password'` → `'POST /auth/reset/confirm'`; newPath `/v3/auth/reset-password` → `/v3/auth/reset/confirm`

Cleared oldPath (no mobile legacy equivalent):
- `'POST /auth/refresh'`, `'POST /auth/logout'`

Added (no precedent, v3-only or no legacy 1:1):
- `'POST /auth/validate-email'`, `'POST /auth/send-otp'`, `'POST /auth/confirm'`, `'POST /auth/logout-all'`, `'GET /auth/me'`, `'POST /auth/reset'`, `'POST /auth/reset/confirm'`

Safety: zero string-literal references to the renamed keys exist outside `feature-flags.ts` (consumers resolve keys via `resolveRouteKey()` which indexes by `oldPath`). Endpoints with empty `oldPath` are gracefully skipped by the URL resolver (`url-route-resolver.ts:96`). No behavioural impact on live mobile at the time of commit — login was the only `target: 'new'` consumer and its `newPath` was already correct.

**M3.1.4b — Adapter v3-direct extension** (`151e6f8`, `apps/mobile/src/app/core/http/mobile-network-adapter.ts` +115)

Added public `post_v3(routeKey, body, opts?)` and `get_v3(routeKey, opts?)` methods + private `callV3Direct`. Same machinery as `callV3` (URL resolution via `resolveUrl`, header building, envelope wrap, error translation) but with simpler input semantics: no legacy body translation (caller supplies v3-shaped body directly); explicit auth token (no `{token}` extraction from body); optional path-param substitution. Defensive `ROUTE_NOT_FOUND` and `ROUTE_NOT_NEW` error envelopes for typos / misconfigured routes.

This unblocked all subsequent flips. Register's `confirm_otp` / `resend_otp`, reset's `send_reset_otp` / `reset_password`, and the refresh-token call itself all go through these methods.

**M3.1.4d — Reset flow refactor** (`af4ae01`, 4 files, +325/-194)

Same pattern as register. Identifier changed from phone to email (matches v3 `ResetController` design — email is canonical, phone is for SMS delivery only). Legacy 4-endpoint flow (`customer/getToken`, `customer/sendOTP`, `customer/validateOTP`, `users/resetMobile`) collapsed to 2 endpoints (`/v3/auth/reset`, `/v3/auth/reset/confirm`). Stage 2 combines code entry + new password entry into one screen because v3's `reset/confirm` takes all three (verification_id, code, new_password) in a single call. **UX upgrade vs legacy**: on success, auto-login to `/account` (legacy redirected to `/login` for manual sign-in); user just demonstrated phone-possession AND set a new password, so they're clearly the account owner. `mapErrorMessage` maps `AUTH_INVALID_CREDENTIALS` and `VERIFICATION_FAILED` both to a single generic message (`text_reset_verification_failed`) to preserve the anti-enumeration property of `/v3/auth/reset`. +5 i18n keys per language.

**M3.1.4e — Refresh-token rotation with single-flight 401 retry** (`0a4158e`, 1 file, +292/-29)

The largest single-file change of the phase. Adds transparent 401 → refresh → retry behaviour to the adapter:

1. Any 401 from a Bearer-authenticated v3 request triggers refresh
2. Single-flight: concurrent 401s share one refresh call via `shareReplay(1)` on `refreshInFlight$`
3. On refresh success: new tokens merged into Preferences (preserving legacy-only fields like `billing_*`, `location`); original request retried with `Bearer <new_token>`; second 401 surfaced without re-refreshing
4. On refresh failure: Preferences['user'] cleared; original 401 surfaced via `translateError` (call sites that check `response_code !== 200` see this as session-expired)

Key implementation pieces:
- `refreshInFlight$: Observable<string | null> | null` field with `shareReplay(1) + finalize()` clearing the slot on completion
- `withRefreshRetry(initialAuthHeader, execute)` wrapper — both `callV3` and `callV3Direct` route through this
- `tryRefresh()` — single-flight refresh; reads `Preferences['user'].refresh_token`, POSTs `/v3/auth/refresh`, updates Preferences, returns new `access_token` or null
- `executeHttpRequest(method, url, body, authHeader)` — pure HTTP dispatch extracted from inline ternaries; used both for the initial call and the post-refresh retry, AND by `tryRefresh` directly to avoid recursion
- `updateStoredTokens(existingBlob, refreshResponse)` — **merges** new fields into the cached blob rather than overwriting (matches the M3.1.3 transform philosophy: preserve legacy-only fields)

Two layers of recursion guards prevent refresh-on-refresh: `callV3Direct` shortcuts `withRefreshRetry` when `routeKey === 'POST /auth/refresh'` OR `authHeader === null`; `tryRefresh` calls `executeHttpRequest` directly, bypassing `withRefreshRetry` entirely. Either alone would suffice; both together cost nothing and make intent obvious.

## Design decisions locked during the phase

These were all decided by user approval in conversation. Recorded here for posterity so M3.1.5+ has visibility into the trade-offs:

| Decision | Locked answer |
|---|---|
| **Reset flow refactor scope** | 1A — Full refactor included in M3.1.4 (was originally a separate sub-phase). Reason: same MessageCentral dead-code cleanup as register; would be wasteful to land twice. |
| **Routing-table fix atomicity** | 2A — Atomic single commit early in the phase (`a05965d`). Reason: prerequisite for all subsequent commits; mistakes are easier to isolate. |
| **Register cleanup approach** | β with cleanup — Full UX restructure + delete MessageCentral dead code (vs minimal preserve-legacy-UX option, which was structurally impossible). |
| **Refresh-token inclusion** | 3-do — Refresh-token rotation included in M3.1.4 (vs deferring to M3.1.5+). Reason: without rotation, every M3.1.5 catalog read would block at the first stale-token boundary. Rotation is a M3.1.5 prerequisite. |
| **Refresh trigger strategy** | 4a-aggressive — Any 401 from a Bearer-authed v3 request triggers refresh + retry, transparent to callers. Reason: simplest behavioural contract; call sites don't need to know about refresh. |
| **Concurrent-401 race protection** | 4b-single-flight — `shareReplay(1)` lock on `refreshInFlight$`; concurrent 401s wait on one refresh call. Reason: prevents thundering-herd refresh-spam that could lock the refresh-token rate limiter. |
| **Mid-flight UX restructure** | Proceed-with-restructure — Register page reordered to "collect info → register → confirm code". Reason: v3's identifier-first OTP design (email canonical, OTP bound to user row) is structurally incompatible with legacy's phone-first ordering. |

## M3 plan vs reality reconciliation

The M3.1 plan originally estimated M3.1.4 at 5-7 days with scope = "register flip + reset flip + refresh-token rotation". Actual scope at close ≈ 6-8 days because:

- Phase 0 reconnaissance uncovered the routing-table audit (sub-phase a, ~0.5d)
- The adapter v3-direct extension was not anticipated; the legacy strangler-fig contract assumed all v3 routes had legacy URL precursors (sub-phase b, ~0.5d)
- Both register and reset turned into UX restructures, not just translate-and-flip (added ~1d each vs estimate)
- Refresh-token rotation single-flight implementation needed care to avoid recursion across the two adapter entry paths (sub-phase e, on estimate)

The phase still shipped same-day because the 5 commits all built clean on first or second attempt and no rework was needed.

## Known issues to address in M3.1.5+

1. **Call-site 401-session-expired redirect behaviour is not wired.** The adapter clears `Preferences['user']` on refresh failure and surfaces the original 401 to the caller. Currently no call site automatically redirects to `/login` on this signal — the caller decides what to do. For M3.1.4 this is acceptable because the only call sites that hit Bearer-authed v3 routes are the auth pages themselves (login/register/reset). When M3.1.5+ flips catalog and profile reads to v3, those pages should be reviewed for session-expired UX (auto-redirect or in-page banner).

2. **Logout flow is not wired.** `/v3/auth/logout` and `/v3/auth/logout-all` are in the routing table but no page calls them. Mobile's current "sign out" just clears `Preferences['user']` locally without revoking server-side. Bears reviewing for M3.1.5+ — leaves orphan refresh tokens alive on the server until natural expiry.

3. **Refresh on v3-direct calls is untested.** The device-test checklist's C9 step is deferred to M3.1.5 because no v3-direct endpoint with `target: 'new'` is currently consumed by a user-facing page (the auth pages all call `/auth/*` endpoints which are anonymous or short-lived-OTP, none of which would 401 in the way that triggers refresh). C9 will run for real when M3.1.5 wires `/v3/me/*` reads.

4. **Pre-existing M3.1.3 billing-fields gap still pending classification.** The M3.1.3 device-test checklist's B3 step asks whether the absence of `billing_*` fields in the v3 login response causes any consumer page to break. Not classified yet because the device test for M3.1.3 hasn't been run yet either. M3.1.5 entry checklist should resolve this before starting.

5. **201 vs 200 response code semantic mismatch.** v3 `/auth/register` returns 201 Created on the wire; the adapter normalises to `response_code: 200` in the legacy envelope. Call sites' `response.response_code === 200` checks still pass — so this is semantically wrong but behaviourally invisible. Worth a cleanup pass in M4 hardening. Documented in the M3.1.3 closeout originally; restated here because register now uses this path.

6. **Refresh-token rotation lifetime** is a server-side concern. Currently each refresh-token use issues a new refresh-token (rotation per use), per v3 design. The mobile adapter merges the new refresh_token into Preferences on each successful refresh. If the server changes the policy to non-rotating, the merge still works (same refresh_token gets stored back). No mobile change needed for that.

## Rollback procedures

Per commit, in reverse order (if any single commit needs to come out):

- **M3.1.4e (refresh-token rotation)** — single-file revert; existing public method surfaces unchanged, so call sites continue to work, just without the 401-handling enhancement.
- **M3.1.4d (reset flow refactor)** — `git revert <af4ae01>`; rebuild. Legacy `customer/*` + `users/resetMobile` endpoints still operational on the legacy backend so the previous flow would work again immediately.
- **M3.1.4c (register flip)** — `git revert <a7dc94f>`; rebuild. Legacy `customer/getToken` + `customer/sendOTP` + `customer/validateOTP` + `users/register` still operational; previous flow works.
- **M3.1.4b (adapter v3-direct)** — single-file revert; no consumers exist if c/d are also reverted.
- **M3.1.4a (routing table)** — single-file revert; no behavioural impact on live mobile at the time of commit because login was the only consumer and its newPath was already correct.

Full M3.1.4 rollback: revert all 5 commits in reverse order; M3.1.3 login flow remains intact.
