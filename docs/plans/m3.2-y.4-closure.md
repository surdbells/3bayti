## 4. New surfaces & contracts

### Terminology
Customer-facing word is **Designer**; the API entity is **vendor**
(VendorSerializer's storefront view is literally "Designer Spotlight").
Routes use `/designer/*`; the service calls `/v3/vendors/*`.

### DesignerService (root singleton, RoutedHttpClient)
Public catalog reads via the routed client (like home-data), NOT the
Bearer-bound direct client. All four routes already existed in the
api-client ENDPOINT_ROUTING table (target=new → v3):

| Method | Endpoint | Returns |
|---|---|---|
| `loadMore({limit,offset})` | `GET /vendors` | accumulating `Designer[]` + `hasMore` |
| `getFeatured(limit)` | `GET /featured-vendors` | `FeaturedVendor[]` |
| `getBySlug(slug)` | `GET /vendors/:slug` | `Designer` (throws on 404) |
| `listProducts(slug,{limit,offset})` | `GET /vendors/:slug/products` | `{ items, hasMore }` |

Directory list is held in the service (accumulating, like OrderService);
single-designer + product lists are stateless returns (per-page
ownership, like order-detail).

### Designer model
Mirrors `VendorSerializer::publicShape`:
`{ id, slug, name, description, logo_url, cover_image_url, is_verified }`.
`description` may carry admin-authored inline HTML (sanitised at write
time) → rendered via `[innerHTML]` on the detail page.

### SSR
`/designer/:slug` → `RenderMode.Prerender` + `getPrerenderParams`
(`fetchVendorSlugs` against `/v3/vendors`), runtime SSR fallback for
the long tail — same model as `/product/:slug`. Build prerendered 100
designer pages. New env override: `VENDOR_API_BASE_URL`.

### Sitemap
`generate-sitemap.mjs` now emits per-designer URLs (priority 0.6,
weekly) + the `/designer` index (priority 0.8). Total 1933 → 2038.

## 5. Patterns reinforced

- **Routed-client service for public catalog reads** (vs Bearer-bound
  direct client for account data) — DesignerService follows
  home-data's convention; tested against `HttpTestingController` by
  asserting the resolved v3 URLs.
- **Accumulating-list-in-service + stateless-detail** split, matching
  OrderService / order-detail.
- **Fail-soft independent fetches**: the directory's featured strip
  and grid are separate; a failure in one never blanks the other.
- **Inline not-found over hard router error** for unknown slugs (Q4.4),
  matching the order-detail bad-id pattern.
- **Prerender + getPrerenderParams for public SEO pages** (vs
  RenderMode.Server for auth-gated user pages in Y.2/Y.3).

## 6. Known follow-ups (NOT Y.4 scope)

- **`/designer/:slug/reviews`** — `DesignerCard.vendorReviewsUrl()` (the
  rating chip) links here; the route doesn't exist yet. Minor secondary
  link. Build it when designer reviews are a priority (candidate for a
  Y.4 follow-up or Y.6-adjacent work).
- **`/featured-vendors` returns 500 in some environments** — observed
  in the build-time prerender log. Pre-existing (noted in the
  api-client feature-flags comment: "legacy /v2/featured-vendors was
  returning 500"). The directory + home page both fail soft (hide the
  spotlight), so it degrades gracefully. Worth an API-side fix
  independent of web.
- **Designer SEO `<title>`/meta** — the detail route sets a static
  title; a SeoService pass (like product/category detail) to set the
  per-designer title + OpenGraph + JSON-LD would improve indexing.
- **Directory pagination** — `/v3/vendors` returns all active vendors
  in one envelope today; the load-more machinery is in place for when
  the endpoint gains real pagination.
