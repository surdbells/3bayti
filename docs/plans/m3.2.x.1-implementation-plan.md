## 0. Why this is M3.2.X.1 (the first M3.2 feature phase)

Per the master plan locked sequence (X → Y → Z), Stream X starts with
items that unblock subsequent phases. `best_sellers` +
`best_sellers_listing` were the only two M3.1.5 catalog endpoints not
flipped to v3, deferred because they needed `order_items` aggregation
data which only existed after M3.1.6 shipped. M3.1.6 closed in
`171fc0a`; both endpoints are now unblockable.

Closing M3.2.X.1 completes the mobile catalog migration that started
in M3.1.5. Every mobile catalog read path will be on v3 after this
phase.

### M3.2.X.1-A — Backend: extend `GET /v3/products` with `sort=best_seller` (~1 day)

**Goal:** Add a `'best_seller'` sort option that ranks products by total quantity sold in completed orders.

**Implementation steps:**

1. **Domain decision (Q-Window):** see §3 below for the aggregation window decision that needs your approval before code begins.

2. **Update `ProductRepository::findActivePaginated`:**

   - Add `'best_seller'` to the sort match expression
   - Implementation strategy: aggregate `SUM(order_items.quantity)` filtered to in-scope orders (per Q-Window) and join. Two options:

     - **Option 2A (simple SQL JOIN):** Add a `LEFT JOIN` to a derived table that aggregates `order_items` per product. Postgres handles this fine for our catalog size (~1900 products × few thousand orders). Recomputed on every request.

     - **Option 2B (materialized view):** Create a `product_sales_aggregates` materialized view, refresh via cron every N hours. Better at scale; overkill for current data volume.

   - **Recommended: 2A.** Catalog size is small; query latency at this scale is well under 100ms. We can introduce 2B in M4 if metrics show contention. Trading flexibility for simplicity is the right call until proven wrong.

3. **Update `ListProductsController::parseSort`:**

   - Add `'best_seller'` to the valid list

4. **Stable tie-break:**

   - Products with zero sales should still appear (just with rank=0)
   - Tie-break for equal sales counts: `createdAt DESC` (newest first), then existing `id DESC`

5. **Backend tests:**

   - `ListProductsControllerTest`: add cases for `sort=best_seller` happy path, products with no sales appear last, pagination consistent
   - `ProductRepositoryTest`: aggregation query unit test (fixtures: 3 products with known sales counts)

**Files modified:**
- `apps/api/src/Http/Controllers/Catalog/ListProductsController.php`
- `apps/api/src/Domain/Catalog/ProductRepository.php`
- `apps/api/tests/Http/Controllers/Catalog/ListProductsControllerTest.php` (new test cases)

**Acceptance criteria:**
- [ ] `GET /v3/products?sort=best_seller&limit=10` returns 10 products ordered by units sold DESC
- [ ] All existing sort values still work (newest, oldest, price_asc, price_desc, relevance)

### M3.2.X.1-B — Backend: add `/v3/products/best-sellers-listing` (vendor-grouped variant) (~0.5 days)

**Goal:** Mirror the legacy `best_sellers_listing` behaviour. Legacy semantics observed in mobile call site: returns products grouped by vendor with each vendor's top-N products.

**Question for you (Q-Listing):** the legacy endpoint's actual semantic is unclear without a Postman call. Three possibilities:

- **Option B1:** Same as `sort=best_seller` but with vendor grouping in the response (vendors with at least one sold product, each vendor showing their top N best-sellers)

## 3. Decisions to lock IN this approval

### Decision M3.2.X.1-Q-Window: Aggregation window

**The question:** "Best seller" can mean different things based on time window:

- **A:** All-time (every completed order ever counts)
- **B:** Last 30 days (rolling window — captures current popularity, doesn't ossify on old hits)
- **C:** Last 90 days (longer window — more data for newer products to accumulate)
- **D:** Configurable via query param (e.g., `?window=30d`)

**Trade-offs:**

- All-time favors older products that have had longer to sell. New products struggle to break in.
- Rolling windows surface current trends. Newer products fairer.
- Configurable adds API surface complexity for limited gain on day one.

**My recommendation: B (last 30 days).** This matches typical ecommerce semantics ("best sellers" implies "right now"). M4 can add a `?window=` param if reporting needs surface. Database query stays simple (just a `WHERE orders.created_at >= NOW() - INTERVAL '30 days'`).

### Decision M3.2.X.1-Q-Listing: best_sellers_listing endpoint shape

(See §M3.2.X.1-B above)

- **B1:** Vendor-grouped (new dedicated endpoint)
- **B2:** Flat alias
- **B3:** Drop the legacy distinction; single `/v3/products?sort=best_seller` endpoint serves both call sites via different `limit`/`offset` params

**My recommendation: B3.** Eliminates an endpoint, simplifies the API surface, matches actual mobile usage observed in `best-sellers.page.ts`.

### Decision M3.2.X.1-Q-Order-Status: which orders count

**The question:** When aggregating sales, which order statuses should be included?

- **A:** Only `delivered` orders (strict: counts only fulfilled sales)
- **B:** `paid`, `fulfilling`, `shipped`, `delivered` (paid orders, regardless of fulfillment status)
- **C:** Same as B plus `refunded` (any product that got money — even if refunded — was sold)

**Trade-offs:**

- A is the strictest signal but lags reality (a recently popular product won't show up until orders deliver, ~5-7 days)
- B is the typical signal (paid = a real sale; fulfillment is a vendor problem)
- C double-counts effectively-cancelled sales

**My recommendation: B.** Refunded orders shouldn't pump up best-seller rankings; pending/failed orders shouldn't count at all. B matches standard ecommerce practice.

### Decision M3.2.X.1-Q-Shadow: shadow window duration

**The question:** Master plan §1.4 prescribes 7 days for shadow mode. Best-sellers is low-risk (read-only, no mutations, no PII). Can we shorten?

- **A:** Standard 7 days (strict adherence to migration discipline)
- **B:** 48 hours (faster iteration; acceptable for low-risk read-only endpoints)
- **C:** Same-day flip with monitoring (highest velocity; only justified if backend tests gave high confidence)

**My recommendation: A (7 days).** Master plan discipline exists for a reason. Best-sellers is low-risk but the operator monitoring window also catches data correctness issues (e.g., a window calculation bug that nobody hand-verified). 7 days isn't worth shortening on the FIRST Stream X phase.
