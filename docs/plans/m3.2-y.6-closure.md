## 3. Decisions taken (operator-confirmed Q6.1–Q6.4)

- **Q6.1 = deactivate + soft-delete.** Deletion sets BOTH
  `deactivate()` (is_active=false) AND `softDelete()` (deleted_at
  stamp). Deactivation locks out immediately (LoginController +
  AuthMiddleware already reject `!isActive()`); the soft-delete stamp
  is for retention/purge + support clarity.
- **Q6.2 = re-auth before deletion.** `DELETE /v3/me` requires
  `current_password`; mismatch → 401 AUTH_INVALID_CREDENTIALS (same
  posture as change-password).
- **Q6.3 = idempotent wishlist POST.** Already-saved → 200 no-op (not
  409). New → 201. The DB unique index `(user_id, product_id)` is the
  race backstop.
- **Q6.4 = products in the existing ProductSerializer shape.**
  `GET /v3/me/wishlist` returns saved PRODUCTS via
  `ProductSerializer::listShapeMany` in a `PaginatedEnvelope`, so the
  wishlist renders with the exact same product-card shape as the
  catalogue.

## 4. Architectural notes carried forward

- **Deletion needed NO migration.** The `User` entity already had
  `deactivate()`/`softDelete()`/`isActive()`/`isDeleted()`, the
  `is_active` + `deleted_at` columns, and
  `RefreshTokenRepository::revokeAllForUser()`. Y.6-A was one
  controller reusing them + a `recordDelete` audit + 204. Order
  history is retained (the soft delete doesn't cascade to orders).
- **Idempotency is the wishlist posture in both directions.** POST
  no-ops when already saved; DELETE returns 204 whether or not the
  row existed. The controller's check-then-act relies on the DB
  unique index as the concurrency backstop.
- **Direct Bearer client again.** Both `ProfileService.deleteAccount`
  and the entire `WishlistService` use the raw `HttpClient` (auth via
  interceptor), not `RoutedHttpClient` — these endpoints aren't in the
  registry and deletion needs a DELETE-with-body. This is now the
  established pattern for any account write outside the registry
  (cart/orders/addresses/measurements/deletion/wishlist).
- **`WishlistService` saved-set is app-wide truth.** A
  `signal<Set<number>>` of saved product ids drives the heart on every
  `ui-product-card` everywhere; toggling on any surface reflects
  instantly. The full product list + meta are held separately for the
  `/account/wishlist` page. A constructor `effect` watches
  `AuthService.isAuthenticated()` and calls `reset()` on the
  signed-in→out transition, so a guest/next user never inherits the
  prior session's saved set. (This keeps core `AuthService.logout()`
  decoupled from the feature service — the dependency points
  feature→core, never the reverse.)
- **The ProductCard heart is now live.** Previously decorative; now
  reflects saved state (`[class.is-saved]` + `aria-pressed` + filled
  red heart) and toggles via `WishlistService` for signed-in users,
  routing guests to `/login`. Fire-and-forget; the saved-set signal
  re-renders. SSR-safe (no eager calls).
- **phpstan id-suppression.** `Wishlist::$id` carries the same
  Doctrine-managed-id `property.unusedType` false positive every
  entity has; suppressed with a single inline `@phpstan-ignore` so the
  baseline stays at exactly 60 (the codebase has no phpstan baseline
  file — the rule is "no net increase").
- **The reusable `ConfirmModal` (built in Y.5-C) carried the deletion
  danger confirmation** — exactly the reuse Y.5-C was sequenced for.

## 5. API surface added (Y.6)

| Method | Path | Notes |
|---|---|---|
| DELETE | `/v3/me` | body `{ current_password }`; deactivate + soft-delete + revoke all sessions; 204; 401 on wrong password; 422 if missing |
| GET | `/v3/me/wishlist?limit=&offset=` | saved products via ProductSerializer list shape in PaginatedEnvelope |
| POST | `/v3/me/wishlist` | body `{ product_id }`; idempotent (201 new / 200 already-saved); 404 if product missing/inactive; 422 if missing |
| DELETE | `/v3/me/wishlist/{productId}` | idempotent; always 204 |

New table `wishlist` (migration `Version20260520000001`): id, user_id FK
(CASCADE), product_id FK (CASCADE), created_at; unique
`(user_id, product_id)`; index `(user_id, created_at)`.

## 6. Known follow-ups (not blocking)

- **Guest wishlist + merge-on-login.** The heart routes guests to
  `/login`; there's no local-first guest wishlist that merges into the
  account on sign-in. (The original ProductCard TODO envisioned this;
  it's a clean future sub-phase — add a device-local saved-set + a
  `POST /v3/me/wishlist/merge` mirroring the cart-merge pattern.)
- **Account-deletion grace / undo window.** Deletion is immediate;
  there's no "we'll delete in 30 days" cooling-off. The soft-delete
  stamp makes a future restore/grace flow possible without schema
  change.
- **Wishlist heart loading/disabled state.** The toggle is
  fire-and-forget with no per-card spinner; a rapid double-tap could
  fire two requests (both idempotent server-side, so harmless, but a
  per-card busy state would be tidier).
- Carried over from earlier streams: per-designer reviews route;
  per-category measurement sets in the web UI; stale api-client
  measurement registry entries.
