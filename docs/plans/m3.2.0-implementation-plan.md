## 0. Why this is M3.2.0 (the gate before any feature work)

Per locked decision Q3 + Q-QI, the quality infrastructure must be in place BEFORE the ~24-32 week M3.2 feature build begins. Specifically:

- **Q3** mandated Playwright + visual regression + automated a11y in CI
- **Q-QI** confirmed building these in M3.2.0 first
- **Q4** clarified apps/web is NOT live (stays at staging.3bayti.ae through all of M3); existing apps/web pages are still publicly visible at staging.3bayti.ae and serving real CDN traffic, so any CI regression breaks the staging deploy

This phase ships **zero new product features**. It produces:

1. Playwright e2e testing for apps/web (baseline coverage on existing pages)
2. Playwright config for apps/mobile (Capacitor-aware; runs locally only — emulators in CI are expensive)
3. Visual regression via Chromatic (selected over Percy — rationale §1.3)
4. axe-core automated WCAG AA scanning in CI
5. Storybook for `packages/shared-ui` (component library scaffold for the Web build)
6. Updated `.github/workflows/web.yml` and a new `quality.yml` workflow

Every subsequent phase (M3.2.X.1 onwards) ships against these gates. A 1-week investment that pays off across the remaining 38-50 weeks of M3.

### 1.3 Chromatic vs Percy — tool selection

**Recommendation: Chromatic.** Rationale:

| Criterion | Chromatic | Percy |
|---|---|---|
| Storybook integration | Native (same company maintains Storybook) | Plugin-based |
| Pricing for our use | Free tier covers 5,000 snapshots/month + unlimited users | Free tier limited to 5,000 snapshots/month + 1 user |
| Playwright integration | First-class via `@chromatic-com/playwright` | First-class via `@percy/playwright` |
| CI integration | Native GitHub Actions support | Native GitHub Actions support |
| Setup complexity | Lower (shared with Storybook) | Slightly higher |
| Visual diff UX | Excellent — git-aware branching | Excellent |
| Component testing | Storybook stories double as visual tests | Manual page captures only |

**Counter-argument:** Percy supports more advanced cross-browser visual diffs (Chrome + Firefox + Safari simultaneously). For a single-app SPA, Chromatic's component-driven model is more valuable than cross-browser pixel comparison.

**Locked: Chromatic.** Documented as decision Q3-Tool.

### 1.4 Existing test infrastructure

- `pnpm test` → `turbo run test` → calls `ng test` per app (Karma/Jasmine baselines exist but no e2e)
- No Playwright config files
- No Storybook config
- No axe-core integration
- API has `phpunit` (PHP testing, separate ecosystem; M3.2.0 does not touch)

### 1.5 What this phase does NOT touch

- **Backend (`apps/api`)** — already has phpunit + phpstan; M3.2.0 only touches the TS surfaces
- **Production runtime** — all changes are tooling/CI. The `staging.3bayti.ae` deployment behavior remains identical.

### M3.2.0-A — Playwright setup for apps/web (1-2 days)

**Goal:** Install Playwright, create config, write baseline smoke tests for the 4 existing routes (home, categories, category-detail, product-detail), wire into CI.

**Implementation steps:**

1. **Install Playwright at workspace root**

   - `pnpm add -D -w @playwright/test@^1.50.0`
   - `pnpm add -D --filter @3bayti/web @playwright/test`
   - Why workspace + per-app: workspace allows version pinning; per-app dep allows `pnpm --filter @3bayti/web test:e2e` to resolve correctly.

2. **Create `apps/web/playwright.config.ts`**

   - `testDir: './e2e'`
   - `fullyParallel: true`
   - `forbidOnly: !!process.env.CI`
   - `retries: process.env.CI ? 2 : 0`
   - `workers: process.env.CI ? 2 : undefined`
   - `reporter: [['html', {open: 'never'}], ['github']]`
   - `use: { baseURL: process.env.PLAYWRIGHT_BASE_URL ?? 'http://localhost:4200', trace: 'on-first-retry', screenshot: 'only-on-failure' }`
   - Single project: `chromium` (latest stable). Cross-browser is M4-tier complexity.
   - `webServer: { command: 'pnpm dev', url: 'http://localhost:4200', reuseExistingServer: !process.env.CI, timeout: 120000 }` — auto-starts dev server for local runs

3. **Create `apps/web/e2e/` directory with 5 baseline test files**

   - `home.spec.ts` — verifies hero carousel renders ≥1 slide, footer brand name present, primary nav links present, sitemap link in footer
   - `categories-index.spec.ts` — `/category` route, verifies category cards render, "Shop by Category" heading
   - `category-detail.spec.ts` — `/category/abayas` (first prerendered slug), verifies ≥1 product card, breadcrumb, ItemList JSON-LD
   - `product-detail.spec.ts` — uses sitemap.xml to pick a known slug, verifies product name, price, image, Product JSON-LD, "Add to cart" button (placeholder for M3.2.Y.2)
   - `responsive.spec.ts` — same routes at viewport sizes 375×667 (mobile), 768×1024 (tablet), 1280×800 (desktop); checks no horizontal scroll, header visible

4. **Add `apps/web/package.json` scripts**

   ```json
   "test:e2e": "playwright test",
   "test:e2e:ui": "playwright test --ui",
   "test:e2e:headed": "playwright test --headed",
   "test:e2e:report": "playwright show-report"
   ```

5. **Add `apps/web/.gitignore` entries** for `playwright-report/` and `test-results/` (turbo already has these in outputs).

6. **Add `apps/web/e2e/README.md`** explaining: how to run locally (`pnpm --filter @3bayti/web test:e2e`), how to update tests after intentional UI changes, how to interpret CI failures, how to use `--ui` for interactive debugging.

7. **Verification:**
   - `pnpm --filter @3bayti/web test:e2e` runs locally and all 5 spec files pass
   - Existing `pnpm --filter @3bayti/web build` still works
   - Existing `pnpm --filter @3bayti/web type-check` still passes
   - apps/web TS error count remains 0

### M3.2.0-B — Playwright setup for apps/mobile (1-2 days)

**Goal:** Playwright config for mobile dev server (`pnpm --filter @3bayti/mobile dev`). Local-only by default (Capacitor in CI requires expensive emulator runners). Coverage limited to the web preview surface — testing the actual native iOS/Android builds is M4 territory.

**Why Capacitor mobile e2e via Playwright works:**

Capacitor mobile apps ARE Angular/Ionic web apps running inside a WebView. Playwright can drive the dev server (Ionic serve) just like a regular Angular app. This catches ~80% of regressions (UI logic, state management, routing) at near-zero CI cost. The remaining 20% (native plugins, hardware interactions, platform-specific UI) needs real device testing per the M3.1.7 device-test-checklist pattern.

**Implementation steps:**

1. **Install Playwright in mobile app**
   - `pnpm add -D --filter @3bayti/mobile @playwright/test`

2. **Create `apps/mobile/playwright.config.ts`**
   - `testDir: './e2e'`
   - `webServer: { command: 'pnpm dev', url: 'http://localhost:8100', timeout: 180000 }` (Ionic serve takes longer)
   - Single project: `chromium`
   - Mobile-sized viewport default: `{ viewport: { width: 390, height: 844 }, userAgent: 'Mozilla/5.0 (iPhone; CPU iPhone OS 17_0 like Mac OS X) AppleWebKit/605.1.15' }`

3. **Create `apps/mobile/e2e/` with 4 baseline spec files**
   - `home.spec.ts` — verifies home tab loads, tab bar present, primary nav functional
   - `auth.spec.ts` — login form renders, validation works (no actual submission against backend)
   - `catalog.spec.ts` — browsing existing categories, product card grid
   - `my-orders.spec.ts` — verifies `/my-orders` route renders (with Preferences mock — see step 4)

4. **Add a `Preferences` mock fixture**
   - Capacitor `Preferences.get('user')` would return null without auth; tests need a mock
   - Use Playwright's `addInitScript` to install a window-level mock that intercepts `@capacitor/preferences` calls before app boot
   - Document the pattern in `apps/mobile/e2e/README.md` for future test authors

5. **Add `apps/mobile/package.json` scripts** — mirror M3.2.0-A pattern (test:e2e, test:e2e:ui, etc.)

6. **CI integration: SKIP for M3.2.0**
   - Document in mobile e2e README that these run locally only
   - Add a placeholder section to `.github/workflows/mobile.yml` (comment block) explaining how to enable when budget permits — actual enablement happens during M3.2.Z work when push notifications need mobile e2e validation

7. **Verification:**
   - `pnpm --filter @3bayti/mobile test:e2e` runs locally and all 4 spec files pass
   - Mobile tsc count stays at 6 baseline
   - Existing `ng build` still works

**Files added: ~9**
**Files modified: 1-2**
**Tests added:** 4 spec files (~10-15 cases)

**Commit message:** `M3.2.0-B — Playwright setup for apps/mobile (local-only baseline)`

### M3.2.0-C — Visual regression with Chromatic (1-2 days)

**Goal:** Wire Chromatic to capture visual snapshots of apps/web pages on every PR. Reviewer sees side-by-side visual diffs before merge.

**Implementation steps:**

1. **Sign up for Chromatic** (operator action; project token issued)
   - **REQUIRES OPERATOR INPUT**: I cannot create a Chromatic account. You'll need to:
     1. Sign up at chromatic.com (free tier; GitHub OAuth)
     2. Connect the surdbells/3bayti repo
     3. Get the project token from project settings → "Manage" → "Configure"
     4. Add `CHROMATIC_PROJECT_TOKEN` to GitHub secrets at `repo settings → Secrets and variables → Actions → New repository secret`

2. **Install Chromatic CLI + Playwright integration**
   - `pnpm add -D -w chromatic@^11.0.0`
   - `pnpm add -D --filter @3bayti/web @chromatic-com/playwright@^1.0.0`

3. **Add Chromatic capture hooks to Playwright tests**
   - Update `apps/web/playwright.config.ts` to use Chromatic's archive-based capture
   - In each spec file, add `await takeArchive(page, 'home-page')` at logical visual checkpoints
   - Why archive-based (not snapshot-based): captures the full DOM + assets so Chromatic can re-render in its own browsers, getting cross-browser results free

4. **Add `apps/web/package.json` script**
   ```json
   "chromatic": "chromatic --exit-zero-on-changes --build-script-name=build --auto-accept-changes \"main\""
   ```
   - `--exit-zero-on-changes` — don't fail CI on visual differences; surface them in PR comment for review
   - `--auto-accept-changes "main"` — when commits land on main, accept current baseline (no manual baseline approval per merge)

5. **CI integration: new step in `.github/workflows/web.yml`**
   - Runs AFTER Playwright tests succeed
   - Runs ONLY on PRs (not on main pushes — main auto-accepts)
   - Posts visual diff link as PR comment
   - Does NOT block merge (set as informational; reviewer sees diff and decides)

6. **Add a `chromatic.json` config in apps/web/**
   - `onlyChanged: true` (TurboSnap — Chromatic detects which stories actually changed based on git diff)
   - `externals: ['**/*.svg', '**/*.png', '**/*.jpg', '**/*.webp']` (don't re-snapshot when only assets change)
   - `skip: 'dependabot/**'` (skip dependabot PRs to save snapshot budget)

7. **First baseline generation**
   - Manually trigger Chromatic from local: `pnpm --filter @3bayti/web chromatic`
   - This establishes the initial baseline against current apps/web state
   - All future PRs diff against this baseline

8. **Documentation**
   - `docs/runbooks/m3.2/chromatic-runbook.md` covering:
     - How to read a Chromatic PR comment
     - How to accept an intentional visual change
     - How to debug a false-positive diff
     - How to reset baselines after major redesigns
     - Budget management (5,000 snapshots/month free tier)

**Files modified: 2** (web.yml CI workflow, playwright.config.ts)
**Operator dependency: Chromatic account + token added to GitHub secrets**

### M3.2.0-D — axe-core CI integration (1 day)

**Goal:** Automated WCAG AA scanning runs on every Playwright test. Zero new violations allowed; existing violations documented for inline remediation.

**Implementation steps:**

1. **Install @axe-core/playwright**
   - `pnpm add -D --filter @3bayti/web @axe-core/playwright@^4.0.0`
   - Same for mobile (`@3bayti/mobile`)

2. **Create `apps/web/e2e/utils/a11y.ts` helper**
   ```typescript
   import AxeBuilder from '@axe-core/playwright';
   export async function expectNoA11yViolations(page, options?) {
     const results = await new AxeBuilder({ page })
       .withTags(['wcag2a', 'wcag2aa', 'wcag21a', 'wcag21aa'])
       .analyze();
     expect(results.violations).toEqual([]);
   }
   ```

3. **Add `await expectNoA11yViolations(page)` to every Playwright spec** at the end of each `test()` block

4. **First run: capture baseline violations**
   - Run locally: `pnpm --filter @3bayti/web test:e2e`
   - Existing apps/web pages may have violations (likely: missing alt text, color contrast, missing labels)
   - Document each violation in `docs/runbooks/m3.2/a11y-baseline.md` with:
     - Page where it occurs
     - WCAG rule violated
     - Plan for remediation (either inline next phase, or M3.2.Y.5 polish phase)

5. **Allowlist baseline violations temporarily**
   - For violations we'll fix inline as we go: create `apps/web/e2e/utils/a11y-allowlist.ts`
   - Each allowlist entry has expiry date + remediation ticket reference
   - `expectNoA11yViolations` checks against allowlist; violations not in allowlist cause failure
   - This pragmatic step prevents M3.2.0 from blocking on a 5-day a11y remediation sprint while still gating new violations

6. **CI integration**
   - Already gated through Playwright run (no new workflow step needed)
   - axe results uploaded as Playwright HTML report artifacts

7. **Documentation**
   - `docs/runbooks/m3.2/a11y-guide.md` covering:
     - WCAG AA standards we hold to
     - How to fix common violations (alt text, labels, headings, contrast, focus)
     - How to add/remove allowlist entries
     - When to use `withRules` exclusions (rare; document reasoning)

**Files added: ~4** (utils/a11y.ts, utils/a11y-allowlist.ts, runbooks/a11y-baseline.md, runbooks/a11y-guide.md)

### Decision M3.2.0-Q3: Mobile e2e CI policy

**The question:** Mobile Playwright via the web preview (Ionic serve) works fine in CI but mobile-specific issues (native plugins, real device gestures) need real device testing.

Options:

- **A:** Run mobile Playwright in CI (web preview only) — cheap; catches Angular/state regressions
- **B:** Run mobile Playwright locally only — saves CI minutes; M3.1.7 device-test pattern continues for native verification
- **C:** Hybrid: run on PR opens + main pushes; not on every commit

**My recommendation: A** with `continue-on-error: true` initially. We learn the false-positive rate before promoting to required check.

### Decision M3.2.0-Q4: Cross-browser scope

**The question:** Playwright supports Chromium + Firefox + WebKit. Each browser triples CI minutes.

Options:

- **A:** Chromium only (~70% of mobile users in UAE per StatCounter; same engine as Edge)
- **B:** Chromium + WebKit (Safari is non-trivial mobile share; catches WebKit-specific bugs early)
- **C:** All three (highest coverage; 3x CI cost)

**My recommendation: A** for M3.2.0. Add WebKit only when we see WebKit-specific bugs (deferred decision).
