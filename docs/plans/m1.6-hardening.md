# M1.6 — Hardening Plan

**Status:** Planned, not yet started
**Date authored:** 9 May 2026
**Predecessor:** M1.7 (account management, complete)
**Successor:** M2 (catalog)
**Estimated total effort:** Comparable to M1.7 — multi-session work

## Why M1.6

M1.5 deployed the API, M1.7 added the account-management surface. Both
shipped knowing some corners were cut. M1.6 is where we go back and
close those gaps before traffic arrives via M2 catalog work.

The cuts fall into four categories:

1. **Correctness gaps** — things that are technically broken but
   haven't surfaced because we don't have real traffic yet. Most
   notable: rate limiting that doesn't actually rate-limit because
   counters live in PHP-FPM worker memory.

2. **Observability gaps** — when production breaks (and it will),
   we'd find out via `tail /var/log/apache2/error.log` if at all.
   No alerts, no aggregation, no traces.

3. **Deploy hardening** — the auto-deploy works but has obvious
   weak spots: bad deploys stay live, two near-simultaneous pushes
   could race, no notifications on failure.

4. **Server hygiene** — accumulated technical debt from the M1.5
   pivot to aaPanel: shared FPM pool, weak SSL ciphers, root
   deploy user, etc.

This plan splits M1.6 into four sub-phases reflecting those categories.
M1.6.1 must ship before M2 starts taking real traffic; the others can
slip if needed.

---

## M1.6.1 — Correctness (BLOCKING for M2)

The four items here are genuine production-correctness issues. Without
them, any of: someone bypassing rate limits, a transitive dep change
silently breaking us in CI, or no audit trail when a user disputes a
profile change.

### M1.6.1.A — Redis backend for state stores

**Problem.** Currently OTP rate-limit counters and refresh-token
denylist live in `OtpService::$attempts` (in-memory array per worker).
Each PHP-FPM worker has its own copy. Restart wipes everything.
With 4+ workers, an attacker can rotate through workers to bypass
limits entirely. This is **rate limiting that doesn't rate-limit**.

**Solution.** Wire Redis as the storage backend for both stores. Use
`predis/predis` (pure PHP, no extension required, simpler ops than
phpredis even though slightly slower).

**Concrete changes:**

  - **Add `predis/predis` to composer.json**
  - **New interface `Bayti\Api\Infrastructure\KeyValueStore`** with
    methods: `get(key)`, `set(key, value, ttlSeconds)`, `incr(key)`,
    `expire(key, ttl)`, `delete(key)`. Atomic where required.
  - **`RedisKeyValueStore`** — predis-backed implementation
  - **`InMemoryKeyValueStore`** — array-backed, kept for tests + local
    dev where Redis isn't available
  - **`OtpService` refactor** — currently tracks attempts via
    `OtpAttempt` rows in Postgres (which IS persistent and works) AND
    in-memory; refactor to use the interface
  - **Refresh-token denylist** — currently checks DB on every
    refresh; can be cache-first (Redis hit means revoked, miss means
    look up DB)
  - **DI config** — bind `KeyValueStore::class` to RedisKeyValueStore
    in production, InMemory in tests
  - **Server config** — Redis already not installed on the box; we
    install via aaPanel UI, set password, expose only on localhost
  - **`.env`** — add `REDIS_DSN=redis://:password@127.0.0.1:6379/0`

**Why both DB and Redis for OTP attempts?** OTP attempt history is
audit data — we want it persisted in Postgres for forensics. The
RATE LIMIT uses Redis because it's hot path (every send checks
"have they tried recently?"). Each layer optimizes for what it does.

**Why predis not phpredis?** phpredis is a C extension, faster, but
adds a deploy dependency (every server needs the extension installed
and the version bumped manually). predis is "composer install" only.
On our scale (~10qps peak realistic) the perf delta is invisible.

**Tests:** existing OTP tests use InMemory; new integration tests
verify Redis backend works. ~5 new tests.

**Estimated effort:** 4-6 hours including server install + DI wiring
+ verification.

### M1.6.1.B — Commit composer.lock

**Problem.** `composer.lock` is in `.gitignore`. Each CI run does
fresh dep resolution, picking up whatever versions match `composer.json`
constraints at that moment. A new patch release of any of our ~50
direct deps + transitive deps could break us silently. We've already
seen this happen (PHP-DI compilation issue mid-M1.5).

**Solution.** Remove from `.gitignore`, commit current `composer.lock`,
update CI to run `composer install --no-dev` (which reads the lock)
not `composer update`.

**Concrete changes:**

  - **`.gitignore`**: remove the `composer.lock` line
  - **`apps/api/composer.lock`**: commit the current lockfile
  - **CI workflow `.github/workflows/api.yml`**: confirm we use
    `composer install` not `composer update` (we already do)
  - **Deploy script `/usr/local/bin/3bayti-deploy.sh`**: same check

**Estimated effort:** 30 minutes including verification that nothing
breaks.

### M1.6.1.C — Audit log infrastructure

**Problem.** Currently every profile change, address change, and
measurement change happens with no record of who did what when.
If a user reports "someone changed my address", we have nothing.
For M2+ orders this becomes existential — order status changes
NEED to be auditable.

**Solution.** Generic audit log table + lightweight emitter. Doctrine
PreUpdate / PostPersist listeners auto-emit on tracked entities.

**Concrete changes:**

  - **New migration `Version20260510000001`**: creates `audit_log`
    table with columns:
    - `id BIGSERIAL`
    - `user_id BIGINT` (the actor — who made the change; nullable if
      system-driven)
    - `subject_type VARCHAR(50)` (entity class basename — User,
      Address, Measurement, Order, etc.)
    - `subject_id BIGINT` (the entity's primary key)
    - `action VARCHAR(20)` (created, updated, deleted, default)
    - `changes JSONB` (before→after diff for updated; full snapshot
      for created/deleted)
    - `ip_address INET` (request IP)
    - `user_agent TEXT`
    - `request_id VARCHAR(40)` (correlation id, M1.6.2 work)
    - `created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()`
    - Indexes on `(subject_type, subject_id)` + `(user_id, created_at)`

  - **`AuditLog` entity + repository** — lightweight, no setters
    after construction
  - **`AuditEmitter` service** — `record(actor, subject, action, changes)`,
    grabs IP/UA from request, writes
  - **Wire into controllers** — at the END of each mutating controller
    action, before the response. Not in the middleware to keep audit
    granular (e.g., we want different `action` for `default` vs
    generic `update`)
  - **Don't use Doctrine event listeners** — tempting, but they don't
    have request context (IP, UA, actor). Manual emit gives full
    control.

**Why JSONB for changes:** flexible schema. Different entities have
different fields; we don't want a column-per-field table. JSONB
also means we can easily query "what changes happened to user 42's
addresses last month" with a single SQL query.

**What gets audited in M1.6.1:**
- User profile updates (PATCH /me/profile)
- Address create / update / delete / set-default (POST/PUT/DELETE/PATCH /me/addresses)
- Measurements upsert / delete (PUT/DELETE /me/measurements)

**What's NOT audited yet:** auth events (login, logout, password
reset). Those are higher-impact and need their own design (where
to write — same table or separate `auth_events`? what's the
retention policy?). Deferred to M1.6 followup or its own micro-phase.

**Tests:** ~8-12 tests covering each mutating action emits audit log
with correct shape, plus the audit emitter unit tests.

**Estimated effort:** 6-8 hours. Migration + entity + emitter + 8
controllers + tests. Touches a lot but each touch is small.

### M1.6.1.D — Smoke test credit drain

**Problem.** Every auto-deploy runs the full smoke test which calls
`/v3/auth/register` with a real phone number. MessageCentral charges
a credit per SMS. ~$0.05/credit, 1 credit per deploy. Active dev
days hit $2-5 in waste.

**Solution.** Either skip the register step in CI, or short-circuit
MessageCentral when a magic test header is present.

**Two options:**

**Option A** — `--skip-register` flag for `smoke.sh`:
- Smoke test stops after liveness + readiness checks (steps 1-2)
- CI deploy passes the flag; manual smoke runs don't
- Trade-off: we lose the "register actually works in prod" signal
  on every deploy

**Option B** — Test-mode header that short-circuits MessageCentral:
- API recognizes `X-Smoke-Test: <hmac-signed-token>` header
- When present, OTP service uses a deterministic mock that returns
  success without calling MessageCentral
- Smoke can use any test phone (e.g. `+971500000000`)
- Trade-off: introduces a bypass mechanism in production code; the
  HMAC has to be cryptographically secure or it's an attack vector

**Recommendation:** Option A. Simpler, no production code changes,
loses a small signal that we don't really act on anyway (the deploy
was succeeding for weeks before we noticed the credit drain).

**Concrete changes (Option A):**

  - **`scripts/smoke.sh`** — add `--skip-register` flag, when set
    skip steps 3-4
  - **CI deploy workflow** — pass the flag when invoking smoke
  - **Manual smoke** — runs full flow as before

**Estimated effort:** 1 hour including testing.

### M1.6.1 total estimated effort

12-15 hours across A, B, C, D. Roughly two focused sessions or one
long day.

### M1.6.1 ship order

Recommend: B (composer.lock) → D (smoke fix) → A (Redis) → C (audit log).

  - B + D are quick wins that compound (every commit afterwards is
    safer)
  - A is the biggest single piece, do it when fresh
  - C has the most controller touches, save for last when patterns
    are established

## M1.6.2 — Observability (SHOULD ship before M2)

### M1.6.2.A — Sentry integration

**Problem.** When PHP throws in production, the stack trace lands
in Apache's error log. No alerts, no aggregation, no historic search.
We won't know about errors until users complain.

**Solution.** `sentry/sentry-symfony` or just `sentry/sdk` (we don't
use Symfony framework, just components). Capture exceptions, add
release tag, capture user context.

**Concrete changes:**

  - **Add `sentry/sdk` to composer.json**
  - **Initialize in Bootstrap** before app starts: read `SENTRY_DSN`
    from env, configure with current `APP_VERSION` as release
  - **HttpException filtering** — don't send 4xx errors to Sentry
    (those are client errors, expected). Send 5xx and unhandled
    exceptions only.
  - **User context** — when JWT successfully decoded in AuthMiddleware,
    set Sentry user context with the user id (NOT email/phone — PII)
  - **Performance monitoring (off for now)** — Sentry's APM is a
    separate concern. Might add in M5.
  - **`.env`** — add `SENTRY_DSN`

**What about logs that aren't exceptions?** Structured logging
(M1.6.2.B) handles those. Sentry is for the "this should never
happen" case; logs are for "I want to see what happened."

**Estimated effort:** 2-3 hours. Sentry setup is short; the
filtering nuances + getting the right release tag automation are
where time goes.

### M1.6.2.B — Structured JSON logging

**Problem.** Currently we use `error_log()` for the few diagnostic
messages we emit. Format: free-form text. Grepping is miserable; no
field-aware filtering.

**Solution.** Monolog with JSON formatter, write to a per-day file
under `apps/api/var/logs/`. Each log entry is one JSON object per line.

**Concrete changes:**

  - **Add `monolog/monolog` to composer.json**
  - **Create `Bayti\Api\Infrastructure\Logger`** wrapping a Monolog
    Logger with our standard fields (request_id, user_id, route)
  - **Request id middleware** — generate UUID per request, add to
    response header `X-Request-Id`, attach to log context
  - **Logger DI binding** — `Psr\Log\LoggerInterface` resolves to
    our wrapper
  - **Remove `error_log()` calls** — there aren't many; replace each
    with `$logger->info()`/`->error()`
  - **Logrotate config** — `/etc/logrotate.d/3bayti-api` for daily
    rotation, 14-day retention
  - **Apache config** — already logs access/error to standard places;
    no changes needed for app logs

**Log levels:**
- DEBUG: only in dev (APP_ENV=dev)
- INFO: state transitions (user registered, order placed)
- WARNING: recoverable but interesting (rate limit hit, password
  reset attempted on unknown email)
- ERROR: unexpected failures (DB query failed, MessageCentral 500)
- CRITICAL: worth waking someone up

Sentry only sees ERROR and above (configurable filter).

**Estimated effort:** 4-5 hours. Monolog setup is fast; the
request-id-correlation middleware + threading the logger through
DI is where the time goes.

### M1.6.2 total estimated effort

6-8 hours across A and B. One focused session.

## M1.6.3 — Deploy hardening (CAN ship anytime)

### M1.6.3.A — Auto-rollback on smoke failure

**Problem.** When CI's deploy step succeeds but smoke fails, the
bad version stays live. Currently the only recovery is SSH +
`git reset --hard <prev>` + re-run deploy script.

**Solution.** Wrap the deploy script in a transaction-like flow:
remember previous SHA, deploy new, run smoke, on smoke failure
rollback to previous SHA + run deploy script again.

**Concrete changes:**

  - **`/usr/local/bin/3bayti-deploy.sh`** — capture pre-deploy SHA
    BEFORE doing anything; if any step fails, `git reset --hard <prev>`
    and re-run dependency resolution + migration revert (if migration
    was applied)
  - **Migration revert is risky** — if the migration was destructive
    (DROP COLUMN), we can't unspill the data. So this only auto-
    rollbacks if no migration was applied during this deploy.
    Migrations on top of migrations don't auto-rollback; they
    require manual investigation.
  - **CI workflow** — separate "smoke test" step from "deploy" step.
    Currently the smoke test is part of the deploy job. Pull it
    out so we can call rollback API on smoke failure. Or simpler:
    do the rollback server-side in the deploy script itself, before
    the SSH session ends.

**Why server-side rollback** is cleaner than CI-orchestrated:
- Network is closer to the box (SSH already established)
- Atomic from CI's perspective (one SSH call, one outcome)
- Deploy log captures the rollback narrative
- CI just sees pass/fail

**Estimated effort:** 3-4 hours. Most of it is testing the rollback
path (and remembering not to test it on production!).

### M1.6.3.B — Concurrent deploy protection

**Problem.** Two pushes within 30s can race. Current behavior:
both deploys run, second wins. Mostly harmless but in edge cases
(migration mid-deploy from one, file-replace from another) we
could get half-applied state.

**Solution.** GitHub Actions workflow concurrency group.

**Concrete changes:**

```yaml
concurrency:
  group: deploy-prod
  cancel-in-progress: false  # don't kill in-flight; queue
```

That's it. 5 lines.

**Why `cancel-in-progress: false`** — killing an in-flight deploy
mid-migration is worse than queueing.

**Estimated effort:** 30 minutes.

### M1.6.3.C — workflow_dispatch trigger

**Problem.** Empty commits don't trigger the workflow (paths filter
excludes them). Manual redeploys require either creating a non-empty
commit or using GitHub UI.

**Solution.** Add `workflow_dispatch:` trigger.

**Concrete changes:**

```yaml
on:
  push:
    branches: [main]
    paths:
      - 'apps/api/**'
      - '.github/workflows/api.yml'
  workflow_dispatch:  # manual trigger
```

**Estimated effort:** 15 minutes.

### M1.6.3.D — Deploy notifications

**Problem.** Deploy failures only show as red X in GH Actions UI.
No Slack ping, no email. If the auto-deploy has been broken for
hours, we discover via "huh, my push didn't go live."

**Solution.** Slack webhook on failure (and optionally success).

**Concrete changes:**

  - **GH Actions** — add `slackapi/slack-github-action@v1` step on
    job failure, include workflow URL + commit + author
  - **Webhook URL** in repo secrets as `SLACK_WEBHOOK_URL`
  - **Slack channel** — `#3bayti-deploys` or similar; user creates

**Why not email:** Slack is more familiar for the user, easier to
filter, easier to integrate with on-call rotation later.

**Estimated effort:** 1-2 hours including Slack workspace setup if
not present.

### M1.6.3 total estimated effort

5-7 hours across A, B, C, D. Half a day.

## M1.6.4 — Server hygiene (CAN defer to M5)

These are real but low-priority. None block M2. Each is small.

### M1.6.4.A — Separate PHP-FPM pool for /v3

**Problem.** Currently /v3 shares the FPM pool with legacy
api.3bayti.ae. One side OOMs → both die.

**Solution.** Define a dedicated pool in
`/www/server/php/83/etc/php-fpm.d/v3-3bayti.conf`:
- `pm = dynamic`
- `pm.max_children = 20` (legacy uses 50; we're smaller)
- `pm.max_requests = 500` (forced recycle, prevents leak accumulation)
- separate socket `/tmp/php-cgi-83-v3.sock`
- separate access/error logs

Apache vhost for `api-v3.3bayti.ae` updates to use the new socket.

**Estimated effort:** 2-3 hours. Mostly testing — get the pool
configs right, verify no regression in either side, restart cleanly.

### M1.6.4.B — SSL cipher tightening

**Problem.** aaPanel auto-config includes RC4, 3DES, MEDIUM, LOW
ciphers. SSL Labs would grade B. No real attacks against modern
TLS 1.2+/1.3 but cleanup is good.

**Solution.** Edit Apache vhost SSLCipherSuite:

```apache
SSLProtocol -all +TLSv1.2 +TLSv1.3
SSLCipherSuite TLSv1.3 TLS_AES_256_GCM_SHA384:TLS_CHACHA20_POLY1305_SHA256:TLS_AES_128_GCM_SHA256
SSLCipherSuite TLSv1.2 ECDHE-ECDSA-AES256-GCM-SHA384:ECDHE-RSA-AES256-GCM-SHA384:ECDHE-ECDSA-CHACHA20-POLY1305:ECDHE-RSA-CHACHA20-POLY1305:ECDHE-ECDSA-AES128-GCM-SHA256:ECDHE-RSA-AES128-GCM-SHA256
SSLHonorCipherOrder on
```

**Estimated effort:** 30 min including SSL Labs verification.

### M1.6.4.C — Separate deploy user (non-root)

**Problem.** Auto-deploy SSH'es as root. If GH Actions secret leaks,
attacker has root via the deploy script.

**Mitigation already in place:** `command=` restriction in
authorized_keys means even with the key, attacker can only run the
deploy script. Limited blast radius.

**Solution.** Create `deploy` user with sudo NOPASSWD only for the
deploy script. SSH key authenticates `deploy@server`, restricted
command runs the deploy script (which sudoes the actual file
operations).

**Why this is real work:** the deploy script needs to:
- `chown` files (can't, no longer root)
- `chattr -i` on .user.ini (can't)
- Restart FPM if needed (can't without sudo)

So the deploy script becomes a wrapper that sudoes specific commands.
Each sudo'd command needs a NOPASSWD entry.

**Estimated effort:** 4-6 hours. Sudo policy is finicky to get
right.

**My recommendation:** defer. The blast radius is already limited
by `command=` restriction. Real risk is low for a hobby-scale app.

### M1.6.4.D — php-cli.ini phantom extension warnings

**Problem.** `php -m` and `composer install` both emit warnings
about extensions that are already loaded:
```
PHP Warning: Module 'curl' already loaded
```
Cosmetic. Confusing in deploy logs.

**Solution.** Edit `/www/server/php/83/etc/php-cli.ini` to comment
out the `extension=curl.so` etc. lines for extensions that PHP
loads as built-ins.

**Estimated effort:** 30 min.

### M1.6.4.E — FPM pool process recycling

**Problem.** Looking at the legacy FPM pool, there are worker
processes from January 31 still running. No `pm.max_requests` set.
Long-lived workers accumulate memory leaks.

**Solution.** Add `pm.max_requests = 500` to the legacy pool
config. Same to the new /v3 pool when we create it.

**Estimated effort:** 30 min.

### M1.6.4 total estimated effort

7-10 hours across A-E if all done. Most of M1.6.4 can defer to M5.

## M1.6 grand total

| Sub-phase | Effort | Blocking M2? |
|---|---|---|
| M1.6.1 — Correctness | 12-15h | YES |
| M1.6.2 — Observability | 6-8h | Should |
| M1.6.3 — Deploy hardening | 5-7h | No |
| M1.6.4 — Server hygiene | 7-10h | No (defer to M5 OK) |

**Range:** 30-40 hours total if everything ships. M1.6.1 alone is
2-3 focused work sessions. Realistic plan:

  - **Session 1:** M1.6.1.B (composer.lock) + M1.6.1.D (smoke fix)
    + M1.6.3.B (concurrency) + M1.6.3.C (workflow_dispatch). Fast
    wins, ~2 hours, builds momentum
  - **Session 2-3:** M1.6.1.A (Redis). Real work, gets done in a
    block
  - **Session 4-5:** M1.6.1.C (audit log). Many small touches
  - **Session 6-7:** M1.6.2 (Sentry + logging)
  - **Sometime later:** M1.6.3.A (auto-rollback) + M1.6.3.D
    (notifications)
  - **Defer to M5 (or never):** M1.6.4 unless something forces it

After M1.6.1 + M1.6.2 ship, we're in good shape to start M2 catalog.

## Open questions for next session

1. **Redis on the box** — install via aaPanel's "App Store" plugin
   (auto-managed, no systemd) or install manually with apt + systemd?
   Probably aaPanel for consistency with how Postgres was installed.

2. **Sentry self-hosted vs SaaS** — SaaS has a free tier (5K events/
   month), more than we need for this stage. Self-hosted is one more
   thing to maintain. Recommend SaaS to start.

3. **Audit log retention** — forever? 90 days? GDPR considerations
   if we ship to EU customers. Probably 1 year retention with monthly
   archival to cold storage. Decide before M3 (orders) since order
   audit retention has stronger requirements.

4. **Slack workspace** — does one exist, or is `#3bayti-deploys` to
   be created? Either way affects M1.6.3.D effort.

5. **composer.lock's PHP-DI bug** — we hit a PHP-DI compilation issue
   in M1.5 that came from a transitive dep update. Committing the
   lock prevents future versions of this happening, but doesn't
   un-paint us into the corner if a security update is needed and
   the new version reintroduces the bug. Need a process for "bumping
   lock with confidence" — periodic `composer update` runs in a
   branch, full test pass, merge.

## Notes

- The plan deliberately scopes M1.6 to "what should ship before M2."
  Items that can defer to M5 (load balancer, autoscaling, CDN, real
  CDN integration for images, multi-region) are explicitly NOT in M1.6.

- Order matters within M1.6.1: composer.lock + smoke fix first
  (5min each), THEN Redis (deep work). Audit log last because it
  touches many controllers and is easier with the patterns from
  Redis settled.

- M1.6.2 (observability) can run partly in parallel with M1.6.1 —
  Sentry doesn't depend on Redis, structured logging doesn't depend
  on audit log. But practically, doing them in series makes for
  cleaner commits and easier rollback.
