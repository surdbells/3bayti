## 0. Why this is M3.2.X.6 (and why we skipped X.5)

Per master plan §2 Stream X, M3.2.X.5 captures real Noon dispute eventType strings. That requires an operator to trigger a sandbox dispute — a manual step Claude cannot perform. Option A (user-selected) skips it for now and moves to X.6, which has no external dependency.

M3.2.X.6 closes a structural gap in the vendor data model. Today `Vendor` has four overlapping boolean status fields:

| Field | Meaning | Set by |
|---|---|---|
| `is_active` | Soft-delete flag (`false` = hidden from storefronts) | Admin (DeleteVendor toggles this) |
| `is_verified` | Admin-attested verification (cosmetic badge) | Admin |
| `is_store_approved` | Initial onboarding approval | Admin (M3.1.7-era) |
| `is_featured` | Designer Spotlight curation (M3.2.X.2) | Admin |

There's no path for:
- **Self-serve onboarding** — vendors today are admin-created via `POST /v3/admin/vendors`. No way for a user to submit themselves for approval.
- **Temporary suspension** — admin can flip `is_active=false` to hide the vendor, but that's the same code path as soft-delete. No distinction between "policy violation hold" and "withdrawn from platform".
- **Status as audit subject** — current admin endpoints only log `UPDATED` with the diff; there's no first-class "vendor was suspended" event.

The new lifecycle resolves these without breaking the existing boolean semantics.

## 1. Pre-flight findings

### 1.1 Master plan inaccuracy — corrected

Master plan §2 row 6 reads:

> "Add `vendor_status` enum to **User entity**; migration with default 'approved' for existing vendors; gate vendor endpoints by status..."

Pre-flight verified this is wrong. The architecture is:

- `User` has `is_vendor` boolean — a role flag
- `Vendor` has `owner_user_id` FK → many Vendor records per User possible (multi-store vendors)
- The store-level data (name, contact_email, products, orders) lives on `Vendor`, not `User`

The status logically belongs to the **store** (Vendor entity), not the **user role**. A user who owns two stores might have one approved and one pending — that's only expressible on the Vendor side.

**Q-Home = A: Status lives on Vendor entity.** Master plan text gets corrected in M3.2.X.6-E closure.

### 1.2 VendorAuthMiddleware gate point

`apps/api/src/Http/Middleware/VendorAuthMiddleware.php` lines 56-58 today:

```php
if (!$user->isVendor()) {
    // ... 403 forbidden
}
```

Only checks the `is_vendor` role flag. Doesn't resolve the user's Vendor records. The middleware's own docblock (lines 56-64) explicitly notes:

> "Vendor lifecycle gate (deferred). A full vendor lifecycle (pending → approved → suspended) would gate access here based on a `vendor_status` column. That column doesn't exist on User yet... For M3.1.7 the boolean flag is enough — operators manually gate via flipping is_vendor."

M3.2.X.6 closes this deferred work. The middleware will:

1. Verify `is_vendor=true` (existing)
2. Resolve the user's Vendor records via `VendorRepository::findIdsByOwnerUser($user)`
3. Reject if the user has ZERO `approved` vendors

Multi-vendor case: if a user owns one suspended + one approved vendor, the middleware lets them through (they're a legitimate vendor for at least one store). The per-controller logic then naturally filters to approved-only stores via the repository's state-aware methods.

### 1.3 VendorAuthMiddleware logger handle

Verified: `VendorAuthMiddleware` already has `LoggerInterface $logger` in its constructor. New 403 paths (suspended-only, no approved stores) can log structured warnings without DI changes.

### 1.4 Existing user → vendor entity resolution pattern

`VendorRepository::findIdsByOwnerUser(User $user): array<int>` already exists. M3.2.X.6 will add:

- `findByOwnerUserAndStatus(User $user, string $status): array<Vendor>` — full entities filtered by status (used by the middleware's gate check)
- `findByOwnerUser(User $user): array<Vendor>` — all entities regardless of status (used by self-serve onboarding to check if user already has stores)

### 1.5 Q-LegacyFlags=A semantics — overlap resolution

The four existing booleans don't go away. The lifecycle becomes the **new source of truth for public visibility**, but the booleans stay for backwards compat with admin tooling and other systems:

| Status | Public visibility (replaces existing combined rule) | Admin booleans still mean... |
|---|---|---|
| `pending` | Hidden from public surfaces (storefront, listings, search) | `is_store_approved=false` (the approval flag is the canonical pending signal) |
| `approved` | Visible per `is_active = true AND is_featured`-driven rules | `is_store_approved=true`; `is_active` still drives soft-delete |
| `suspended` | Hidden from public surfaces; ORDERS frozen (vendor can't transition items) | `is_store_approved` could be either (a previously-approved vendor can still be suspended) |

**The migration backfill (sub-phase A):**
- Existing rows with `is_store_approved=true AND is_active=true` → `status='approved'`
- Existing rows with `is_store_approved=true AND is_active=false` → `status='suspended'` (soft-deleted post-approval is functionally a suspension)
- All other rows → `status='pending'`

After backfill, the rules are kept in sync via setters that respect both flags. New admin transitions emit dual writes (e.g. approve sets `status='approved'` AND `is_store_approved=true`).

## 2. Schema design

```sql
ALTER TABLE vendors ADD COLUMN status VARCHAR(16) NOT NULL DEFAULT 'pending';
ALTER TABLE vendors ADD COLUMN status_changed_at TIMESTAMPTZ NULL;
ALTER TABLE vendors ADD COLUMN status_reason TEXT NULL;

-- Backfill existing rows (idempotent; runs once at migration time)
UPDATE vendors SET status = 'approved'
  WHERE is_store_approved = TRUE AND is_active = TRUE;
UPDATE vendors SET status = 'suspended'
  WHERE is_store_approved = TRUE AND is_active = FALSE;
-- All remaining rows keep the default 'pending'

UPDATE vendors SET status_changed_at = NOW() WHERE status != 'pending';

-- Index for the middleware's hot query: gate by owner + approved status
CREATE INDEX idx_vendors_status_owner ON vendors (status, owner_user_id);

-- Constraint to prevent future drift
ALTER TABLE vendors ADD CONSTRAINT chk_vendors_status
    CHECK (status IN ('pending', 'approved', 'suspended'));
```

**Why `VARCHAR(16)` not PostgreSQL ENUM:** Adding states later (e.g. `rejected`) doesn't require `ALTER TYPE`. Same rationale as `notification_logs.status` in M3.2.X.4.

**Why `status_reason TEXT`:** When admin suspends a vendor, they may want to attach a human-readable reason ("repeated quality issues"). Stored as free text rather than enum because reasons are operational, not categorical.

**Why `status_changed_at`:** Forensic data — "when was this vendor approved?" / "how long has this vendor been suspended?" without grepping audit logs.

**Why the composite index `(status, owner_user_id)`:** The middleware's hot query is "find approved vendors for this user". Covers it efficiently.

## 3. Decisions to lock IN this approval

### Q-Home: Where does the status live?

- **A: Vendor entity** (recommended; matches actual ownership model — a user can own multiple stores)
- B: User entity (master plan said this; pre-flight overrides — doesn't work for multi-store users)
- C: Separate `vendor_lifecycle` table (overkill — 3 enum values + 1 nullable text + 1 timestamp don't justify normalization)

### Q-StateModel: Which status values?

- **A: `pending` / `approved` / `suspended` (3 states)** (recommended; covers all current operational needs)
- B: Add `rejected` (admin explicitly rejects an onboarding application; not appeals-friendly — `rejected` is a terminal state requiring a separate appeals workflow we don't have)
- C: Add `under_review` (between pending and approved; only useful if admins need to track "I started looking at this" — current ops doesn't track that)

### Q-LegacyFlags: What happens to existing boolean fields?

- **A: Keep `is_store_approved` + `is_active` for backwards compat; lifecycle is the new source of truth for public visibility** (recommended)
- B: Drop the booleans (breaking change for admin tooling, legacy reporting; high risk for no immediate benefit)
- C: Mark deprecated with @deprecated docblock; remove in a later phase (additional ceremony for no gain — they're not actually deprecated, just demoted)

### Q-Backfill: Migration semantics for existing vendors

- **A: `is_store_approved=true AND is_active=true` → `approved`; `is_store_approved=true AND is_active=false` → `suspended`; rest → `pending`** (recommended; preserves the existing operational semantics)
- B: All existing → `approved` (oversimplification; soft-deleted vendors would re-appear publicly)
- C: All existing → `pending` and require re-onboarding (operationally disruptive; existing vendors with live products would vanish from storefronts)

### Q-MiddlewareGate: Where does the status check live?

- **A: VendorAuthMiddleware resolves Vendor + gates on at least one `approved` store** (recommended; single chokepoint, follows existing `VendorAuthMiddleware` doc comment's "deferred enhancement" plan)
- B: Per-controller status checks (more flexible but duplicates logic across 4+ controllers; risk of inconsistency)
- C: Hybrid — middleware allows through if user has `is_vendor=true`, controllers filter by status (current behavior with the per-controller fix; weakest isolation)

### Q-Audit: What gets audited?

- **A: State transitions only — via existing `ACTION_UPDATED` with the status diff in changes** (recommended; matches `M3.2.X.2-D`'s `is_featured` audit pattern; no new constants needed)
- B: All admin reads of vendor data (would explode the audit table for routine listing operations)
- C: Custom `ACTION_VENDOR_*` constants (`ACTION_VENDOR_APPROVED`, `ACTION_VENDOR_SUSPENDED`) — more semantic but breaks the existing audit-event taxonomy convention
