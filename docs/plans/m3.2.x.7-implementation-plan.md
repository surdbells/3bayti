## 0. Background

UAE marketplace. Market data: ~60% of customers prefer Arabic; ~40% prefer English. The current notification system supports only English emails. M3.1.7-H shipped the email infrastructure (ZeptoMail, templates, fan-out, error handling) and M3.2.X.4 added observability (notification_logs). M3.2.X.7 closes the language gap.

## 1. Pre-flight findings

### 1.1 No locale field exists

Verified absence of `locale` / `language` / `preferredLanguage` columns on:
- `User` entity (apps/api/src/Domain/User/User.php)
- `Order` entity (apps/api/src/Domain/Order/Order.php)
- `Vendor` entity (apps/api/src/Domain/Catalog/Vendor.php)

The only locale-adjacent code: `apps/web/src/app/core/seo/seo.service.ts` defaults the OpenGraph `og:locale` to `en_AE`. That's frontend SEO metadata, not a customer preference.

### 1.2 No locale-resolution logic in the backend

`OrderNotificationService::safeSend` accepts a recipient email string. It has no concept of which language to render in. Adding locale routing requires:
1. A field on User to hold the preference
2. A resolver helper to map a recipient (string email) back to a User and read the preference
3. Routing inside the renderer to pick the right localized template

### 1.3 `wrapHtml()` lacks `lang=` and `dir=` attributes

Current markup:
```html
<!DOCTYPE html>
<html>
<head>...</head>
<body style="...">
```

Missing `<html lang="en" dir="ltr">` / `<html lang="ar" dir="rtl">`. Without these, email clients (Apple Mail, Outlook, Gmail) won't render Arabic text properly in RTL. Adding them is a one-line change but critical.

### 1.4 No customer-facing UI for setting language preference

Out of scope for M3.2.X.7 (consumer-side work). The locale field will be set via:
- An admin endpoint (PATCH /v3/admin/users/{id} with new `preferred_locale` field — minimal addition)
- An authenticated user endpoint (PATCH /v3/me/profile with new `preferred_locale` field — minimal addition)
- Fallback: infer from User.country='AE' → suggest Arabic, but defer to explicit preference if set

The full customer-facing UI to change language sits in a future apps/web or apps/mobile phase.

### 1.5 Quality gate baselines (entry)

- Backend phpunit: **660 / 2291**
- phpstan: **60 baseline**
- All TSC baselines preserved

## 2. Locale routing design

```
┌─────────────────────────────────────────────────────────────┐
│  OrderNotificationService::safeSend(to, template, order)    │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│  resolveLocaleForRecipient(string $email): string           │
│  Returns 'en' or 'ar' based on:                             │
│    1. If recipient matches Order.user.email                 │
│       → use User.preferredLocale (or default)               │
│    2. If recipient matches Vendor.contact_email (any        │
│       vendor in the order's items)                          │
│       → use Vendor.preferredLocale (or default)             │
│    3. If recipient matches admin recipient list             │
│       → always 'en' (Q-VendorAdminLocale = A locked)        │
│    4. Default → 'en' (Q-FallbackBehavior = A locked)        │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│  OrderEmailTemplateRenderer::render(template, order, extra, │
│                                     locale)                 │
│  Returns RenderedEmail with locale-specific:                │
│    - subject                                                 │
│    - textBody                                                │
│    - htmlBody (with correct lang= + dir= attributes)        │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
                        Mailer ships
```

## 3. Decisions to lock IN this approval

### Q-Scope: What's in this phase?

- **A: Templates + minimal locale routing (User.preferredLocale field + resolver + admin/profile endpoint touches)** (recommended)
- B: Only templates; hardcode all sends to English; route via locale later (low value — Arabic-speaking users never see Arabic emails)
- C: Full i18n including frontend UI for setting preference (~10 days; overshoots the 3-5 day target)

### Q-LocaleField: Where does the locale live?

- **A: `User.preferredLocale` field (nullable VARCHAR(8))** (recommended; matches the "user has a preference" model)
- B: Separate `user_preferences` table (overkill — single field doesn't justify normalization; future locale-related preferences can be added later)
- C: Snapshot `Order.locale` at placement time (snapshot-style; loses ability to change user's preference and apply going forward)

Selected: **A**. `Vendor.preferredLocale` also added (per Q-VendorAdminLocale=A) for vendor email routing.

### Q-LocaleValues: Which values are valid?

- **A: `en` / `ar` (BCP-47 short tags)** (recommended; simplest)
- B: `en-AE` / `ar-AE` (with region) — adds noise; we have no per-region content to localize
- C: Full BCP-47 with country variants — overshoot

### Q-FallbackBehavior: What if user has no locale?

- **A: Default to English (current behavior)** (recommended; preserves existing behavior for users who never set a preference)
- B: Infer from User.country='AE' → `ar` (problematic — many UAE residents are non-Arabic-speaking expats; would default many users to Arabic incorrectly)
- C: Send both languages in one email (UX nightmare — overlong, harder to scan)

### Q-VendorAdminLocale: Vendor + admin email locale

- **A: Vendor uses its own `preferredLocale` field; admin emails always English** (recommended; admins use English internally per company convention; vendors may be Arabic-first businesses)
- B: All admin/vendor emails always English regardless (simpler but misses Arabic-first vendor businesses)

### Q-TemplateFormat: How are translations stored?

- **A: Inline in PHP renderer methods (one method per locale per template)** (recommended; matches the existing pattern; PHP heredoc handles Arabic UTF-8 cleanly; type-checker catches missing keys)
- B: JSON catalog files (heavier indirection; harder to keep type-safe; needs a loader)
- C: PHP arrays in a Translations.php class (still indirection; lose the IDE/static-analysis benefits of explicit methods)

## 6. Risks

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| Arabic translations have grammatical errors or awkward register | Medium | Medium | Closure runbook calls out the recommended native-speaker review pass before production. Translations are Modern Standard Arabic, formal register, neutral tone — least likely to land badly. Sub-phase E provides reviewable artifacts (subject lines + sample text bodies). |
| RTL HTML breaks in older email clients (Outlook 2007-2010) | Medium | Low | Use simple table-based HTML with inline styles + explicit `dir="rtl"` on the wrapping `<html>`. Modern Outlook (2016+) and all webmail clients handle this correctly. Older Outlook degrades gracefully to LTR rendering of RTL text (readable, just not visually correct). |
| Locale routing miscategorizes a recipient | Medium | Medium | LocaleResolver decision tree is explicitly tested (sub-phase A test). The fallback is always English (current behavior preserved). Sub-phase D tests the integration end-to-end. |
| Existing email tests break due to renderer signature change | High | Low | The new `$locale` parameter defaults to `'en'`, so tests that don't pass it preserve current behavior. Verified pattern from M3.2.X.4-B (lazy EM resolution) avoids upstream breakage. |
| Arabic numeral / date formatting confusion (Eastern Arabic vs Western Arabic numerals) | Medium | Low | Lock decision in -C: use Western Arabic numerals (the regular `1, 2, 3`) throughout. UAE business convention favors these for clarity in commercial documents; reserves Eastern Arabic numerals (`١, ٢, ٣`) for religious/cultural contexts. |
| Encoding issues with Arabic UTF-8 in PHP heredoc | Low | Low | PHP 8.3 handles UTF-8 cleanly in heredocs. ZeptoMail accepts UTF-8 email bodies. Test verifies the full byte sequence survives the pipeline by asserting specific Arabic substrings. |
| Customer changes preference mid-order lifecycle | Low | Low | User.preferredLocale is read at SEND time, not snapshotted at order creation. If a customer changes from en→ar between "order placed" and "order shipped" emails, they'll get the first in English and the second in Arabic. Acceptable behavior; no need to lock locale per-order in this phase. |
| Translation rolls out before native-speaker review | Medium | Medium | M3.2.X.7-E closure runbook explicitly documents the review recommendation as an operator follow-up. The translations CAN deploy without review and produce reasonable output; review is a polish step, not a correctness gate. Operator decision. |
| Vendor.preferredLocale not set for most vendors | High | Low | Default fallback is English; same as customer fallback. Vendors who want Arabic email confirmations need to opt in via PUT /v3/admin/vendors/{id}. Not a regression — current state is "everyone gets English". |
| Estimated effort balloons beyond 5 days | Low | Medium | Each sub-phase is independently testable; per-sub-phase approval gates catch scope drift. Pre-flight inspection confirmed all assets exist. |

## 7. What is NOT in M3.2.X.7

- Customer-facing UI in apps/web or apps/mobile to change `preferred_locale` (consumer-side; out of scope; should be added in a future phase)
- SMS or OTP localization (out of scope; only emails in this phase)
- Admin tool UI to view/manage vendor or user locale (consumer-side)
- Mobile app changes (no mobile email rendering)
- Translation review by a native Arabic speaker (recommended in closure runbook as operator follow-up; not a hard blocker for code completion)
- Additional locales beyond `en` / `ar` (e.g. `fr`, `hi`, `ur`) — out of scope; the architecture supports adding more later by extending SUPPORTED_LOCALES + adding renderer methods
- Eastern Arabic numerals (`١, ٢, ٣`) — using Western Arabic numerals throughout per UAE business convention
- Currency conversion / locale-specific number formatting (`AED 1,000.00` vs `1.000,00 د.إ`) — keeping single format `1,000.00 AED` / `1,000.00 د.إ` for simplicity
- Bidirectional text mixing (Arabic with embedded Latin) edge cases — the wrapping `<html dir="rtl">` handles most cases; complex mixing left for later phases if needed
- Localizing the admin email (dispute.opened.admin) — locked to English per Q-VendorAdminLocale=A
- Backfilling preferred_locale for existing users (Q-FallbackBehavior=A: NULL = English; no backfill needed)
- Email subject prefix tagging (e.g. `[AR]`/`[EN]`) — would clutter; recipient knows their own language preference
