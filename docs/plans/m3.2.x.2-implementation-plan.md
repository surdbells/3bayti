## 0. Why this is M3.2.X.2

Per master plan §2 Stream X row 2:

> `/v3/featured-vendors` endpoint + apps/web flip — 1-2 days — Curated vendor list with embedded top-N products; admin-managed list; apps/web Designer Spotlight strip currently returns 500.

Two motivations:

1. **Apps/web Designer Spotlight is broken in production.** `apps/web/src/app/features/home/home-data.service.ts` calls `GET /featured-vendors` which is currently routed to legacy `/v2/featured-vendors`. That legacy endpoint is failing in production (returns 500). Until M3.2.X.2 ships, the home page Designer Spotlight section degrades silently to empty (per the `catchError` in `home-data.service.ts::cached()`), but the user-visible result is a missing strip.

2. **Stream X dependency.** Several later Stream X phases need vendor curation infrastructure: M3.2.X.6 (vendor lifecycle states) extends the same admin endpoints; M3.2.X.13 (vendor analytics) and M3.2.X.14 (vendor performance metrics) display data filtered by featured status. Getting the curation column in place now unblocks several downstream phases.

The phase is "1-2 days" in the master plan, but pre-flight inspection revealed a wider scope than expected (no `is_featured` column exists on the Vendor entity; needs migration, DTO, controller, serializer extensions, admin UI consideration). My revised estimate is **2-3 days**.


**Apps/web action:** Just flip `target: 'old'` → `target: 'new'` after backend ships. One-line change.

### 1.2 Expected response shape (apps/web contract)

From `apps/web/src/app/features/catalog/designer-card.ts::FeaturedVendor`:

```typescript
interface FeaturedVendor {
  slug: string;
  name: string;
  description: string | null;
  rating: number | null;
  rating_count: number;
  products: FeaturedVendorProduct[];  // up to 4 thumbnails
}

interface FeaturedVendorProduct {
  id: number | string;
  slug: string;
  image_url: string;
  name: string;
}
```

Envelope: `{ data: FeaturedVendor[], meta: {total, limit, offset, has_more} }` per the standard `PaginatedEnvelope::build` used by `ListVendorsController`.

### 1.3 Backend side — what's missing

**No `is_featured` column on `vendors` table.** Pre-flight inspection of `apps/api/src/Domain/Catalog/Vendor.php` shows:
- `is_active` (boolean) ✓
- `is_verified` (boolean) ✓
- `is_store_approved` (boolean) ✓
- `is_featured` — **MISSING**

This is the central piece of work. Without a featured flag, there's no curation criterion. The phase must:

1. Add `is_featured` column to `Vendor` entity + migration
2. Default to `false` for all existing vendors
3. Add admin endpoint capability to toggle (extend `UpdateVendorInput` DTO)
4. Create `ListFeaturedVendorsController` returning featured vendors with embedded top-N products
5. Register route `GET /v3/featured-vendors`
6. Extend `VendorSerializer` to include rating + rating_count (currently only `publicShape` is used; no rating fields)
7. Embed top-N products via `VendorProductSerializer` or inline shape

### 1.4 Existing assets that help

- `Vendor` entity exists with rich field set
- `VendorRepository::findActive()` exists (returns active vendors)
- `VendorSerializer::publicShape` exists (foundation to extend)
- `ProductRepository::findActivePaginated([vendorId])` exists (for embedded products)
- `PaginatedEnvelope::build` standardized
- `UpdateVendorController` + `Dto/UpdateVendorInput` exist (extend for `is_featured`)
- Apps/web `FeaturedVendor` type already defined; matching it is the contract

### 1.5 Rating data — gap surfaced

`FeaturedVendor.rating` + `rating_count` are required by apps/web. But:

- `Vendor` entity has no rating fields
- There IS a `Review` entity (per master plan + existing code)
- Computing rating on the fly per request is expensive at scale

**Three options for rating data** (locks as decision Q-Rating; see §3):

- **A:** Real-time aggregate via SQL `AVG()` in the controller's query (simple; ~OK for 4 featured vendors at a time)
- **B:** Denormalized columns on `Vendor` (rating_avg, rating_count) + recompute on review create/edit/delete
- **C:** Skip rating for v3 endpoint launch; return `null` + `0`. Add rating in a follow-up phase

**My recommendation: A.** Featured Spotlight is at most 4 vendors per request; SQL aggregate is cheap. Defer denormalization to M3.2.X.13 (vendor analytics) which does broader vendor metrics work.

### 1.6 Embedded products — gap surfaced

`FeaturedVendor.products` contains up to 4 product thumbnails (id, slug, image_url, name).

For each featured vendor, query top 4 active products. Could be:

- **A:** Newest 4 active products (`createdAt DESC`)
- **B:** Featured products of that vendor (uses Product.isFeatured if exists)
- **C:** Top-selling 4 products of that vendor (uses `order_items` aggregation — same primitive as M3.2.X.1)

**My recommendation: A.** Newest is the simplest, deterministic, and adequate for Spotlight UX. Top-selling per vendor adds N+1 query cost and depends on M3.2.X.1's window choice which would couple two phases. Defer the "smartest products" choice to M3.2.X.13.

## 3. Decisions to lock IN this approval

### Decision M3.2.X.2-Q-Rating: how to source vendor rating data

The apps/web `FeaturedVendor` contract requires `rating: number | null` and `rating_count: number`. Vendor entity has no rating fields today.

- **A:** Real-time SQL aggregate per request (`AVG(rating)` over Review rows). Adds 1 query per featured vendor (N+1) but Spotlight is at most 4 vendors. Cost: cheap.
- **B:** Denormalize `rating_avg` + `rating_count` columns on Vendor. Recompute on Review create/edit/delete via domain events. Cost: more migrations, more entity surface, more invariant maintenance.
- **C:** Return `null` + `0` for v3 launch. Defer rating to a follow-up phase. Cost: apps/web Spotlight won't show ratings (component handles this gracefully — rating chip hidden when `rating_count === 0`).

**My recommendation: A.** Spotlight is 4 vendors max; the SQL aggregate cost is negligible. Denormalization is premature optimization here. Skipping rating loses signal on the most curated surface — wrong trade-off.

### Decision M3.2.X.2-Q-EmbeddedProducts: which N products per vendor

`FeaturedVendor.products` has up to 4 product thumbnails.

- **A:** Newest 4 active products (`createdAt DESC`). Deterministic, simple, fast.
- **B:** Top-selling 4 products via `order_items` aggregation (same primitive as M3.2.X.1's `best_seller` sort, but scoped per vendor + with the same 30-day window per Q-Window=B).
- **C:** Vendor-curated. Admin picks which 4 products show up. Requires UI work in admin app + a vendor_featured_products join table.

**My recommendation: A.** Simplest, fastest, gives reasonable UX. Defer "smartest selection" to a vendor analytics phase if data shows the simple choice underperforms.

### Decision M3.2.X.2-Q-Sort: featured vendor result order

When multiple vendors are featured, what's the order?

- **A:** Alphabetical by name (deterministic; reflects no preference; stable).
- **B:** `featured_at` timestamp DESC (newest-featured first; requires a `featured_at` column or `is_featured` to record when set).
- **C:** Admin-controlled `featured_order` integer column (admin picks order; most flexibility, most schema cost).

**My recommendation: A.** Alphabetical is the simplest sensible default for the launch. If business needs ordering, B can be added later via a `featured_at` column (cheap migration; no data migration needed since false → no-op).

### Decision M3.2.X.2-Q-LimitClamp: max `?limit=` value

Apps/web requests `limit=4`. Direct API consumers might request more.

- **A:** Clamp at 12 (matches the `STRIP_LIMIT` constant in `home-data.service.ts`).
- **B:** Clamp at 50 (consistent with other catalog endpoints).
- **C:** No clamp (rely on the natural limit of `is_featured = true` vendor count).

**My recommendation: A.** Spotlight is curated; nobody needs 50 featured vendors. Lower clamp keeps response size predictable.

### Decision M3.2.X.2-Q-Shadow: shadow window for the flip

- **A:** No shadow window. Apps/web is the only consumer; the legacy endpoint is currently broken (500). Flipping to v3 can't make things worse. Single-commit flip in `-E`.
- **B:** Operator-driven 3-day shadow window with structured logging in `RoutedHttpClient`. Adds elapsed time but verifies shape parity before flipping.
- **C:** Apps/web stays on legacy until production traffic verifies v3 endpoint via direct curl + integration tests; flip happens in a separate commit `-F` after operator sign-off.

**My recommendation: A.** Legacy is broken anyway; v3 going wrong would be at most identically broken. Single-commit flip with the option to revert via one-line change if anything regresses.

## 5. Risks

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| Rating SQL is slow at scale | Low (Spotlight = 4 vendors) | Medium | Aggregate at request time; M3.2.X.13 will denormalize if metrics demand |
| Apps/web tsc breaks on response shape mismatch | Low | High | Sub-phase B serializer test verifies exact keys against apps/web `FeaturedVendor` interface |
| Empty featured set is mishandled | Medium | Low | Sub-phase C explicit test: 0 featured vendors returns valid empty envelope |
| Migration fails to roll back | Low | Medium | Migration has explicit `down()` dropping the column |
| Admin endpoint accidentally exposes commission_rate to public | Low | High | `featuredShape` is a distinct method from `adminShape`; explicit field list prevents leak |
| Embedded product query is N+1 | Medium | Low | Each featured vendor gets 1 query for their products; total ≤ 5 queries (1 + N=4) per request — acceptable. If profiling shows hot, batch via single query in a follow-up |
| `is_featured = false` migration breaks existing tests | Low | Low | Default value is `false`; existing `findActive()` queries unchanged |
| Vendor with `is_featured = true` but `is_active = false` shouldn't appear | Medium | Medium | `findFeatured()` MUST filter `is_active = true AND is_featured = true` (explicit in repository test) |
| Apps/web Designer Spotlight Playwright spec doesn't exist yet | High | Low | Verify in `apps/web/e2e/` what coverage exists; if none, sub-phase E doesn't add new coverage (defer per Q-Verify=A pattern from M3.2.X.1.5) |

- Denormalized rating columns on Vendor (Q-Rating=A picked real-time SQL; B is M3.2.X.13)

- Vendor-curated featured products (Q-EmbeddedProducts=A picked newest 4; C is M3.2.X.13+)
- Admin-controlled featured order (Q-Sort=A picked alphabetical; B/C are follow-up phases)
- `featured_at` timestamp tracking (deferred until Q-Sort decision changes)
- Apps/mobile flip — mobile uses `customer/featured` (not `featured-vendors`); different endpoint; out of scope here
- Apps/portal changes (vendor portal is M3.3)
- Backend pagination for featured vendors (Spotlight is curated; pagination is overkill)
- Anything M3.2.X.1-C-FLIP-related (separate operator-driven workflow)
