## 🎯 Quick-decision summary (TL;DR)

> **What:** Replace the current "caller passes a raw `discount` amount to `POST /v3/checkout/initiate`" model with a server-authoritative promo code engine. Backend defines promo codes, validates them, computes the discount amount, persists the redemption against the order, and exposes a `POST /v3/cart/quote` endpoint that returns a price breakdown without committing to checkout yet.
>
> **Why:** Per master plan §3, "Promo codes" is the first Tier 2 feature; pairs with M3.2.Y.2-E (web checkout summary) and a future M3.2.Z mobile counterpart. The current architecture is a security gap — `InitiateCheckoutInput.discount` is a client-supplied decimal string that the server trusts (see `InitiateCheckoutController` line 90: "Discount/coupon resolution: caller passes amount (same — quote endpoint comes in M3.2.x)"). M3.2.X.8 is that quote endpoint.
>
> **Pre-flight discovery (refines scope significantly):**
>
> - `Order` entity ALREADY has a `discount` DECIMAL(10,2) column + `setDiscount()` setter + `recomputeTotals()` that floors `total` at zero. No new money-column work is needed on the order; X.8 layers persistence of the *attribution* (which promo was applied, computed amount) on top.
> - `POST /v3/checkout/initiate` already accepts `discount` from the client (insecure; deliberate per the M3.1.6 note). X.8 introduces server-authoritative resolution — the client passes a `promo_code` string and the server computes the amount.
> - `Cart` entity has no promo binding. Decision Q-PromoBinding below: bind promo to cart (persistent across page reload) vs. quote-only (recompute every quote call). **Recommended A:** quote-only stateless; the cart stays clean, mobile/web can store the active code in client-side state. (The redemption is locked at checkout-initiate time, which is the only moment that actually matters for fraud.)
> - No `promo_codes` / `promo_redemptions` table exists anywhere in `apps/api/migrations`. Greenfield schema.
> - Q7=B (no anonymous-session model) and the existing `AuthMiddleware` on `/v3/cart/*` and `/v3/checkout/*` mean **every redemption is tied to an authenticated `users.id`** — per-user redemption caps are trivial.
> - `Order::computeTotal` already floors at zero (`bccomp($net, '0.00', 2) < 0 ? '0.00' : $net`). The engine does NOT need to re-floor; passing `discount > subtotal+delivery_fee` is safe.
> - No backend feature-flag plumbing — adapter-layer flips happen on apps/web and apps/mobile (per X.1.5 / X.2 / X.3 pattern). The new endpoints just ship; consumers opt in.
>
> **8 decisions to lock:**

## 0. Background

The 3bayti checkout has accepted a client-supplied `discount` decimal since M3.1.6f1 (see `InitiateCheckoutInput::$discount`). The DTO comment line 90 of `InitiateCheckoutController` explicitly flags this as temporary, with the resolver deferred to "M3.2.x" — this is that phase. Without server-side resolution, a malicious client could pass any discount amount and the server would honor it (the only floor is `total >= 0`, which means a `discount = 99999.00` on a 50 AED order is "valid" — the user pays 0 AED).

Tier 2 master plan §3 lists promo codes as the *first* deferred Tier 2 feature to land. Sequence:

1. **M3.2.X.8** — this plan: the engine + admin + customer-quote endpoint (~5-7 days)
2. **M3.2.Y.2-E** — web checkout summary surfaces the promo code field (already in Stream Y plan)
3. **Future M3.2.Z.7** (not yet on master plan; one-line addition recommended in closure) — mobile checkout surfaces the promo code field

## 1. Pre-flight findings

### 1.1 `Order` already has a `discount` field

```
apps/api/src/Domain/Order/Order.php:108  private string $discount = '0.00';
apps/api/src/Domain/Order/Order.php:497  computeTotal($subtotal, $deliveryFee, $discount)
apps/api/src/Domain/Order/Order.php:500  $net = bcsub($gross, $discount, 2);
apps/api/src/Domain/Order/Order.php:502  Floor at zero — a discount can't make the order negative.
```

No new money column on `orders` is required. X.8 layers (a) a new table that stores *which* promo was redeemed and *how much* was attributed, plus (b) a new FK column `orders.promo_redemption_id` (nullable) for the inverse lookup.

### 1.2 `POST /v3/checkout/initiate` accepts a raw client discount today

```
apps/api/src/Http/Controllers/Checkout/Dto/InitiateCheckoutInput.php:53
  #[Assert\Regex(pattern: '/^\d+(\.\d{1,2})?$/', message: '...')]
  public readonly string $discount;
```

X.8 introduces a sibling `promo_code` field on the same DTO. Server logic in -D:

- If `promo_code` is supplied: resolve it via `PromoCodeResolverService`; ignore any client-supplied `discount`.
- If `promo_code` is absent and `discount` is supplied: log a `Notice` header on the response (`X-Bayti-Deprecation: client-supplied discount accepted as-is; pass promo_code instead`); current behavior preserved for backward compatibility with the live mobile build until the next mobile release ships.
- If neither: `discount = '0.00'`, current default behavior.

This is the **only** backward-compat consideration in the phase. After mobile is updated to send `promo_code`, the operator can drop the legacy `discount` field in a future X-phase or M3.4 cleanup.

### 1.3 No promo infrastructure exists

```
$ grep -ril "promo\|coupon" apps/api/src --exclude-dir=Migration
```

Returns hits only on the `discount` field references, the legacy migration step (which carries `ldiscount` from legacy `customer_orders.discount`), and the M3.1.6 comments referenced above. Greenfield schema, greenfield resolver, greenfield admin.

### 1.4 Auth + admin patterns are stable

- `/v3/cart/*` and `/v3/checkout/*` are under `AuthMiddleware` ([routes.php:158-198](../../apps/api/config/routes.php))
- `/v3/admin/*` is under `AdminAuthMiddleware` → `AuthMiddleware` (routes.php:275-330)
- `AuditEmitter::snapshotXxx` pattern (X.7-D) accepts the entity and returns a `string[]` for the diff payload — promo CRUD mirrors `snapshotVendor`

### 1.5 `Cart` carries `currency='AED'` already

```
apps/api/src/Domain/Cart/Cart.php:80-81
  #[ORM\Column(type: 'string', length: 3)]
  private string $currency = 'AED';
```

Promo codes carry their own `currency` column defaulting to 'AED'. Engine in -B validates that promo currency matches cart currency (rejects with 422 if mismatch). v1 only has 'AED' so this is theoretical guardrail; M3.2.X.15 (multi-currency) will exercise it.

### 1.6 Q-Unification pattern from X.7 applies

When X.7-D pivoted, the lesson was: **before adding a new field, check whether an existing field already serves the use case**. Pre-flight for X.8:

- `Order.discount` exists → reuse, don't duplicate. ✓
- `Order.currency` exists → no need for a sibling on the promo-redemption row. ✓
- `Cart.currency` exists → reuse for currency check. ✓
- `User.id` is the redemption owner → no separate `customer_id` column. ✓

The only genuinely new persistence is the two new tables (`promo_codes`, `promo_redemptions`) plus one nullable FK column on `orders`.

## 2. Architecture

### 2.1 New database tables

**`promo_codes`** — the catalog of available codes (admin-managed).

| Column | Type | Notes |
|---|---|---|
| `id` | BIGSERIAL PK | |
| `code` | VARCHAR(64) UNIQUE NOT NULL | Case-INSENSITIVE match (UPPER index); admin can type 'welcome10', users can type 'WELCOME10' or 'welcome10' |
| `description` | TEXT NULL | Admin-only context |
| `discount_type` | VARCHAR(16) NOT NULL | CHECK in (`percentage`, `fixed_amount`) per Q-DiscountTypes=A |
| `discount_value` | DECIMAL(10,2) NOT NULL | For `percentage`: 0.01-100.00 (e.g. `10.00` = 10%). For `fixed_amount`: AED amount. |
| `currency` | VARCHAR(3) NOT NULL DEFAULT 'AED' | Per §1.5 |
| `min_subtotal` | DECIMAL(10,2) NULL | Per Q-MinOrderSubtotal=A. Cart subtotal must be ≥ this for code to apply. |
| `max_discount_amount` | DECIMAL(10,2) NULL | Caps total discount (e.g. "10% off, max 50 AED"). For `fixed_amount`, unused. |
| `usage_limit_global` | INT NULL | Total redemptions across all users. NULL = unlimited. |
| `usage_limit_per_user` | INT NULL | Per-user redemptions. NULL = unlimited. (Defaults to 1 in admin UX, but schema permits NULL.) |
| `valid_from` | TIMESTAMPTZ NULL | Code unusable before this. NULL = no lower bound. |
| `valid_until` | TIMESTAMPTZ NULL | Code unusable after this. NULL = no upper bound. |
| `is_active` | BOOLEAN NOT NULL DEFAULT TRUE | Admin can soft-disable a code (preserves history). |
| `created_at` | TIMESTAMPTZ NOT NULL | |
| `updated_at` | TIMESTAMPTZ NOT NULL | |

Indexes:
- `uq_promo_codes_code` UNIQUE on `UPPER(code)` (Postgres functional index; SQLite tests use CITEXT-like collation or app-layer normalization — the entity layer always stores UPPER-cased).
- `ix_promo_codes_is_active_valid` on `(is_active, valid_until)` for "list currently-valid codes" admin filter.

**`promo_redemptions`** — one row per successful redemption.

| Column | Type | Notes |
|---|---|---|
| `id` | BIGSERIAL PK | |
| `promo_code_id` | BIGINT FK → promo_codes(id) ON DELETE RESTRICT | Can't delete a code that's been redeemed. |
| `user_id` | BIGINT FK → users(id) ON DELETE RESTRICT | Customer who redeemed. |
| `order_id` | BIGINT FK → orders(id) ON DELETE CASCADE | Removed if order is hard-deleted. |
| `discount_amount` | DECIMAL(10,2) NOT NULL | Snapshot of computed discount at redemption time. |
| `code_snapshot` | VARCHAR(64) NOT NULL | Snapshot of the code text at redemption time (admin can rename later). |
| `discount_type_snapshot` | VARCHAR(16) NOT NULL | Snapshot (admin can change later). |
| `discount_value_snapshot` | DECIMAL(10,2) NOT NULL | Snapshot. |
| `redeemed_at` | TIMESTAMPTZ NOT NULL | |

Indexes:
- `uq_promo_redemptions_order_id` UNIQUE on `order_id` (one promo per order per Q-ConflictPolicy=A).
- `ix_promo_redemptions_promo_code_id` for `usage_limit_global` enforcement.
- `ix_promo_redemptions_user_id_promo_code_id` for `usage_limit_per_user` enforcement.

**`orders.promo_redemption_id`** — new nullable FK column.

```sql
ALTER TABLE orders
  ADD COLUMN promo_redemption_id BIGINT NULL REFERENCES promo_redemptions(id) ON DELETE SET NULL;
CREATE INDEX ix_orders_promo_redemption_id ON orders(promo_redemption_id);
```

### 2.2 Domain layer

**`Bayti\Api\Domain\Promo\PromoCode`** — entity.
**`Bayti\Api\Domain\Promo\PromoCodeRepository`** — `findByNormalizedCode(string)`, `findActiveById(int)`, paginated list with filters.
**`Bayti\Api\Domain\Promo\PromoRedemption`** — entity.
**`Bayti\Api\Domain\Promo\PromoRedemptionRepository`** — `countByPromoCodeId(int)`, `countByUserAndPromoCode(int, int)`, `findByOrderId(int)`.
**`Bayti\Api\Domain\Promo\PromoCodeResolverService`** — the engine. Methods:
- `resolveForCart(Cart $cart, User $user, string $rawCode): PromoResolution` — returns a value-object `{promoCode, discountAmount, currency}` or throws `PromoNotApplicableException` (mapped to HTTP 422 with structured error code).
- `recordRedemption(PromoCode, User, Order, string $discountAmount): PromoRedemption` — called inside `InitiateCheckoutController`'s EM transaction.

**Validation chain (in order; first failure stops the chain):**

1. `code` is not empty after `mb_strtoupper(trim($raw))`
2. `PromoCode` row exists for normalized code (else 422 `PROMO_NOT_FOUND`)
3. `promo.is_active = true` (else 422 `PROMO_INACTIVE`)
4. `now() >= promo.valid_from OR valid_from IS NULL` (else 422 `PROMO_NOT_YET_VALID`)
5. `now() <= promo.valid_until OR valid_until IS NULL` (else 422 `PROMO_EXPIRED`)
6. `promo.currency = cart.currency` (else 422 `PROMO_CURRENCY_MISMATCH`)
7. `cart.subtotal >= promo.min_subtotal OR min_subtotal IS NULL` (else 422 `PROMO_MIN_SUBTOTAL_NOT_MET` — error payload includes `min_subtotal` for client UX)
8. `globalUsageCount < promo.usage_limit_global OR usage_limit_global IS NULL` (else 422 `PROMO_GLOBAL_LIMIT_REACHED`)
9. `userUsageCount < promo.usage_limit_per_user OR usage_limit_per_user IS NULL` (else 422 `PROMO_USER_LIMIT_REACHED`)
10. Compute `discountAmount`:
    - `percentage`: `bcdiv(bcmul(cart.subtotal, discount_value, 4), '100', 2)`; clamped to `max_discount_amount` if set.
    - `fixed_amount`: `discount_value`; clamped to `cart.subtotal` (can't discount more than the subtotal).
11. Return `PromoResolution(promoCode, discountAmount, currency)`.

### 2.3 HTTP surface

**Customer:**

- `POST /v3/cart/quote` — body: `{ promo_code?: string }`. Returns a price breakdown:
  ```json
  {
    "data": {
      "currency": "AED",
      "subtotal": "120.00",
      "delivery_fee": "0.00",
      "discount": "12.00",
      "total": "108.00",
      "applied_promo": {
        "code": "WELCOME10",
        "discount_type": "percentage",
        "discount_value": "10.00",
        "discount_amount": "12.00"
      }
    }
  }
  ```
  Auth required (cart is user-bound). Idempotent. Pure read; no DB writes. Returns 422 with structured error code from §2.2 chain on rejection.

  Note: `delivery_fee` in v1 is always `'0.00'` because the delivery-fee-calculator endpoint is still deferred (per M3.1.6 note). When that ships in a future X-phase, the same endpoint shape just starts returning the real fee. The promo engine integrates cleanly with that future change since `min_subtotal` is the only field that cares about pre-discount totals, and that's the cart subtotal (not subtotal + fee).

**Customer (modified):**

- `POST /v3/checkout/initiate` — adds optional `promo_code` field on `InitiateCheckoutInput`. Server-side flow inside the EM transaction in -D becomes:
  1. Existing: load cart, addresses, generate order reference
  2. **NEW:** If `promo_code` is supplied → resolve via `PromoCodeResolverService::resolveForCart`. If resolution fails, abort with 422 (the `promo_redemptions` row is never written). Cart is NOT marked converted on failure; user keeps their cart and can retry.
  3. **NEW:** If `promo_code` resolved, the server-computed `$discount` overrides any client-supplied value.
  4. Existing: snapshot cart → order, snapshot addresses
  5. **NEW:** Insert `PromoRedemption` row (FK → promo_codes, user, order).
  6. **NEW:** Set `order.setDiscount($discountAmount)` and `order.setPromoRedemption($redemption)`.
  7. Existing: persist order; `Order::recomputeTotals` recalculates `total` with new discount.
  8. Existing: outside-transaction Noon INITIATE call.

  The redemption write being inside the transaction matters: if Noon INITIATE fails post-transaction, the order exists in `pending_payment` state AND the redemption exists. That's correct — the redemption is committed against this order_reference. If the order ultimately fails / is canceled (M3.1.7-F flow), the cancel logic in `CancelOrderService` does NOT automatically reverse the redemption; the redemption row stays as historical attribution but the order's `discount` is moot. For limit-counting purposes, `promo_redemptions` joined to `orders.status NOT IN (terminal_failed_states)` is the live-redemption count — implemented via `countByPromoCodeIdEffective` which excludes orders in `canceled` / `payment_failed`. (Future cleanup: when an order is canceled, *delete* its redemption row to free the slot — but that's a behavior change that should be its own approval gate; v1 keeps redemptions immutable post-write.)

**Admin:**

- `GET /v3/admin/promo-codes` — paginated list with filters: `is_active`, `discount_type`, `valid_from_lte`, `valid_until_gte`, `code` (LIKE), `limit`, `offset`. Same pattern as `/v3/admin/notification-logs` from X.4.
- `GET /v3/admin/promo-codes/{id}` — single record with redemption count.
- `POST /v3/admin/promo-codes` — create. Audit `ACTION_CREATED`.
- `PUT /v3/admin/promo-codes/{id}` — update. Audit `ACTION_UPDATED` with diff snapshot.
- `DELETE /v3/admin/promo-codes/{id}` — **soft delete**: sets `is_active = false` (preserves redemption FK integrity). Audit `ACTION_DELETED`. If the row has zero redemptions, falls through to hard delete (cleanup affordance for typos).

## 5. Risk register

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| Promo redemption races (concurrent checkout-initiate exhausts global limit) | Low | Medium | `usage_limit_global` enforcement is best-effort at write time; the engine reads count → validates → writes inside the EM transaction. A true race would require two concurrent transactions; the chance is small in a marketplace this size. If it occurs, the second redemption succeeds (engine doesn't lock) but the final state has `N+1` redemptions against a `usage_limit_global = N` — admin can spot via the list endpoint and revoke. Acceptable for v1; a `SELECT ... FOR UPDATE` upgrade is a future hardening item. |
| Client retries the same promo+cart pair and double-counts | Low | High | UNIQUE constraint on `promo_redemptions.order_id` makes double-write impossible. Since each `/v3/checkout/initiate` generates a fresh order_reference, retries before the order is committed produce DIFFERENT orders and DIFFERENT redemptions, which is correct (the first failed attempt's order stays in `pending_payment` until cleanup). Idempotency at the checkout layer is via `PaymentTransaction.idempotency_key` (M3.1.6 pattern), which already handles double-tap. |
| Mobile clients on legacy build keep sending raw `discount` | Certain | Low | Backward-compat path preserved in -D; deprecation header emitted; operator drops the legacy field in a future cleanup phase after mobile is updated. |
| Order cancellation doesn't reverse the redemption → user "used" a one-time code on a canceled order | Medium | Low | Documented v1 limitation; per Q-RedemptionTracking=A the redemption row is historical. Future hardening: on `CancelOrderService`, if `order.promoRedemption !== null`, delete the redemption (or flag it canceled). Out of v1 scope — admin can manually delete via the admin endpoint. |
| Admin creates a promo code that conflicts with the legacy raw-discount path | Low | Low | The legacy path doesn't reference the promo system at all — `discount` is just a number. No conflict. |
| `min_subtotal` is in AED but cart could one day be in USD (per future X.15) | Theoretical | Low | Currency check (validation step 6) gates this; if cart.currency !== promo.currency, code rejects. X.15 will revisit. |
| Postgres functional unique index (`UPPER(code)`) doesn't apply on SQLite test fixtures | Medium | Low | Entity-level normalization (always store and lookup as UPPER) provides the same guarantee at the app layer; the DB constraint is defense in depth. Tests run on SQLite/MySQL portably. |

## 6. Compatibility with existing patterns

X.8 explicitly follows these conventions established in earlier phases:

- **Lazy EM resolution** (X.4-B): `PromoCodeResolverService` does NOT eagerly resolve repositories in `__construct`; resolves inside `resolveForCart()` via `$this->em->getRepository(PromoCode::class)` with `instanceof` check.
- **DTO explicit constructor with defaults + `trim()` normalization** (X.7): `QuoteCartInput::$promo_code = $promo_code !== null ? mb_strtoupper(trim($promo_code)) : null`.
- **Migration timestamps**: most recent shipped is `Version20260518000001` (X.7-A). X.8-A claims `Version20260518000002`.
- **Status taxonomy enforcement** (X.6): `discount_type` VARCHAR(16) with CHECK constraint at DB level + `ALL_DISCOUNT_TYPES` const on entity + assertion in setter.
- **Audit snapshot pattern** (X.7-D): `AuditEmitter::snapshotPromoCode` mirrors `snapshotVendor` shape.
- **HttpException::validation** expects `array<string, list<string>>` (phpstan-driven).
- **`@phpstan-ignore-next-line property.unusedType`** for Doctrine IDENTITY id columns.
- **Q-Unification pattern** (X.7-D pivot): pre-flight already done in §1.6 — no duplicate fields added.
