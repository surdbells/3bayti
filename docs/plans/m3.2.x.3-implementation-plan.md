## 0. Why this is M3.2.X.3

Per master plan §2 Stream X row 3:

> `/v3/categories/:slug` augmentation with embedded products + meta — 1 day — Match legacy v2 response shape; apps/web category-detail page currently uses v2.

The apps/web `/category/:slug` route currently routes to legacy `/v2/categories/:slug` because the existing v3 endpoint returns only category metadata + children — no embedded products and no `meta` block. Apps/web's `CategoryDetailEnvelope` expects a richer shape:

```typescript
interface CategoryDetailEnvelope {
  data: CategoryDetail;  // includes products: Product[]
  meta: CategoryDetailMeta;  // { total_products, page_size }
}
```

Apps/web's `home-data.service.ts`-style pattern is in `category-detail.ts::fetchCategoryDetail$()` — single GET call returns the full landing page. Without v3 augmentation, apps/web stays on legacy v2 indefinitely, which works today but blocks the M3.4 legacy retirement milestone.

This phase augments the existing v3 endpoint to match the legacy v2 shape exactly, then flips apps/web. Master plan estimated 1 day; pre-flight inspection puts it at **1.5-2 days** because:
- Existing `GetCategoryController` returns `PaginatedEnvelope::single($shape)` (no `meta`)
- `CategorySerializer::publicShape` does NOT include `product_count` or `icon_name` fields the apps/web type expects
- Tests need to verify the exact wire shape against the apps/web `CategoryDetailEnvelope` interface

### 1.2 Expected wire contract

From `apps/web/src/app/features/categories/category.model.ts`:

```typescript
interface Category {
  id: number;
  slug: string;
  name: string;
  description: string | null;
  image: { url: string } | null;       // ← v2 shape (object with url)
  icon_name?: string | null;            // ← Lucide icon name fallback
  product_count: number;                // ← raw category count
}

interface CategoryDetail extends Category {
  products: Product[];                  // ← 20 products (first page)
}

interface CategoryDetailMeta {
  total_products: number;               // ← approved+published count
  page_size: number;
}
```

Envelope: `{ data: CategoryDetail, meta: CategoryDetailMeta }`.

### 1.3 Existing v3 GetCategoryController response shape

Current output (verified by reading `GetCategoryController.php`):

```json
{
  "data": {
    "id": 5,
    "slug": "abayas",
    "name": "Abayas",
    "description": "...",
    "display_order": 1,
    "image_url": "https://cdn/abayas.jpg",
    "path": "/5",
    "parent_id": null,
    "children": [...]
  }
}
```

Gaps vs apps/web `CategoryDetailEnvelope`:

| Field | Apps/web expects | Current v3 emits | Action |
|---|---|---|---|
| `image` (object form) | `{ url: string } \| null` | `image_url: string \| null` (flat) | Add `image: image_url ? {url} : null` |
| `icon_name` | `string \| null` | absent | Add from `Category::$icon` field |
| `product_count` | `number` (raw) | absent | Add COUNT query (all products, no status filter) |
| `products` | `Product[]` (20 items) | absent (only `children`) | Add via `ProductRepository::findActivePaginated` |
| `meta.total_products` | `number` (filtered) | absent | Add — same as the `findActivePaginated` total |
| `meta.page_size` | `number` | absent | Add literal 20 |
| `children` | not in interface | emitted | Keep (harmless extra; apps/web ignores) |

### 1.4 Categories total_products semantics

Apps/web's `category.model.ts` comment is explicit:

> `meta.total_products` ≠ `product_count`. `product_count` is the raw count in the category JOIN (includes products from non-approved vendors). `total_products` is the count after WHERE filters (published + store_approved). The latter is what we display.

In v3 terms:
- `product_count` = total products in category (no status filter)
- `total_products` = active products in category (the count returned by `ProductRepository::findActivePaginated`)

For a clean category these will usually match. For categories with inactive vendors / draft products they may differ. Apps/web displays `total_products` (correctly the active count); `product_count` is informational.

### 1.5 Existing assets that help

- `GetCategoryController` exists; needs augmentation, not rewrite
- `CategoryRepository::findBySlug` + `findChildren` already in place
- `ProductRepository::findActivePaginated(['categoryId' => N, 'limit' => 20, 'sort' => 'newest'])` returns `{items, total}` — exact shape needed
- `ProductSerializer::listShape` matches apps/web's `Product` interface exactly (no work needed here)
- `CategorySerializer::publicShape` to extend (add `image`, `icon_name`, `product_count`)
- `PaginatedEnvelope::build($items, $total, $limit, $offset)` matches the meta needs (returns `{data, meta:{total, limit, offset, has_more}}`)

Note on meta shape: `PaginatedEnvelope::build` returns `meta: {total, limit, offset, has_more}` but apps/web expects `meta: {total_products, page_size}`. This is a **different** envelope shape — the existing helper doesn't apply. The controller must construct the response manually.

### 1.6 Sub-categories (`children`) handling

Apps/web's `CategoryDetail` interface does NOT include a `children` field. The current v3 endpoint emits `children` as part of `data`. Two options:

- Keep emitting `children` (harmless extra field; TypeScript ignores unknown keys at runtime)
- Drop `children` to match apps/web's strict interface

**My recommendation:** Keep emitting. Removing it would be a breaking change for any other consumer that depends on the current v3 shape (the admin tool, future portal). Apps/web's strict interface is enforced at compile time only; runtime accepts extra keys.

## 3. Decisions to lock IN this approval

### Decision M3.2.X.3-Q-PageSize: products per category page

Apps/web's existing v2 path returns 20 products. The apps/web component renders the FIRST page only (`category-detail.ts` docblock says pagination beyond page 1 is deferred to W2.1b). Question: how many products should v3 embed per request?

- **A:** Hard-coded 20 (matches legacy v2 behavior; apps/web pagination not yet built)
- **B:** Configurable via `?limit=` query param, default 20, clamped to [1..50]
- **C:** Larger default (e.g. 40) since the category page WILL eventually paginate

**My recommendation: A.** Apps/web currently consumes the first 20 only. Matching legacy minimizes wire-contract drift, and adding pagination support is the next phase's concern (M3.2.X.3 augmentation, not category pagination). Configurable limit is unused complexity until apps/web ships pagination UI.

### Decision M3.2.X.3-Q-Sort: product ordering inside the category

Apps/web doesn't specify a sort order; legacy v2 returned products in `created_at DESC` (newest first). For v3:

- **A:** Newest first (`sort=newest` in `findActivePaginated`) — matches legacy
- **B:** Featured first then newest (would require composite sort)
- **C:** Random within first page (e.g. seed shuffle by request) — discovery-style UX

**My recommendation: A.** Match legacy. Apps/web users currently see newest-first; preserving that minimizes regression surface. Featured-first is a separate UX decision and belongs in a dedicated phase that also adds the corresponding sort to the catalog page.

### Decision M3.2.X.3-Q-Children: emit children array

Current v3 endpoint emits `children` as part of `data` (direct subcategories). Apps/web's `CategoryDetail` interface doesn't include `children`. Question: keep or drop?

- **A:** Keep emitting (harmless extra field; future consumers may want it; admin tool likely uses it)
- **B:** Drop to match apps/web's strict interface exactly
- **C:** Move to a separate `?include=children` query param

**My recommendation: A.** Removing a field that's been in the v3 response is a breaking change for any consumer that depends on it (the admin tool already does — verified earlier). TypeScript's structural typing ignores unknown keys at runtime; the strict interface check happens at compile time only on apps/web side.

### Decision M3.2.X.3-Q-Empty: category with zero active products

Behavior when a category exists, is active, but has no active products:

- **A:** Return 200 with `data.products: []` and `meta.total_products: 0`
- **B:** Return 404 (treat as "nothing to show")
- **C:** Return 200 with a sentinel `data.empty: true` flag

**My recommendation: A.** Empty isn't an error. Apps/web's existing component handles `products: []` gracefully (the description template branches on `total === 0`). 404 would break the breadcrumb display + SEO meta. Sentinel flags are unidiomatic.

### Decision M3.2.X.3-Q-Shadow: shadow window for the flip

- **A:** No shadow window. Apps/web is the only consumer; v3 must match v2 shape exactly per the contract; single-commit flip in `-D`.
- **B:** 3-day operator-driven shadow window with logging in `RoutedHttpClient`.
- **C:** Apps/web stays on legacy in a separate commit `-E` after operator sign-off.

**My recommendation: A.** Same rationale as M3.2.X.2-Q-Shadow=A: the contract is locked at compile time (apps/web tsc interfaces), and the v3 endpoint matches it after -C. Revert is one feature-flag flip if regression surfaces. Apps/web's `as unknown as CategoryDetailEnvelope` cast provides a runtime safety net if any field is missing.
