## 4. Architectural notes carried forward

- **Two HTTP clients, deliberately.** Profile + password use the
  `RoutedHttpClient` (`PATCH /me/profile`, `PATCH /me/password`,
  envelope-normalised). Measurements use the **Bearer-bound direct
  HttpClient** (`firstValueFrom(http.get('https://api-v3…/v3/me/measurements/default'))`)
  because the api-client registry's measurement entries are stale
  (legacy `/me/measurements/:id` shapes) and don't match the live v3
  routes. This mirrors how cart/orders/addresses already talk to v3
  directly. **If a future sub-phase wants measurements on the routed
  client, the registry entries must be rewritten first** — they are
  currently wrong, not just absent.
- **Password change rotates tokens.** `PATCH /me/password` revokes ALL
  refresh tokens (including the caller's) and returns a fresh pair.
  `AuthService.applyPasswordChange()` adopts the new access token + user
  so the session survives; without it the next request 401s on a
  revoked token. This is the canonical pattern for any future endpoint
  that rotates credentials.
- **`ConfirmModalComponent` is the standard confirm primitive.**
  Presentational + controlled (`[open]` in, `(confirm)`/`(cancel)`
  out), `[danger]` + `[busy]` variants, full a11y (role=dialog,
  aria-modal, aria-labelledby/describedby, autofocus via `ngOnChanges`
  + deferred `setTimeout`, Escape + backdrop cancel). The two remaining
  native `confirm()` sites (order cancel, address delete) were
  retrofitted onto it in Y.5-C; **there are now no `window.confirm()`
  calls left in the web app.** Y.6 account deletion reuses this modal.
- **Diff-based profile submit.** `/account/profile` sends only changed
  keys (leaning on the API's RFC 7396 Merge Patch); an emptied text
  field is sent as `null` (clears it); no changes → no API call + an
  info toast.
- **Measurements value-accessor caveat.** `<input type="number">` +
  `formControlName` hands the control a `number | '' | null`, not a
  string. `buildUpsert` normalises defensively (`String(v).trim()`)
  before serialising — copy this if reusing the page's form pattern.

## 5. API surface touched (all pre-existing; no API code shipped in Y.5)

| Method | Path | Notes |
|---|---|---|
| GET | `/v3/me/profile` | `{ data: { user } }` |
| PATCH | `/v3/me/profile` | Merge Patch: first_name, last_name, gender, dob, locale (NOT phone) |
| PATCH | `/v3/me/password` | current_password + new_password(min 8) → fresh token pair; 401 AUTH_INVALID_CREDENTIALS on wrong current |
| GET | `/v3/me/measurements/default` | `{ measurements: Measurement \| null }` — never 404s |
| PUT | `/v3/me/measurements/default` | `{ values:{key:number 0–500}, notes?≤1000 }` → `{ measurements }` |
| DELETE | `/v3/me/measurements/default` | 204 |

## 7. What Y.6 needs to start

Y.6 (Account deletion + Wishlist) is **approved**; Q6.1–Q6.4 are
**confirmed**:

- **Q6.1** — deletion sets BOTH `deactivate()` (is_active=false) AND
  `softDelete()` (deleted_at stamp).
- **Q6.2** — deletion REQUIRES `current_password` re-auth (401
  AUTH_INVALID_CREDENTIALS on mismatch, same pattern as change-password).
- **Q6.3** — wishlist POST is idempotent (already-saved → no-op success,
  not 409).
- **Q6.4** — `GET /v3/me/wishlist` returns saved products via the
  existing `ProductSerializer` list shape in a `PaginatedEnvelope`.

De-risking already done (see transcript):
- **Deletion needs NO migration.** The `User` entity already has
  `deactivate()`/`softDelete()`/`isActive()`/`isDeleted()`, the
  `is_active` + `deleted_at` columns, and `RefreshTokenRepository::
  revokeAllForUser()`. Both `LoginController` and `AuthMiddleware`
  already reject `!isActive()` users. Y.6-A is one controller reusing
  these + an audit record + 204.
- **Wishlist is net-new** — migration (`wishlist` table: id, user_id FK,
  product_id FK, created_at, unique(user_id,product_id)) + entity +
  repository + 3 endpoints (GET paginated products, POST idempotent,
  DELETE by productId), under the `/v3/me` route group, DI-autowired.

Planned sub-phases (run continuously per operating criteria):
Y.6-A deletion backend → Y.6-B deletion web → Y.6-C wishlist backend →
Y.6-D wishlist web → Y.6-E Y.6 closure.
