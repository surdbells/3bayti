## 0. Why this is M3.2.X.4

Per master plan §2 Stream X row 4:

> `notification_log` persistence table + wire to OrderNotificationService — 2-3 days — Schema: order_id, template, recipient, status, sent_at, error_kind, raw_event; covers M3.1.7-H observability gap; admin endpoint `GET /v3/admin/notification-logs` for triage.

Two motivations:

1. **Observability gap.** M3.1.7-H shipped the full email infrastructure but per `OrderNotificationService.php` lines 33-40:
   > "Idempotency... We do NOT track 'already sent' state — duplicate calls cause duplicate emails. Acceptable trade-off vs. introducing a notification_log table for M3.1.7. Future: add notification_log if we get reports of duplicate emails from genuine retries."

   The current state: emails go out, failures get logged to `LoggerInterface` (PSR-3) but nothing is queryable. If a customer says "I never got my order confirmation," ops has no way to verify whether the email was sent, deferred, bounced, or never attempted. This phase closes that gap.

2. **Triage surface.** `GET /v3/admin/notification-logs` lets admins filter by order, template, status, recipient to diagnose specific incidents. Today this requires `kubectl logs | grep`.

## 1. Pre-flight findings

### 1.1 The hook point — `OrderNotificationService::safeSend()`

`apps/api/src/Notification/OrderNotificationService.php::safeSend()` is THE single chokepoint for all 10 email templates across all 7 lifecycle events. Every email goes through this private method which:
1. Renders the template via `OrderEmailTemplateRenderer::render()`
2. Calls `$this->mailer->send(...)` (the `MailerInterface`)
3. Catches `MailerException` (with `$e->kind` — see §1.4) and logs
4. Catches any `\Throwable` and logs

The architecture is already perfect for logging — every send is funneled through one method. Adding `notification_log` write requires:
- Modify `safeSend()` to write a `NotificationLog` row before and/or after each `mailer->send()` call
- No changes to lifecycle methods (`orderPlaced`, `orderPaid`, etc.)
- No changes to controllers / callers (15+ call sites unaffected)

### 1.2 What metadata is available in `safeSend()`

The method already has all the metadata the schema needs:
- `$to`: recipient email (string)
- `$template`: `EmailTemplate` enum (string-backed: e.g. `'order.placed.customer'`)
- `$order`: `Order` entity → `$order->getId()`, `$order->getOrderReference()`
- `$extra`: context for the template (vendor_items, refund_amount, etc.)
- On failure: `MailerException::$kind` (transport/network/rate_limit/auth/unknown) or `\Throwable::class`

### 1.3 MailerException error kinds (constants exist)

## 2. Schema design (detailed)

```sql
CREATE TABLE notification_logs (
    id BIGSERIAL PRIMARY KEY,

    -- Subject: which order this notification is about (NULLABLE because
    -- future non-order notifications could land here too, but for M3.2.X.4
    -- every row has order_id).
    order_id INTEGER NULL REFERENCES orders(id) ON DELETE SET NULL,

    -- Which email template was rendered (string value of EmailTemplate enum,
    -- e.g. 'order.placed.customer').
    template VARCHAR(64) NOT NULL,

    -- Recipient email address as it was sent to. Captured at send time;
    -- preserved even if the user's email changes later — this is an audit
    -- trail, not a live link.
    recipient VARCHAR(255) NOT NULL,

    -- Status taxonomy (locked by Q-Status; see §3):
    --   'sent'     → mailer->send() returned without exception
    --   'failed'   → caught MailerException or \Throwable
    --   'skipped'  → guard hit (no_email, contact_email_unset, etc.)
    status VARCHAR(16) NOT NULL,

    -- Timestamp of attempt. Set on row creation; immutable.
    -- For 'sent' rows: the moment we believed delivery succeeded.
    -- For 'failed' rows: the moment we caught the exception.
    -- For 'skipped' rows: the moment we decided not to send.
    -- (NOT the moment the email LANDED in the recipient's inbox —
    --  ZeptoMail doesn't give us that signal in M3.2.X.4 scope.)
    sent_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),

    -- For 'failed' rows: which MailerException kind, or the exception
    -- class name for non-MailerException failures.
    -- Null for 'sent' and 'skipped' rows.
    error_kind VARCHAR(32) NULL,

    -- For 'failed' rows: the exception message + class for debugging.
    -- Null for 'sent' and 'skipped' rows.
    -- For 'skipped' rows: the reason short-code ('no_email',
    -- 'contact_email_unset', etc.).
    error_message TEXT NULL,

    -- Reserved for future webhook events from ZeptoMail (bounce, complaint).
    -- Null for now; column exists so future webhook handler can update.
    -- (M3.2.X.4 doesn't wire ZeptoMail webhooks — that's a follow-up
    -- if/when bounce visibility is needed.)
    raw_event JSONB NULL,

    -- Audit timestamps. created_at = sent_at by design (immutable);
    -- updated_at moves when raw_event is updated by future webhook.
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- Indexes
CREATE INDEX idx_notification_logs_order_id    ON notification_logs (order_id);
CREATE INDEX idx_notification_logs_template    ON notification_logs (template);
CREATE INDEX idx_notification_logs_status      ON notification_logs (status);
CREATE INDEX idx_notification_logs_sent_at     ON notification_logs (sent_at DESC);
CREATE INDEX idx_notification_logs_recipient   ON notification_logs (recipient);

-- Composite for the most-common admin query pattern:
--   "show me failed sends in the last 24h"
CREATE INDEX idx_notification_logs_status_sent_at ON notification_logs (status, sent_at DESC);
```

**Why JSONB for `raw_event`:** PostgreSQL native; cheap when null; future webhook handler can `UPDATE notification_logs SET raw_event = $1 WHERE ...` with a single column write.

**Why `order_id` is `ON DELETE SET NULL` (not CASCADE):** Notification log is an audit trail. If an order is hard-deleted (rare; almost always soft-delete via status), we keep the notification history with order_id=null rather than losing the audit trail.

**Why no `updated_at` index:** Updates are rare (only when webhook lands); no admin query filters on it.

### Why explicitly NO `vendor_id` column

`OrderNotificationService::sendToVendors` sends ONE email per unique vendor in the order, but the `recipient` column already captures the vendor's `contact_email`. The vendor_id is derivable from `order_id + recipient` if needed. Adding `vendor_id` would:
- Be NULL for customer + admin emails (sparse, anti-pattern)
- Force the lifecycle methods to know about vendor IDs (they currently work in entity terms)
- Add an FK that breaks if a vendor is hard-deleted

The cost of looking up "which vendor was this email for" via query is small (admin tool joining `vendor.contact_email = nl.recipient WHERE nl.order_id = X`); the cost of always-null vendor_id columns for customer emails is real.

## 3. Decisions to lock IN this approval

### Decision M3.2.X.4-Q-Status: status taxonomy

How granular should the `status` column be?

- **A:** Three values — `sent`, `failed`, `skipped` (skipped = guard short-circuited)
- **B:** Two values — `sent`, `failed` (skipped silently logged but NOT persisted)
- **C:** Four values — `sent`, `failed`, `skipped`, `deferred` (deferred = future async queue retries; not relevant today)

**My recommendation: A.** Skipped sends ARE valuable observability data — they tell ops "this customer's order has no notifications because their email is empty." Excluding them loses that signal. `deferred` doesn't apply since M3.2.X.4 is fire-and-forget (no retry queue yet).

### Decision M3.2.X.4-Q-RawEvent: include raw_event column now

The column is reserved for future ZeptoMail webhook payloads (bounce, complaint, delivered). Should we ship the column now or defer?

- **A:** Ship `raw_event JSONB NULL` now; column exists ready for future webhook handler
- **B:** Defer; add column when webhook handler ships
- **C:** Ship + also wire a minimal webhook receiver in this phase (~+1 day)

**My recommendation: A.** Empty JSONB columns cost nothing (PostgreSQL stores null efficiently). Adding the column later is cheap but requires a migration. Pre-allocating means future webhook handler is a code-only change. Wiring the webhook in this phase (C) would balloon scope; defer to a dedicated phase when ZeptoMail webhook secrets + integration tests warrant it.

### Decision M3.2.X.4-Q-Audit: admin endpoint audit emission

Per master plan §1.3 / M3.1.7-D pattern: admin endpoints emit `AuditLog::ACTION_VIEWED` rows when admins read sensitive data.

- **A:** Emit `ACTION_VIEWED` audit row per `GET /v3/admin/notification-logs` request (same pattern as `ListAdminOrdersController`)
- **B:** No audit emission (this isn't sensitive customer data — just operational logs)
- **C:** Audit only when filter includes specific user/order (broad list view is non-audit)

**My recommendation: A.** Match the established admin-endpoint pattern. The notification log contains recipient email addresses — debatably sensitive — and consistency with `ListAdminOrdersController` keeps the audit trail comprehensive. Adding the audit emit is 2 lines of code; the cost of inconsistency is higher.

### Decision M3.2.X.4-Q-Retention: data retention strategy

How long do notification log rows live?

- **A:** Forever (no retention policy in this phase; rows accumulate; future phase adds retention if volume becomes a concern)
- **B:** Auto-purge rows older than 90 days via nightly job
- **C:** Soft-delete after 90 days (`deleted_at` column); keep for compliance

**My recommendation: A.** At expected volume (~10-100 notifications/day) the table grows at ~36K rows/year. PostgreSQL handles millions of rows easily; the retention question becomes real at ~10M rows (years away). Add B later if volume warrants. Deferring keeps M3.2.X.4 focused on the observability gap.

### Decision M3.2.X.4-Q-Backfill: historical data

The legacy `LoggerInterface` calls from M3.1.7-H to now have logged notification attempts to PSR-3. Should we attempt to backfill `notification_logs` rows from those logs?

- **A:** No backfill — table starts populated from M3.2.X.4 deploy onwards
- **B:** Operator-driven backfill script (parse PSR-3 logs, insert rows)
- **C:** Backfill from order_status_history → infer which notifications would have been sent

**My recommendation: A.** PSR-3 logs are timestamped in Sentry / log aggregator — that's the existing source of truth for pre-M3.2.X.4 events. Backfilling synthetic rows risks "fake" data that misleads triage. Starting fresh from the deploy date is cleaner; old triage continues to use logs.

### Decision M3.2.X.4-Q-FilterSet: admin endpoint filters

Which query parameters does `GET /v3/admin/notification-logs` accept?

- **A:** `order_id`, `template`, `status`, `recipient`, `since` (ISO datetime), `until`, `limit` (default 20, max 100), `offset`
- **B:** A plus full-text search on `error_message` via `?q=`
- **C:** A plus `error_kind` filter for failed sends triage

**My recommendation: A + the `error_kind` filter from C.** The combined set covers all expected triage queries:
- "Why didn't order #42 get its emails?" → `?order_id=42`
- "All bounced emails today" → `?status=failed&since=...`
- "All failures by transport error" → `?status=failed&error_kind=transport`
- "Customer's email history" → `?recipient=alice@...`

`?q=` full-text on error_message is rarely useful for ops (errors are templated) and adds complexity for one extra index.

## 6. Risks

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| Notification log write failure blocks primary action | Low | **CRITICAL** | `NotificationLogRepository::save()` wrapped in try/catch INSIDE `safeSend`; any failure → log to PSR-3 + continue. Existing safeSend architecture is the right place; preserve it. Sub-phase B explicit test for this. |
| Database write contention slows email sending | Low | Medium | Single INSERT per send is cheap. PostgreSQL connection already open per request. Async queue not introduced (kept fire-and-forget; aligned with M3.1.7-H "Idempotency" docblock). |
| Schema migration breaks on existing data | Low | Low | New table; no data migration; pure CREATE TABLE. Roll back via DROP TABLE. |
| Admin endpoint exposes PII inappropriately | Low | High | recipient email + error_message are admin-only; route under `/v3/admin` group with both AuthMiddleware + AdminAuthMiddleware. Sub-phase C 403 regression test verifies. |
| Index choices wrong; queries slow | Low | Low | Six indexes cover all expected filter combinations; composite (status, sent_at) covers the hot "failures in last 24h" query. Refine post-deploy if a real query pattern emerges. |
| Duplicate notification_log rows from concurrent sends | Low | Low | Each `safeSend()` call writes exactly one row; no idempotency key in M3.2.X.4 (deferred to a future phase if needed). |
| `raw_event JSONB` column wasted if webhook never lands | Low | Low | JSONB null is cheap; pre-allocating the column avoids a future migration. Q-RawEvent=A locked rationale. |
| Backfill questions surface from operator | Medium | Low | Q-Backfill=A locked: no backfill; PSR-3 logs remain the pre-M3.2.X.4 source. Document this clearly in the closure runbook. |
| Estimated effort balloons beyond 3 days | Low | Low | Pre-flight inspection confirmed all assets exist (entity pattern, repo pattern, admin endpoint pattern, audit emission pattern); mechanical work. |

## 7. What is NOT in M3.2.X.4

- ZeptoMail webhook receiver for bounce / complaint events (deferred; column `raw_event` pre-allocated)
- Async notification queue / retry mechanism (deferred; fire-and-forget preserved)
- Apps/web or apps/portal admin UI consuming the endpoint (consumer-side work; out of scope)
- Apps/mobile changes (no mobile interaction with notification logs)
- Idempotency keys to deduplicate sends (deferred; M3.1.7-H "Future" note remains the design rationale)
- Data retention policy / auto-purge (Q-Retention=A; defer until volume warrants)
- Backfilling historical notifications from PSR-3 logs (Q-Backfill=A)
- Per-locale logging (just stores the template enum value; locale resolution happens in renderer)
- Email open / click tracking (not in scope; requires pixel + click-tracking webhook)
- Re-send / retry endpoint for failed sends (operator manually re-triggers via existing lifecycle methods)
