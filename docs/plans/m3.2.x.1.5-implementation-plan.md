## 0. Why this is M3.2.X.1.5 (a numbered insertion between X.1 and X.2)

This phase fixes a real correctness gap discovered during M3.2.X.1-C
implementation: the M3.1.5 catalog migration shipped the
**infrastructure** (transforms registry, feature flags table, the
MobileNetworkAdapter itself) but stopped short of migrating
**call sites** to use the adapter.

The practical consequence: 14 of the 16 catalog read endpoints in
`packages/api-client/src/feature-flags.ts` have `target='new'` set,
but the call sites that invoke them call `networkService.post_request`
directly — never consulting the flag — and therefore continue to hit
legacy URLs in production. The flags work in principle but have no
observable effect today.

M3.2.X.1 partially addressed this for `best_sellers` and
`best_sellers_listing` (4 call sites migrated). M3.2.X.1.5 finishes
the job for the rest of catalog reads, so subsequent Stream X phases
(M3.2.X.2 featured-vendors, etc.) operate against an actually-flag-
aware mobile.

This is a **prerequisite** for the rest of Stream X. Inserting as
M3.2.X.1.5 keeps the numbering clear about its dependency.

## 3. Decisions to lock IN this approval

### Decision M3.2.X.1.5-Q-Scope: scope of the migration

**The question:** Should this phase migrate ONLY catalog reads (~20-25 call sites) or also tackle the broader gap (~95 sites total)?

- **A:** Only catalog reads currently in `feature-flags.ts` (this plan as written)
- **B:** Catalog reads + the 5 catalog mutations (addWishlist, removeWishlist, addToCart, etc.) — adds ~1-2 days
- **C:** All ~95 sites — adds ~5-7 days; broad surface

**My recommendation: A.** Stream X is about backend completion + flag-driven mobile read flips. Mutations are a Mobile Stream Z concern. Going broader risks blowing up the Stream X timeline for marginal short-term benefit.

### Decision M3.2.X.1.5-Q-Verify: testing strategy

**The question:** How aggressively should we verify each migration?

- **A:** Type-check + mobile tsc baseline preservation per sub-phase, plus Playwright mobile e2e for the migrated pages where coverage exists
- **B:** A + add Playwright e2e coverage for pages we migrate that don't yet have it (adds ~1 day)
- **C:** A + new mobile e2e coverage + manual smoke test on real device per sub-phase (~2 days)

**My recommendation: A.** The migration is mechanical (drop-in signature swap). Type-check + tsc baseline catches structural breakage. Existing Playwright mobile e2e (12 tests) provides smoke coverage for `/`, `/intro`, `/login`, `/register`, `/my-orders` — none of the catalog pages have e2e yet, and adding it is M3.2.0-B's job/scope-creep. Defer e2e additions to dedicated phases.

### Decision M3.2.X.1.5-Q-Order: sub-phase order

**The question:** The sub-phase ledger lists A→B→C→D→E. Should we instead migrate by call-volume priority?

- **A:** Order as written (-A starts with home.page where the user actually lands first; lowest blast-radius surface)
- **B:** Order by call-count (chat.service.ts has 10 calls but it's non-catalog and not in this phase — irrelevant; for catalog scope, order by file is fine)
- **C:** Risky-first (single-product migration first since it has path params and depends on adapter's :id substitution)

**My recommendation: A.** home.page is what users see first; if anything regresses there it's most visible and we catch it fastest.

### Decision M3.2.X.1.5-Q-Shadow: per-sub-phase shadow window?

**The question:** Should each sub-phase get its own 7-day shadow window before the next begins?

- **A:** No — these are drop-in signature swaps; the FEATURE FLAG remains `target='new'` (already shadowed during M3.1.5); migrating the call site just enables the flag to take effect. No new shadow window needed; just verify type-check passes.
- **B:** Yes — each sub-phase ends with a 7-day operator window before proceeding. Adds ~4 weeks elapsed time to the phase.
- **C:** One shadow window at the end covering all sub-phases together — ~7 days operator window after E lands.

**My recommendation: A.** The feature flags are already in `target='new'` and have been since M3.1.5. The endpoints work; we're just unbreaking the wiring. New shadow windows would be redundant. Operators can still validate informally before/after each sub-phase via app smoke test.

## 5. Risks specific to M3.2.X.1.5

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| A transform missing for a route we activate | Medium | High | Each sub-phase reads transform registry first; if missing, defer to a supplementary sub-phase; type-check catches it at compile time |
| Path-param substitution edge case for `read_vendor` | Medium | Medium | Adapter has handled this for orders+auth flows; -C sub-phase explicitly verifies the substitution works |
| Behavior diff between legacy `customer/single_product` and v3 `/v3/products/:id` | Medium | Medium | M3.1.5 already shadowed + flipped these endpoints with `target='new'`; the call-site migration only enables the existing flag, doesn't change semantics |
| Hidden mutation calls misidentified as reads | Low | Low | Audit explicitly separates POST methods that legacy treats as reads (vs mutations); when in doubt, defer to next phase |
| Mobile bundle size increase from importing adapter everywhere | Low | Low | Tree-shaking + single shared instance via DI keeps overhead negligible |
