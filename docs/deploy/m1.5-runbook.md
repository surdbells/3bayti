# M1.5 Deployment Runbook

Step-by-step guide for taking the API from local-dev-only (state at end of
M1.4) to running at `https://api-v3.3bayti.ae` on DigitalOcean App Platform.

This is a one-time setup. After this, deploys happen automatically on every
push to `main` (assuming the optional CI deploy workflow is enabled — see
section "Automatic deploys" near the end).

---

## What you're about to set up

| Component | Service | Tier (initial) | Cost (est) |
|---|---|---|---|
| API service | DigitalOcean App Platform | basic-xxs | $5/mo |
| PostgreSQL 16 | DO Managed Database | db-s-1vcpu-1gb | $15/mo |
| Redis | Upstash | Free tier | $0 |
| SMS OTP | MessageCentral CPaaS | Per-message pricing | ~$0.02/SMS |
| Email | ZeptoMail | Free tier (10k/month) | $0 |
| Object storage | Cloudflare R2 | 10 GB free / class-A free | $0 to start |
| DNS | Whoever manages 3bayti.ae | n/a | n/a |

**Initial monthly cost: ~$20-25** for staging tier. Production scaling raises
this — most likely the API tier (basic-xs at $12/mo) and Postgres tier
(db-s-2vcpu-2gb production at $50/mo).

## Prerequisites — before starting this runbook

Make sure you have:

- Access to the DNS records for `3bayti.ae` (Cloudflare or wherever it lives)
- A credit card for DigitalOcean billing
- ~2 hours of uninterrupted time for the first run-through
- The `doctl` CLI installed locally — `brew install doctl` on macOS, or
  follow https://docs.digitalocean.com/reference/doctl/how-to/install/

## Phase 1 — Account setup (~30 min)

These can be done in parallel.

### 1.1 DigitalOcean

1. Sign up at https://cloud.digitalocean.com/registrations/new
2. Verify email + add billing
3. Generate a Personal Access Token:
   - Go to API → Tokens → Generate New Token
   - Name: "3bayti deploy"
   - Scope: full read+write
   - **Save the token** — you can't view it again after closing the page
4. `doctl auth init` and paste the token

### 1.2 Upstash (Redis)

1. Sign up at https://console.upstash.com/login
2. Create a Redis database:
   - Name: `3bayti-redis`
   - Type: Regional (cheaper than Global; we don't need multi-region)
   - Region: `eu-west-1` (Ireland — closest to Frankfurt App Platform)
   - TLS: enabled
3. Copy these values from the database details page (you'll paste them
   into App Platform secrets later):
   - `Endpoint` (the `something.upstash.io` host)
   - `Port` (usually 6379)
   - `Password`

### 1.3 MessageCentral (production CPaaS)

1. Sign up at https://www.messagecentral.com/
2. Verify your business — they require KYC for SMS sending
3. Get UAE coverage approved (this can take 1-3 business days)
4. From the dashboard, note:
   - Customer ID
   - API Key
   - Account email
5. Configure an OTP message template (something like
   "Your 3bayti verification code is {OTP}. Valid for 5 minutes.")

### 1.4 ZeptoMail

(Required only for M3+ email features; can skip for M1.5 deploy.)

1. Sign up at https://www.zoho.com/zeptomail/
2. Add `3bayti.ae` as a sending domain
3. Add the SPF + DKIM + DMARC DNS records they show you (the runbook for DNS
   in section 1.6 covers how to add records)
4. Create a Mail Agent + API token

### 1.5 Cloudflare R2

(Required only for M2+ image features; can skip for M1.5.)

1. Cloudflare account (you probably already have one if 3bayti.ae is on CF)
2. R2 → Create bucket: `3bayti-uploads`
3. Manage R2 API Tokens → Create API token with read+write to that bucket
4. Note the `Account ID` shown on the R2 page

### 1.6 DNS

You need to add ONE record for M1.5; you already have the others if your
existing site works.

For now, just record the existing setup (we'll add the api-v3 record after
DigitalOcean assigns us an App Platform URL in Phase 3):

```
3bayti.ae           A or CNAME (existing — points at staging.3bayti.ae infra)
staging.3bayti.ae   A or CNAME (existing)
```

After Phase 3 you'll add:
```
api-v3.3bayti.ae    CNAME → 3bayti-api-XXXX.ondigitalocean.app
```

## Phase 2 — Generate secrets locally (~5 min)

Generate the cryptographic values App Platform needs.

```bash
# JWT signing key (64 bytes hex = 128 chars)
php -r "echo bin2hex(random_bytes(64)) . PHP_EOL;"

# APP_SECRET (32 bytes hex = 64 chars)
php -r "echo bin2hex(random_bytes(32)) . PHP_EOL;"
```

**Save these somewhere private** — you'll paste them into App Platform.
A password manager (1Password, Bitwarden) is the right place.

## Phase 3 — First deploy (~30 min, but counts deploy time)

### 3.1 Validate the spec

```bash
cd /path/to/3bayti
doctl apps spec validate apps/api/.do/app.yaml
```

If this errors, fix the spec before continuing. (Most likely: typo in env
var name, or a referenced GitHub repo / branch DigitalOcean can't access.)

### 3.2 Create the app

```bash
doctl apps create --spec apps/api/.do/app.yaml
```

This:
- Creates the App Platform application
- Provisions the Postgres database (this takes ~5 min)
- Builds the Dockerfile (this takes ~3-5 min the first time; subsequent
  builds use cached layers and are faster)
- Runs the predeploy migration job (will fail this first time — see 3.4)

The CLI prints an `App ID`; save it.

### 3.3 Get the App Platform URL

```bash
doctl apps get <app-id>
```

The output includes a `default_ingress` field like
`https://3bayti-api-abc12.ondigitalocean.app`. Copy this.

### 3.4 Paste secrets into App Platform

The first deploy will fail because the placeholders (`PASTE_AT_DEPLOY_TIME`)
are not real values. Fix this via the dashboard:

1. Go to https://cloud.digitalocean.com/apps
2. Click into `3bayti-api`
3. Settings → App-Level Environment Variables (or Service-level for the api
   component — check both spots; the spec puts most at service level)
4. For each secret marked `PASTE_AT_DEPLOY_TIME` in `apps/api/.do/app.yaml`,
   paste the real value:

   | Variable | Value to paste |
   |---|---|
   | `APP_SECRET` | The 32-byte hex from Phase 2 |
   | `JWT_SECRET` | The 64-byte hex from Phase 2 |
   | `MESSAGECENTRAL_CUSTOMER_ID` | From section 1.3 |
   | `MESSAGECENTRAL_KEY` | From section 1.3 |
   | `MESSAGECENTRAL_EMAIL` | From section 1.3 |
   | `REDIS_HOST` | From section 1.2 (the `.upstash.io` host) |
   | `REDIS_PASSWORD` | From section 1.2 |

5. Click "Save" — this triggers a new deployment automatically

6. Also set the same `JWT_SECRET` + DB secrets on the **migrate job**
   (App Platform jobs don't share env with sibling services). Look for a
   "Job-Level Environment Variables" section.

### 3.5 Watch the deploy

Either via dashboard (real-time logs) or CLI:

```bash
doctl apps logs <app-id> --follow
```

What you should see:
- Build phase: composer install runs, Dockerfile builds successfully
- Predeploy phase: `[migrate] starting migration runner` → `[migrate]
  database reachable` → migration applies → `[migrate] migrations applied
  successfully`
- Service start: supervisord starts nginx + php-fpm; nginx logs show first
  health-check request from App Platform

If predeploy fails, check the migrate job logs specifically:
```bash
doctl apps logs <app-id> --type=job --component=migrate
```

### 3.6 Verify with smoke test

Once the deploy is "Active":

```bash
./apps/api/scripts/smoke.sh https://3bayti-api-abc12.ondigitalocean.app
```

You should see steps 1-3 pass, then step 4 (OTP confirm) gracefully skip
because real MessageCentral won't accept code `000000`. That's expected.

If steps 1-3 fail, **stop and investigate** — the app isn't actually working
even though App Platform might mark it "Active".

### 3.7 Add custom domain DNS

In whoever manages your DNS (Cloudflare etc.):

```
Type:   CNAME
Name:   api-v3
Target: 3bayti-api-abc12.ondigitalocean.app
TTL:    Auto / 300
```

If using Cloudflare:
- Set the proxy mode to "DNS only" (gray cloud) at first
- Wait until App Platform shows the cert is valid (~5-15 min after DNS
  propagates)
- Optionally switch to "Proxied" (orange cloud) afterward for CF's CDN +
  WAF benefits, BUT make sure App Platform's edge isn't being double-proxied
  (test smoke.sh after the switch)

App Platform polls DNS every minute or so; the dashboard's domain section
will eventually show "Active" with a green checkmark.

### 3.8 Verify production URL

```bash
./apps/api/scripts/smoke.sh https://api-v3.3bayti.ae
```

Same expected output as 3.6 — steps 1-3 pass, OTP step gracefully skips.

## Phase 4 — Real OTP test with a real phone (~10 min)

Optional but recommended. Verifies MessageCentral integration works end-to-end.

1. Pick a phone number you control. Use the real E.164 format (`+971...`).
2. Make sure it's NOT already in the DB (use a fresh email too).
3. Use curl to register manually:

```bash
curl -X POST https://api-v3.3bayti.ae/v3/auth/register \
  -H "Content-Type: application/json" \
  -d '{
    "email": "your-real-email@example.com",
    "phone": "+971XXXXXXXXX",
    "password": "TestPassword123!",
    "country_code": "AE"
  }'
```

Expected: 201 with a `verification_id`. Save the verification_id.

4. **Wait for the SMS.** Should arrive within ~10 seconds. If not, check the
   MessageCentral dashboard for delivery logs.

5. Confirm with the real code:

```bash
curl -X POST https://api-v3.3bayti.ae/v3/auth/confirm \
  -H "Content-Type: application/json" \
  -d '{
    "verification_id": "<the verification_id from step 3>",
    "code": "<the 6 digits you received>"
  }'
```

Expected: 200 with full token pair.

6. If you get `OTP_VERIFICATION_FAILED`, the most common cause is that the
   code has already been used or expired (5 min limit). Re-register with a
   different email and try again.

If step 4 never delivers an SMS, the issue is one of:
- MessageCentral coverage (your number may be in a region they don't serve
  yet)
- Country code mismatch (we strip the leading `+971` but pass `971` as the
  countryCode param; verify your MessageCentral account allows UAE)
- Account funding (some MessageCentral accounts require pre-payment)

## Phase 5 — Enable automatic deploys (optional, ~10 min)

By default, every push to `main` triggers an App Platform deploy because we
set `deploy_on_push: true` in `app.yaml`. So this is already on.

To DISABLE automatic deploys (e.g., if you want manual gating):
1. Edit `apps/api/.do/app.yaml`
2. Change `deploy_on_push: true` to `deploy_on_push: false`
3. `doctl apps update <app-id> --spec apps/api/.do/app.yaml`

Manual deploys then go via:
```bash
doctl apps create-deployment <app-id>
```

## Rollback procedure

If a deploy goes bad (smoke test fails, app crashes, migrations leave bad
state):

### Option A — App Platform's UI rollback

Apps → 3bayti-api → Deployments → click the previous good deployment →
"Rollback to this deployment". App Platform redeploys the old image; the
process takes ~3 min. The PRE_DEPLOY job runs again, which means migrations
run again — be aware that migrations are typically forward-only, so a
rollback to a deploy whose migration set is OLDER than the current DB state
just no-ops on migrations (Doctrine sees they're already applied).

### Option B — Revert + push

```bash
git revert <bad commit>
git push
```

App Platform sees the new commit and deploys it.

### Option C — Database restore (worst case)

If a migration corrupted data:

1. Apps → 3bayti-api → Database (the attached Postgres) → Backups
2. Pick a point-in-time snapshot from BEFORE the bad migration
3. "Restore from this backup" — creates a new database
4. Update `app.yaml` to point at the restored DB (or use DO's "promote
   restored DB to primary" feature)
5. Re-deploy

PITR retention is 7 days on production tier, fewer on development tier.

## Operational checklist (post-deploy)

After the first successful deploy, work through these:

- [ ] Smoke test passes against `https://api-v3.3bayti.ae`
- [ ] Real-phone OTP flow works (Phase 4)
- [ ] Cloudflare proxy enabled (optional but recommended)
- [ ] Sentry DSN configured (optional, for error tracking)
- [ ] Set up DigitalOcean monitoring alerts:
  - High CPU sustained
  - High memory sustained
  - 5xx response rate elevated
  - Deploy failures
- [ ] Schedule manual smoke-test runs in CI weekly (catches infrastructure
      regressions even when no code changes)
- [ ] Document the App ID, App Platform URL, and any operational details
      in your team's internal runbook (team-internal — don't commit to repo)

## Troubleshooting

### Deploy fails at "build" phase

Almost always a Dockerfile issue. Check the build logs in the App Platform
dashboard. Common causes:
- A `composer install` failure (network blip, or a private package that
  needs auth that App Platform doesn't have)
- Missing system package — add to the `apk add` line in `Dockerfile`

### Deploy fails at "predeploy" phase (migrate job)

Check job logs:
```bash
doctl apps logs <app-id> --type=job --component=migrate --follow
```

Most common: DB connection refused. Verify the postgres component is
attached to the migrate job (env vars include `${db.HOSTNAME}`).

### App is "Active" but smoke test fails

Most common: secrets not actually set. The deploy succeeds because the
container started, but at the first /v3/auth/register call the code throws
because (e.g.) `JWT_SECRET` is the literal string `PASTE_AT_DEPLOY_TIME`.

Look at app logs:
```bash
doctl apps logs <app-id> --type=run --follow
```

PHP errors will be in there.

### Smoke test passes for /health but fails for /auth

Database migrations didn't run, or ran on the wrong DB. Verify by:
```bash
doctl databases connection <db-id> --format URI
psql "<that uri>" -c "SELECT * FROM doctrine_migration_versions;"
```

You should see one row per migration applied (just M1.1's
`Version20260507000001` for now).
