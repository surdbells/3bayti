# M1.5 Deployment Runbook — aaPanel / Apache (Real-World)

Step-by-step deployment of the API to an existing aaPanel-managed Ubuntu
server, alongside a legacy backend on the same box. This is the deploy
path actually used for `https://api-v3.3bayti.ae` as of May 2026.

For the alternate DigitalOcean App Platform path, see
[m1.5-runbook.md](./m1.5-runbook.md). Either path produces an
equivalently functional /v3 API; the choice is operational
(infrastructure-as-managed vs server-as-managed).

---

## Why this runbook exists separately

The DO App Platform runbook assumes a clean container-based deploy. The
aaPanel path has different constraints:

- aaPanel ships its own PHP build (with non-standard module paths)
- PHP CLI is more strictly hardened than FPM (`disable_functions`)
- aaPanel injects `.user.ini` files with `open_basedir` restrictions
- aaPanel's Apache vhost templates need customization for a Slim app
- aaPanel sets the immutable file attribute on configs it manages

This runbook captures the workarounds we found through real deployment.

---

## Prerequisites

- Ubuntu 22.04+ (we tested on 24.04 LTS)
- aaPanel 7.x or compatible
- Apache (running, NOT nginx — even if aaPanel has nginx config files
  lying around, they're typically stale leftovers; check `ss -tlnp`)
- PHP 8.3 installed via aaPanel
- Postgres 18 installed via aaPanel plugin (or apt — the runbook works
  for either, as long as `psql` is in PATH or you use the full binary
  path)
- Composer 2.7+ available (aaPanel ships an older one — `composer
  self-update` brings it current)
- `git`, `mkdir`, `chown`, `chmod` (standard tools)
- DNS record `api-v3.3bayti.ae` → server IP (NOT proxied, gray cloud
  on Cloudflare)

## Phase 1 — PHP CLI fixes

aaPanel's PHP CLI configuration is more hardened than FPM:

- `disable_functions` blocks `putenv` and `proc_open` in CLI but not FPM
- Some extensions configured in `php.ini` (FPM) but not `php-cli.ini`
- Phantom `extension=` lines for non-existent .so files generate warnings

Run these checks:

```bash
# Check what's available
ls /www/server/php/83/lib/php/extensions/no-debug-non-zts-20230831/

# Check disable_functions difference between FPM and CLI
grep -E "^disable_functions" /www/server/php/83/etc/php.ini
grep -E "^disable_functions" /www/server/php/83/etc/php-cli.ini
```

### Fix CLI: add `pdo_pgsql` extension (if missing)

```bash
INI="/www/server/php/83/etc/php-cli.ini"
cp -p "$INI" "${INI}.bak.$(date +%Y%m%d_%H%M%S)"

cat <<'EOF' >> "$INI"

; --- Added for /v3 API: enable pdo_pgsql in CLI ---
extension = /www/server/php/83/lib/php/extensions/no-debug-non-zts-20230831/pdo_pgsql.so
EOF
```

### Fix CLI: add `igbinary` + `redis` (load order matters: igbinary first)

```bash
cat <<'EOF' >> "$INI"

; --- Added for /v3 API: igbinary + redis (igbinary MUST be first) ---
extension = /www/server/php/83/lib/php/extensions/no-debug-non-zts-20230831/igbinary.so
extension = /www/server/php/83/lib/php/extensions/no-debug-non-zts-20230831/redis.so
EOF
```

### Fix CLI: re-enable `proc_open` and `putenv` in disable_functions

Composer requires both. The FPM config already allows them (verifies
this is consistent with aaPanel's own posture).

```bash
sed -i 's/,putenv,/,/g; s/,proc_open,/,/g' "$INI"
```

### Verify

```bash
php -m | grep -E "^(pdo_pgsql|igbinary|redis)$"
# Should output all three, one per line.
# Some warnings about curl/gd/gettext/exif/mysqli are cosmetic and
# can be ignored for now (cleanup item for M5 hardening).
```

## Phase 2 — PostgreSQL hardening

aaPanel's Postgres install ships with `trust` authentication for ALL
local connections. Anyone on the box can connect as the postgres
superuser without a password. We harden this before going to production.

### Set a password for `postgres` superuser

```bash
POSTGRES_PASSWORD="$(openssl rand -base64 24)"
echo "POSTGRES SUPERUSER PASSWORD (save to your password manager):"
echo "  $POSTGRES_PASSWORD"

sudo -u postgres /www/server/pgsql/bin/psql -d postgres <<SQL
ALTER ROLE postgres WITH PASSWORD '${POSTGRES_PASSWORD}';
SQL
```

### Switch `pg_hba.conf` from `trust` to `scram-sha-256`

```bash
HBA="/www/server/pgsql/data/pg_hba.conf"
cp -p "$HBA" "${HBA}.bak.$(date +%Y%m%d_%H%M%S)"

# Keep header comments, replace active rules
{
    grep -E "^#|^$" "$HBA"
    cat <<'EOF'

# Hardened auth — replaced trust with scram-sha-256
local   all             all                                     peer
host    all             all             127.0.0.1/32            scram-sha-256
host    all             all             ::1/128                 scram-sha-256
local   replication     all                                     peer
host    replication     all             127.0.0.1/32            trust
host    replication     all             ::1/128                 trust
EOF
} > "${HBA}.new"

mv "${HBA}.new" "$HBA"
chown postgres:postgres "$HBA"
chmod 600 "$HBA"

# Reload Postgres (no restart — won't drop existing connections)
sudo -u postgres /www/server/pgsql/bin/pg_ctl reload -D /www/server/pgsql/data
```

### Create the application database + role

```bash
BAYTI_API_PASSWORD="$(openssl rand -base64 24)"
echo "bayti_api PASSWORD (save to password manager + .env):"
echo "  $BAYTI_API_PASSWORD"

sudo -u postgres /www/server/pgsql/bin/psql -d postgres <<SQL
CREATE ROLE bayti_api WITH LOGIN PASSWORD '${BAYTI_API_PASSWORD}';
CREATE DATABASE bayti_v3
    OWNER = bayti_api
    ENCODING = 'UTF8'
    TEMPLATE = template0
    LC_COLLATE = 'en_US.utf8'
    LC_CTYPE = 'en_US.utf8';
ALTER DATABASE bayti_v3 SET search_path TO public;
SQL
```

### Verify role isolation

```bash
# bayti_api can connect to bayti_v3
/www/server/pgsql/bin/psql -h 127.0.0.1 -U bayti_api -d bayti_v3 \
    -c "SELECT current_user, current_database();"

# bayti_api cannot connect to other databases
/www/server/pgsql/bin/psql -h 127.0.0.1 -U bayti_api -d postgres \
    -c "SELECT 1;" 2>&1 | grep -q "permission denied" && \
    echo "✓ isolation working" || echo "✗ check auth"
```

## Phase 3 — Clone repo and install

### Generate SSH deploy key

```bash
ssh-keygen -t ed25519 \
    -C "3bayti-deploy@$(hostname)" \
    -f /root/.ssh/3bayti_deploy \
    -N ""

cat /root/.ssh/3bayti_deploy.pub
# Copy this output and add as a deploy key in GitHub:
# https://github.com/<user>/<repo>/settings/keys
# Allow write access: NO (we only pull from this box)
```

### Configure SSH to use this key for github.com

```bash
cat >> /root/.ssh/config <<'EOF'

# 3bayti deploy key
Host github.com
    HostName github.com
    User git
    IdentityFile /root/.ssh/3bayti_deploy
    IdentitiesOnly yes
EOF
chmod 600 /root/.ssh/config

# Verify
ssh -T -i /root/.ssh/3bayti_deploy -o StrictHostKeyChecking=accept-new git@github.com
# Expected: "Hi <user>/<repo>! You've successfully authenticated..."
```

### Clone

```bash
git clone --depth 1 git@github.com:surdbells/3bayti.git /www/wwwroot/3bayti
```

### Install PHP dependencies

```bash
cd /www/wwwroot/3bayti/apps/api
composer self-update --2  # ensure modern composer

composer install \
    --no-dev \
    --optimize-autoloader \
    --no-interaction \
    --no-progress \
    --prefer-dist
```

### Configure `.env`

```bash
cd /www/wwwroot/3bayti/apps/api
cp .env.example .env
chmod 600 .env
chown www:www .env
nano .env
```

Fill in:

| Var | Value |
|---|---|
| `APP_ENV` | `prod` |
| `APP_VERSION` | git short-sha (e.g. `bdb6919`) |
| `APP_URL` | `https://api-v3.3bayti.ae` |
| `APP_SECRET` | `bin2hex(random_bytes(32))` (64 hex chars) |
| `DB_HOST` | `127.0.0.1` |
| `DB_PORT` | `5432` |
| `DB_DATABASE` | `bayti_v3` |
| `DB_USERNAME` | `bayti_api` |
| `DB_PASSWORD` | from Phase 2 |
| `DB_SSLMODE` | `prefer` |
| `JWT_SECRET` | `bin2hex(random_bytes(64))` (128 hex chars) |
| `MESSAGECENTRAL_*` | from your MessageCentral dashboard |

Verify lengths:

```bash
grep -E "^(APP_SECRET|JWT_SECRET)=" .env | while IFS='=' read -r k v; do
    echo "$k: ${#v} chars"
done
# Expected: APP_SECRET 64, JWT_SECRET 128
```

### Run migration

```bash
php bin/migrate.php --dry-run
# Expect: APP_ENV=prod, database reachable, "1 migrations executed (dry-run)"

php bin/migrate.php
# Expect: same but real, no (dry-run) qualifier
# Followed by: "generated N proxy classes in /www/wwwroot/.../var/cache/doctrine/proxies"
```

## Phase 4 — Apache vhost via aaPanel UI

1. **Website** → **Add Site**
2. Domain: `api-v3.3bayti.ae`
3. **Root directory** (Option B — direct deep path):
   `/www/wwwroot/3bayti/apps/api/public`
4. PHP version: PHP-83
5. Database: None (we're managing Postgres outside aaPanel)
6. SSL: skip for now (Phase 6)
7. Click **Submit**

aaPanel writes a vhost file to:
- `/www/server/panel/vhost/apache/api-v3.3bayti.ae.conf`

It also injects an immutable `.user.ini` at:
- `/www/wwwroot/3bayti/apps/api/public/.user.ini`

with content:
```
open_basedir=/www/wwwroot/3bayti/apps/api/public/:/tmp/
```

### Fix the open_basedir restriction (CRITICAL)

The default `.user.ini` only allows `public/` and `/tmp/`. PHP can't
even reach `vendor/autoload.php` (one level up). We expand it:

```bash
USERINI="/www/wwwroot/3bayti/apps/api/public/.user.ini"
chattr -i "$USERINI"        # remove immutable flag

cat > "$USERINI" <<'EOF'
; aaPanel-managed PHP config. Customised for 3bayti API:
; - Expand open_basedir to the full apps/api/ directory so vendor/,
;   src/, config/, var/, etc. are all readable.
open_basedir=/www/wwwroot/3bayti/apps/api/:/tmp/
EOF

chmod 644 "$USERINI"
chattr +i "$USERINI"        # restore immutable flag
```

### Apply the .htaccess from repo

The repo ships `apps/api/public/.htaccess` with Slim's rewrite rules.
After git clone it should already be on disk. Verify:

```bash
ls -la /www/wwwroot/3bayti/apps/api/public/.htaccess
# Should show ~800 bytes, owned root:root (will run as www at request time)
```

If somehow missing, `git checkout apps/api/public/.htaccess` from the
repo restores it.

## Phase 6 — TLS via aaPanel (Let's Encrypt)

1. **Website** → click `api-v3.3bayti.ae`
2. **SSL** tab
3. Choose **Let's Encrypt** (or "Apply Free Certificate")
4. Domain pre-fills `api-v3.3bayti.ae`
5. Click **Apply**

After ~30 seconds, aaPanel:
- Drops cert files at `/www/server/panel/vhost/cert/api-v3.3bayti.ae/`
- Adds `<VirtualHost *:443>` block to the vhost file
- Toggles HTTP→HTTPS redirect (recommended: enable this)

### Verify

```bash
curl -i https://api-v3.3bayti.ae/v3/health
# Expected: HTTP/2 200, same JSON body

# Check cert details
echo | openssl s_client -servername api-v3.3bayti.ae \
    -connect api-v3.3bayti.ae:443 2>/dev/null \
    | openssl x509 -noout -issuer -subject -dates
# Expected: issuer = Let's Encrypt, subject CN = api-v3.3bayti.ae,
# notAfter ~90 days out
```

## Operational notes for this deploy

### Future deploys

The auto-deploy script `/usr/local/bin/3bayti-deploy.sh` handles
this end-to-end. Triggered by GitHub Actions over SSH on every push
to main that passes CI. The script:

1. `cd /www/wwwroot/3bayti && git fetch + reset --hard origin/main`
2. `cd apps/api && composer install --no-dev --optimize-autoloader`
3. **Clear PHP-DI compilation cache** (`rm -rf var/cache/di/*`) —
   M1.6.1.A discovered this. PHP-DI compiles the container in prod
   for performance; the compiled cache is keyed off the SOURCE
   `di.php` at compile time. Adding new bindings without clearing
   the cache means the compiled container stays out of date and new
   bindings silently don't resolve. Symptom: a new service registered
   in `di.php` returns null when fetched from the container.
4. `php bin/migrate.php` (idempotent — no-ops if no new migrations
   + regenerates Doctrine proxies into `var/cache/doctrine/proxies/`)
5. `sed APP_VERSION=<sha> /env` so `/v3/health` shows current commit
6. (No FPM reload needed — same socket, same code path; PHP picks
   up new files on next request because OPcache validates timestamps)

For manual triggering, see "workflow_dispatch" trigger in
`.github/workflows/api.yml` (M1.6.3.C). Or push any change matching
the path filter (`apps/api/**` or workflow file itself).

### M1.6.1.A — Redis on the box

Redis 7.x installed via aaPanel App Store. Running on
`127.0.0.1:6379`, no password (deferred to M1.6 followup —
defensible because bound to localhost only, but defense-in-depth
should add password before broader traffic).

App reads `REDIS_DSN` from `.env` to wire RedisKeyValueStore. Format:

  REDIS_DSN=redis://127.0.0.1:6379                     (no password)
  REDIS_DSN=redis://:password@127.0.0.1:6379           (with password)
  REDIS_DSN=redis://:password@127.0.0.1:6379/0         (with database)

Verify Redis is wired correctly via `/v3/health/ready`:

  $ curl -s https://api-v3.3bayti.ae/v3/health/ready
  { "checks": { "database": "ok", "redis": "ok" } }

If `redis` key is missing, the DI container fell back to
InMemoryKeyValueStore — usually means REDIS_DSN env var isn't being
read or the DI cache is stale (clear `var/cache/di/*`).

### Things you'll forget after a few weeks

- aaPanel rewrites vhost configs when you change site settings via UI.
  The HTTP→HTTPS redirect block, DENY FILES rules, and PHP handler
  block are ALL aaPanel-managed. Don't hand-edit; use UI.
- aaPanel re-creates `.user.ini` if you change site PHP settings.
  Check `lsattr` and `cat` after any UI change to that site.
- Postgres 18's data lives at `/www/server/pgsql/data/`. NOT
  `/var/lib/postgresql/`. `pg_dump`, `pg_basebackup` etc need full
  path: `/www/server/pgsql/bin/pg_dump`.
- The PHP-FPM master PID can change if aaPanel reloads PHP. Don't
  hardcode it anywhere.

### Logs

- API errors: `/www/wwwlogs/api-v3.3bayti.ae-error_log`
- API access: `/www/wwwlogs/api-v3.3bayti.ae-access_log`
- PHP-FPM: `/www/server/php/83/var/log/php-fpm.log`
- Postgres: `/www/server/pgsql/data/log/postgresql-*.log`

### Cleanup items deferred to M1.6 hardening

1. Phantom extension warnings in `php-cli.ini` and `php.ini`
   (curl/gd/gettext/exif/mysqli `extension=` lines for built-ins)
2. SSL cipher hardening (aaPanel's auto-config includes weak ciphers)
3. `composer.lock` not committed in repo (CI uses dependency
   resolution each run instead of locked deps)
4. /v3 sharing legacy FPM pool (could split if isolation needed)
5. Pool process recycle (legacy pool has Jan31 worker processes
   visible — `pm.max_requests` not set anywhere)
