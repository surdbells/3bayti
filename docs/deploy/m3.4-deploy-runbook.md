# 3bayti M3.3 / M3.4 — Production Deployment Runbook

**Date:** 2026-05-23
**Scope:** v3 API (aaPanel) · web (Cloudflare, staging.3bayti.ae) · portal (Cloudflare, app.3bayti.ae) · mobile
**Migrated data:** Products, Vendors, Users (confirmed in scope)

---

## Infrastructure summary (how this project actually deploys)

| Component | Host | Deploy mechanism |
|---|---|---|
| **v3 API** | aaPanel server (`/www/wwwroot/3bayti`) | **Automatic** — GitHub Actions SSHes in on push to `main`, runs `/usr/local/bin/3bayti-deploy.sh` (pull + composer + **`bin/migrate.php`** + cache clear). Gated by repo var `ENABLE_AUTO_DEPLOY=true`. |
| **Web storefront** | Cloudflare Workers | **Automatic** — `web.yml` deploy job runs `wrangler deploy` on push to `main`. |
| **Portal** | Cloudflare | **Manual** — `portal.yml` only builds (hosting was TBD). Deploy is a manual `wrangler pages deploy`. |
| **Mobile** | App Store / Play Store | No release needed this cycle (API backward-compatible). |

**The database migration runs itself.** Once the migration file is on `main` and `ENABLE_AUTO_DEPLOY=true`, the aaPanel deploy script applies it via `bin/migrate.php`. There is no manual `doctl`, no DigitalOcean App Platform, no pre-deploy job.

## Schema changes in this release

Migration: `apps/api/migrations/Version20260523000001.php` (already on `main`, commit `c2de697`).

| Object | Type | Impact |
|---|---|---|
| `vendors.notification_prefs` | ADD COLUMN JSONB NULL | Additive (M3.4-B) |
| `promo_codes.vendor_id` | ADD COLUMN BIGINT NULL | Additive (M3.3.1-F vendor coupons) |
| `support_tickets` | CREATE TABLE | New (M3.4-G) |
| `support_ticket_messages` | CREATE TABLE | New (M3.4-G, FK CASCADE) |
| `product_collections` | CREATE TABLE | New (M3.4-H, unique slug) |

All additive. Zero existing rows modified. Safe on live DB. `down()` is fully reversible.

- [ ] `git log origin/main --oneline -1` shows `c2de697` (or later) — migration is on `main`
- [ ] Repo var `ENABLE_AUTO_DEPLOY` is `true` (GitHub → Settings → Secrets and variables → Actions → Variables). **If this is not `true`, the API will NOT deploy or migrate.**
- [ ] Required deploy secrets exist: `DEPLOY_SSH_KEY`, `DEPLOY_HOST`, `DEPLOY_USER` (and optionally `API_SMOKE_URL`)
- [ ] Cloudflare secrets exist for web auto-deploy: `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID`
- [ ] Database backup taken (aaPanel → Databases → backup, or `pg_dump` — see Step 1)
- [ ] Team notified (portal has a ~5 min window during DNS cut to app.3bayti.ae)

## Step 1 — Back up the database (5 min)

Even though the migration is additive and reversible, take a backup first.

On the aaPanel server:

```bash
# aaPanel: Databases → select 3bayti DB → Backup
# OR via CLI on the server:
pg_dump -U 3bayti -h 127.0.0.1 -d 3bayti -F c \
  -f /www/backup/pre-m34-deploy-$(date +%Y%m%d).dump
```

Verify the dump file exists and is non-empty:
```bash
ls -lh /www/backup/pre-m34-deploy-*.dump
```

## Step 2 — Add app.3bayti.ae to CORS on the server (3 min)

The deploy script does **not** touch env vars, so the portal's new domain must be added to `CORS_ALLOWED_ORIGINS` manually in the server's `.env`.

On the aaPanel server:

```bash
cd /www/wwwroot/3bayti/apps/api

# Inspect current value
grep CORS_ALLOWED_ORIGINS .env

# Edit .env — add https://app.3bayti.ae to the comma-separated list.
# Keep vendor.3bayti.ae for now (remove in the 7-day cleanup).
# Result should look like:
#   CORS_ALLOWED_ORIGINS=https://staging.3bayti.ae,https://3bayti.ae,https://app.3bayti.ae,https://vendor.3bayti.ae
nano .env
```

No FPM reload needed — the API reads `.env` per request. Verify after the deploy completes (Step 4) with the curl in Step 8.

> Do this **before or right after** triggering the deploy. It's independent of the migration; it only affects whether the portal's browser requests are allowed cross-origin.

## Step 3 — Trigger the API deploy (automatic on push)

The migration is already on `main`. If `ENABLE_AUTO_DEPLOY=true`, **the deploy already ran (or will run) automatically** on the push that landed `c2de697`.

To trigger a fresh deploy manually (e.g. if auto-deploy was off and you just enabled it):

```bash
# Option A — re-run via workflow_dispatch (GitHub UI):
#   Actions → "API — ..." workflow → Run workflow → branch: main

# Option B — push an empty commit to re-trigger:
git commit --allow-empty -m "chore: trigger API deploy for M3.4 migration"
git push origin main
```

What the deploy script does on the server (per `m1.5-runbook-aapanel.md`):
1. `git fetch + reset --hard origin/main`
2. `composer install --no-dev --optimize-autoloader`
3. Clear PHP-DI compiled cache (`rm -rf var/cache/di/*`) — required so new Ticket/Collection controllers + repositories resolve
4. **`php bin/migrate.php`** — applies `Version20260523000001` (idempotent)
5. Update `APP_VERSION` in `.env` to the new commit SHA

Watch the GitHub Actions run:
```bash
# GitHub → Actions → latest "API" run on main → "deploy" job logs
# Confirm the SSH "Trigger deploy" step succeeds (green).
```

## Step 4 — Verify the migration applied (3 min)

After the deploy job is green:

```bash
# API liveness + version
curl -s https://api-v3.3bayti.ae/v3/health | python3 -m json.tool
# Expected: {"status":"ok","version":"c2de697...","db":"connected"}
```

On the server, confirm the new schema objects exist:
```bash
cd /www/wwwroot/3bayti/apps/api

# Dry-run shows "Already at latest version" if migration applied:
php bin/migrate.php --dry-run

# Or query the DB directly:
psql -U 3bayti -h 127.0.0.1 -d 3bayti -c "
  SELECT table_name FROM information_schema.tables
  WHERE table_schema='public'
    AND table_name IN ('support_tickets','support_ticket_messages','product_collections');
"
# Expect 3 rows.

psql -U 3bayti -h 127.0.0.1 -d 3bayti -c "
  SELECT column_name FROM information_schema.columns
  WHERE table_name='vendors' AND column_name='notification_prefs';
"
# Expect 1 row.

psql -U 3bayti -h 127.0.0.1 -d 3bayti -c "
  SELECT column_name FROM information_schema.columns
  WHERE table_name='promo_codes' AND column_name='vendor_id';
"
# Expect 1 row.
```

**If the migration did not run:** the most likely cause is `ENABLE_AUTO_DEPLOY` not being `true`, so the deploy job was skipped. Set it and re-trigger (Step 3). As a last resort, SSH in and run `php bin/migrate.php` manually.

## Step 6 — Build + deploy the portal to Cloudflare (10 min)

Portal CI builds but does **not** deploy (hosting was TBD). Deploy it manually to Cloudflare Pages.

### 6a. Build (locally or pull the CI artifact)

```bash
cd apps/portal
pnpm install
pnpm run build --configuration production
# Output: dist/abayti/browser/  (must contain index.html)
ls dist/abayti/browser/index.html
```

### 6b. Deploy to Cloudflare Pages

```bash
# First time only — create the Pages project:
npx wrangler pages project create 3bayti-portal --production-branch main

# Every deploy:
npx wrangler pages deploy dist/abayti/browser \
  --project-name 3bayti-portal \
  --branch main
# Output: a *.pages.dev preview URL — test the portal there before DNS cut.
```

> Cloudflare credentials: the same `CLOUDFLARE_API_TOKEN` / `CLOUDFLARE_ACCOUNT_ID` used by web CI, or `wrangler login` interactively.

### 6c. (Recommended) Wire portal into CI for future deploys

`portal.yml` currently stops at build. To make portal deploys automatic like web, add a `deploy` job mirroring `web.yml` (guarded by `if: github.ref == 'refs/heads/main'`) that runs `wrangler pages deploy dist/abayti/browser --project-name 3bayti-portal`. Out of scope for this deploy; noted for follow-up.

## Rollback

**Migration didn't run / deploy job skipped:** set `ENABLE_AUTO_DEPLOY=true`, re-trigger (Step 3), or SSH in and `php bin/migrate.php`.

**API deployed but broken:**
```bash
# On the server — roll back code:
cd /www/wwwroot/3bayti
git reset --hard <previous-good-sha>
cd apps/api && composer install --no-dev --optimize-autoloader && rm -rf var/cache/di/*

# Roll back the migration (only if the new schema is the problem):
php bin/migrate.php prev      # or run the down() SQL from Version20260523000001.php
# down() is all DROP TABLE/COLUMN IF EXISTS — safe.
```

**Portal broken:** redeploy the previous build —
```bash
git checkout <previous-sha> -- apps/portal
cd apps/portal && pnpm run build --configuration production
npx wrangler pages deploy dist/abayti/browser --project-name 3bayti-portal --branch main
```

**DNS wrong:** revert the Cloudflare record; TTL ~300s, propagates in <5 min.
