# 3bayti M3.3 / M3.4 — Production Deployment Runbook

**Date:** 2026-05-23  
**Scope:** v3 API · web (staging.3bayti.ae) · portal (app.3bayti.ae) · mobile (Android + iOS)  
**Migrated data:** Products, Vendors, Users (confirmed in scope)  
**Total estimated time:** 90–120 min (most of it is App Platform build time)

---

## What is being deployed

| Component | Domain | Change summary |
|---|---|---|
| **v3 API** | `api-v3.3bayti.ae` | 30+ new endpoints; 5 new/altered schema objects; M3.4 migration |
| **Web storefront** | `staging.3bayti.ae` | No code changes — redeploy to pick up API env var updates |
| **Portal** | `app.3bayti.ae` ← **new domain** (was `vendor.3bayti.ae`) | Full v3 migration; zero legacy calls |
| **Mobile** | App Store / Play Store | No code changes in this release — only if API-breaking changes force it |

### Schema changes in this release (migration `Version20260523000001`)

| Object | Type | Impact |
|---|---|---|
| `vendors.notification_prefs` | ADD COLUMN JSONB NULL | Additive — no existing row affected |
| `promo_codes.vendor_id` | ADD COLUMN BIGINT NULL | Additive — vendor coupon scoping |
| `support_tickets` | CREATE TABLE | New |
| `support_ticket_messages` | CREATE TABLE | New |
| `product_collections` | CREATE TABLE | New |

**All changes are additive. Zero existing data is modified. Safe to run on live DB.**

## Step 1 — Take a database backup (5 min)

Do this before anything else. Even though the migration is additive and reversible, a backup is non-negotiable.

### 1a. Manual snapshot (DigitalOcean dashboard)

1. Go to **Databases** → select your Postgres instance
2. **Backups** → **Create Snapshot**
3. Name it: `pre-m34-deploy-YYYYMMDD`
4. Wait for "Snapshot complete" (usually 2–3 min)

### 1b. Verify via `doctl`

```bash
doctl databases list
# Note the DB ID
doctl databases backups list <DB_ID>
# Confirm the snapshot appears in the list
```

## Step 2 — Update API environment variables (3 min)

The API's CORS header needs `app.3bayti.ae` added (the portal's new domain).

### 2a. Via doctl

```bash
# Get the App ID
doctl apps list
# Look for: 3bayti-api
# Note the ID (format: xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx)

doctl apps update <APP_ID> --spec - << 'EOF'
# Paste ONLY the envs section change:
# Change CORS_ALLOWED_ORIGINS to include app.3bayti.ae
EOF
```

### 2b. Via dashboard (easier)

1. **Apps** → **3bayti-api** → **Settings** → **App Spec**
2. Find the `CORS_ALLOWED_ORIGINS` env var
3. Change the value from:
   ```
   https://staging.3bayti.ae,https://3bayti.ae,https://vendor.3bayti.ae
   ```
   to:
   ```
   https://staging.3bayti.ae,https://3bayti.ae,https://app.3bayti.ae,https://vendor.3bayti.ae
   ```
   > Keep `vendor.3bayti.ae` until DNS fully cuts over. Remove it in a cleanup deploy next week.
4. **Save** — this triggers a redeploy of the API

### 2c. Watch the redeploy

```bash
doctl apps list-deployments <APP_ID> --format ID,Phase,Progress
```

The pre-deploy migration job runs first. If migration fails, the deploy aborts — no traffic disruption to the old version.

## Step 4 — Deploy the web storefront (5–10 min build)

The web app at `staging.3bayti.ae` runs on Cloudflare Workers. It has no code changes in this release but should be redeployed to ensure environment variables (if any changed) are picked up.

```bash
cd apps/web

# Set environment for production build
export SITE_URL=https://staging.3bayti.ae

# Install dependencies
pnpm install

# Build (Angular SSR + static assets)
pnpm run build
# This runs: prebuild (inject-environment.mjs) → ng build → postbuild (sitemap)
# Artifacts land in: dist/3bayti-web/browser/ and dist/3bayti-web/server/

# Deploy to Cloudflare Workers
pnpm run deploy
# This runs: wrangler deploy (reads wrangler.jsonc)
# Output: "Published 3bayti-web (X.XXs)"
```

**Verify:**
```bash
curl -s https://staging.3bayti.ae | grep -o "<title>[^<]*</title>"
# Expected: <title>3bayti | ... </title>

curl -I https://staging.3bayti.ae
# Expected: HTTP/2 200
```

## Step 6 — Deploy the portal to app.3bayti.ae

The portal is a static Angular SPA (no SSR). It can be deployed to Cloudflare Pages, an nginx static server, or any static host.

### Option A — Cloudflare Pages (recommended)

```bash
# First time (creates the Pages project)
npx wrangler pages project create 3bayti-portal \
  --production-branch main

# Every deploy
npx wrangler pages deploy dist/abayti/browser \
  --project-name 3bayti-portal \
  --branch main
```

Then in Cloudflare dashboard:
1. **Pages** → **3bayti-portal** → **Custom domains**
2. **Add a domain**: `app.3bayti.ae`
3. Cloudflare will add the DNS record and provision the cert automatically (2–5 min)

### Option B — Nginx static server (aaPanel / existing server)

If you're running aaPanel (as per `m1.5-runbook-aapanel.md`):

```bash
# On the server
rsync -avz --delete dist/abayti/browser/ /www/wwwroot/app.3bayti.ae/

# Nginx vhost config for app.3bayti.ae
# (create via aaPanel → Website → Add site → domain: app.3bayti.ae)
# Then edit the vhost to add SPA fallback:
```

aaPanel nginx vhost config (add inside `server {}` block):

```nginx
root /www/wwwroot/app.3bayti.ae;
index index.html;

# SPA routing — all non-asset paths serve index.html
location / {
    try_files $uri $uri/ /index.html;
}

# Long-cache hashed assets
location ~* \.(js|css|woff2|png|jpg|ico|svg)$ {
    expires 1y;
    add_header Cache-Control "public, immutable";
}
```

The mobile app (`apps/mobile`) **does not need a new release** for this deployment. The app hardcodes `https://api-v3.3bayti.ae` as its v3 base URL and the API is backward-compatible.

**However, verify the mobile app still works** by opening it on a real device and confirming:
- [ ] Home page products load
- [ ] Login works
- [ ] Checkout flow works (critical path)

If any endpoint is broken, the mobile app's `MobileNetworkAdapter` will fall back to the legacy API for `target: 'old'` routes — no user-facing breakage expected.

### When to release the mobile app

Only required if:
1. A critical API contract changed (none in M3.3/M3.4)
2. New mobile features are bundled (none in M3.3/M3.4)

## Rollback procedure

### If the migration fails (deploy aborts automatically)
No action required — old API version is still serving. Fix the migration and redeploy.

### If the API deploy succeeds but is broken
```bash
# Roll back to previous deployment
doctl apps list-deployments <APP_ID>
# Note the previous deployment ID
doctl apps create-deployment <APP_ID> --force-rebuild
# Or via dashboard: Deployments → previous deploy → Rollback

# Roll back the migration (only if tables/columns are causing issues)
# Connect to DB and run the down() SQL from Version20260523000001.php
# These are safe DROP TABLE IF EXISTS / DROP COLUMN IF EXISTS statements
```

### If the portal deploy is broken
```bash
# Redeploy the previous portal build from git
git checkout <previous-commit> -- apps/portal
pnpm run build --configuration production  # in apps/portal
pnpm run deploy  # Cloudflare Pages / rsync to server
```

### If DNS is wrong
Revert the DNS record in Cloudflare. TTL is typically 300s — changes propagate in under 5 minutes.
